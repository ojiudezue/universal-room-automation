# Universal Room Automation — VibeMemo

*Last updated: 2026-06-10 | Version 1 | Contributors: ojiudezue*

## How This Started

URA is a Home Assistant custom integration managing 31 rooms across 5 zones with 7 domain coordinators (Presence, Energy, HVAC, Safety, Security, Music Following, Notifications). It automates room behavior based on occupancy detection, Bayesian prediction, energy optimization, and cross-coordinator signals.

## Key Decisions

**Single-threaded DB write worker (v3.22.8):** SQLite only allows one writer at a time. Instead of multiple connections fighting for the lock, all writes serialize through one asyncio.Queue processed by one persistent connection. Reads use independent transient WAL connections. This eliminated all write contention from the v3.18.4 "database is locked" crisis.
→ [001](users/ojiudezue/entries/001_db_single_writer_architecture.json)

**Write worker as background task with graceful shutdown (v4.2.15-16):** The write worker runs forever — using `async_create_task` made HA wait indefinitely for startup completion. Changed to `async_create_background_task`. On shutdown/reload, pending writes are now flushed (5s budget, fresh connection) instead of failed with RuntimeError. Data integrity preserved across restarts.
→ [005](users/ojiudezue/entries/005_db_write_worker_startup_fix.json)

**Startup catch-up prune removed (v4.2.14):** Added in v4.2.8 to clear orphaned table backlogs, delayed to 30 min in v4.2.13, removed in v4.2.14. Regardless of delay, it saturated the write queue for 15+ minutes on every boot, blocking all DB reads. Nightly 2:30 AM maintenance is the sole cleanup mechanism. The one-time backlog it was designed to clear is gone.

**Energy measurement trust hierarchy (v4.2.16+):** Three independent measurement sources — Envoy (solar gateway), Emporia Vue (mains CTs), SmartHub (utility meter) — don't agree. Envoy drifts ~5 kWh/day from utility billing. Trust hierarchy for cumulative accuracy: SmartHub > Emporia/SPAN > Envoy. Envoy remains primary for real-time (sub-second resolution). SmartHub will calibrate bill predictions. Emporia mains will populate the empty `grid_import_2` column in energy_history for historical cross-validation. Shipping divergence reporting first (B-Lite), deferring auto source switching (B3) until 2-4 weeks of data validates the pattern.
→ [003](users/ojiudezue/entries/003_energy_measurement_trust_hierarchy.json)

## Current Architecture

- **Write path:** 44 write methods → `_db()` → asyncio.Queue → single background write worker → one persistent SQLite connection. Graceful 5s flush on cancel.
- **Read path:** 43 read methods → `_db_read()` → transient WAL connections. Zone sensors cached 5 min, Bayesian accuracy cached 30 min.
- **Startup:** First-cycle writes deferred 5 min with 0-60s jitter. No catch-up prune. Bayesian predictor registered before DB load (survives init failure). Write worker is a background task (doesn't block startup). ~5 min warmup.
- **Energy:** Envoy primary for real-time, CostTracker uses Emporia mains for billing. Utility meter integration planned (B-Lite).
- **EV control:** TOU pause + grid cap pause. Battery drain auto-pause planned (Cycle A).
- **DB:** 810 MB, WAL mode, 30s busy_timeout. Nightly 2:30 AM prune (7 tables, rotating start, 5-min budget). SQLite-over-SMB reads blocked by persistent write worker — known limitation, not a code bug.

## v4.7.33 A-F5 + Optimization Coordinator scoping (2026-06-08, cont.)

Closed the A-F5 follow-up the marathon had deferred, then scoped URA's largest planned subsystem. → [020](users/ojiudezue/entries/020_v4733_af5_ttl_plus_optimization_coordinator_scoped.json)

The clean resolution: since URA never writes `preset_mode=manual`, a mid-window non-manual→manual transition is unambiguously the user → pass it through. LIVE + validated (PR #374).

**Four inspections, one keeper.** Operator flagged a Frigate camera *motion* sensor (`device_class=motion`) living in zone_1's `CONF_ZONE_CAMERAS` — a list documented person-detection-only — which `check_zone_occupancy_confidence` trusts wholesale with no device_class filter, feeding the stale-sensor guard. He removed it from config; the durable code guard is a low-pri backlog plan. The other three (DB-write-worker boot transient, fan-during-solar-banking, zone-state-across-restart) were ruled NO-OP.

**Bayesian audit:** exactly ONE shipped engine (the coordinator-level `BayesianPredictor`, occupancy, live + healthy at 97% data-quality / 85.6% hit-rate) and the per-room "comfort ParameterBelief" is design-only scaffolding (zero code). ## Envoy boot-decoupling + the attainability redesign marathon (2026-06-12/13)

A dead Enphase Envoy broke the v5.3.6 post-deploy boot — all 40 entries stranded — but the release was exonerated by diff. → [023](users/ojiudezue/entries/023_v537_v538_envoy_decoupling_attainability_redesign_marathon.json) Root cause was v4.2.29's coupling: `after_dependencies:[enphase_envoy]` let HA's stage-2 timeout cancel URA's queued setups when enphase_envoy hung, and a one-shot Envoy validation lost a ~17s boot race so the EnergyCoordinator silently never registered. The broken boots also exposed RestoreEntity unavailable-coercion (Bug Class #52: `unavailable` last-state restored as OFF, disabling all 6 intended-ON EC switches). **v5.3.7** fixed all three — registry-based three-way validation, EC always registers when enabled (runtime is already None-safe, the boot gate was the only hard coupling), `after_dependencies` removed, restore guards — and proved itself the same night under the exact fault it was built for.

Then the deeper one. A good-solar day where the EVs' off-peak ensure-on charging consumed *all* production drove the battery to 10% entering peak, while the forecast-class-only arbitrage gate never looked at the buffer. A live manual-arbitrage exercise (operator + assistant) rode today's peak (10%→45%) and measured the Enphase actuation constants — reserve-bump charge onset ~22min, charge_from_grid cloud enable ~35min, full rate ~16kW — which then became **v5.3.8**: a new `attain` arbitrage phase that fires on *realized* solar-divergence regardless of forecast class (operator principle: "no solar **reaching** the battery → need for arbitrage"), plus D1b mid-peak continuation (the state-matrix "no charging outside off_peak" invariant narrowed, not deleted: "arbitrage IS arbitrage... if we can't cover mid_peak we absolutely need to cover peak"). v5.3.8 was the heaviest cycle the repo has run — **1 build + 4 fix-ups + 7 reviews** (two full framing-disjoint Tier-2-DB passes + a focused pass-3) — because builders **twice** shipped HOLD as a one-tick emission the drain fallback immediately unwound, and **twice** gated reboot-recovery on a RAM latch that boots False. The breakthrough was brief discipline: when two builders fail the same requirement, prescribe the **mechanism** (HOLD is a STATE routed before the predicate AND the fallback; reboot recovery derives from **hardware** state, not a RAM latch), not the behavior. Test authority eroded just as hard — review proved deleting the entire solar term passed 26/26 and HOLD reserve=0 passed everything — so mutation-anchored tests became a standing gate (7 mandatory mutations on the final fix-up). Both LIVE. Two durable hazards banked: toggling the EC-enabled switch triggers a watchdog restart, and EC reverts manual Enphase flips every cycle — battery decisions must live *inside* the decision loop. Load shedding was split: correctness fixes stay a normal cycle, capability expansion (pool sub-tiers, forecast coupling) becomes a foundations-first/IP track.
