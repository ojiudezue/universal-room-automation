The smoking gun: **`study_a_closet` shows 5,306 kWh "today" with power = 0 W right now**. Power can't be 0 if 5,306 kWh were really consumed today. The sensor is reading something cumulative, not daily.

## Root cause — `coordinator.py:1444-1490` (room energy_today computation)

```python
energy_sensors = self._get_config(CONF_ENERGY_SENSORS, [])
if energy_sensors:
    total_delta = 0.0
    midnight_reset = now.date() > self._last_energy_reset.date()    # ← suspect
    for sensor_id in energy_sensors:
        state = self.hass.states.get(sensor_id)
        if state is None or state.state in ("unknown", "unavailable"):
            continue
        try: current_value = float(state.state)
        except (ValueError, TypeError): continue
        # SET BASELINE on midnight or first seen
        if midnight_reset or sensor_id not in self._energy_baselines_today:
            self._energy_baselines_today[sensor_id] = current_value
        baseline = self._energy_baselines_today[sensor_id]
        total_delta += max(0, current_value - baseline)
    if midnight_reset:
        self._last_energy_reset = now
    data[STATE_ENERGY_TODAY] = total_delta
```

The intent is correct: compute today's delta from a `TOTAL_INCREASING` cumulative sensor by snapshotting a baseline at midnight and subtracting.

### Defects

**Defect 1 — `_energy_baselines_today` is in-memory only (line 215).** Not persisted across restarts. Behavior on restart:
- First read after restart: baseline = current cumulative reading.
- Following reads: delta = current − that baseline.
- Result: room energy_today shows "energy since last URA restart", NOT "energy since midnight".
- If URA restarts mid-day, you lose the morning. If URA hasn't restarted in days, baseline gets stale.

**Defect 2 — Possible timezone-mismatch in midnight detection (line 1455).** `now.date() > self._last_energy_reset.date()`. `_last_energy_reset` is initialized at line 211 with `dt_util.now().replace(hour=0, ...)` (timezone-aware local). If `now` here is naive UTC or different tz-awareness, `.date()` comparison can fail to fire midnight reset on the right day.

If midnight_reset fails to fire and the baseline stays stuck for many days:
- Day 1 midnight: baseline correctly set.
- Day 2: midnight_reset should fire but doesn't. Baseline stays at Day 1 reading.
- Day N: delta = current − Day 1 baseline = N days of accumulated energy.

This matches the symptom — `study_a_closet` showing 5,306 kWh "today" with `power=0W`. That's not today's delta; it's many days of accumulation.

**Defect 3 — Wrong source-sensor configuration** (config-side, not code-side). If a user picks `sensor.span_panel_X_consumed_energy` (lifetime kWh) as their `CONF_ENERGY_SENSORS`, even with the baseline logic working, a one-time install mistake amplifies all the above.

### Downstream cascade

The astronomical `energy_today` from rooms then propagates:

- `EnergyCostPerOccupiedHourSensor` (`aggregation.py:2424`): `energy_kwh × ec.tou_engine.get_effective_import_rate()` over occupied hours. **Rate from EC is correct; energy from rooms is wrong.** $81.25/h is downstream of the room bug.
- `EnergyCoverageDeltaSensor` (`aggregation.py:2234`): `whole_house − rooms_total`. Whole house comes from a separate sensor (correct daily integration). Rooms total inherits the inflated values. Delta shows impossibly negative.
- Per-room `energy_cost_today`, `energy_cost_weekly`, `energy_cost_monthly` (`coordinator.py:1804-1811`): all multiplications of the broken `STATE_ENERGY_TODAY` by static rate.

**The EC sensors are correct.** EC computes `energy_cost_today = $3.14` from SPAN's daily integration. This is the ground truth.

## Things that ARE working correctly

- `EnergyWasteIdleSensor` — uses `STATE_POWER_CURRENT` (current watts), not energy. Correctly sums vacant rooms with power > 5W.
- `predicted_heating_need`, `predicted_cooling_need`, `predicted_energy_today` — these are independent of the room aggregation bug. They use HVAC + per-day historical patterns. Live values plausible.
- `MostExpensiveCircuitSensor` — uses EC's `_circuits._circuits[].cumulative_energy_wh` directly. Field is named "cumulative" but the live $0.92 is plausible. Need a follow-up read to confirm whether this is daily-since-midnight or lifetime.
- EC's own sensors (`tou_period`, `tou_rate`, `current_energy_rate`, `energy_cost_today`, `battery_strategy`, etc.) — all correct, sourced from SPAN + TOU engine.

## Architectural pattern (the "sequence" the user flagged)

URA's energy code was built in three layers, in this order:

1. **v3.x era — rooms.** Rooms had `CONF_ELECTRICITY_RATE` (per-room override + integration default) and `CONF_ENERGY_SENSOR` (single, then plural in v4.1.0). `STATE_ENERGY_TODAY` and `STATE_ENERGY_COST_TODAY` (= energy × static rate) computed in `coordinator.py:1804-1811`.

2. **v4.0–4.2.0 era — house aggregation sensors.** New sensors in `aggregation.py` summed across rooms (`EnergyCoverageDeltaSensor`, `EnergyCostPerOccupiedHourSensor`, etc.). Some pulled from rooms; some pulled from EC; mostly mixed.

3. **v4.0.0–v4.2.0 era — Energy Coordinator.** EC introduced TOU rates, SPAN circuit awareness, accurate net-energy computation, and `current_effective_rate`. EC is the proper source of truth for cost. But rooms and pre-EC sensors still use the legacy `CONF_ELECTRICITY_RATE` static config.

The result is **layered drift**: rooms compute one cost, house sensors compute another, EC computes a third. Three numbers that disagree — exactly what the user is observing.

## Hotfix vs. comprehensive refactor — assessment

### Option A — Hotfix (v4.2.27 / v4.2.28)

Surgical fixes to the broken sensors:

1. **Persist `_energy_baselines_today` to disk via HA `Store` helper.** ~30 lines. Eliminates the restart-loses-baselines problem (Defect 1).
2. **Fix midnight-reset timezone consistency** in `coordinator.py:1455`. Use `dt_util.now()` consistently, ensure `_last_energy_reset` is also `dt_util.now()`-derived. ~5 lines (Defect 2).
3. **Add a guard:** if `current_value < baseline` (a sensor reset, like a smart-plug reboot), reset baseline to current and log warning. Currently `max(0, current_value - baseline)` returns 0 (silent), which is OK, but the baseline never recovers either.
4. **Live diagnostic:** add a service `ura.dump_room_energy_baselines` that prints all baselines for debugging.
5. **Keep `STATE_ENERGY_COST_TODAY` using static rate for now** (this hotfix doesn't touch the EC migration — that's separate).

**Pros:** Fast (~1 day total dev + review). Stops dashboards showing absurd values immediately. Surgical, well-scoped.
**Cons:** Doesn't fix the architectural drift. Three layers will continue to disagree on absolute cost numbers (legacy static rate vs. EC TOU rate).

### Option B — Comprehensive refactor: v5.0 "Energy Architecture Alignment"

Make EC the single source of truth for cost. Rooms become contributors of POWER (their actual measurement), and receive APPORTIONED cost back from EC.

**Architecture sketch:**
1. **EC owns the rate.** All cost calculations use `EC.current_effective_rate` (TOU-aware). Static `CONF_ELECTRICITY_RATE` becomes fallback only when EC isn't configured.
2. **Rooms publish power and energy_today (delta correctness fixed) to a shared bus.** EC subscribes; sums across rooms; computes total whole-house energy and cost.
3. **EC apportions cost back** to each room via `room_share = my_kWh / total_kWh × house_cost`. Rooms expose `room_cost_today` derived from this share.
4. **House-level sensors** (`energy_coverage_delta`, `cost_per_occupied_hour`, `optimization_potential`, etc.) all read from EC's authoritative state.
5. **Room cost calculations in `coordinator.py:1804-1811` removed** — replaced with EC subscription.
6. **Migration plan** for users who have `CONF_ELECTRICITY_RATE` set: keep as a fallback (no UX disruption); EC use is implicit when EC is configured.

**Pros:**
- One source of truth — three numbers become one.
- TOU-aware costs throughout (matches reality).
- Easier to add new layers (zones, circuits) without inventing yet another rate path.
- Cleaner code overall — less duplication.
- Fixes BACKLOG items E (TOU migration) and the broken sensors at the same time.

**Cons:**
- Significant blast radius. Touches `coordinator.py`, `aggregation.py`, `domain_coordinators/energy.py`, every cost-related sensor.
- ~600-800 production lines + ~400 tests + config flow migration.
- Tier 2 review cycle (2 reviews + live validation).
- 2-3 weeks for design, build, review, deploy.
- Risk: introducing regressions in EC's already-stable code paths.

### Recommendation: **Both, sequenced**

- **v4.2.28 hotfix (next):** Apply Defects 1+2+3 fixes. Stop the absurd dashboard values now. Static-rate cost computation continues. Restart-survivability via `Store` helper. ~80 lines + tests + Tier 1 review.

- **v5.0 plan (after the hotfix lands):** Comprehensive Energy Architecture Alignment. Plan doc styled like B5 / B3. EC-as-source-of-truth, room apportionment, eliminate legacy paths. Schedule for July-August 2026.

This sequence:
- Stops the bleeding now (visible defects affecting dashboards).
- Doesn't ship a half-baked refactor under hotfix pressure.
- Lets the architectural change have proper Tier 2 review and live validation.
