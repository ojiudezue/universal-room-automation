### A2 GUEST exit gate

`presence.py:2374-2415`. The gate triggers only when `current_state == HouseState.GUEST` AND `new_state in {HOME_DAY, HOME_EVENING, HOME_NIGHT}`. The exit timer `_guest_exit_quiet_since` is set when the exit condition first becomes true (line 2386-2387), checked against `_guest_persistence_seconds` (default 300s from coordinator init), and reset to `None` when the engine declines to exit or transitions GUEST→GUEST (`:2411, 2414-2415`).

v4.7.2 D5 entry-side code at `presence.py:1751-1843` is **UNTOUCHED** — verified by inspecting that file region for v4.7.15 commit diffs (no edits in that range). Plan §14 mandate observed. ✓

### Findings

**A2-H1 [HIGH] — `_guest_exit_quiet_since` reset path leaks across non-exit GUEST cycles.**
Read the `else:` branch at `presence.py:2412-2415`:
```python
else:
    # Either not in GUEST, or engine did not signal exit — reset timer.
    if current_state != HouseState.GUEST or new_state == HouseState.GUEST:
        self._guest_exit_quiet_since = None
```

This means: when `current_state == HouseState.GUEST AND new_state is None` (the WAKING block at `:2366` can set this, OR the engine can return None directly — though the latter currently does not happen in `infer()`), the `else` branch's inner `if` evaluates `current_state != HouseState.GUEST` (False) AND `new_state == HouseState.GUEST` (False since None ≠ HouseState.GUEST) → both False → `_guest_exit_quiet_since` is NOT reset.

Combined with the outer `if` at `:2374` which requires `new_state is not None`, the cycle `new_state=None` skips the inner exit gate, falls into the `else`, then refuses to reset. On the next tick, if conditions change (e.g. engine returns HOME_DAY), the timer carries stale arm from a prior cycle.

Concrete scenario:
1. Tick N: GUEST state, engine returns HOME_DAY, exit guard arms `_guest_exit_quiet_since=T0`, gate blocks → `new_state=None`.
2. Tick N+1: engine returns HOME_DAY again 60s later, exit gate checks `quiet_seconds = 60s < 300s`, blocks.
3. Tick N+2: engine returns GUEST (transient signal returned) — the outer `if` at `:2374` is False because `new_state==HouseState.GUEST`. Falls to `else`. Inner `if`: `current_state==HouseState.GUEST AND new_state==HouseState.GUEST` → second clause `new_state == HouseState.GUEST` is True → reset. ✓ Actually OK in this case.

Reconsidered: the only way to leak is `new_state=None`, which `infer()` does not produce. The WAKING gate at `:2366` sets it to None but only when `current_state==SLEEP`, never when `current_state==GUEST`. So in practice the leak is unreachable today.

**Downgrading to MEDIUM (A2-M1):** the boolean is defensible only by reading the whole call chain. Recommend a clearer reset rule — reset whenever `current_state != HouseState.GUEST OR new_state is None OR not exit-shaped`. Either restructure or comment exhaustively. Risk: a future cycle introducing a `new_state=None` path inside GUEST (e.g. an observation-mode short-circuit) would silently break this guard.

**Fix sketch:**
```python
else:
    # Reset on any tick that is not "GUEST→HOME_*" — be defensively explicit.
    if current_state != HouseState.GUEST or new_state in (None, HouseState.GUEST):
        self._guest_exit_quiet_since = None
```

**A2-H1 [HIGH] revised — Timer does not arm if engine never re-evaluates the exit shape.**
There is also an asymmetry: the gate requires the engine to return a HOME_* state for the timer to advance. But if `unidentified_count` flickers (`0 → 1 → 0`) every few ticks, the engine returns GUEST on the `1` ticks (no exit signalled), `_guest_exit_quiet_since` is reset, and the timer never accumulates. That is *correct* behaviour — flickering means the exit is not sustained. But the test in `test_d3_guest_exit_persists_against_single_frame_frigate_fp` should explicitly cover both:
- (a) the single-frame `unid=0` blip then back to `unid=1` — engine returns GUEST, timer resets, exit not granted ✓
- (b) sustained `unid=0` for 5+ ticks — engine returns HOME_DAY, timer accumulates past 300s, exit granted ✓

Confirm Reviewer C audits the test fixture to ensure both branches are present.

`presence.py:2353-2357` passes `"house_state": current_state` (`HouseState.SLEEP`). Pattern D inside helper at `:783-799` does not actually consume `house_state` — only `sustained_occupancy_seconds`. So passing it is informational. Fine, no fix.

### Findings

**A5-H1 [HIGH] — Asymmetric hysteresis at consensus value (0.5 / 0.7) is documented but NOT implemented.**

README claims (lines 58-59):
> The hysteresis is asymmetric: the gate engages at 0.5 but does NOT re-disable until consensus recovers above 0.7

Plan §3 D6 spec (line 519):
> Asymmetric hysteresis: defer if <0.5, resume only at >0.7.

Code at `hvac.py:806`:
```python
if consensus < 0.5 and secs_since_transition < 30:
```

This is **single-threshold** on consensus value. The "hysteresis" the code actually provides is time-window-based: the gate stops firing 30s after a transition regardless of consensus value. There is no `_d6_currently_deferring` state variable, no upper threshold, no "resume at 0.7" branch. A consensus of 0.6 (between 0.5 and 0.7) makes the gate immediately stop firing — no waiting for the recovery threshold.

Impact:
1. **Test gap:** `test_d6_hvac_gate_resumes_at_0_7_hysteresis` (plan D6 test list) cannot pass as currently implemented. Reviewer C should verify this test exists and fails OR was removed.
2. **Live-validation gap:** the operator runbook tells the operator to expect different behaviour from what the gate does.
3. **Behavioral gap:** during a longer consensus dip (e.g. 0.45 → 0.55 → 0.45 oscillation), the time-based hysteresis is the only thing preventing flap, and that runs out 30s after the last transition. Consensus-flap inside the 30s window will see the gate flip on/off as consensus crosses 0.5.

**Fix options:**
- (a) **Add the upper threshold.** Track `self._d6_gate_engaged: bool = False`. Engage at `< 0.5`. Disengage at `> 0.7`. Decouple from `secs_since_transition`.
- (b) **Update README + plan to remove the 0.7 claim.** Document the gate as single-threshold with a 30s time window from the last transition. This is the smaller change and matches what shipped.
- (c) **Ship as-is + add the upper threshold in a v4.7.15.1 fix-up.**

Operator must pick before live validation; otherwise Review D will mis-classify the gate as broken.

## A7 — CRITICAL: scope="room_level_weighted" gap for v4.7.16 D3

**File:** `presence.py:707-825` (helper dispatch).

### Finding

**A7-H1 [HIGH] — v4.7.16 D3's planned `scope="room_level_weighted"` will silently no-op against the v4.7.15 helper.**

The v4.7.15 helper recognises exactly 4 scopes (`house_inference`, `zone_aggregator`, `waking_transition`, `guest_exit`). The default fall-through at `:824` returns `VetoDecision(False, 0.0, "", scope)`. The plan (§10 "Hand-off to v4.7.16", line 760) anticipates a fifth scope:

The instructions to Reviewer A name a **different** scope: `room_level_weighted`. Whichever wins, the current helper will fall through to `fired=False` for it. v4.7.16 D3's room-level veto will be a silent no-op on first ship, only discoverable via live-validation. That's an avoidable cycle of fix-up churn.

### Recommendation — pick ONE before merging v4.7.15

I recommend **option (b): v4.7.16 should reuse one of the 4 existing scopes** rather than adding a new pattern to v4.7.15.

Rationale:
1. v4.7.15 has already shipped 5 patterns in 6 deliverables; the cycle is at the upper bound of Tier 2-DB scope. Adding a 6th pattern to absorb v4.7.16's needs blurs the cycle boundary and adds review surface to v4.7.15 that the operator did not budget for.
2. v4.7.16's "room-level weighted" pattern is structurally a `zone_aggregator` variant at a sub-zone granularity. The existing Pattern C (zone non-sleep) already accepts `state_context["room_sensors_quiet_seconds"]` and `state_context["zone_name"]`. v4.7.16 can extend the same scope with additional context keys (`state_context["room_id"]`, `state_context["scanner_areas"]`) and Pattern C's body can branch on whether `room_id` is present.
3. This keeps the scope namespace tight (4 stable scopes instead of one per cycle).

If the operator prefers option (a), the change to v4.7.15 is small:
```python
# Pattern F — v4.7.16 D3 room-level weighted (forward-stub, fires False).
if scope == "room_level_weighted":
    # v4.7.15 ships the dispatch slot; v4.7.16 fills in the body.
    return VetoDecision(False, 0.0, "room_level_weighted not yet implemented", scope)
```
At minimum, ship the stub so v4.7.16 doesn't surprise-fail. But the cleaner answer is to fold into Pattern C.

If the operator prefers option (c), document explicitly in the v4.7.16 planning doc that D3 is "phase 2" behind a v4.7.16.1 fix-up.

**The blocking question:** Which scope name will v4.7.16 use, and where does the dispatch live? Resolve before tagging v4.7.15.
