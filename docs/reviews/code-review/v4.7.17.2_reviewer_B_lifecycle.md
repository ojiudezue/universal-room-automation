#### B-H1 — Listener-vs-hydrate race window in `WeatherProviderManager.async_setup`

**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:152-176`
**Bug class:** Bug Class #45 (concurrent reload race) — adapted to first-setup ordering

**Issue.** `async_setup` registers state-change listeners (lines 152-161) BEFORE calling `_hydrate_rolling_window_from_store()` (line 173). Between listener-add and the next event-loop yield, any provider state-change event scheduled by HA core fires `_handle_provider_state_change`, which schedules `_refresh_all_providers()` as a tracked task.

That task awaits `_refresh_lock`. The setup coroutine then `await`s `_hydrate_rolling_window_from_store()` (which itself awaits `Store.async_load()`), yielding the loop. During that yield, the queued refresh task can acquire `_refresh_lock`, run a full refresh, and call `_record_daily_apparent_high()` against the **not-yet-hydrated, empty** `_apparent_high_ring`. That call appends today's entry and persists a 1-entry ring to Store.

Then `_hydrate_rolling_window_from_store()` returns from `async_load()` with the OLD pre-race ring contents (already read before the racing write completed) and ASSIGNS them to `self._apparent_high_ring`, silently discarding today's entry from memory. The next `_record_daily_apparent_high` call rewrites Store from the rehydrated ring (still missing today's entry until the next refresh re-appends), so the race entry is lost from disk too.

**Why it matters.** Probability is low (depends on provider state changes during HA bootstrap before `Store.async_load` returns), but the corruption mode is silent — the operator gets a ring missing one calendar day, the rolling median is slightly off, no log signal. Across the warmup phase (first 7 days), losing even one entry delays DPM emission by another day.

**Suggested fix.** Either:
1. Move listener registration AFTER the hydrate await — small window of dropped state-change events during the first probe is preferable to a corrupted ring.
2. Acquire `_refresh_lock` for the duration of hydrate, so any racing refresh-task waits behind the hydrate.

Recommended: option 1. Listener registration before first probe is not load-bearing — the immediate `_refresh_all_providers()` at line 176 catches whatever state was current at setup time.

```python
# Hydrate FIRST (before any state-change listener can fire a refresh task)
await self._hydrate_rolling_window_from_store()

# Now register listeners
for entity_id in providers:
    if not entity_id:
        continue
    unsub = async_track_state_change_event(...)
    self._unsub_handles.append(unsub)

# Initial probe
await self._refresh_all_providers()
```

#### B-M1 — Apparent-vs-raw temperature mixing in the rolling ring

**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:446-453, 478-485`
**Bug class:** Cross-coordinator data-shape inconsistency (no QC class number yet)

**Issue.** The cached forecast's `apparent_high` field has three confidence modes (line 446-453):
- `"high"` — provider exposed apparent_temperature attribute; value is true apparent
- `"fallback_raw"` — single provider, no apparent attr; value is raw temperature
- `"apparent_unavailable_fallback_raw"` — multiple providers, apparent missing; value is raw

`_record_daily_apparent_high` (line 478-485) records whatever `apparent_high` is, regardless of confidence. So the rolling ring can contain a mix of true-apparent and raw-fallback values across days. The median computed in `_rolling_median_apparent_high` mixes the two semantics. The operator-visible `relative_delta = today_apparent − ring_median` then jumps by 3-5°F purely from a provider transition between has-apparent and no-apparent — which can trigger a spurious tighten or relax with no actual weather change.

**Why it matters.** Cross-coordinator concern: the WPM's apparent-vs-raw heuristic was designed for a single-tick consumer (sensor attribute display). v4.7.17.2 now consumes WPM in a TEMPORAL aggregate that assumes value-shape stability over 14 days. The two semantics aren't comparable.

**Suggested fix.** Either:
1. Skip ring-recording when `apparent_confidence` is `fallback_raw` or `apparent_unavailable_fallback_raw`. Pro: pure semantics. Con: ring fill-in slows during periods of degraded provider quality.
2. Record the confidence alongside each entry (`(date_iso, value, confidence)` tuples) and exclude `fallback_raw` entries from median computation.
3. Document the limitation in `baseline_delta_for_zone` docstring and surface a sensor attribute `ring_contains_fallback_raw=True` so the operator can debug spurious jumps.

Recommended: option 1 (simplest, most defensible). The MIN_DAYS=7 floor already accepts some warmup delay; another day or two of degraded-provider skip is acceptable.

#### B-M2 — DPM mutates HVAC coordinator's PresetManager `_current_season` as a side-effect of seasonal lookup

**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:413-436, 619-644`
**Bug class:** Cross-coordinator state mutation (no QC class — this is the canonical "Coordinator boundary leak" anti-pattern)

**Issue.** The Tier 1 H1 fix correctly switched DPM to use the HVAC-coordinator-owned `PresetManager` instance via `resolved_pm`. But `_build_overrides_with_reason` then calls `_pm.get_seasonal_setpoints("home")` on that shared instance (line 635). Looking at `hvac_preset.py:132-133`:

```python
if season is None:
    season = self._current_season or self.determine_season()
```

`determine_season()` MUTATES `self._current_season`. So if HVAC's `async_setup` has not yet run `_preset_manager.determine_season()` (line 421 in hvac.py) when DPM evaluates, DPM's call chain mutates `_current_season` on HVAC's shared PresetManager.

Same-event-loop, no concurrent reader → no immediate data race. But this violates coordinator boundaries: DPM (under EC) is now a write-source for HVAC-owned state. If HVAC later adds a guard that reads `_current_season == ""` to detect "season not yet computed", DPM will have already silently set it. Pre-existing pattern (HVAC's own call also mutates), so not v4.7.17.2-introduced — but v4.7.17.2 increases the call frequency from "1× per HVAC tick" to "1× per zone per EC tick" (~ ×N_zones higher).

**Why it matters.** Quiet coupling. The next person who tries to lazy-init seasonal state on HVAC will get unexpected behavior because DPM has been racing to set it.

**Suggested fix.** Treat the resolved_pm read-only. Have DPM call `resolved_pm.current_season or "summer"` rather than letting `get_seasonal_setpoints` fall through to `determine_season()`. Or call `get_seasonal_setpoints("home", season=resolved_pm.current_season or "summer")` explicitly so the mutation path is not entered.

```python
_season = getattr(_pm, "current_season", "") or "summer"  # explicit fallback
_season_pair = _pm.get_seasonal_setpoints("home", season=_season)
```

Bonus: removes the implicit assumption that the local clock's month determines DPM's seasonal baseline — at minimum makes the assumption explicit and centralizes the fallback policy.

#### B-M3 — Winter gate uses cached `current_season` only; no re-evaluation across season boundary without HA restart

**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:419-431`
**Bug class:** Stale-cache + lifecycle (related to Bug Class #14 — config staleness)

**Issue.** The winter gate reads `getattr(resolved_pm, "current_season", "")`. As noted in B-M2, that field is set ONCE by `PresetManager.determine_season()` — HVAC calls it at setup (`hvac.py:421`) and at another path (`hvac.py:672`). There is no scheduled re-evaluation.

If HA runs across an Oct 31 → Nov 1 boundary without a restart, the cached `_current_season=shoulder` stays. DPM continues emitting overrides through Nov 1+. The winter gate never fires until the next HA restart.

Symmetrically: if HA restarts on Feb 28 and runs to Mar 1, the gate stays winter through the shoulder season's start, causing DPM to silently no-op for an extra day or more.

**Why it matters.** The winter-gate behavior is the v4.7.17.2 cycle's most visible safety boundary. Operator expectation per planning doc §3 is "skip Nov-Feb." Reality is "skip Nov-Feb when HA happens to have determined season since the boundary crossing." Calendar-driven HA installs (always on, rarely restarted) will see late-by-N-hours behavior at every season boundary.

**Suggested fix.** Two options:
1. **DPM-side, lightweight:** Have the winter gate call `resolved_pm.determine_season()` (not `current_season`) so each evaluation re-checks the calendar. Side-effect-wise this is the same as B-M2's mutation problem so prefer the explicit form: compute season locally in DPM from `dt_util.now().month` and the same `SUMMER_MONTHS / WINTER_MONTHS` sets the PM uses.
2. **HVAC-side, durable:** Schedule a daily `dt_util.now().replace(hour=0, minute=5)` re-evaluation of `determine_season()` in HVAC's setup. Solves the problem for any other caller of `current_season` too.

Recommended: option 1 — keep DPM self-sufficient; HVAC's stale-season is a pre-existing concern not in scope.

```python
# Compute the winter check directly from clock — no shared mutable state.
from .hvac_const import WINTER_MONTHS
if dt_util.now().month in WINTER_MONTHS:
    return [], "winter_season"
```

This also eliminates the need for the `resolved_pm`-lookup-just-for-winter-check codepath (lines 419-436) which currently swallows exceptions silently with `fail-open` semantics — making the gate ineffective when the coordinator manager isn't bootstrapped yet.

#### B-M4 — `Store.async_save` not debounced; same-day repeated forecasts write disk on every refresh

**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:586-628`
**Bug class:** Resource cost (no QC class) + boot burst risk (related to Bug Class #44 — untracked background tasks)

**Issue.** `_record_daily_apparent_high` dedupes by date but persists on every value change. `Store.async_save()` is synchronous (immediate write via executor). A weather provider that updates its forecast attribute every 10 minutes during the day will:
- Same-date entry already exists.
- New value differs (forecasts get refined).
- Update entry, await `async_save` → disk write.
- ~144 writes/day per active provider (every 10 min).

For 3 providers refreshing in series at provider-state-change time, this could be hundreds of small writes/day. Not catastrophic, but unnecessary.

The bigger concern is **boot burst**: at HA startup, all three weather providers transition `unavailable → has-state` in close succession. Each transition fires `_handle_provider_state_change`, each schedules a refresh task, each runs (serialized by `_refresh_lock`) and writes the ring. The first three writes happen in close succession during the busiest part of HA startup.

**Why it matters.** Boot performance is already a Bug Class #44 concern in this codebase. v4.7.17.2 adds 3-N persist calls during bootstrap. Tiny payloads (a few hundred bytes) but real disk I/O at the wrong time.

**Suggested fix.** Use `Store.async_delay_save()` with a coalescing delay (HA's standard pattern; e.g., 5-second delay). HA's Store layer already implements debouncing for this use case.

```python
# Replace direct async_save with delay_save
self._apparent_high_store.async_delay_save(
    lambda: {"ring": [list(entry) for entry in self._apparent_high_ring]},
    delay=5,  # seconds — coalesce within-tick repeated writes
)
```

Two side benefits:
1. The lambda is evaluated at write time, so coalesced writes always reflect the latest ring state.
2. No need for the explicit `await` in the caller — `async_delay_save` returns immediately.

Caveat: ensure the delayed save is flushed on `async_teardown`. HA Store's `async_save_data` or `async_remove` typically handles this; verify by reading HA source.

#### B-L1 — `_record_daily_apparent_high` mutates ring before persist; partial-cancel leaves memory ahead of disk

**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:597-608`
**Bug class:** Restart resilience (related to Bug Class #44)

**Issue.** The append+evict happens at lines 605-607 BEFORE `await self._persist_ring()` at line 608. If the task is cancelled between the append and the persist (e.g., during `async_teardown` because the user triggered an HA stop), in-memory ring is one entry ahead of disk.

On next setup, `_hydrate_rolling_window_from_store` replaces the in-memory ring from disk, dropping the unpersisted entry. Acceptable behavior — the next refresh recreates the entry — but worth a comment.

**Suggested fix.** Either (a) persist first then mutate (rollback semantics), or (b) add a comment acknowledging the design choice and that the cancel-window is an accepted trade-off.

Or just adopt B-M4's `async_delay_save` pattern, which eliminates the await on the hot path.

#### B-L2 — `SIGNAL_DYNAMIC_PRESET_TRANSITIONED` fires on bucket transition even when downstream override emission fails

**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:509-530, 532-557`
**Bug class:** Signal dispatch hygiene (Bug Class #45 family — payload-shape stability)

**Issue.** A bucket transition (line 511-513) updates `_active_bucket` + `_last_transition_at` AND dispatches `SIGNAL_DYNAMIC_PRESET_TRANSITIONED` at line 522. Then `_build_overrides_with_reason` is called (line 538). If that returns `([], "home_range_not_configured")` because the resolved PM seasonal lookup fails (e.g., HVAC PresetManager not yet initialized, exception caught at line 640-644), the operator sees:
- A transition signal fired.
- `_active_bucket` updated.
- Zero overrides emitted.
- Skip reason = `home_range_not_configured`.

Subscribers of `SIGNAL_DYNAMIC_PRESET_TRANSITIONED` may have updated UI based on transition; the override-applied signal `SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED` (dispatched by EC at line 2813 only when overrides actually changed) WON'T fire because the override count went from 0 to 0. Operator sees a transition with no override change → confusing.

Pre-existing pattern but amplified by v4.7.17.2 (more failure modes in the build path due to PM dependency).

**Suggested fix.** Either:
1. Defer the transition signal until AFTER `_build_overrides_with_reason` succeeds, OR
2. Add a sentinel attribute to the signal payload (`"overrides_emitted": bool`) so subscribers can filter.

Recommended: option 1. The state mutation can stay (operator's bucket truly DID transition based on relative_delta); only the signal should be conditional. Code change:

```python
# Defer dispatch until after build
_transition_happened = False
if elapsed_min >= dwell_min and _passed_boundary_with_buffer(...):
    previous = current_bucket
    self._active_bucket[zone_id] = str(fresh_bucket)
    self._last_transition_at[zone_id] = now
    current_bucket = str(fresh_bucket)
    _transition_happened = True
    _transition_payload = {...}

# ... build overrides ...

if _transition_happened and overrides:  # only dispatch on real outcome
    async_dispatcher_send(self.hass, SIGNAL_DYNAMIC_PRESET_TRANSITIONED, _transition_payload)
```

#### B-L3 — Date-boundary mixing: `dt_util.now()` for ring keys vs `dt_util.utcnow()` elsewhere

**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:484`
**Bug class:** Timezone hygiene (related to Bug Class #11)

**Issue.** Ring entries use `dt_util.now().date().isoformat()` (HA local timezone). `_cached_forecast.fetched_at` uses `dt_util.utcnow()`. For a US-Central deployment, "today" in local vs UTC differs for 5-6 hours around midnight. Edge case: a forecast arriving at 23:30 local (04:30 UTC next day) records local-today; same forecast cached as UTC-tomorrow.

In a single-timezone single-house deployment this is benign. But across an HA restart at midnight local time, two consecutive forecasts could end up under two different ISO date strings (one for local-today, one for local-tomorrow). The ring would gain an extra entry. The MIN_DAYS=7 floor masks the issue from operator-visible behavior, but the ring is slightly inflated.

**Suggested fix.** Consistently use one or the other. `dt_util.now().date()` is operator-meaningful (matches what HA's frontend displays). Keep it; just document that the "day" semantic is HA-local-time, and that hydrate's 21-day cutoff uses local-date too (which it does already — `cutoff_date = dt_util.now().date() - timedelta(days=21)`). Add a `_LOGGER.debug("apparent_high_ring keyed by local date %s", ...)` for diagnosability.

No code change urgent.

## Cross-Coordinator Interaction Summary

The v4.7.17.2 cycle increases coupling between:
- **EC** (caller of DPM, owner of skip_reasons dict, dispatcher of skip-reasons signal)
- **DPM** (under EC; now ALSO reads from HVAC's PresetManager AND mutates its `_current_season` indirectly — B-M2)
- **HVAC** (owner of PresetManager; previously isolated to HVAC's own setup path)
- **WPM** (now persists state via HA Store; new disk-I/O surface — B-M4)

The single most fragile new edge is **DPM → HVAC PresetManager mutation** (B-M2). Fixing it (read-only access) restores the coordinator-isolation discipline.
