# v4.3.2 Code Review — Arbitrage Slider Snap-Back Fix

**Tier:** 1 (Hotfix — single-method behavior fix; one file changed)
**Date:** 2026-05-06
**Predecessor:** v4.3.1

## Scope

One method body in `custom_components/universal_room_automation/number.py:457-505` (`ArbitrageSOCNumber.async_added_to_hass`). Reverts the v4.3.0 review H6 conditional that broke slider persistence across entry reloads.

## Bug summary

User reported: drag `arbitrage_soc_trigger` from 30 to 20 in EC device card, leave, reload integration, slider shows 30. Even after multiple reload attempts.

Root cause: the v4.3.0 H6 fix's `config_explicit` check was a flawed proxy for "user changed config flow this run." Since `entry.options[conf_key]` is set during initial config-flow setup and never cleared, `config_explicit` is always True after first setup. The check therefore always skipped RestoreEntity, and `__init__`'s read of `entry.options[conf_key]` always won. Slider drags went into RestoreEntity but were ignored on every reload.

The existing `OffPeakDrainNumber` works correctly because it never had the H6 conditional — it always uses RestoreEntity unconditionally.

## Fix

Remove the `config_explicit` branch. Match `OffPeakDrainNumber.async_added_to_hass` exactly: always restore from RestoreEntity if present.

The `__init__`'s seed-from-`entry.options` remains as the initial value for first-ever startup when no RestoreEntity record exists yet. From then on the slider is canonical.
