## CRITICAL Findings

### B1: SIGNAL_ENERGY_COORDINATOR_READY fires BEFORE hass.data registration -- _handle_ec_ready always gets None

**Severity:** CRITICAL
**Bug Class:** #5 (Startup Race)
**Files:** energy.py:622, switch.py:654-684, __init__.py:2030-2031

**The problem:** The entire purpose of D2 is to fix the EC startup race for sub-switches. But the fix itself has a startup race.

The signal dispatch chain is:

1. `__init__.py:2030` -- `await coordinator_manager.async_start()`
2. Inside async_start, `manager.py:267` -- `await coordinator.async_setup()` for each coordinator
3. Inside energy's async_setup, `energy.py:622` -- `async_dispatcher_send(self.hass, SIGNAL_ENERGY_COORDINATOR_READY)`
4. `__init__.py:2031` -- `hass.data[DOMAIN]["coordinator_manager"] = coordinator_manager` (AFTER async_start returns)

When the signal fires at step 3, `hass.data[DOMAIN]["coordinator_manager"]` has NOT been set yet (that happens at step 4). Every subscriber's `_handle_ec_ready()` calls `_get_energy()`, which does `self.hass.data.get(DOMAIN, {}).get("coordinator_manager")`. This returns None. The handler logs a warning and returns without restoring -- `_deferred_restore` stays True, but no further signal will fire.

**Impact:** D2 is entirely defeated in practice. The sub-switches that missed the timer chain will never restore their saved values. This is the exact symptom the feature was designed to fix.

**Fix options (ranked):**

(a) **Move `hass.data[DOMAIN]["coordinator_manager"] = coordinator_manager` to BEFORE `await coordinator_manager.async_start()`** in `__init__.py`. The coordinator_manager object is fully constructed and has all coordinators registered; the assignment just publishes the reference. Other code paths that read it should be safe since they run on the same event loop.

(b) **Alternative: have `_handle_ec_ready` access the coordinator via the signal payload** rather than via `hass.data` lookup. The signal could pass the EnergyCoordinator instance as a payload argument:
```python
async_dispatcher_send(self.hass, SIGNAL_ENERGY_COORDINATOR_READY, self)
```
And the handler receives it directly:
```python
def _handle_ec_ready(self, energy) -> None:
    ...
    setattr(energy, attr_name, self._deferred_value)
```

Option (a) is simpler and aligns with the existing SIGNAL_NM_READY pattern (NM is set into hass.data before the signal fires -- see `__init__.py:2020`). Option (b) avoids touching __init__.py but changes the signal contract.

## HIGH Findings

### B2: Force-charge override state not cleared on entry unload/reload

**Severity:** HIGH
**Bug Class:** #36 (Lifecycle teardown state leakage)
**File:** energy_pool.py:211, energy.py:3316-3336

**The problem:** `EVChargerController._force_charge_until` is an in-memory datetime that persists for the lifetime of the EVChargerController object. When the CM config entry is unloaded (or the integration reloads), `energy.async_teardown()` runs, but it does not clear `_force_charge_until`. The teardown calls `_save_evse_state()` but that method does not persist the override state.

Scenarios:

1. **Reload mid-override:** User presses the force-charge button, then reloads the CM entry. The EVChargerController is destroyed and recreated. The 30-minute window is lost. The user sees no indication -- the `override_active_until_iso` attribute on the switch goes from a valid ISO string to None without explanation. Expected: either persist and restore, or at minimum log a warning.

2. **Not a data-loss risk** (the override expires naturally), but the UX gap is that the user pressed an admin button, got a notification saying "override until HH:MM", and then a reload silently cancelled it.

**Fix:** Either (a) persist `_force_charge_until` in `_save_evse_state()` and restore it in the DB restore path, or (b) log a clear warning in `async_teardown` when an active override is being dropped, and document this as expected behavior.

### B3: ECSubSwitchesSyncedSensor.is_on only checks EC registration, NOT actual per-switch sync state

**Severity:** HIGH
**Bug Class:** #5 (Startup Race)
**File:** binary_sensor.py:1940-1945

**The problem:** The docstring and entity description say the sensor "reports whether the 5 EC sub-switches have completed their saved-state restore." But the implementation of `is_on` only checks whether `_get_energy()` returns non-None -- i.e., whether the EnergyCoordinator is registered in hass.data. It does NOT check whether any sub-switch still has `_deferred_restore == True`.

This means the sensor transitions to "no problem" (False) as soon as the EC is registered, regardless of whether the sub-switches have actually completed restore. The sensor's stated purpose -- detecting stuck restores -- is not fulfilled.

**Fix:** The sensor needs access to the actual per-switch deferred-restore state. Two approaches:
(a) Have EnergyCoordinator expose a method `sub_switches_synced() -> bool` that checks the 5 switch entities' `_deferred_restore` attributes (requires entity registry lookup).
(b) Maintain a counter on the EC side: each `_handle_ec_ready` callback decrements a "pending restores" counter on the coordinator. The sensor reads this counter.

Either way, the current implementation is a cosmetic sensor -- it tells you EC is registered, not that sub-switches are synced.

## MEDIUM Findings

### B4: button.py accesses energy._observation_mode (private attribute) and energy._send_nm_alert (private method)

**Severity:** MEDIUM
**Bug Class:** Encapsulation violation (not a numbered class -- candidate for documentation)
**File:** button.py:1302-1317

**The problem:** `EVSEForceChargeButton.async_press()` reaches into `energy._observation_mode` (private attribute) and `energy._send_nm_alert(...)` (private async method). These are implementation details of EnergyCoordinator.

If `_observation_mode` is renamed or `_send_nm_alert` signature changes, the button breaks at runtime with an AttributeError -- no static analysis or test will catch it beforehand.

**Fix:** EnergyCoordinator already exposes `observation_mode` as a public property (energy.py:3731). Use `energy.observation_mode` instead of `energy._observation_mode`. For `_send_nm_alert`, either promote it to a public method or add a dedicated `async_notify_override(message)` method on EC that handles the observation-mode gate internally.

### B5: ECEvTouSwitch.extra_state_attributes duplicates the expired-override check from get_status()

**Severity:** MEDIUM
**Bug Class:** DRY violation / divergent expiry logic
**File:** switch.py:757-771, energy_pool.py:750-759

**The problem:** Two separate code paths independently check `now_utc >= until` to decide whether the override is expired:
- `energy_pool.py:get_status()` (for sensor attrs)
- `switch.py:ECEvTouSwitch.extra_state_attributes` (for switch attrs)

Both use `dt_util.utcnow()` independently. In a race condition where the decision cycle runs between the two reads, the switch could show `override_active_until_iso: None` while the sensor still shows the ISO string (or vice versa). More importantly, if the expiry-check logic needs to change, it must be updated in three places (these two + `determine_actions`).

**Fix:** Have `ECEvTouSwitch.extra_state_attributes` read from `ev_controller.force_charge_until` (the raw property) and let a single canonical method on EVChargerController determine whether it's expired. Or simply delegate to `ev_controller.get_status()["force_charge_until_iso"]`.

### B6: sensor.py _build_situation_attrs accesses energy._tou and energy._battery (private attributes)

**Severity:** MEDIUM
**Bug Class:** Same encapsulation issue as B4
**File:** sensor.py:5828-5842

**The problem:** `_build_situation_attrs` accesses `energy._tou` and `energy._battery._get_entity(...)`. Both are private implementation details. EnergyCoordinator already exposes public properties `tou_engine` (line 3343) and `battery_strategy` (line 3348). Use those instead.

## LOW Findings

### B7: Test file sys.modules + _FIXED_NOW contaminates process-wide dt_util mock

**Severity:** LOW
**Bug Class:** Test isolation (not numbered)
**File:** test_v47x_ev_tou_hardening.py:48-101

**Confirmed contamination risk:** The test file sets `sys.modules["homeassistant.util.dt"]` with `utcnow = _fixed_utcnow` (returning `_FIXED_NOW = datetime(2026, 5, 27, 14, 0, 0, tzinfo=timezone.utc)`) at module import time via `sys.modules.setdefault(...)`. Since it uses `setdefault`, it will NOT overwrite if another test file already loaded the real `homeassistant.util.dt`. However:

1. If THIS file loads FIRST in the pytest collection order, its mock becomes the process-wide `homeassistant.util.dt` module for all subsequent imports.
2. The `test_v47x_weather_manager.py` file has its OWN `_FIXED_NOW` at a different time (and uses the same `setdefault` pattern). Whichever loads first wins.
3. The D3 tests explicitly work around this by using far-future (2099) and far-past (2000) timestamps instead of relying on `_FIXED_NOW`, which is good defensive practice. But the `_build_situation_attrs` tests in D4 might be sensitive to the exact `utcnow()` return if the grid-cost computation executes.

**Impact:** The user's heads-up is confirmed. When run in the full suite, test execution order determines which `_FIXED_NOW` value `homeassistant.util.dt.utcnow()` returns globally. This can cause spurious failures in time-sensitive weather tests.

**Mitigation (not in scope for this cycle):** Each test file should use `unittest.mock.patch` to scope its time mocks to individual test methods/classes, rather than mutating `sys.modules` at import time.

### B8: binary_sensor.py uses dt_util.dt.datetime type hint at class level

**Severity:** LOW
**Bug Class:** Fragile type reference
**File:** binary_sensor.py:1939

```python
self._ec_ready_at: dt_util.dt.datetime | None = None
```

This references `dt_util.dt.datetime` -- i.e., `homeassistant.util.dt` -> its `dt` sub-attribute (which is Python's `datetime` module) -> `datetime` class. This works because HA's `dt` module imports `datetime as dt` internally. But it is fragile: a direct `from datetime import datetime` would be clearer and less dependent on HA's internal import alias.

### B9: No test coverage for ECEvTouSwitch.extra_state_attributes

**Severity:** LOW
**Bug Class:** Test gap
**File:** switch.py:749-771

The new `ECEvTouSwitch` subclass adds `extra_state_attributes` that checks the force-charge override. No test exercises this property. The D3 tests exercise the controller layer (`EVChargerController.get_status()`) but not the switch entity's attribute rendering. A test should verify that:
- When no override is active, attrs include `{"override_active_until_iso": None}`
- When override is active, attrs include the ISO string
- When EC is not registered, attrs is `{}`

## Positive Findings (Things Done Right)

**Bug Class #42 compliance:** All new callback registrations use bound methods (`self._handle_ec_ready`, `self._handle_ready`, `self._handle_update`). Zero lambda wrappers around `async_create_task`. The `_handle_ec_ready` method is correctly decorated `@callback` (synchronous) -- no `async_create_task` call, no coroutine creation. Full compliance with the v4.6.15 lesson.

**Bug Class #38 compliance:** Every `async_dispatcher_connect` call in switch.py, binary_sensor.py, and button.py is wrapped in `self.async_on_remove(...)`. No listener leaks on reload.

**Bug Class #19 compliance:** The D2 signal-driven approach replaces timer-based retries with event-driven completion. The timer chain is kept as a fast-path but the signal is the unbounded fallback. No new `async_create_task` calls introduced. The `_retry_restore` chain correctly keeps `_deferred_restore = True` when retries exhaust, allowing the signal handler to complete the job.

**Bug Class #11/#21 (timezone):** All override timestamps use UTC-aware datetimes via `dt_util.utcnow()`. The `set_force_charge_override` contract documents that the caller must supply UTC-aware datetime. `button.py:async_press` uses `dt_util.utcnow() + timedelta(minutes=30)` which is correct.

**D1 strict re-pause:** The `_paused_by_us` guard removal is clean. The set is still used correctly for the *resume* path (off-peak only resumes EVSEs that URA paused). The enforcement path (peak/mid_peak) now re-issues `switch.turn_off` idempotently every tick. Force-charge override check is evaluated once before the EVSE loop (not per-EVSE), which is correct since the override is global.

**D4 sensor enrichment:** `_build_situation_attrs` is wrapped in a try/except that never lets D4 break the sensor read. All computation is over already-loaded state (no I/O, no DB queries). This is clean.
