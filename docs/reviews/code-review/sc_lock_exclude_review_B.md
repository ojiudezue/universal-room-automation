## Findings

| # | SEV | Site | Bug class | Finding |
|---|---|---|---|---|
| B1 | MEDIUM | `_async_away_engage` ~:1774-1813 | Stale snapshot across await / reentrancy | `cfg` is captured once and the loop `await`s `lock.lock` per entity. A release that lands mid-loop (`on_hazard`, away switch OFF, an arrival, or `_away_release_on_disable`) clears/unlocks the targets so far, but the loop keeps going and the next entity passes `away_lock_predicate(ent, cfg)` against the stale cfg. Hazard and dwell are still satisfied (persons still not_home), so a 2nd away-lock entity gets **locked after a hazard release**. The same applies to kill-switch OFF, because the predicate reads `away_lock_on(cfg)` from the snapshot. Repro: two away-lock entities, all away, dwell fires, smoke CO alarm hazard runs on the yield after entity 1's `async_call`, and entity 2 still gets `lock.lock`. Fix: before each entity, re-read `cfg = self._cfg()` and bail out if a release epoch counter (bumped in `_away_release` / `_away_release_on_disable`) has changed since the engage started. |
| B2 | MEDIUM | `_away_attempted` not persisted (:207, `_store_payload` :1749) | Restart resets one-shot latch (M6) | The since-stamps are persisted (H1), but `_away_attempted` is not. After any restart or CM reload mid-outing, `_on_boot_recheck` -> `_away_rearm` sees due already in the past and engages again. Effects: (a) a door a human unlocked after the engage (ownership_lost, which should be final for this formation) gets re-locked; (b) the passage-mode LOW advisory fires again on every restart. Repro: away lock engages at T, at-home guest unlocks E at T+1h, HA update restarts at T+2h, and at boot+120 s E gets `lock.lock`. Fix: persist an `away_attempted_formation` marker (e.g. the max since-stamp at attempt time) and treat it as attempted while the stamps are unchanged. |
| B3 | LOW | `_away_setup` :625-641 | Restart edge | An owned lock whose listed person already reads `home` at setup (arrived while HA was down) is never released. The restored edge (`old_val is None`) is skipped by design and no setup/boot-recheck reconcile exists. E stays locked until a human unlocks it. The fail-safe direction is to release owned locks at boot recheck when any listed person reads home. |
| B4 | LOW | `_away_release` :895-901 | Ownership leak | If the entity is in flight only (never owned) and its state reads unavailable/unknown, the in-flight entry is popped and the entity is skipped, but it is not in `away_lock_owned`. If the lock later comes back `locked`, nothing owns it and a later release won't unlock it. Keep it in `away_lock_owned` when skipping. |
| B5 | LOW | `_save_store` :1763 + per-reload `Store(...)` (security.py:706) | Delayed-save across reload | `async_delay_save(…, 1.0)`; teardown does not flush, and each SC setup builds a new `Store`. An ownership change less than 1 s before a CM reload (e.g. editing `security_away_lock_entities`, a reload key) can be lost: the old timer writes, then the new instance's setup save overwrites with its stale load. The same residual exists for `residents`. Sub-second, operator-edit-triggered. Fix: `await self._store.async_save(self._store_payload())` in `async_teardown`. |
| B6 | LOW | `_away_on_person` / live edit of `security_away_lock_persons` | Live-read without re-evaluation | Adding a person who is already `not_home` to the list gives them no since-stamp until their next edge, so `_away_due_ts` returns None and nothing engages. Removing the last at-home person from the list doesn't rearm either. Documented-acceptable (parallels INV-5 "OFF->ON never catches up"); note it in the SC doc. |

## Cleared (holds because)

- **Timers/listeners teardown**: `_away_dwell_unsub` is in the teardown attr list (:622), `_away_readback_unsubs` is cleared (:313-315), the away-lock state tracker is appended to `_other_unsubs` (:524-528), and the engage task goes through `_spawn` -> `_tasks` and is cancelled at teardown (:650). Each callback checks `_torn_down` first.
- **@callback (#64)**: `_on_away_dwell`, `_on_away_readback`, `_on_away_lock_event` carry the module `callback` shim (:55-67), which sets `_hass_callback` explicitly. The partial-wrapped readback follows the same pattern as the shipped garage `_on_readback`.
- **H2 read-back vs arrival**: the in-flight entry is set before the `await` (:795). `_away_release` pops it, cancels the read-back, and unlocks even when the state still reads unlocked (:896-907). The engage loop's `if ent not in inflight: continue` (:804) stops the read-back from re-arming. `_on_away_lock_event` ignores in-flight entities (:875). Holds, apart from the next-entity case in B1.
- **Store merge-writes**: `_store_payload` always serialises all three keys from memory. Load is per-key and guarded (:975-991), and a corrupt away key cannot poison `residents`.
- **Boot window**: `_in_boot_window` == `GARAGE_LOCKOUT_BOOT_RECHECK_S` (120 s), so edges inside the window don't arm and `_on_boot_recheck` re-arms (:597). Restored edges (`old_val None`) never release.
- **Person subscriptions**: every `person.*` is subscribed (:504-505), so away-lock persons who are lockout-excluded still get edges. `_last_real` is now kept for all persons, and garage effects stay resident-gated (:433-439).
- **CM reload vs live-read keys**: `security_lock_sweep_exclude`, `away_lock_enabled` and `away_lock_persons` are in both `_NO_LIVE_ATTR_KEYS` and `OPTIONS_RELOAD_SUPPRESS_KEYS` (`__init__.py`). `away_lock_entities` reloads because its tracker is registered at setup. The two are consistent.
- **Switch-off routing / garage byte-identical**: `switch.py:5261` passes `self._conf_key`. The garage key falls through to the unchanged branch (`on_kill_switch_changed`, :385+), and the away key returns before touching `reason`/`release_gen`/re-engage. The `_notify_failure` refactor builds the same garage coro (`_garage_failure_coro`). `_record` keeps the garage record shape. The garage suite (240 tests) passes.
- **SC-disable release**: `async_release_if_disabled` runs the garage branch and then `_away_release_on_disable`, independently of the garage kill switch (M4). Unlocks are bounded by `GARAGE_LOCKOUT_TEARDOWN_RELEASE_TIMEOUT_S`. (The dwell can still fire during the garage branch's awaits; that is covered by B1's epoch fix.)
- **Aggregator/optimizer consumers**: `locks_excluded` is added via `.get(..., 0)` with a stable key shape (`sensor.py:7773`). `get_compliance_summary` filters by key so the rate stays at or below 100 %. `house_status.doors` wraps `_sweep_excluded` in try/except. `_sweep_excluded` reads cfg live and never raises.

## Verdict

**FIX-REQUIRED (MEDIUM)**: B1 and B2. Neither is a garage-lockout regression; both are away-lock behaviours that violate the stated M6/hazard intent on reachable paths. LOWs B3-B5 are worth fixing in the same pass (each 1-10 LoC); document B6.
