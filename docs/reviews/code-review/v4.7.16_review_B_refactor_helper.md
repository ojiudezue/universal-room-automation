- Outer `try/except` at line 2074-2168 wraps the entire zone-iteration loop. Any uncaught exception inside the loop is logged at WARNING and resets `self._v4716_zone_verdicts = {}` (line 2168) — fail-safe. [B1.OK-3]

- Early-boot fail-open: line 2078-2083 — if `person_coordinator is None` OR `get_ble_tier` attribute missing, every room is assigned `weight=1.0`. This matches the plan §4 "Rooms with no `CONF_SCANNER_AREAS` configured continue to be classified as Tier 1". [B1.OK-4]

The helper call proceeds (line 2114-2135); if helper returns `VetoDecision(False, ...)` or None, the verdict is recorded but no downstream side effect fires. **No accidental veto of a legitimately-empty zone.** [B1.OK-6]

### Findings

#### B1.MEDIUM-1 — Per-cycle cost is real, downstream consumers are zero

[`presence.py:2057-2168`]

D3 runs every `_run_inference` cycle. For each zone (~5-15 in operator's house), it iterates `tracker.room_names` (~2-6 rooms per zone), calls `person_coordinator.get_ble_tier(room_name)` per room, builds a `state_context` dict per zone, calls `should_veto_due_to_reliable_signals` per zone (currently always returns None because helper missing), and writes `self._v4716_zone_verdicts[zone_name] = {...}` per zone.

`person_coordinator.get_ble_tier` (`person_coordinator.py:1163-1209`) is itself non-trivial — on a Tier 1 short-circuit it is fast (`norm in self._direct_ble_rooms`), but on Tier 2 / 0 it walks **every** URA config entry via `hass.config_entries.async_entries(DOMAIN)` (line 1190) and string-normalizes each `room_name` (line 1197). For a house with ~30 URA entries and ~10 zones × ~4 rooms = 40 weight lookups per cycle, this is ~40 × ~30 = ~1200 string normalizations per cycle.

**No downstream code reads `_v4716_zone_verdicts`** (grep verified: `_v4716_zone_verdicts` has 5 hits — all writes/inits inside `presence.py`; zero readers). D3 is currently a fully side-effect-free computation whose only artifact is the per-cycle dict.

This is not a correctness bug — but it consumes per-tick CPU for diagnostic data that nothing observes. Plan §6 Reviewer B explicitly asks "What's the per-cycle wall-clock overhead on a 30-room install?" — there is no perf benchmark in `quality/tests/test_v4716_room_veto_density.py` that measures it.

**Action:** acceptable to ship as-is (the work is bounded and the plan explicitly describes D3 as wiring scaffolding for v4.7.16's downstream cycles). **Should flag for v4.7.15 build agent**: when the helper lands, surface verdicts via a sensor attribute or diagnostic — otherwise the per-cycle cost remains unjustified.

#### B1.MEDIUM-2 — D3 runs during `house_state == "sleep"`; produces verdicts that may mislead

[`presence.py:2057-2168`]

There is no guard on `house_state` before the D3 loop. During sleep, room sensors are intentionally degenerate (mmWave drops motionless body, PIR can't fire, cameras blind) — this is the EXACT scenario v4.7.13 was built to handle in the zone aggregator's `is_on` path (`aggregation.py:3201-3203` calls `_sleep_person_fallback_occupied`).

But D3 doesn't know any of that. It computes `weights[room_name] = 1.0` for Tier 1 rooms regardless of sleep state, sums them into `aggregate_weight`, calls the helper (which won't match because scope="room_level_weighted" isn't in Patterns A-D), and records the result. **If a v4.7.16.x cycle later wires `_v4716_zone_verdicts` into downstream gating without adding a sleep-state carve-out, the gating will fire incorrectly during sleep** — the room's BLE-tier-1 weight will look like a strong "I should be occupied" signal even when sensors are silent because the occupant is motionless asleep.

This is a forward-looking risk, not a current bug. The verdict has no consumer today. But the planning doc §3 D3 ("Boundary case — what happens when all weights are 0") only considers the inverse case (Tier 0 zones); it does not consider the SLEEP case where Tier 1 rooms still show high weights but the underlying sensor data is structurally degraded.

**Action:** when wiring `_v4716_zone_verdicts` into a future consumer, add a `house_state == "sleep"` short-circuit (probably: skip D3 entirely during sleep, or set all weights to 0 during sleep — matches v4.7.13's design intent of trusting person-tracker over sensor data during sleep). **Surface this as a v4.7.16-pre-followup note.**

#### B1.LOW-1 — Redundant `_v4716_zone_verdicts` re-init shadows `__init__` site

[`presence.py:560` and `:2073`]

Line 560 initializes `self._v4716_zone_verdicts: Dict[str, Dict[str, Any]] = {}` in `__init__`. Line 2073 re-initializes the same field at the top of every `_run_inference` cycle. The re-init at line 2073 is correct (we want fresh data per tick), but the annotation `Dict[str, Dict[str, Any]]` repeated at line 2073 is misleading — Python doesn't enforce it at runtime, and type-checker convention is to annotate only once.

**Action:** drop the type annotation at line 2073 (`self._v4716_zone_verdicts = {}`) to make it clear this is a reset, not a new declaration. Cosmetic.

### Verified facts

- `should_veto_due_to_reliable_signals` does **NOT** exist anywhere in the codebase yet (grep verified: 0 implementations; 3 references — all in v4.7.16's own D3 block). [B2.OK-1]

- v4.7.16 D3 uses `getattr(self, "should_veto_due_to_reliable_signals", None)` at `presence.py:2111-2113`. The `if helper is not None:` guard at line 2114 means a None return from `getattr` correctly skips the call. **No TypeError risk when helper is absent.** [B2.OK-2]

- `VetoDecision` shape: builder reads `.fired`, `.confidence`, `.reason` via `getattr` with safe defaults (lines 2147, 2152, 2157). v4.7.15 plan §3 D1 declares `VetoDecision` as `@dataclass(frozen=True)` with exactly those three fields. **Shape compatible.** [B2.OK-4]

### Findings

#### B2.HIGH-1 — `state_context.scope="room_level_weighted"` is NOT in v4.7.15 plan's Patterns A-D; helper will silently return fired=False

[`presence.py:2118-2129` and `docs/planning/PLANNING_v4.7.15_universalize_bug_class_48_veto.md:207-256`]

v4.7.15 plan §3 D1 enumerates four scopes in the helper body:

| Pattern | Scope | Triggers |
|---|---|---|
| A | `"house_inference"` | `all_tracked_persons_away` + `unidentified_count==0` |
| B | `"zone_aggregator"` + `house_state=="sleep"` | `zone_persons_home` |
| C | `"zone_aggregator"` + non-sleep states | `zone_persons_home` + sustained quiet |
| D | `"waking_transition"` | `person_tracker_home` + sustained occupancy |
| (default) | anything else | `VetoDecision(False, 0.0, "")` |

v4.7.16 D3 calls with `state_context["scope"] = "room_level_weighted"` (line 2119). This matches none of A/B/C/D. v4.7.15's helper will fall through to the default `return VetoDecision(False, 0.0, "")` (plan line 255).

Worse: the call passes `reliable_signals=[]` and `transient_signals=[]` (lines 2116-2117). Even if v4.7.15 adds a Pattern E for `"room_level_weighted"`, the helper has no signals to evaluate — all the weighting data lives in `state_context["room_weights"]` and `state_context["aggregate_weight"]`. The v4.7.15 helper signature explicitly treats `reliable_signals` and `transient_signals` as the discriminator lists; `state_context` is meant for ambient context (house_state, zone_name, timestamps). This is an **architectural mismatch**, not a typo.

Three remediation paths exist; pick one and document in v4.7.15's build:

1. **Add Pattern E inside the helper** that switches on `state_context["scope"] == "room_level_weighted"` and consumes `state_context["aggregate_weight"]` directly (ignoring the empty signal lists). Slightly awkward — breaks the helper's signal-driven design — but minimal change to v4.7.16.

2. **Reshape D3 to translate weights into `reliable_signals`** — e.g. emit `ReliableSignal(kind="ble_proximity_present", value=True)` for each Tier-1 room and let v4.7.15's Pattern A logic handle the aggregation. Requires defining a new `kind` in v4.7.15's enumeration AND modifying D3's call site. Cleaner design, larger change.

3. **Accept that v4.7.16 D3 is diagnostic-only** until a v4.7.16.x follow-up wires it properly. D3 already records the verdict in `_v4716_zone_verdicts` — operators get visibility into weights/aggregate even though the helper isn't matching. **This is essentially what's shipped today.**

**Action:** the planning doc §0.7 explicitly mitigates this ("if v4.7.15 ships with a different helper signature than this doc assumes, D3 in this cycle is the integration point and will be re-spec'd in a v4.7.16-pre-build note"). The mitigation has implicitly already kicked in — D3 is calling against an incompatible contract. **For ship purposes this is acceptable** because the helper is missing entirely; the verdict-recording code is harmless. **For v4.7.15 build agent: read §"B2 v4.7.15 helper-signature handoff requirement" below.**

## B2 v4.7.15 helper-signature handoff requirement

**This subsection exists so the v4.7.15 builder and fix-up agents do not silently let the gap persist.**

When v4.7.15 D1 ships and the helper becomes callable on `PresenceCoordinator`, v4.7.16's D3 block at `presence.py:2057-2168` will start invoking it with:

- `reliable_signals = []`
- `transient_signals = []`
- `state_context = { "scope": "room_level_weighted", "zone_name": <str>, "house_state": <str>, "room_weights": <dict>, "aggregate_weight": <float>, "all_tracked_persons_away": <bool>, "tracked_count": <int>, "now": <datetime> }`

The v4.7.15 plan's Patterns A-D do **NOT** recognize `scope="room_level_weighted"`. Default fallthrough returns `VetoDecision(False, 0.0, "")` — harmless but means v4.7.16's diagnostic block writes `veto_fired=False, veto_confidence=0.0, veto_reason=""` to every zone's verdict dict regardless of the actual weighting.

**Required v4.7.15 actions (pick one):**

A. **Recommended:** add Pattern E inside `should_veto_due_to_reliable_signals` that recognizes `scope == "room_level_weighted"` and gates on `state_context["all_tracked_persons_away"]` + `state_context["aggregate_weight"]` thresholds (e.g., if all persons away AND aggregate_weight < 1.0 → veto). Document the threshold semantics in v4.7.15 plan addendum.

B. Alternative: in v4.7.15's helper, document that `room_level_weighted` is explicitly OUT of scope for v4.7.15 — the helper will return `fired=False`. v4.7.16's D3 then becomes a documented stub that v4.7.16.x will rewire after v4.7.15 establishes the helper.

C. Wholesale alternative: v4.7.16.x rewrites D3 to construct `reliable_signals` properly (e.g., `ReliableSignal(kind="ble_proximity_present", value=True)` per Tier-1 room) and call with `scope="house_inference"` so Pattern A applies. This effectively dissolves v4.7.16 D3 into v4.7.15's Pattern A.

**Required test addition (in v4.7.15 or v4.7.16.x):** a behavioral test that mounts D3's call and asserts the helper returns the expected verdict. Currently the only test is a source-grep that confirms the helper-signature comment exists (`test_verify_helper_signature_comment_present` at `quality/tests/test_v4716_room_veto_density.py:384`) — that does not exercise the contract.

**Where this is logged for v4.7.15 build pickup:** this section. Also captured in the build report? — confirm during v4.7.15 D1 build.
