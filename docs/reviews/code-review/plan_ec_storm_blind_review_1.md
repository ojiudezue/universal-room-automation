## HIGH

**H1. INV-2 does not cover the EVSE overlay, and the overlay writes the reserve on every blind tick.** `_apply_evse_battery_hold` runs on the decision after `determine_mode` returns (`energy.py:6468`, `:7183`). It has an append branch (`energy.py:5463-5528`) for when the decision has no reserve action. That branch appends `number.set_value(max(hold_soc, _last_reserve_level_desired, dp))` with **no deadband**: its only gate is stand-down. `_evse_hold_soc` is captured when the hold starts (`:6467`). If an EVSE was charging before the Envoy went blind, the value stays an int all through the blind episode. Repro: EVSE charging at SOC 55, then the Envoy goes fully blind. On each blind tick where `_reserve_action` hits the deadband and returns None, the overlay appends a write, and C1 logs a row. INV-2's "steady blind hold gives zero reserve actions after the first" is then false. Stage A Live (b) breaks too: the overlay reason is `"Envoy unavailable …" + " + EVSE hold"`, so it matches the "starts with Envoy unavailable" query. Edge case 6 claims "no 45 write", but the overlay actually writes 60 on every tick. **Fix:** scope INV-2 explicitly to the post-overlay action list. Then either (a) give the blind case a deadband in the overlay append branch, which breaks Non-goal 1's "overlay internals unchanged" and needs saying so, or (b) state the overlay re-send as a known limit, reword INV-2 and Live (b) to exclude `+ EVSE hold`, and add `test_blind_hold_with_standing_evse_hold`.

**H2. The "governor golden unchanged" acceptance is already false for the `blind` case.** In `quality/tests/fixtures/reserve_governor_golden.json`, the `blind` case has `"last_reserve_level_desired": null` and an unconditional `set_value 10`. D-A3 stamps `_last_reserve_level_desired` in the blind branch, which changes that key. It also routes de-escalation through `_reserve_action`, which adds the ≥2 deadband and the stand-down skip. Today the de-escalation write at `energy_battery.py:5662-5668` has neither, so the action list changes whenever the hardware is already within 2 of `reserve_soc`. The plan says "if any case differs, stop", so the builder will stop on an intended change. **Fix:** limit the golden-unchanged criterion to the seven sighted cases. Re-baseline `blind` with a stated diff (desired stamped, de-escalation now behind the deadband and stand-down), and list that in the README's behaviour changes.

**H3. D-B1's polygon demotion contradicts design principle 1 and the D-B2 "no-regression" claim.** Principle 1 says locality "never demotes a HOLD-warn product". D-B1 says SVR/TOR/EWW "are classified at most `notice`" unless P2(b) proves `?point=` is polygon-exact, and P2(b)'s stated default is "not built". Today SVR/TOR hold through the substring list (`inclement.py:141-149`). D-B2 calls keeping them "a no-regression choice". So under the default probe outcome, a Tornado Warning returned by the point query is demoted from full_hold to notice. That is a strict loss of protection on the highest-consequence product, and the one direction the plan's own asymmetry argument forbids. **Fix:** pick one rule. Either "an alert the point query returns is local; polygon checks can only *confirm*", so SVR/TOR stay at table tier when P2(b) is NO, which matches principle 1. Or make the demotion an explicit, operator-approved supersession with its own acceptance criterion. Correct INV-3 and `test_svr_not_point_local_is_notice` to match.

**H4. D-B3's staleness trigger can't fire in the scenario it exists for.** The integration source shows two things. (1) `last_updated` is a **separate sensor entity** (`sensor.py:19-24`, the `SENSOR_TYPES["last_updated"]` timestamp sensor), not an attribute of the alerts sensor that `_read_nws_alerts` reads (`energy_battery.py:2640-2653`, which reads only `attributes.Alerts`). (2) Both entities are `CoordinatorEntity`s. When the API fetch fails, `coordinator.py:138-144` raises `UpdateFailed`. The usual HA contract is that `CoordinatorEntity.available` then follows `last_update_success`, so the alerts sensor goes `unavailable`, its attributes disappear, `_read_nws_alerts` returns None, and the hold drops on the next tick. I'm citing that contract, not a line I read this session, so P2 should confirm it from recorder history. The trigger also involves a naive `datetime.now()` (`coordinator.py:126,182`), which is a timezone hazard. "A storm can take the internet down" therefore leads to an unavailable entity, not a stale timestamp. The keep-known-holds branch never engages, and the plan has no field to configure the `last_updated` entity. **Fix:** key D-B3 on "the alerts entity is unavailable/unknown, or its `state.last_updated` is older than `NWS_ALERTS_STALE_S`". Use the HA State object's own `last_updated`/`last_reported`, which needs no second entity. Keep the last classified HOLD set in RAM to support that. Add P2(e): recorder history of the alerts entity across a known internet drop. Acceptance should be "alerts entity unavailable plus a known WSW keeps the hold to Ends".

**H5. D-L2's calendar role will not resolve on this house.** The plan adds "new EC role `grid_event_calendar`, defaulted in `EC_ROLE_KEY_DEFAULTS`, with no UI field". `EC_ROLE_KEY_DEFAULTS` reaches options only through the one-shot pin in `__init__.py:820-900`. That pin is idempotent on `EC_DEFAULTS_PINNED_FLAG`, which is already set on this install, and it stamps the version without re-running (`__init__.py:791, 892`). `_get_entity` returns `self._entities.get(key, default)` (`energy_battery.py`, `_get_entity`), and Rev 5 removed house-specific code defaults. Net effect: the sweep has no entity, writes nothing, and Live (b) ("N > 0") fails. That would at least be a discriminating failure, but it's built in. Re-running the pin means an options write, which the plan forbids everywhere else (reload hazard). **Fix:** state the resolution mechanism. Options: a second versioned pin that writes only the new key, with the reload-suppress reasoning written out; or an options-flow field, which conflicts with Non-goal 6, so it needs the operator; or a registry lookup at call time. Add an acceptance criterion: "role resolves on this house after restart, with no `async_update_entry` in the log".

**H6. P3-02 is marked "Fixed", but the review's actual request is unmet, and edge case 9 goes the other way.** P3-02 asked for "a test: blind hold, operator manually lowers reserve, no re-dispatch". That was the 2026-07-15 lesson that v5.17.5 D3 encoded. The plan answers with no stamp (correct for the sweep), but edge case 9 says the next blind tick "re-asserts the floor" from the *decision* side. `_reserve_action` compares against the live write-leg state, sees the operator's lower value, and re-writes. That may be the right call under the floor-write exception in the operator doctrine, but it reintroduces the fight-the-operator behaviour through a different path, and §11 records it as fixed. **Fix:** move P3-02 to "Superseded by decision: blind re-asserts only the registered floor; operator escape = EC enable switch", get an explicit operator ack at the plan checkpoint, and add `test_blind_hold_reasserts_floor_after_manual_lower` with the intended assertion stated, whichever way the operator rules.

## MEDIUM

**M1. `force_redispatch` is not "gated off under blind" for the first ~10 minutes.** The I-D3 gate is `_desired_stamped_at` age > 600 s (`energy_battery.py:6750-6772`). The decision tick is about 5 min, so for one or two blind ticks the stamp is still fresh from the last sighted tick, and a write-verify watchdog retry can re-send `_effective_reserve_desired` (`energy_write_verify.py:1707-1735`). That composes the desire, which blind now stamps, with the inclement floor, which blind now updates. §5 and INV-2 ("at most one reserve set_value") don't count this path. The value respects the floor, so INV-1 is safe, but the INV-2 count is not. State it as a known limit, or have the blind branch invalidate the stamp. Writing None to `_desired_stamped_at` is not a "refresh", but it does change I-D3 semantics, so get it reviewed.

**M2. `_reserve_action(reserve_level) -> dict | None` loses the folded value.** `_result` must stamp `_last_reserve_level_desired` from the post-fold value (D-A2, `:6532-6534` today), and the blind branch must stamp "the target it computed". When the deadband suppresses the action, the dict is None and the folded target is gone. Specify `-> tuple[int | None, dict | None]` (folded target, action), or have the fold live in a separate pure `_fold_reserve(level)` that both callers use before `_reserve_action`. Otherwise the builder re-derives the fold, which puts a second fold site in the code (Bug Class #53).

**M3. The blind hold base is undefined when both sources are None.** D-A3.2 uses `base = _last_reserve_level_desired or write-leg state`. After a restart into blind, desired is None, and with the Envoy blind and the cloud degraded the write-leg state can be None too. `max(F, None)` raises. Specify: base None means emit F, and `_blind_pre_raise = None`, so release targets `reserve_soc` (or no release; say which). Add a test.

**M4. Stage L ships before Stage A, but its producers assume the decision runs while blind.** D-L1 writes "on each decision tick" and the D-L2 open row "embeds the current inclement decision". Until Stage A ships, a fully blind tick returns at `energy_battery.py:5576` before `_inclement_decision`. So in the exact episodes the ledger exists for (outage plus blind Envoy), alerts first seen while blind are not logged, and the open row carries a stale `_last_inclement_decision`. Either hook D-L1 to the alerts read independently of the blind gate (`_read_nws_alerts` is a pure state read), or record `decision_age_s` in the open row and say so.

**M5. About 19 `"off_peak"` literal sites outside inclement are unclassified, and the Stage D pin misses them.** A grep of `(==|!=) "off_peak"` / `in ("off_peak"` gives energy.py 8, energy_battery.py 5 (including the `tou_transition_into == "off_peak"` chunk reset in `determine_mode`), energy_pool.py 5, energy_tou.py 3, hvac_predict.py 1, sensor.py 2. Each of these is an "is bottom rate" decision and has the same portability rationale as the 9 H sites. The `TOU_PERIOD_NAME_LITERAL_SITES` pin as written only catches new `peak`/`mid_peak` literals. Classify them in §8 (they are probably all H-equivalent and byte-identical) and extend the pin, or state the exclusion and why.

**M6. Stage A's "Depends on: none" contradicts the arc's gate.** Arc step 2's gate is "Governor live-validated" (`ARC_energy_coordinator_resilience.md:17`). The status log says there are no `reserve_write` rows yet because the Envoy is hung. Stage A's Live (b)/(c) read those rows. Make Stage A depend on the governor's live row check passing, or record the operator waiving the arc gate.

**M7. Interaction with arc steps 8 and 9 is not stated (the parked-trigger sweep).** EC-OBSERVATION-MODE-RESERVE-BYPASS-1 says the CM evaluate path ignores observation mode. The timer path gates at `energy.py:6591`. INV-4 makes blind de-escalation fire on `tou_transition_into` top rank, which is a new trigger at every shoulder/winter 17:00 (and winter 05:00) edge. Those edges are exactly where the evaluate path runs `determine_mode` (`energy.py:7164`). So Stage A widens a known observation-mode bypass from summer-peak-only to every day, and B-L1's double consume can produce two de-escalation dispatches per edge. Non-goal 7 excludes fixing steps 8-11, which is fine, but the plan must name this widening, and either sequence step 8 before Stage A or accept it as a known limit with the operator.

**M8. INV-1's live falsifier can't see full_hold or the blind floor.** The governor row's `inclement_floor`/`floor_ok` is partial_hold only (`energy.py:9150-9160`), and Non-goal 1 freezes the row. A sub-floor write under sighted full_hold, or under the blind `max(reserve_soc, partial, 60)` floor, leaves no row-level evidence. Say that INV-1 for full_hold and the blind floor is provable in-suite only, or allow one additive row field, `tick_floor`. That is a payload change and would need its own Tier 2-DB note.

**M9. The §4 consumer table is incomplete for the decision and the floor.** Missing: `sensor.py:9376-9385` (eight `inclement_*` strategy attrs, display; `inclement_expires_at` changes meaning under D-B1); `energy.py:10438-10452` (ladder validator reads `partial_hold_reserve_floor`; config, not decision, but a `reserve_floor` consumer); `_resolve_hold_owner` (`energy_write_verify.py:1752-1760`, which now sees blind-tick decisions and so changes the row's `hold_owner` during blind); the `hold_depth` threading through the attain/arbitrage helpers (`energy_battery.py:5042-5445`). The `energy_write_verify.py:1933` citation is a comment. The live reads are `_inclement_partial_hold_floor` at `:1659`, called from `:1730` and `:1935`.
