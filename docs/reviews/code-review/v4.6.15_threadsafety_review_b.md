## Summary

- Files changed: 2 (sensor.py, notification_manager.py)

## Findings

### B1 — `functools.partial(async_method)` + iscoroutinefunction (MEDIUM, downgraded from hypothetical CRITICAL)

**Status:** SAFE on HA core (no action needed)

The task brief flagged a potential CRITICAL: `inspect.iscoroutinefunction(functools.partial(async_method))` returns `False` on Python 3.10 and earlier, which would cause HA's `HassJob` to misclassify the partial as `Callback` instead of `Coroutinefunction`, meaning the coroutine would be created but never awaited — the exact bug we're fixing, re-introduced.

Local Python 3.9.6 confirms `iscoroutinefunction(partial)` returns False.

**However, HA's `get_hassjob_callable_job_type()` explicitly unwraps partials before checking:**
```python
def get_hassjob_callable_job_type(target):
    check_target = target
    while isinstance(check_target, functools.partial):
        check_target = check_target.func
    if inspect.iscoroutinefunction(check_target):
        return HassJobType.Coroutinefunction
    ...
```

`partial(self._fire_digest, person_id, person_cfg)` will be unwrapped to `self._fire_digest`, which IS a coroutine function, so HassJob classifies it correctly. The digest WILL fire correctly.

**Verdict:** Safe regardless of Python version. HA core handles this case explicitly.

### B2 — `_handle_db_ready` callbacks use `async_create_task` (MEDIUM, NOT a ship blocker)

**Bug class:** #19 (Untracked Background Tasks) — partial overlap

Two `_handle_db_ready` callbacks in sensor.py (lines 11425-11426 and 11551-11552) still use:
```python
def _handle_db_ready(*_a, **_kw) -> None:
    self.hass.async_create_task(self._async_refresh())
```

**The dispatcher path verification:**
- `async_dispatcher_send` (sender) has internal `hass.verify_event_loop_thread()` assertion
- `SIGNAL_DATABASE_READY` is dispatched from `__init__.py` inside an `async` setup function
- Therefore the callback is guaranteed to run on-loop
- Therefore `hass.async_create_task()` is called from the event loop thread and will NOT trigger the frame-helper warning

**This is a fundamentally different context** from the timer-callback sites that were fixed. Timer callbacks could fire from HA's scheduler thread; this dispatcher callback is on-loop.

**Remaining concerns:**
1. The task created by `async_create_task` is untracked (Bug Class #19) — if the entity is removed before the task completes, the task could write to a torn-down entity. Pre-existing issue, not introduced by this fix.
2. One-shot callbacks (self-unsubscribe after first fire), so the exposure window is narrow (only during startup when DB initializes after the sensor).

**Verdict:** Not a regression from this fix. Recommend a follow-up ticket to convert to awaited calls (e.g., make `_handle_db_ready` async since dispatcher supports async callbacks per HA source), but NOT a ship blocker.

### B3 — Timer fires during entity removal race window (LOW)

**Bug class:** #38 (async_listen unsubscribes tracked)

The cleanup pattern is:
```python
self.async_on_remove(
    lambda: self._unsub_timer() if self._unsub_timer else None
)
```

In HA's single-threaded event loop, `async_remove` and timer callbacks are both scheduled on the same loop. The unsub callback executes synchronously (it's a `@callback`-decorated callable). Between the point where `async_remove` starts and the unsub fires, no timer tick can interleave because there's no `await` between them.

The NEW behavior changes the risk profile subtly: in the old code, late-firing timers would `async_create_task` that silently failed. In the new code, HA's `async_run_hass_job` with `background=True` creates an `eager_task`. If the coroutine tries to `async_write_ha_state()` on a removed entity, HA logs a warning but does not crash.

Defense-in-depth: all 3 `_async_refresh` methods guard:
```python
database = self.hass.data.get(DOMAIN, {}).get("database")
if database is None:
    return
```

**Verdict:** No regression. Race window effectively zero due to single-threaded event loop semantics.

### B4 — Re-entrancy: timer overlap between intervals (LOW, informational)

Per HA source, `async_track_time_interval` uses `async_run_hass_job(job, now, background=True)`. The `background=True` flag means the coroutine is scheduled as `eager_task` and NOT awaited inline. The next interval tick is scheduled independently.

- Overlap IS possible — if `_async_refresh` takes longer than the interval, two instances could run concurrently
- Behaviorally identical to old code (which also used `async_create_task` — fire-and-forget)
- `URADBSizeSensor` (filesystem stat, sub-millisecond): no concern
- `OverrideFrequency` / `ComplianceRate` (DB queries): uses `database._db_read()` with aiosqlite context manager + connection pool isolation. Two concurrent reads are safe.

**Verdict:** No change in behavior. No action needed.

### B5 — Entry reload survivability (LOW, informational)

When URA's CM entry reloads:
1. Entities removed (`async_remove` → `async_on_remove` callbacks fire → unsub timers)
2. New entities created and `async_added_to_hass` schedules fresh timers

The guard `if self._unsub_timer else None` handles the edge case where removal happens before `async_added_to_hass` completed. The NM's `async_teardown` iterates `self._digest_unsubs` and calls each unsub.

"Timer fires mid-reload targeting old entity while new entity hasn't started" is impossible — old entity's unsub fires synchronously before new entity is created.

**Verdict:** Safe.

### B6 — `_fire_digest` `_now` parameter receives datetime (LOW, informational)

`async_track_time_change` passes `localized_now` (a datetime) as the first positional arg. With `partial(self._fire_digest, person_id, person_cfg)`, the call becomes:
```python
self._fire_digest(person_id, person_cfg, localized_now)
```

This maps to:
```python
async def _fire_digest(self, person_id, person_cfg, _now=None)
```

`_now` receives the datetime. Method body never references `_now`. Parameter name and default are documentary.

**Verdict:** Correct.
