## Verdict: **FIX-FIRST**

Code change is correct as written — D1 properly re-sources the wake timer from raw tiers, D2 properly nests inside the SLEEP→WAKING + `wake_decision.fired` branches, and the existing logic Reviewer A signed off on is sound. **But the deploy plan as stated cannot work and will produce a misleading restart-test result.**

The operator's stated test ("leave the live house stuck in SLEEP, deploy this fix, restart HA, confirm wake") is structurally incompatible with how URA restores house state today. **`HouseStateMachine` has no persistence** (`manager.py:143` constructs it fresh; `house_state.py:111` initializes `_state = HouseState.AWAY`; grepping the repo turns up exactly one consumer of `house_state_log` — `_transitions_today` hydration at `presence.py:1158-1173`, the state itself is *never* restored). After `restart`, the house begins at AWAY and re-derives SLEEP only via the inference path. This affects what the restart-test demonstrates, but more importantly it surfaces a real ordering hazard (B-CRIT-1 below) that this fix-up should close in-cycle.

## Critical finding (B-CRIT-1): the restart-test is structurally broken

**Walk the path.** Operator says "house is stuck in SLEEP, I deploy + restart HA, I want to see it wake."

1. `manager.py:143` — `self._house_state_machine = HouseStateMachine()` (no args).
2. `house_state.py:109-119` — `__init__(self, initial_state=HouseState.AWAY, ...)` → `self._state = HouseState.AWAY`.
3. There is no `RestoreEntity` for the house state machine, and no DB-read that hydrates `_state` (only `_transitions_today` is read back from `house_state_log` at `presence.py:1158-1173`). Confirmed by repo-wide grep: zero hits for any `house_state_machine._state = ...` or `set_override(...SLEEP)` in restoration paths.
4. Post-restart, `_run_inference("startup")` runs at `presence.py:1262`. `current_state = manager.house_state_machine.state` → `AWAY`.
5. `census_count` was seeded at `:1228-1259` (e.g., 1). `any_zone_occupied` is whatever the trackers have NOW (see B-HIGH-1).
6. `_inference_engine.infer()` with `census_count=1, current_state=AWAY` → `:526-528` returns `HouseState.ARRIVING`. Not SLEEP.
7. Next tick (any trigger) → `current_state=ARRIVING` → `:533-535` returns `_time_based_home(hour)`. At 12:57 CDT (current time) → `HOME_DAY`. Still not SLEEP.
8. So the house **never lands in SLEEP after a restart-during-the-day**. The deadlock the operator wants to demonstrate the fix against **does not exist on the post-restart instance**, because the bug requires being IN SLEEP and the post-restart trajectory under current local time can't get to SLEEP without first being in HOME_NIGHT past 23:00.

**This is the show-stopper for the operator's restart-test.** The fix is correct, but the test as planned will produce the result "house woke" regardless of whether D1/D2 are even in the deployed code — because the house starts at AWAY and walks to a HOME_* state organically.

**Two ways to make the test actually exercise the fix:**

A. **Drive the test through a real SLEEP transition.** Operator restarts at e.g. 05:55 local with census > 0 and a HOME_NIGHT-like trajectory; let HA reach 23:00 hysteresis → SLEEP, then 06:00 → WAKING. This validates the gate, not the deadlock. Not a meaningful proof of the fix.

B. **Inject a SLEEP override via the existing `set_state` service.** `__init__.py:3060-3081` exposes a service that calls `manager.house_state_machine.set_override(HouseState(state))`. Operator can:
   ```
   service: universal_room_automation.set_house_state
   data: { state: sleep }
   ```
   The override path **does** propagate `tracker.set_sleep(True)` (verified at `__init__.py:3082-3086` — yes, `set_sleep(True)` is called on override too). Then wait past `sleep_end + 3h` (or pre-set local time / use a backstop-window already past). The D2 backstop will fire.

**Important caveat for path B:** `set_override` sets `_override` on the state machine itself (`house_state.py:119-120`). The property `state` returns `_override if set else _state` (`house_state.py:122-127`). The WAKING gate reads `manager.house_state_machine.state` at `presence.py:2570`, which DOES return the override → the gate sees SLEEP → D1/D2 apply.

But: does `transition(WAKING)` get accepted while `_override` is set? Read `house_state.py:155-189` — `can_transition` and `transition` operate on `self._state`, **not** on the override. So `transition(WAKING)` will succeed and update `_state` from AWAY to WAKING, **but the `state` property keeps returning SLEEP because the override is still pinned**. Result: backstop fires, `_wake_backstop_fires` increments, but `sensor.ura_presence_coordinator_presence_house_state` stays at "sleep" because the override is still active. The operator's "did it wake" check on the sensor will say NO.

**Operator must `clear_override()` (via the same service with `state: auto` if supported, or manually flip the override-sensor) to see the wake.** This is a real procedural gotcha that needs to be in the deploy plan, not the code.

**Recommended fix-first action:** rewrite the deploy-test in the planning doc § "Live" with the path-B procedure spelled out (set_override → wait → confirm `_wake_backstop_fires` increments + WAKING transition logged in `house_state_log` → clear_override → confirm sensor flips). This is documentation, not code, but it's the difference between "shipped a real fix" and "shipped a fix that nobody can validate."

If the operator instead chooses to let the house enter SLEEP naturally tonight and restart-test tomorrow morning, then `set_sleep(True)` is correctly applied via the SLEEP transition path at `presence.py:3078-3080`, and the test works as Reviewer A described — but only after a full natural sleep cycle, which conflicts with "deploy + restart NOW."

## High findings

### B-HIGH-1: First-tick raw_occupied is False even when mmwave is on

`_discover_room_sensors` (`:1424-1489`) walks the entity registry and calls `tracker.register_entity(...)` + `async_track_state_change_event(...)`. **It does NOT read current sensor state — it only subscribes to FUTURE state-change events.**

So at `_run_inference("startup")` (`:1262`), every `tracker._room_occupied` dict is empty (nothing was populated by `update_room_occupancy` yet). `_derived_mode` evaluates:
- Tier 3 (BLE): `_ble_occupied=False` (set later via `update_ble_presence`).
- `_has_sensors=True` (set by `register_entity` at `:382`).
- Tier 1: `any(self._room_occupied.values())` → `any([])` → `False`.
- Tier 2: `_any_camera_occupied()` — `_camera_last_seen` is empty → returns False.
- Falls through to `:268`: returns AWAY.

**`raw_occupied` is False on the startup tick even if the mmwave is physically ON.** It only becomes True when a state-change event fires (`_handle_occupancy_change`). If the sensor's state doesn't change for a while post-boot, `raw_occupied` stays False.

This is mitigated by D2's backstop (which uses `census_count > 0`, not raw_occupied) — so even if the timer never accumulates, the backstop window will force the wake. **But the timer-based D1 path is effectively dead on the first tick post-restart.** Reviewer A's claim that the operator restart-test confirms D1 is wrong; the test confirms D2 only.

**Recommended fix-first:** at the end of `_discover_room_sensors`, do a one-shot read of current state for each registered entity_id and call `update_room_occupancy(...)` to seed `_room_occupied` from `hass.states.get(...)`. Same pattern for cameras at `_discover_zone_cameras`. ~15 LoC. Without this, D1 has a multi-minute lag after every restart before the wake timer can even start accumulating — Jaya has to physically move past a sensor to seed it.

If the operator accepts D2-only post-restart and D1-only steady-state, document it.

### B-HIGH-2: `_run_inference` is not serialized

`_run_inference` is `async`. It's invoked at six sites as `self.hass.async_create_task(self._run_inference(...))`:
- `:1777` (census_update)
- `:1822` (occupancy_change)
- `:1861` (camera_detection)
- `:2039` (deferred_retry)
- `:2214` (guest_room_occupancy)
- `:3612, :3616` (geofence_arrive/leave)

Plus periodic at `:1999`. There is no `asyncio.Lock` guarding the body. Within `_run_inference` there are many `await`s — most notably `await self._inference_engine.infer(...)` (well, it's sync; but plenty of awaitable DB/dispatcher work happens after it).

Read the timer-update block (`:2542-2568`):
```python
any_zone_raw_occupied = any(t.raw_occupied for t in self._zone_trackers.values())
_now_utc = dt_util.utcnow()
if any_zone_raw_occupied:
    if self._first_positive_zone_occupied_since is None:
        self._first_positive_zone_occupied_since = _now_utc
else:
    self._first_positive_zone_occupied_since = None
```

This is itself synchronous and atomic per task. **But** the read at `:2860` (`sustained_seconds = ... _first_positive_zone_occupied_since`) happens after multiple awaits (e.g., `infer()` is sync, but the helper invocations at `:2756` and the per-zone loops above can be expensive enough to yield the event loop in practice). If Task A reads `_first_positive_zone_occupied_since = T0` at `:2860`, and Task B (a concurrent camera_detection tick) sets it to None at `:2568` between A's read and A's gate-check, A still uses its local `sustained_seconds`. No corruption per se, but **two concurrent ticks can both observe `wake_decision.fired = True` and both attempt the transition** — `manager.house_state_machine.transition(WAKING)` is called twice; the second is rejected by hysteresis (SLEEP→WAKING dwell), and the dispatcher would re-fire SIGNAL_HOUSE_STATE_CHANGED if both succeeded (the transition() return-check prevents that, so it's fine).

Also: `self._wake_backstop_fires += 1` (`:2894`) is not atomic in CPython if interleaved at the bytecode level (it isn't, given the GIL + no awaits between read and write — actually safe). But conceptually, if six tasks all spawn and pass the backstop check in a burst, the counter increments six times for what is logically one event. Cosmetic on the diagnostic surface.

**Recommended fix-first:** wrap the body of `_run_inference` in `async with self._inference_lock:` (init the lock in `__init__`). Single-shot lock, no contention in steady state. Five lines. Even if the current racewindow doesn't bite, this is the kind of v4.7.15.1 fix-up A-M2 territory — "diagnostic surface invariant" — that future cycles will rely on.

Alternative: accept and document. If accepted, add an explicit note that `_first_positive_zone_occupied_since` is best-effort under concurrent ticks. Reviewer A did not surface this — the static correctness pass missed it because the single-task view is clean.

## Medium findings (briefly)

**B-MED-1 (cross-coordinator on forced wake):** when D2 fires, the resulting WAKING transition dispatches `SIGNAL_HOUSE_STATE_CHANGED` with `confidence=0.8` (engine default for SLEEP→WAKING at `:546`). HVAC's listener at `hvac.py:428` reacts to *every* WAKING transition; it does not branch on whether this was an organic or backstop wake. No regression — current HVAC behavior is fine — but worth documenting that a backstop-forced WAKING is indistinguishable to downstream consumers. The plan's "fall through WITHOUT suppressing" comment is correct in intent.

**B-MED-2 (restart timer state):** `_first_positive_zone_occupied_since` is reset to None on every restart. Combined with B-HIGH-1, this means post-restart the wake timer has zero accumulated history. Acceptable single-install behavior; the 90s sustained threshold is short enough that it doesn't materially delay a real wake. Document in the plan.

## Low findings (briefly)

**B-LOW-1 (set_sleep on first SLEEP transition only):** `set_sleep(True)` is only called when `new_state == HouseState.SLEEP` is *accepted* (`:3060+3078`). On a startup tick that goes straight from AWAY to SLEEP (impossible per the state machine — VALID_TRANSITIONS at `house_state.py:38-45` doesn't include SLEEP), this never fires. The `__init__.py:3082-3086` override path *does* call `set_sleep(True)` on override-to-SLEEP, which is the operator's only restart-day SLEEP path (see B-CRIT-1 path B). Confirmed safe.

**B-LOW-2 (test gap):** the test file pre-seeds SLEEP state. It doesn't exercise the boot-ordering path (B-HIGH-1) or the restart-restored timer reset (B-MED-2). Adding `test_v47181_first_tick_raw_occupied_false_when_unseeded` and `test_v47181_backstop_fires_post_restart_via_override` would close the boot-path coverage gap. ~30 LoC.
