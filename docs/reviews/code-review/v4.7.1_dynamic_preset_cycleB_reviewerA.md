### CRITICAL

#### A1: `get_options` lambda captures stale closure in EC lazy init (Bug Class #14)

**File:** `energy.py:2553-2558`
**Bug class:** #14 (Config Snapshot Staleness)

```python
# Lazily instantiate DynamicPresetOverrideSource (avoids circular import)
if self._dynamic_preset_source is None:
    from .dynamic_preset import DynamicPresetOverrideSource
    self._dynamic_preset_source = DynamicPresetOverrideSource(
        hass=self.hass,
        get_options=lambda: cm_options,  # <--- STALE CLOSURE
    )
```

`cm_options` is a local variable constructed fresh at lines 2533-2536 on EVERY call to `_async_evaluate_dynamic_presets`. The `DynamicPresetOverrideSource` is only created on the FIRST call (when `self._dynamic_preset_source is None`). The lambda `lambda: cm_options` captures the local `cm_options` from the scope of that first call. On all subsequent calls (every 5 minutes), a new `cm_options` is built but the source still returns the original one.

**Impact:** The source reads stale CM options indefinitely after the first evaluation tick. User changes to bucket boundaries, dwell, or hysteresis via CM options flow take effect only after HA restart. This defeats the entire Bug #14 prevention strategy that `evaluate_and_emit` was designed around.

**Fix:** Replace the lambda with one that reads fresh CM options each time:

```python
def _get_fresh_cm_options():
    for entry in self.hass.config_entries.async_entries(_DOMAIN_KEY):
        if {**entry.data, **entry.options}.get(CONF_ENTRY_TYPE) == ENTRY_TYPE_COORDINATOR_MANAGER:
            return {**entry.data, **entry.options}
    return {}

self._dynamic_preset_source = DynamicPresetOverrideSource(
    hass=self.hass,
    get_options=_get_fresh_cm_options,
)
```

Or simply make `get_options` a method on the EC that the source calls.

#### A2: Number entity sliders are fully disconnected from evaluation logic (Bug Class #14 + #32)

**Files:** `number.py:1607-1617` (DynamicPresetDwellMinutesNumber), `number.py:1677-1684` (DynamicPresetHysteresisFNumber)
**Bug class:** #14 (Config Snapshot Staleness), #32 (Form Field With No Runtime Reader)

Both number entities store slider values only in `self._value` via RestoreEntity. Their `async_set_native_value` methods do NOT:
1. Write to `entry.options` (the comment at line 1614-1615 says "source reads from get_options()" but see A1 above -- `get_options` is stale)
2. Push the value directly to the `DynamicPresetOverrideSource` instance

Combined with A1, this means: the user changes the dwell slider to 30 minutes. The number entity stores `self._value = 30.0` and persists it in RestoreEntity. But the `DynamicPresetOverrideSource._get_options()` still returns the original CM options dict with `dwell=60`. The source never reads the slider value.

**Impact:** Both runtime-tunable number entities (dwell and hysteresis) are completely inert -- they show a value but that value has zero effect on the evaluation logic. The user has no way to tune dwell or hysteresis at runtime without editing CM options and restarting HA.

**Fix:** Either:
(a) Make the number entities push their values to the DynamicPresetOverrideSource directly via a setter (matching the pattern used by EC sub-switches), OR
(b) Make them write to `entry.options` AND fix A1 so the source reads fresh options

Option (a) is simpler and follows the existing URA v4.3.2 "mirror pattern" (RestoreEntity = runtime store; entry.options = seed only).

#### A4: `DynamicPresetOverridesAppliedSensor._attr_state_class = "measurement"` may cause LTS issues

**File:** `sensor.py:6776`
**Bug class:** None (matches HA recorder pattern issue)

```python
_attr_state_class = "measurement"
```

The `DynamicPresetOverridesAppliedSensor` state is an integer count of zones with active overrides. This count changes infrequently (once per weather shift, typically 0-5 per day) and resets to 0 on HA restart (since `_dynamic_preset_overrides` is in-memory). Setting `state_class = "measurement"` causes HA's long-term statistics to record this as a time-weighted measurement. Since the value is volatile (resets on restart) and discontinuous, this creates misleading LTS data.

Compare with `EnergyRecentDecisionsSensor` (line 6835 region) which explicitly omits `state_class` for the same reason: "HA long-term statistics would record a discontinuous time series for it."

**Impact:** Misleading historical statistics in the HA Energy dashboard. Not a data-integrity bug per se, but inconsistent with the pattern established 200 lines earlier for `EnergyRecentDecisionsSensor`.

**Fix:** Remove `_attr_state_class = "measurement"` or set to `None`.

### MEDIUM

#### A5: `resolve_range` tiebreak rule differs from Guest Mode Phase 1 spec

**File:** `preset_overrides.py:157-202`
**Bug class:** None (spec drift)

The Guest Mode Phase 1 plan section 6 says: "per-field highest-priority-wins, **narrowest-range tiebreak**. Ties by priority -> narrowest (lower for `*_high`, higher for `*_low`); still tied -> alphabetical source."

The actual `resolve_range` implementation uses a simpler rule: highest priority wins; first-seen-at-that-priority wins (Python sort is stable, so insertion order for equal priorities). There is NO narrowest-range tiebreak and NO alphabetical tiebreak.

**Impact:** Currently safe because dynamic_preset (priority=30) and guest_mode (priority=50) never tie. But if a future source ships at priority=30 alongside dynamic_preset, the resolution is arbitrary (depends on list order). This violates the spec the plan OWNS.

**Action:** Acceptable for this cycle since no tie is possible. Document that the tiebreak rule is simplified and should be upgraded before any same-priority source ships.

#### A7: `_build_overrides` does not validate `cool_low <= cool_high - MIN_DEADBAND` before emitting

**File:** `dynamic_preset.py:426-500`

The override records emitted by `_build_overrides` read `effective_home_low` and `effective_home_high` directly from zone_data plus offset. No deadband validation is performed on the emitted values. If the user configures `cool_home_low=74.0` and `cool_home_high=74.0` (or even `cool_home_low=75.0` with `cool_home_high=74.0`), the override will be emitted with an inverted or zero-deadband range.

The `OverrideEngine.resolve_range()` does clamp after composition (`resolved_low > resolved_high - MIN_DEADBAND`), so the final resolved range is safe. But:
1. The per-source override itself is semantically invalid
2. The diagnostic sensor will show a confusing range to the user

The form-save validation in `config_flow.py:5024-5036` catches `low > high - MIN_DEADBAND`, so this should not happen in practice. But the offset is applied at runtime, not form-save time, so a zone with `cool_home_high=62` and `offset=0` would pass validation, but later with `offset=-2` (currently offset range is 0-3, so negative offset is not possible in the current schema).

**Impact:** Low in practice due to form-save validation + offset range constraint. Defensive check recommended.

**Action:** Defer. Add a defensive clamp in `_build_overrides` in a polish cycle.

#### A8: Sleep auto-derive uses raw `home_high` from config, not `effective_home_high` with offset applied

**File:** `dynamic_preset.py:484-487`

```python
# Auto-derive from home range
effective_sleep_high = compute_sleep_high(float(home_high), zone_offset)
effective_sleep_low = effective_home_low
```

When `sleep_low` and `sleep_high` are not configured (user left them blank, relying on auto-derive), the code calls `compute_sleep_high(float(home_high), zone_offset)`. Here `home_high` is the RAW value from zone_data (line 450), not `effective_home_high` which has `zone_offset` already applied (line 459).

`compute_sleep_high(home_high, zone_offset)` does: `max(74, home_high - 1) + zone_offset`. This is correct per the plan: "sleep_effective = max(74, home_high - 1) + offset". The raw `home_high` is the correct input because the formula applies offset AFTER the floor check, and the raw value represents the baseline before offset.

**Impact:** None -- this is correct. I am noting it explicitly because it looks like a bug at first glance but is actually the intended behavior per plan section B.B.5.

**Action:** No change needed. Already correct.

## OverrideEngine Foundational Audit

### Schema fidelity vs Guest Mode Phase 1 spec

| Spec Field (PLANNING_v4.7.x_guest_mode_actuation_phase1.md section 4.2) | PresetOverride Dataclass | Match? |
|---|---|---|
| `source` (str enum, required) | `source: str` | YES |
| `preset` (str enum, required) | `preset: str` | YES |
| `cool_low` (float, optional) | `cool_low: float or None = None` | YES |
| `cool_high` (float, optional) | `cool_high: float or None = None` | YES |
| `heat_low` (float, optional, reserved) | `heat_low: float or None = None` | YES |
| `heat_high` (float, optional, reserved) | `heat_high: float or None = None` | YES |
| `priority` (int, required) | `priority: int` | YES |
| `active_when` (predicate id, reserved) | `active_when: str or None = None` | YES |

Extra fields in implementation: `zone_id: str or None = None`, `bucket: str or None = None`. These are Cycle B dynamic-preset-specific extras, not in the Phase 1 spec. They are non-persisted compute-time attributes. Acceptable extension.

### Priority ordering

- guest_mode = 50, dynamic_preset = 30, vacation = 70 (reserved), manual = 100 (reserved)
- Priority constants defined in `energy_const.py` as `GUEST_MODE_PRIORITY: Final = 50` and `DYNAMIC_PRESET_PRIORITY: Final = 30`
- Test `test_priority_ordering` verifies `DYNAMIC_PRESET_PRIORITY < GUEST_MODE_PRIORITY`
- `resolve_range` sorts by priority descending, first non-None opinion wins per-field
- Guest Mode wins over Dynamic Preset when both active: VERIFIED by test `test_guest_mode_wins_when_both_active_same_zone`

### Composition semantics

Multiple sources can emit for the same zone simultaneously. Resolution rule: per-field highest-priority-wins (first at that priority in sorted order). No field-level merge -- the highest-priority source's opinion on each field independently wins. This is simpler than the spec's narrowest-range tiebreak but correct when no ties exist.

### Reload behavior

The OverrideEngine itself is stateless -- no stored references to dropped overrides. It receives the full override list on each `resolve_range` call. If a source de-registers mid-cycle, it simply stops emitting records into the list, and the next resolution omits them. Clean.

The `DynamicPresetOverrideSource` is owned by the EC. If the EC reloads, `_dynamic_preset_source` is re-created (None-checked at line 2553). On reload, cross-restart state is restored via the `DynamicPresetActiveBucketSensor` RestoreEntity path. No stale references.

### active_when predicate evaluation

Three supported predicates (line 137-155):
1. `None` -> always active
2. `"house_state == 'guest'"` -> string equality check against `house_state` param
3. `"dynamic_preset"` -> always active (dynamic preset manages its own gating before inserting records)

Evaluation is a simple string match -- O(1), called once per override per resolution call. No regex, no parsing. Cheap enough for every decision tick.

### Foundational verdict

The OverrideEngine is well-designed for its scope: stateless, per-resolution, no side effects. The schema matches the spec. Priority ordering is correct. The deadband clamp in `resolve_range` is a good safety net. The `describe_active` diagnostic surface is clean.

The tiebreak simplification (A5) is the only spec drift and is acceptable since no ties are possible with current priority assignments.

**Assessment:** The OverrideEngine is sound for a 3-year foundation. The CRITICAL issues (A1, A2) are in the integration layer (energy.py + number.py), not in the engine itself.

## Specific Danger Assessment

### 1. OverrideEngine foundational bugs manifesting 6 cycles from now

Low risk. The engine is stateless and schema-faithful. The `build_guest_mode_overrides` helper (A3) is dead code but harmless. The real risk is in the integration layer where the lambda closure (A1) and number entity disconnect (A2) create a false sense of live-tunability.

### 2. Dwell/hysteresis writeback gap

**HIGH severity** (A2). The user changes the slider, expects it to take effect within the next decision cycle (5 min). It does not. The only recourse is to figure out "edit CM options and restart HA." This is a usability bug, not a docs note. The builder flagged this gap but classified it as "reload required" -- in practice, no user will figure that out.

### 3. Composition with OverrideArrester (manual override)

Not yet wired. The Cycle B code emits override records into `_dynamic_preset_overrides` on the EC, but there is no consumer that applies them to the thermostat via `climate.set_temperature`. The HVAC apply path (Guest Mode Phase 1 D2) does not exist yet. So OverrideArrester flap is not possible in this cycle. When D2 ships, the reviewer for that cycle must verify the 3-way interaction.

### 4. EC decision cycle budget

`_async_evaluate_dynamic_presets` iterates canonical HVAC zones (typically 3-5 in this install). Each zone evaluation is synchronous (`evaluate_and_emit` is O(1) string comparisons + dict lookups). The async wrapper acquires a lock but contention is zero (called from the single EC decision cycle). Total added wall-clock: sub-millisecond per zone, <5ms total. No budget concern.
