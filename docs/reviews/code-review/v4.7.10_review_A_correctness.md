## Detailed Findings

### A-H1 (HIGH) — `rc=128` halts deploy; regresses mirror-only contract

**Surface:** `scripts/deploy.sh:97-100`

```bash
elif [ "$rc" -eq 130 ]; then
  echo "  [error] gitea push interrupted by user (SIGINT)" >&2
  exit 130
else
  echo "  [error] gitea push exited with unexpected code $rc" >&2
  exit "$rc"
fi
```

**Behavior under `set -e` inside `dual-push.sh`:** When `git push gitea $BRANCH` (line 123 of dual-push.sh) fails with a network/auth/repo-path-mismatch error, `git push` returns **128**, `set -e` triggers an immediate exit from `dual-push.sh` with that exit code, and the caller (`deploy.sh` step 4) sees `rc=128`. The current dispatch:

- `rc=0` → silent success.
- `rc=1` → `[warn]` and continue.
- `rc=2` → `[error]` and halt.
- `rc=130` → `[error]` SIGINT and halt.
- **`rc=128` → falls into the `else` branch → `[error] gitea push exited with unexpected code 128` → `exit 128` → deploy halts.**

**Why this is wrong:**

1. Planning §6 row 2 explicitly classifies "rc=1 (auth fail / push rejected)" as `[warn] proceed`. Real `git push` auth failures return **128**, not 1. (Rejected non-fast-forward pushes return 1; auth failures, network failures, and unable-to-access-repository return 128.) The planning matrix conflates two distinct exit-code regimes.
2. README §2 says: *"GitHub origin success is the deploy success criterion. Gitea is mirror-only, not a hard requirement."* — but with the current narrow dispatch, any gitea auth/network failure (rc=128) halts the deploy AFTER origin has already pushed, after the gh PR has not yet been created, leaving the operator in a half-deployed state (origin pushed, no PR, no release).
3. The pre-v4.7.10 code (`|| echo "[warn]..."`) swallowed **all** non-zero codes including 128. D4's stated intent ("narrow the swallowed exit-code range; only treat exit codes 1-3 as expected") still does not cover 128. So even by D4's own spec, this is a bug.

**Repro (mental trace):**

1. `.env.local` has correct keys; `gitea` remote URL has stale repo path (e.g., `Okosisi/old-name.git` instead of `Okosisi/universal-room-automation.git`).
2. Preflight in `dual-push.sh` PASSES (host check is substring match on `gitea.phalanxmadrone.com` — does not validate the repo path).
3. `inject_gitea_creds` rewrites URL with creds, runs `git push gitea develop`.
4. Gitea returns HTTP 404 / "repository not found"; `git push` exits **128**.
5. `set -e` in `dual-push.sh` exits with 128. Trap restores clean URL. Good so far.
6. `deploy.sh` step 4 sees `rc=128`, hits the `else` branch, prints `[error] gitea push exited with unexpected code 128`, `exit 128`.
7. **Deploy halts after origin push, before PR creation.** Operator must manually run `gh pr create`, `gh pr merge`, `gh release create`. Net result: a worse failure mode than the pre-v4.7.10 swallow-all.

**Required fix (one of):**

Option A (minimal, preserves D4 intent): Extend the warn-and-continue branch to the common git-push error codes.

```bash
elif [ "$rc" -eq 1 ] || [ "$rc" -eq 128 ]; then
  echo "  [warn] gitea mirror push failed (rc=$rc; preflight, auth, network, or repo-path issue) — origin already pushed; gitea is mirror-only"
  echo "  [warn] catch up later with: bash scripts/dual-push.sh --gitea-only develop"
```

Option B (cleaner, matches planning intent of "expected gitea-side failures"): Treat 0 / 2 / 130 / 143 as special and everything else (including 1 and 128 and 129) as `[warn] continue`.

```bash
if [ "$rc" -eq 0 ]; then
  :
elif [ "$rc" -eq 2 ]; then
  echo "  [error] gitea push had a script-level error" >&2; exit 2
elif [ "$rc" -eq 130 ] || [ "$rc" -eq 143 ]; then
  echo "  [error] gitea push interrupted (rc=$rc)" >&2; exit "$rc"
else
  echo "  [warn] gitea mirror push failed (rc=$rc) — origin pushed; gitea is mirror-only"
  echo "  [warn] catch up later with: bash scripts/dual-push.sh --gitea-only develop"
fi
```

Recommend **Option B**: it correctly captures "any unexpected non-script-error, non-signal exit is a gitea-side mirror failure — warn and continue." Option A leaves rc=129/127/126 (other-signal, missing-binary, permission-denied) as halts, which is also wrong for a mirror-only push.

**Why this passed all 8 tests:** Test 6 explicitly stubs `dual-push.sh` to `exit 2`. Test 7 stubs `exit 130`. No test stubs `exit 128`. The "unexpected rc" branch has no test coverage; this is also A-M2.

**Severity rationale:** HIGH not CRITICAL because (a) the pre-cycle state would also have failed in this case (with a `[warn]`), and (b) origin push still completes — no data loss. But the deploy halts mid-pipeline (no PR, no release) in the most common gitea failure mode, which is strictly worse UX than the predecessor.

### A-M1 (MEDIUM) — Preflight `.env.local` key-count check doesn't prevent shell injection on later source

**Surface:** `scripts/dual-push.sh:78-88` (preflight) → `scripts/dual-push.sh:106-107` (later source)

**Issue:** Preflight validates `.env.local` via `grep -c '^GITEA_USER='` and `grep -c '^GITEA_TOKEN='` (lines 82-83). This only confirms the keys are PRESENT; it does not confirm the file is safe to `source`. Later, `inject_gitea_creds` at line 107 runs:

```bash
set -a; source .env.local; set +a
```

If `.env.local` contains a line like:

```
GITEA_USER=foo
GITEA_TOKEN=bar
EVIL_COMMAND=$(rm -rf /tmp/whatever)
```

The `source` will EXECUTE the command substitution. The preflight `grep -c` for `^GITEA_USER=` matched 1; the grep for `^GITEA_TOKEN=` matched 1; preflight passes. The user-controlled `.env.local` is then sourced.

**Severity:** MEDIUM (not HIGH) because:
- `.env.local` is gitignored and lives only on the operator's machine. The attack vector is the operator pasting hostile content into their own dotfile, which is implausible.
- The threat model for URA is single-user-single-machine (per `feedback_single_user_no_backcompat`).
- Reviewer C's secret-hygiene framing is the proper home for "what's in .env.local"; this is flagged here only because the preflight-vs-source ordering creates a state-machine assertion ("preflight passed → source is safe") that does not hold.

**Recommendation (optional):** In a future cycle, replace `set -a; source .env.local` with a stricter parser that only reads `KEY=VALUE` lines and rejects everything else. Not blocking for v4.7.10.

### A-M3 (MEDIUM) — `deploy.sh:50` glob fails fail-closed if `domain_coordinators/` is ever empty

**Surface:** `scripts/deploy.sh:50-51`

```bash
"$COMPONENT_DIR"/*.py \
```

Under `set -u` (active at line 8 via `set -euo pipefail`), if the glob produces zero matches, `git add` receives the literal pattern `custom_components/.../*.py`, which fails with `pathspec 'custom_components/.../*.py' did not match any files`. The combined script exits non-zero.

Currently both directories always have files, so this is latent. But:

**Not introduced by this cycle** — pre-existing bash-rigor gap. Mentioned here only because the cycle's stated `bash -n` parse-check (planning §8 gate 2) only catches syntax errors, not runtime glob-empty behavior. If the team is making "bash rigor" a v4.7.10 deliverable, this is the next-tier gap.

**Fix (optional):** `shopt -s nullglob` at the top of `deploy.sh`, OR explicit `compgen -G` checks per glob.

**Severity:** MEDIUM and **out of scope for v4.7.10 strict file-touch contract** — flag for backlog.

### A-M5 (MEDIUM) — `GITEA_CLEAN_URL` may remain empty in dry-run-with-`.env.local` path; trap restore is then a no-op on later signal

**Surface:** `scripts/dual-push.sh:108-121`

```bash
inject_gitea_creds() {
  if [[ -f .env.local ]]; then
    # shellcheck disable=SC1091
    set -a; source .env.local; set +a
    if [[ -z "${GITEA_USER:-}" || -z "${GITEA_TOKEN:-}" ]]; then
      echo "[dual-push] .env.local missing GITEA_USER or GITEA_TOKEN" >&2
      return 1
    fi
    local repo="${GITEA_REPO:-Okosisi/universal-room-automation}"
    GITEA_CLEAN_URL="https://${EXPECTED_GITEA_HOST}/${repo}.git"   # <-- only set HERE
    if $DRY_RUN; then
      ...
      return 0
    fi
    git remote set-url gitea "https://${GITEA_USER}:${GITEA_TOKEN}@..."
    ...
```

`GITEA_CLEAN_URL` is set on line 113 BEFORE the dry-run guard at line 114. Good — dry-run mode does have a clean URL set, so the trap could restore it if a signal arrives. ✓

But in the `else` branch (no `.env.local`, line 126-135), **`GITEA_CLEAN_URL` is never set**. Tracing forward:

- `restore_gitea_url()` (line 49-53) checks `if [[ -n "$GITEA_CLEAN_URL" ]]` before doing anything. If empty, the trap is a no-op.
- In the no-`.env.local` branch, the script never rewrites the remote URL — it relies on osxkeychain. So there's nothing to restore. The no-op trap is CORRECT.

**Conclusion:** Not actually a bug — the state machine is self-consistent. The restore is gated on URL-rewrite having happened; URL-rewrite only happens in the `.env.local` branch; `GITEA_CLEAN_URL` is set in that same branch before the rewrite. Trap correctness holds.

**Downgrade:** This is actually a NON-FINDING after the trace. Including it in the matrix as MEDIUM was overcautious. Reclassifying as **LOW (already-correct, no action)** — leaving it in the index for transparency so the next reviewer doesn't re-trace.

### A-L1 (LOW) — Trap runs twice on SIGINT (INT then EXIT) — benign

**Surface:** `scripts/dual-push.sh:54` — `trap restore_gitea_url EXIT INT TERM`

When SIGINT fires during `git push gitea $BRANCH`:
1. INT trap handler `restore_gitea_url` runs.
2. `set -e` exits the script with the failed command's status (130).
3. EXIT trap handler `restore_gitea_url` ALSO runs.

`restore_gitea_url` is idempotent (just `git remote set-url`), so two invocations are harmless. But: someone reading the script might wonder. A comment near the trap explaining intentional double-fire would help.

**Recommendation:** Add a one-line comment above line 54: `# trap idempotent; INT+EXIT may fire serially — restore_gitea_url is safe to call twice.`

**Severity:** LOW. No behavioral impact.

### A-L2 (LOW) — Re-run idempotency not asserted by any test

**Surface:** `quality/tests/test_deploy_scripts.py`

The planning framing item #2 ("Idempotency under retry") is asserted by manual trace but not by an automated test. Specifically: re-running `dual-push.sh --gitea-only develop` after a successful prior run should be a no-op (both pushes succeed because both remotes are up to date; trap restores clean URL).

Recommend a test that runs `--gitea-only develop` twice in sequence against the same `tmp_repo` and asserts:
- Both invocations rc=0.
- Final `.git/config` URL matches initial URL (trap fired both times).
- The fake-git log shows `push gitea develop` invoked twice.

**Severity:** LOW. The behavior is correct by construction; this is a regression-prevention nice-to-have.

### A-L3 (LOW) — Duplicate-flag tolerance is silent

**Surface:** `scripts/dual-push.sh:33-43`

`--gitea-only --gitea-only develop` sets the flag twice — second iteration is a no-op assignment. `--dry-run --gitea-only --dry-run develop` similarly fine.

This is technically tolerant (CORRECT), but a typo like `--gitea-only --gitea-onlyy develop` would set the flag once and then hit the unknown-flag branch (A-M4) and exit 1 — confusing UX where the first occurrence "succeeded" and the second didn't.

**Recommendation:** Either explicitly accept duplicates (current behavior is fine) or warn on duplicates. Lowest-cost fix: do nothing; document in the script header that flag parsing is tolerant.

**Severity:** LOW. No correctness impact.
