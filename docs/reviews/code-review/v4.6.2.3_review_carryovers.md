### Path A (automation.py) — `handle_humidity_based_fan_control`

Walked the function top-to-bottom for the post-restart-mid-cycle scenarios:

**Scenario A1: Coordinator wakes, fan is physically ON, humidity now is 70% (above 65% threshold).**
- L1654-1656: humidity_fans non-empty, humidity not None — proceed.
- L1659-1660: `_is_hvac_managing_fans()` — patched to False in tests; in production, if HVAC mgr owns the fan, we return early and never seed. That's correct: Path B will run instead.

- L1685-1690: anchor is None AND fan observed on → seed both `_humidity_on_since` and `_humidity_fan_triggered_time` to `now`, log INFO.

- L1713-1718: not suppressed — skip.
- L1722: `fan_is_on = True` (just seeded).
- L1724: `humidity >= threshold (70 >= 65)` → True. Re-issue `turn_on` to homeassistant domain. Idempotent. OK.

**Scenario A2: Coordinator wakes, fan ON, humidity 60% (in hysteresis band).**
- Seeding fires. Cap doesn't. Suppression off. `fan_is_on = True`.
- `humidity >= threshold (60 >= 65)` → False.
- `elif fan_is_on and humidity <= off_threshold (60 <= 55)` → False.
- Falls to hysteresis hold (implicit `else`). No service call. Fan stays on, anchor set. Correct.

**Scenario A3: Coordinator wakes, fan ON, humidity 45% (below off threshold).**
- Seeding fires. Cap doesn't. Suppression off. `fan_is_on = True`.
- `humidity >= 65` False.
- `elif fan_is_on and humidity <= 55 (45 <= 55)` → True. Min-runtime check: `elapsed = (now - now).total_seconds() = 0 < timeout (60s default)`. Fan stays on. **This is finding #1's behavioral footprint**: the fan that was running for 10 minutes pre-reload now gets a fresh 60s min-runtime hold. Documented as intentional.

**Scenario A4: Coordinator wakes, fan OFF (pre-reload cap fired or user toggled), humidity 70%.**
- L1685: `_fan_is_actually_on(humidity_fans) → False`. No seeding. `_humidity_on_since` stays None.
- L1693: cap check skipped (anchor is None).
- L1722: `fan_is_on = False` (triggered_time is None).
- L1724: `humidity >= 65` → True. Set `_humidity_fan_triggered_time = now`, `_humidity_on_since = now`. Issue `turn_on`. Correct.

**Scenario A5: Sleep policy off interaction.**
- L1663-1673 returns early BEFORE the seeding block. Anchor stays None after sleep-policy turn_off. Correct — fan was just turned off by policy.

**Scenario A6: HVAC-managing interaction.**
- L1659-1660 returns early. No seeding in Path A. Path B (hvac_fans.py) is responsible for seeding when HVAC manages. Correct.

**Scenario A7: Cap-fire suppression flow after seeding.**
- t=0: fan on, reload, humidity=70. Anchor seeded to t=0, `triggered_time=t=0`. Cap not fired. fan_on branch re-issues turn_on.
- t=max_runtime+1: cap check fires. `turn_off` issued, `_humidity_on_since = None`, `_humidity_fan_triggered_time = None`, `_humidity_cap_suppressed = True`. Returns.
- Confirmed by `test_max_runtime_cap_fires_after_full_window` and `test_max_runtime_suppression_blocks_immediate_retrigger`.

## QUALITY_CONTEXT.md recommendations

No new bug classes warranted from this cycle. The seeding pattern (state-anchor re-establishment on coordinator wake) is a useful idiom that could be captured as a positive pattern. Consider adding to QUALITY_CONTEXT.md under a "Patterns" section (separate from bug classes):

> **Pattern: Reload-Mid-Cycle Anchor Seeding.** When a coordinator holds in-memory state that anchors time-based gates (max-runtime caps, min-runtime holds, debounce windows) and that state can be reset by options-flow reload, the eval path should detect a "live" actuator at startup and seed the anchor to `now`. The seed must be monotonic (`if anchor is None`) so subsequent ticks do not slide the reference forward. This restores the gate's stated purpose at the cost of resetting the gate's history — an acceptable tradeoff for in-memory state that is not RestoreEntity-persisted.

This is borderline — it may not warrant a permanent QUALITY_CONTEXT entry if the codebase only has 1–2 such gates. Leaving as a discretionary recommendation for the maintainer.
