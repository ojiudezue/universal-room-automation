## Framing (per plan)

**Falsifiable invariant.** Under any legal upstream state — including a SPAN-app circuit rename between boot N and boot N+1 — a `circuit_power` baseline that was warm before the rename (`sample_count >= CIRCUIT_MIN_SAMPLES`) remains warm and re-attached to the correct discovered `entity_id` after the rename, WITHOUT relearning from 0 and WITHOUT emitting the "no matching circuit" WARN. Existing non-SPAN baselines (safety `rate_of_change`, diagnostics per-coordinator scopes, energy `peak_import_kw` / `soc_at_peak_start` / `daily_import_cost` / `solar_forecast_error_pct`) MUST be byte-identical across the migration boot.

## Findings

| ID | Sev | Bug class | Finding | Status |
|---|---|---|---|---|
| A-HIGH-1 | HIGH | migration transactionality | The one-shot migration loop (`_migrate_scopes_to_unique_id` in `energy.py`) issued sequential `UPDATE metric_baselines SET scope = ... WHERE ...` calls plus a sentinel-row INSERT — without an explicit transaction. A crash / HA-supervisor kill mid-loop would leave a partial migration + no sentinel, and the next boot would re-run the loop over the ALREADY-migrated rows (some rows already keyed by unique_id) → possible corruption (row keyed on unique_id gets its scope re-written to a friendly_name that no longer resolves). | **FIXED** (`3de22a85`) — migration is now wrapped in `BEGIN IMMEDIATE ... COMMIT`; sentinel INSERT is the last statement inside the transaction so mid-crash = full rollback = safe re-attempt. Anchored by test: mutation removing the `BEGIN IMMEDIATE` fails a named test that simulates mid-loop abort. |
| A-MED-1 | MEDIUM | accounting | Migration summary log line under-counted "migrated" when a friendly_name resolved to a unique_id that already had a row (dedup collision) → the operator's post-deploy N value could look wrong. | **FIXED** — accounting split into `migrated`, `deduped_into_existing`, `skipped_no_unique_id`, `already_unique_id`; all four surfaced in the summary log line. |

## Bug-class frequency + recommendations

- **Display-name used as persistence key across a renameable upstream** — 1 (the parent bug the cycle exists to fix; scope = friendly_name where friendly_name is operator-mutable in the SPAN app). **Recommend QUALITY_CONTEXT.md gain a bug class:** any persistence key derived from a display / user-facing string on an upstream integration is a rename bomb; the audit is "does the upstream let the operator rename this — if yes, key on registry `unique_id` or DB primary key, never the display string." One-line rule; would have prevented this cycle.
- **Hand-copied SQL in tests** — 2 (C-HIGH-2 shape-blind predicate; C-MED-1 hand-copied DDL). Same underlying pattern seen in v4.6.3 Review C findings. **Recommend re-emphasizing** the Tier 2-DB rule that behavioral test fixtures extract schema from production DDL constants and drive production code paths, not their own INSERT/UPDATE/DELETE.
