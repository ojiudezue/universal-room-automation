### Phone-tracker lag during ARRIVING (worth naming)

When a person walks in the door, `person.X` flips `not_home → home` over a 30–90 s window depending on phone-tracker provider. During that window:
- `all_tracked_persons_away=True` (still)
- Camera Tier 2 may already see them → `any_zone_occupied=True`
- Inference engine: veto fires → AWAY

This *could* delay legitimate ARRIVING by one inference cycle (default 30 s for AWAY hysteresis per house_state.py:88). In practice this is acceptable: the symptom this cycle fixes is much worse (multi-hour Bryant compliance violations), and the lag is bounded by the AWAY hysteresis floor. Not flagging as a finding — the plan §4 explicitly accepts this trade-off ("confidence 0.95" wins by design) — but call out as **NIT-1** below to surface the trade-off in the veto-fired INFO log so an operator who sees it during an arrival event can identify the cause from logs.

## Detailed findings

### NIT-1 — Veto-fired INFO log omits which persons triggered the veto

**Location:** `domain_coordinators/presence.py:2007-2014`

**Description:** The veto-fired log says "all %d tracked persons away" with `tracked_count` but does not list which person keys / locations were observed. During an ARRIVING-lag misfire (see state-machine matrix note), an operator reading logs would have to cross-reference HA state history to identify whose phone tracker was lagging. Naming the persons + their last-known `location` value would make the log self-diagnostic.

**Fix:**
```python
# At presence.py:2007-2014, replace the existing _LOGGER.info call:
if (
    all_tracked_persons_away
    and self._unidentified_count == 0
    and new_state == HouseState.AWAY
    and current_state != HouseState.AWAY
):
    person_summary = ", ".join(
        f"{k}={(v or {}).get('location') or '?'}"
        for k, v in (person_coordinator.data or {}).items()
    ) if person_coordinator else "<no person_coordinator>"
    _LOGGER.info(
        "v4.7.14: Person-tracker veto fired — all %d tracked persons "
        "away (%s), no unidentified; forcing AWAY (was %s, "
        "any_zone_occupied=%s)",
        tracked_count,
        person_summary,
        current_state.value,
        any_zone_occupied,
    )
```

**Severity:** NIT (observability polish; not a correctness bug)

**Recommendation:** Defer to follow-up patch unless trivially absorbed into the deploy.

### NIT-2 — Confidence stickiness on `return None` paths is inherited but not new

**Location:** `domain_coordinators/presence.py:411-412` (and parallel pre-existing path at 398-399)

**Description:** When the veto path returns `None` (already AWAY), `self._confidence` is **not** updated. The same pattern exists in the AND-gate `return None` branch at line 398-399, so this isn't a new bug — but it's worth noting for the record. `PresenceHouseStateSensor.extra_state_attributes` reads `presence.confidence` (sensor.py:3622), so during a sustained no-transition window the sensor displays the confidence value from the *last actual transition*, not the most recent veto evaluation. Existing reviewers may have already accepted this; flagging only because the new code is the second site that exhibits the pattern.

**Fix:** Not required. Optional future improvement: set `self._confidence = 0.95` on the `return None` branch too so the sensor reflects "the veto is still affirmatively choosing AWAY at 0.95 confidence" rather than a stale value.

**Severity:** NIT (existing pattern; called out for completeness only)
