## C1 — Test fixture authority (Bug Class #44)

### Summary

Tests are a HYBRID of (a) direct production-code execution via the real
`StateInferenceEngine.infer()` and (b) **in-test mirrors** of the H2/H3
filter logic in `_run_inference`. The mirrors are honest, documented as
mirrors, and source-level invariants are added alongside to catch
production-side semantic drift. This is acceptable for this cycle but it is
not pure Bug Class #44 compliance; the rationale and the residual risk are
captured below so v4.7.15 can rectify with the helper-extraction.

### Why H2/H3 are hybrid (and what the risk is)

The H2/H3 filters live inside `_run_inference` at `presence.py:1903-1972` —
an `async` method on `PresenceCoordinator` that depends on `self.hass`,
`hass.data[DOMAIN]["person_coordinator"]`, full coordinator wiring, and
the cascade of `_compute_signal_consensus` / dispatcher payload. Driving
the REAL `_run_inference` from a test would require fully constructing a
`PresenceCoordinator` with `hass.data` populated and the entire
`infer()` plumbing — which is the v4.7.15 D1 helper-extraction work, NOT
v4.7.14.1's job.

Given the hotfix scope (3 small filter clauses), the planner explicitly
allowed in-test mirrors PROVIDED they are accompanied by source-level
invariants. The hotfix follows that contract:

1. **Mirror functions named `_phone_trustworthy` / `_tracking_active`** at
   `test_v4714_1_forgotten_phone_hotfix.py:298-305, 514-516` — identical
   logic to production helpers at `presence.py:1925-1937, 1939-1950`.
2. **Source-level invariants** that catch a drift between mirror and
   production:
   - `test_h2_filter_present_in_source` — `_phone_trustworthy` literally
     appears in `presence.py` (test line 487).
   - `test_h2_filter_references_phone_left_behind_entity` — production
     reads `binary_sensor.<slug>_phone_left_behind` (test line 493).
   - `test_h2_filter_uses_hass_states_get` — production helper body
     contains `self.hass.states.get(...)` (test line 504). Catches the
     "developer rewrote `_phone_trustworthy` to use the wrong surface"
     drift.
   - `test_h3_filter_references_tracking_status` — production references
     `tracking_status` field (test line 668).
   - `test_h3_imports_tracking_status_active` — production uses the
     `TRACKING_STATUS_ACTIVE` constant, not a string literal (test line
     674). Bug Class #22 mitigation.

This is the SAME pattern the v4.7.14 D1 fixture used. It is acceptable.

### Residual risk and recommendation

The risk window is the gap between "mirror function in test" and "production
helper in `_run_inference`." If a future cycle (specifically v4.7.15 D1's
shared-veto helper extraction) refactors `_phone_trustworthy` / `_tracking_active`
into the shared utility, the in-test mirror will silently drift unless the
source-level invariants are updated. The current invariants are robust:

- They check for `def _phone_trustworthy` literally appearing in the source.
  When v4.7.15 D1 extracts this into the shared helper, this assertion will
  FAIL (correctly) — forcing the v4.7.15 builder to update the test.
- They check for `tracking_status` and `TRACKING_STATUS_ACTIVE` appearing.
  These will continue to pass after v4.7.15 D1 extraction because the
  shared helper still uses these names.

The source-level guard at line 487 (`assert "_phone_trustworthy" in
PRESENCE_SRC`) is a deliberate trip-wire. When v4.7.15 D1 lands, the
v4.7.15 builder MUST update this test to point at the shared helper name —
NOT to delete it.

**Finding C1 — MEDIUM:**

The in-test mirrors of H2/H3 are an acceptable hybrid pattern for this

### Specific widenings (all in TestD5RunInferenceOr + TestD5ExitConditionGuard + TestB1GuestRoomGateInGuestState)

Two patterns:

| Pattern | Before | After | Sites |
|---|---|---|---|
| Pattern 1 (TestD5* and TestB1 follow-up) | `body = presence_src[idx:idx + 7000]` | `body = presence_src[idx:idx + 9000]` | 7 sites |
| Pattern 2 (TestB1GuestRoomGateInGuestState block) | `body = presence_src[idx:idx + 6000]` | `body = presence_src[idx:idx + 9000]` | 5 sites |

All widen the search window for assertions inside the `_run_inference`

- `_run_inference` starts at `presence.py:1882` (v4.7.14.1 tip).
- H2 adds `_phone_trustworthy` helper definition (+ docstring + body) at
  `presence.py:1925-1937` (~13 lines, ~700 chars).
- H3 adds `_tracking_active` helper at `presence.py:1939-1950` (~12 lines,
  ~700 chars).
- Together, H2+H3 push downstream assertions ~1400 chars further into the
  function body.

Pattern 1 (7000 → 9000) adds 2000 chars of headroom, accommodating H2+H3
plus some margin. Pattern 2 (6000 → 9000) widens more aggressively but
similarly correctly.

### Is the post-widen window still tight enough?

**Window size 9000 is reasonable.** The full `_run_inference` body at
v4.7.14.1 is approximately 9300 characters from `async def
_run_inference(` to its closing return. The new windows essentially cover
the entire function body — which is appropriate for these assertions
because they prove that specific strings (`"_discover_guest_rooms"`,
`"_guest_room_gate_armed"`, `"or guest_room_gate_armed"`, `"0.9"`, `"0.8"`,

`"HouseState.GUEST"`, `"Bug Class #46"`) appear SOMEWHERE inside the
function. They do not pin location-specific structure.

**Cost:** the assertions are now true if the string appears anywhere in
`_run_inference`. If a future cycle moves the D5 confidence wiring outside
`_run_inference` entirely, these tests will FAIL — which is the desired
trip-wire behavior. They continue to catch the regressions they were
designed to catch.

**Is there a risk the widened window catches an unrelated match?** Low. The
strings asserted are domain-specific (`_guest_room_gate_armed`,
`HouseState.GUEST`, `Bug Class #46`) and not likely to appear elsewhere
in `_run_inference`. The two literal numbers (`"0.9"` and `"0.8"`) are
more vulnerable — they could appear in an unrelated confidence value — but
the existing tests at v4.7.14 baseline already had this risk and have not
mis-fired in production.

### C3 verdict: APPROVE

The 7000 → 9000 widening is the second time this window has been widened
(it went from 5000 → 7000 in v4.7.14 per the docstring). The pattern is
load-bearing test hygiene against the v4.7.x stretch's repeated additions

## C4 v4.7.15 merge-order recommendation

**This is the critical output of Reviewer C. Surfaced as a discoverable
section for the v4.7.15 builder.**

### Current state of v4.7.15 branch (as of this review)

`feature/v4.7.15-universalize-bug-class-48` has shipped D1, D2, D3, D4

The two branches are siblings, not parent-child.

### v4.7.15 D1 helper signature (from `presence.py:707-824` on the v4.7.15 branch tip)

```python
def should_veto_due_to_reliable_signals(
    self,
    *,
    reliable_signals: List[ReliableSignal],
    transient_signals: List[TransientSignal],
    state_context: Dict[str, Any],
) -> VetoDecision:
```

Pattern A (`scope == "house_inference"`) processes:
- `reliable_signals` of kind `"person_tracker_away"` (boolean)
- `reliable_signals` of kind `"person_tracker_home"` (boolean)
- `transient_signals` of kind `"unidentified_person_count"` (count)
- `state_context["tracked_count"]` (integer)

It fires when `tracked_count > 0 AND all_away AND not any_home AND unid == 0`,
returning `VetoDecision(True, 0.95, "all_tracked_persons_away (no guests)", scope)`.

### Critical gap in v4.7.15 D1

**Pattern A does NOT consume `census_count`, `phone_left_behind`, or
`tracking_status`.** Verified by reading the helper body at
`presence.py:735-751` on v4.7.15 D3 tip (`36db5ca`). The helper's Pattern A
is a faithful reimplementation of the v4.7.14 inline veto **before** the
v4.7.14.1 hotfix. v4.7.15 D2/D3 do not touch the `_run_inference`
computation block at `presence.py:2106-2129` — it remains identical to the
v4.7.14 baseline (verified by grep on `36db5ca` tip).

This means v4.7.15 as currently committed has:
- A shared helper that DOES NOT implement v4.7.14.1's tightenings.
- An inline veto-feeding computation block that LACKS H2/H3 filters.
- An `infer()` veto predicate that LACKS H1 `census_count == 0` clause.

### Naive merge outcome (DO NOT do this)

If v4.7.15 lands first AND v4.7.14.1 then rebases onto v4.7.15:
- H1 trivially merges (touches `infer()` body; v4.7.15 didn't touch this).
- H2/H3 land in `_run_inference` and create the inline filters v4.7.15
  expected to live ELSEWHERE (in the helper). Result: duplicated logic.
  The v4.7.15 helper's Pattern A would silently overlap with H2/H3 inline
  filters; only one path consumes the result (the inline filters feed
  `all_tracked_persons_away` to `infer()`, while the helper writes
  `_last_veto_decision` for diagnostics). Working but messy and prone to
  drift.

If v4.7.14.1 lands first AND v4.7.15 then rebases onto v4.7.14.1:
- v4.7.15 D1 helper Pattern A needs to be updated to consume `census_count`,
  `phone_left_behind`, and `tracking_status` BEFORE the merge ships — or it
  ships as a regression of v4.7.14.1's tightenings inside the helper.
- v4.7.15 D2/D3 inline computation block needs the H2/H3 filters carried
  forward verbatim, OR the v4.7.15 helper consumes them, with the inline
  block reduced to building the `ReliableSignal[]` and `TransientSignal[]`
  inputs.

### Recommended merge order

**v4.7.14.1 ships first.** Reasons:
1. v4.7.14.1 is a self-contained 3-clause hotfix with clean, surgical
   diffs. Lower review/merge risk.
2. v4.7.14.1 has live operator value (closes Gap A/B/C false-positives
   the operator has flagged).
3. v4.7.15 builds the architectural backbone — it's the cycle that
   SHOULD consume v4.7.14.1's tightenings into its shared helper, not
   v4.7.14.1's job to consume v4.7.15's helper.
4. The v4.7.15 plan §3 D1 explicitly says "v4.7.14 path leaves `infer()`
   veto behavior bit-identical" — that promise is broken by v4.7.14.1
   shipping AFTER v4.7.15 without a rebase update.
