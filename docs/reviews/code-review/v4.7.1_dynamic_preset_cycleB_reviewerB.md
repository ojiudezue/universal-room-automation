## Findings

### CRITICAL

#### B1: `get_options` lambda captures stale `cm_options` at lazy-init time (Bug Class #14)

**File:** `energy.py:2553-2558`
**Bug Class:** #14 (Config Snapshot Staleness)

```python
# Lazily instantiate DynamicPresetOverrideSource (avoids circular import)
if self._dynamic_preset_source is None:
    from .dynamic_preset import DynamicPresetOverrideSource
    self._dynamic_preset_source = DynamicPresetOverrideSource(
        hass=self.hass,
        get_options=lambda: cm_options,  # <-- STALE CLOSURE
    )
```

The `lambda: cm_options` captures the `cm_options` local variable **from the first invocation** of `_async_evaluate_dynamic_presets`. On all subsequent 5-min ticks, the DynamicPresetOverrideSource calls `self._get_options()` which returns the frozen dict from the first tick. Lines 2532-2536 re-read `cm_options` on each tick, but the lambda was bound to the value from tick #1.

**Impact:** After a user changes bucket boundaries, dwell, or hysteresis in CM options, the DynamicPresetOverrideSource silently ignores the change until HA restart. This directly violates the plan's Bug #14 prevention claim ("_refresh_config() at top of evaluate_and_emit reads fresh CONF values") -- the source does call `_get_options()` fresh, but the lambda it receives always returns the same stale dict.

**Fix:** Replace the stale lambda with a fresh-reading closure:

```python
self._dynamic_preset_source = DynamicPresetOverrideSource(
    hass=self.hass,
    get_options=self._get_cm_options,  # bound method, reads fresh each call
)
```

Where `_get_cm_options` is a new method on EnergyCoordinator that re-reads from `hass.config_entries.async_entries` each call.

### HIGH

#### B2: Number entities (dwell/hysteresis) are disconnected from DynamicPresetOverrideSource config reads

**Files:** `number.py:1588-1620` (DynamicPresetDwellMinutesNumber), `number.py:1656-1683` (DynamicPresetHysteresisFNumber), `dynamic_preset.py:348-354`
**Bug Class:** #32 (Form Field With No Runtime Reader)

The two Number entities store their values locally (`self._value`) and persist via RestoreEntity. When the user adjusts the dwell slider from 60 to 30, `async_set_native_value` sets `self._value = 30.0` and writes HA state. However:

1. DynamicPresetOverrideSource reads `CONF_DYNAMIC_PRESET_DWELL_MINUTES` and `CONF_DYNAMIC_PRESET_HYSTERESIS_F` from `self._get_options()` (the CM entry.options dict).
2. The Number entities do NOT call `self.hass.config_entries.async_update_entry()` to push their new values back to CM options.
3. Comment at `number.py:1618` says "Push to EC's DynamicPresetOverrideSource via CM options proxy (source reads from get_options() on each evaluate call -- Bug #14)" but then does nothing to push.

**Result:** Adjusting the dwell or hysteresis Number slider has ZERO runtime effect. The DynamicPresetOverrideSource always reads the CM options dict, which contains the original install-time values. The user changes the slider, sees the new value, but behavior does not change.

**Note:** Even if B1 is fixed (so `get_options` reads fresh CM options), these Number entities still don't write to CM options. The plan calls them "runtime-tunable" -- they are not. Either:
- (a) The Number entities must `async_update_entry` to push their value into CM options, or
- (b) DynamicPresetOverrideSource must read from Number entity state instead of CM options for these two knobs, or
- (c) The Number entities must write directly to `self._dynamic_preset_source` attributes.

**Fix:** Option (a) is simplest and consistent with URA patterns. Add `self.hass.config_entries.async_update_entry(self._entry, options={**self._entry.options, CONF_KEY: value})` in `async_set_native_value`.

But this interacts with B1 -- even after the entry update, if the lambda still returns the frozen first-tick dict, the update won't be seen. Both B1 and B2 must be fixed together.

#### B3: `SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED` emitted even when no overrides changed

**File:** `energy.py:2612-2618`
**Bug Class:** None (new finding -- signal noise)

```python
self._dynamic_preset_overrides = updated_overrides

# Dispatch signal for sensors to refresh
try:
    from homeassistant.helpers.dispatcher import async_dispatcher_send
    from .signals import SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED
    async_dispatcher_send(self.hass, SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED)
except Exception:
    pass
```

`SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED` fires on EVERY 5-min tick, even when the bucket hasn't changed, no zone has transitioned, and all overrides are identical to the previous tick. This causes 3 sensors to call `async_write_ha_state()` every 5 minutes unnecessarily -- 288 state writes per day per sensor, 864 total, all producing identical state.

While not functionally broken, this is a performance drag. Compare to `SIGNAL_DYNAMIC_PRESET_TRANSITIONED` which fires only on actual transitions.

**Impact:** HA recorder bloat + unnecessary event-loop work on every tick.

**Fix:** Compare `updated_overrides` with `self._dynamic_preset_overrides` before dispatching. Only fire the signal if there's an actual change. Simple approach: serialize the override list to a hashable key (e.g., tuple of (zone_id, preset, cool_low, cool_high) per override) and compare.

### MEDIUM

#### B4: DynamicPresetActiveBucketSensor RestoreEntity injection races with EC lazy init

**File:** `sensor.py:6586-6610`
**Bug Class:** #5 (Race Conditions on Startup)

`DynamicPresetActiveBucketSensor.async_added_to_hass()` calls `_try_restore_to_source()` which attempts to inject the restored bucket into `DynamicPresetOverrideSource`. But the source is lazily created in `_async_evaluate_dynamic_presets()`, which only runs on the first EC decision tick (up to 5 minutes after startup).

At sensor setup time, `_get_dynamic_preset_source(hass)` returns None because the source hasn't been instantiated yet. The method has a `if source is None: return` guard, so the inject silently fails. The sensor's `native_value` will return `self._restored_bucket` via its fallback -- correct for display. But the DynamicPresetOverrideSource has no knowledge of the restored bucket, so on the first decision tick it will treat the zone as "first evaluation" and bypass the dwell check entirely.

**Impact:** After restart, the first evaluation always produces a "first evaluation" log and sets the bucket without dwell gating. If the weather forecast shifted during the restart window, the bucket could transition immediately instead of respecting the dwell from the pre-restart state.

**Practical severity:** LOW to MEDIUM. The first tick after restart will likely classify the same bucket (weather doesn't change that fast), and even if it does transition, it only fires once. But it does violate the Bug #10 contract.

**Fix:** Either:
- (a) Create the DynamicPresetOverrideSource eagerly in `EnergyCoordinator.__init__` (non-lazy), or
- (b) On the first `_async_evaluate_dynamic_presets()` call, check if any per-zone sensors have pending restores and inject them before evaluating.

#### B5: `_async_evaluate_dynamic_presets` is awaited inside the decision cycle -- budget impact unverified

**File:** `energy.py:2298-2301`
**Bug Class:** None (EC cycle budget)

The evaluation is `await`ed inside `_async_decision_cycle`:

```python
await self._async_evaluate_dynamic_presets()
```

Inside this method, each zone calls `await self._dynamic_preset_source.async_evaluate_and_emit(...)` which acquires an asyncio.Lock and then calls the synchronous `evaluate_and_emit()`. With 3 canonical zones, this is 3 lock acquisitions + 3 synchronous evaluations per tick.

The synchronous evaluation is fast (no I/O, just dict reads + comparisons + math). The async wrapper + lock acquisition adds minimal overhead. The real concern is the per-tick `iter_canonical_hvac_zones()` call + Zone Manager entry scan + WPM `baseline_delta_for_zone()` per zone.

**Assessment:** Likely within budget (well under 1 second total for 3 zones). But no benchmark exists. The plan's acceptance criterion "EC decision cycle still completes within existing duration budget (no >5s additions)" is untested.

**Fix:** Not blocking -- add a timing log at DEBUG level to measure actual latency in production.

#### B6: Observation-mode gating incomplete -- overrides stored but no actuation gate visible

**File:** `energy.py:2298-2301, 2610`
**Bug Class:** #23 (Observation Mode Gating)

The comment at line 2300 says "Gated by observation_mode on the actuation side (Bug #23 -- eval always runs)." The evaluation runs and `self._dynamic_preset_overrides` is populated even in observation mode.

But where exactly is the observation-mode gate on the actuation side? The override records are stored in `self._dynamic_preset_overrides` which sensors read. In observation mode, the overrides are still stored, signals are still dispatched, and sensors still show the active bucket + ranges.

The plan says "actuation gating is HVAC coordinator's responsibility." This is architecturally correct -- the HVAC coordinator should check observation mode before applying any preset override to the thermostat. However, the current build does NOT include any code that reads `self._dynamic_preset_overrides` for actuation purposes. The overrides are computed, stored for sensor display, and that's it. No code path currently calls `OverrideEngine.resolve_range()` to compose the final range and apply it to a thermostat.

**Assessment:** This is technically safe because the actuation path doesn't exist yet (it's presumably a future cycle that wires OverrideEngine output to HVAC preset changes). But it means observation mode is gated by omission, not by design. When the actuation path is eventually added, it MUST check `self._observation_mode` before calling any thermostat service.

**Risk:** MEDIUM -- the actuation path is missing entirely, which is technically correct but means the feature computes overrides without applying them to anything. The sensors show what would happen, but nothing happens. This is consistent with the plan's scope (compute + emit into OverrideEngine for visibility), but the reviewer notes this for the future wiring cycle.

Per tick with 3 canonical zones:
1. CM entry scan: O(entries) -- typically 3-5 entries, fast
2. WPM `current_apparent_forecast_high()`: attr read, O(1)

6. Per zone: `evaluate_and_emit()`: bucket classify + dwell check + override build, O(1)
7. Lock acquisition: asyncio.Lock, uncontended (no concurrent callers), O(1)

Estimated total: < 10ms for 3 zones. Well within budget.

## Migration Correctness

### Double-emission risk

Guest Mode and Dynamic Preset both produce `PresetOverride` records, but through different paths:
- Guest Mode: `OverrideEngine.build_guest_mode_overrides()` -- static helper, called from HVAC coordinator
- Dynamic Preset: `DynamicPresetOverrideSource.evaluate_and_emit()` -- called from EC decision cycle

These paths are independent. No code currently aggregates both lists into a single `OverrideEngine.resolve_range()` call at runtime -- the tests do this (TestOverrideEngine), but production code does not yet compose them.

**Assessment:** No double-emission risk because the two sources don't share a codepath. When the actuation cycle wires them together, it must collect from both sources before calling `resolve_range()`.

### Source-shape contract

Dynamic Preset `PresetOverride` records verified field-by-field:
- `source`: `"dynamic_preset"` (OVERRIDE_SOURCE_DYNAMIC_PRESET constant) -- correct
- `priority`: `DYNAMIC_PRESET_PRIORITY` = 30 -- correct, lower than Guest Mode = 50
- `preset`: `"home"` or `"sleep"` -- correct
- `cool_low`: float from zone_data config -- correct
- `cool_high`: float from zone_data config + zone_offset -- correct
- `active_when`: `"dynamic_preset"` -- matches `_eval_predicate` handler
- `zone_id`: set correctly per zone
- `bucket`: set correctly per evaluation

**Verdict:** Shape is correct. Priority ordering verified.

### Override removal

When Dynamic Preset's evaluation determines a zone should NOT have an override (feature toggled off, zone opts out, or delta is None), `evaluate_and_emit()` returns `[]`. The caller in `energy.py:2594-2601` stores the empty list:
```python
updated_overrides[zone_id] = overrides  # = []
```

Then `self._dynamic_preset_overrides = updated_overrides` replaces the entire dict. Zones with empty lists effectively have their overrides removed from sensor visibility.

However, there is no explicit `OverrideEngine.remove_override(source, zone)` call because the OverrideEngine is stateless -- it resolves per-call from a supplied list. The "removal" is implicit: the next tick's override list simply doesn't include the removed zone's records.

**Assessment:** Correct for the current architecture (stateless engine). If the engine becomes stateful in a future cycle, explicit removal will be needed.

## Restart Resilience

### OverrideEngine restart behavior

`OverrideEngine` is stateless -- it has no stored overrides. On restart, it comes up clean. Overrides are re-computed on the first EC decision tick (within 5 minutes of restart). No automatic re-emission occurs before the first tick.

Between restart and first tick, sensors show restored bucket values (via RestoreEntity) but `_dynamic_preset_overrides` in EC is an empty dict. Sensors that read from this dict will show zero overrides until the first tick repopulates them.

**Assessment:** Brief gap (up to 5 min) where `DynamicPresetOverridesAppliedSensor` shows 0 overrides and `DynamicPresetRangeSensor` shows None, while `DynamicPresetActiveBucketSensor` shows the restored bucket. Cosmetic inconsistency during startup window. Not blocking.

### Dwell timer across restart

Dwell timer uses `last_transition_at` from RestoreEntity sensor. Bug #10 compliance depends on B4 (sensor restore injection races with lazy source init). If B4 is fixed, dwell survives restart correctly.

But none of these paths consume Dynamic Preset overrides.

When the actuation path is eventually added, it MUST include an observation-mode check. The plan's Bug #23 mitigation is a design intent, not an implemented gate.

**Assessment:** SAFE for this build. The gate-by-omission is acceptable because there's no actuation path to gate.
