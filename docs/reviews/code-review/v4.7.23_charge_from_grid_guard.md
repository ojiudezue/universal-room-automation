# Code Review — v4.7.23 Charge-from-Grid Guard Fix

**Scope:** Battery arbitrage grid-import guard no longer counts the battery's
own charge inrush against the breaker-protection cap, and a single
battery-CT-lag tick at CHARGE entry can no longer false-lock the whole
off-peak chunk.

**Files:**
- `domain_coordinators/energy_battery.py` — `_effective_import_kw()` (new),
  `_grid_import_guard_triggered()` (rewritten as thin predicate),
  `_get_arbitrage_phase` guard branch (2-consecutive-trip lock),
  `reset_arbitrage_chunk()` (streak reset), `__init__` (counter).
- `domain_coordinators/energy_const.py` — `ARBITRAGE_GUARD_CONSECUTIVE_TRIPS_TO_LOCK = 2`.
- `quality/tests/test_energy_battery.py` — 8 existing guard tests converted to
  the 2-tick lock; new `TestArbitrageGuardBatteryExclusion` cases.

**Tier:** 2 (two framing-disjoint reviews). The fix is small (2 source files)
but sits on the energy arbitrage hot path where a wrong sign or a stale-CT
misread either trips the panel breaker or silently kills off-peak charging —
both expensive failure modes — so it got the two-review bar rather than a
single hotfix pass.

---

## The bug

`_grid_import_guard_triggered()` compared TOTAL `net_power_w` (house + EV +
**battery charge inrush**) against the 12 kW cap. Arbitrage CHARGE itself
drives `net_power` above the cap, so the guard self-aborted every chunk.
Observed live: net 18.6 kW with the battery charging 15.8 kW and non-battery
draw flat ~2.8 kW tripped the 12 kW cap.

**Fix:** `effective = net_power_w − max(0, battery_power_w)`. Only the
non-battery draw (the thing that can actually trip the breaker) is compared
to the cap. `max(0, …)` ensures a *discharging* battery (negative
`battery_power_w`) can never *raise* the effective import.

**Verdict: GO on correctness.**

## Review B — Async / lifecycle / sensor-lag

| ID | Sev | Finding | Status |
|----|-----|---------|--------|
| B-H1 (H-B1) | HIGH | **CT-lag false-lock.** At CHARGE entry the Envoy battery-power CT lags `net_power` by one poll: tick 1 reads full inrush on net while the battery still reads ~0 → effective ≈ net → over cap → a one-shot lock killed the entire off-peak chunk to pure sensor lag. | **FIXED** — lock now requires `ARBITRAGE_GUARD_CONSECUTIVE_TRIPS_TO_LOCK = 2` consecutive over-cap ticks. Tick 1 defers (returns CHARGE, logs `trip 1/2`); tick 2 locks. A genuine house+EV overdraw still locks within one extra ~30 s tick — well inside the physical breaker margin. Streak resets on any under-cap tick AND in `reset_arbitrage_chunk()`. Regression test `test_ct_lag_tick_does_not_false_lock_chunk` + `test_sustained_overdraw_locks_on_second_consecutive_tick`. |
| B-M1 (M-B1) | MED | **`_arbitrage_guard_aborted_kw` semantic change.** It now records the EFFECTIVE (non-battery) import that exceeded the cap, not total net. The diagnostic sensor that surfaces it will read lower than pre-fix for the same event. | Accepted — single-user install, no external consumer of this attribute; the effective value is the one the guard actually compared, so the diagnostic is now *more* truthful. Documented here per Plan-Completion-Tracking. |
| B-M2 | MED | Decision/diagnostic divergence: previously the guard predicate read the sensors, then the abort path re-read them — a second read could diverge from the value compared. | **FIXED** — `_effective_import_kw()` takes ONE snapshot and threads `(effective, net, batt_charge)` into both the comparison and the diagnostic record. |
| B-L1 | LOW | Counter is plain in-memory int; not persisted across restart. A restart mid-chunk resets the streak to 0. | Accepted — a restart already resets `_arbitrage_chunk_completed`/chunk state; losing one tick of streak is harmless (worst case one extra deferred tick after reboot). |

**Verdict: was NO-GO pending B-H1; B-H1 now FIXED → GO.**
