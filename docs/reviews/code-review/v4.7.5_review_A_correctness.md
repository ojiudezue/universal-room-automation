### H1 — `async_step_zone_rooms` bypasses `_auto_mirror_to_siblings` while the comment claims otherwise

**Bug class:** Bug Class #33 — Sibling Helper Skipped (per QUALITY_CONTEXT.md §"Sibling Helper Skipped").
**File:** `custom_components/universal_room_automation/config_flow.py:5355-5384`.

The build comment at line 5357-5361 reads:

```
# v4.7.5 D4: rooms are per-house-zone (MIRROR_KEYS_ZONE_ROOMS
# is empty by design — Entertainment has different rooms than
# Master Suite). Use the auto-mirror helper anyway so the
# rename path stays atomic with the save (one
# async_update_entry total, even when the zone is renamed).
```

…but the code below it does **not** use the helper. It performs an inline `merged = …`, `zones = {…}`, rename-handling, then `self.hass.config_entries.async_update_entry(zm_entry, options=…)` directly. The other six editor steps (media, hvac, energy, persons, cameras, dpm) **do** route through `_auto_mirror_to_siblings`. Rooms is the lone exception.

**Why this matters (not just cosmetic):**
1. **Spec contract violation.** PLANNING_v4.7.5 §D4 says "Pattern repeated at each of the 7 call sites" and §7 (Bug Class #33 row) says "D4 has 7 call sites; missing one means save-without-mirror on a sibling-sharing zone." Rooms is intentionally `MIRROR_KEYS_ZONE_ROOMS = frozenset()`, so the *mirror* is correctly a no-op — but the design intent is that the helper centralises the write so that future maintenance (e.g., adding a shared-thermostat-tied per-room field) doesn't require re-locating the call site.
2. **Test deception.** `test_v475_d4_mirror_keys_module_constants_present` asserts the constant exists; `test_v475_d4_per_house_zone_mirror_sets_empty` asserts it's empty; but **no test asserts that `async_step_zone_rooms` actually invokes the helper**. Any future maintainer who wants to add a shared-thermostat field to the rooms surface (e.g., "shared HVAC zone label") would expect the auto-mirror to handle it — and silently get a non-mirror.
3. **Diff hygiene.** The comment says one thing; the code does another. Reviewer scanning the file will be misled.

**Suggested fix.** Either:

a. **Route rooms through the helper.** Refactor the rename + mirror so the helper handles it. Sketch:
```python
# Pre-helper rename: move the slot key directly on the entry
if old_zone_name != zone_name and old_zone_name in (merged.get("zones") or {}):
    # Use a tiny shim or extend _auto_mirror_to_siblings to take an
    # optional rename_from kwarg
    ...
_persistent_payload = {
    CONF_ZONE_DESCRIPTION: user_input.get(CONF_ZONE_DESCRIPTION, ""),
    CONF_ZONE_ROOMS: selected_rooms,
}
self._auto_mirror_to_siblings(
    zm_entry, zone_name, _persistent_payload,
    MIRROR_KEYS_ZONE_ROOMS,
)
```

b. **Fix the comment** to honestly say "rename + save are inline because the helper doesn't (yet) support rename. Mirror is a no-op for rooms." Then file a follow-up to extend the helper.

I recommend (b) for v4.7.5 (smaller blast radius) and add a TODO referencing v4.7.6. Either way, add a test:

```python
def test_v475_d4_zone_rooms_uses_single_async_update_entry(...):
    """Saving zone_rooms produces exactly ONE async_update_entry call."""
```

…so we lock the atomicity property that the rest of the helper-routed steps already enjoy.

### H3 — Lazy Canonical Resolution: `" + "` split fallback is silently name-collidable

**Bug class:** New — Lazy Canonical Resolution (v4.7.5), correctness sub-class.
**File:** `custom_components/universal_room_automation/domain_coordinators/energy.py:2592-2597`.

```python
zone_data = zm_zones.get(zone_name, zm_zones.get(zone_id, {}))
if not zone_data and " + " in zone_name:
    for _part in zone_name.split(" + "):
        _part = _part.strip()
        if _part in zm_zones:
            zone_data = zm_zones[_part]
            break
```

The canonical merge in `hvac_zones.py:788-790` produces labels of the form `f"{existing['zone_name']} + {zm_zone_name}"` — concatenated by the literal `" + "` (space-plus-space) on the right side, but the left side is just whatever `existing['zone_name']` already was. **The merge does NOT escape `+` characters inside the original zone names**, and `iter_canonical_hvac_zones` does not normalise the input zone-name strings.

**Edge cases that break:**
1. A user names a house zone `"Living + Dining"` (single zone, single label). At read time, `zone_name = "Living + Dining"` matches `" + " in zone_name` → splits to `["Living", "Dining"]`. Neither part is in `zm_zones` (the key is `"Living + Dining"`), so the loop exits without setting `zone_data` — but `zm_zones.get(zone_name)` has already succeeded on the very first line because `"Living + Dining"` IS a real key. So this exact case is actually safe by short-circuit.
2. **The real collision case:** a user names a house zone `"Living + Dining"` *and* another zone `"Living"` exists in the same ZM. The merge logic doesn't combine them (different thermostats), so both are real keys. `iter_canonical_hvac_zones` returns `zone_name = "Living + Dining"` (unmerged, since it's solo on its thermostat). `zm_zones.get("Living + Dining")` succeeds → uses correct data. **No collision.** Good.
3. **Where it DOES break:** Two zones `"Living"` and `"Dining"` share a thermostat. Canonical merge produces `zone_name = "Living + Dining"`. A *third*, unrelated zone is named `"Living + Dining"` (rare but legal — config flow doesn't reject `+` in names). Now `zm_zones.get("Living + Dining")` succeeds with the wrong zone's data (the unrelated standalone one) — never enters the fallback split. Wrong DPM data is silently applied.
4. **Also breaks:** Two zones `"A + B"` and `"C"` share a thermostat → merged label `"A + B + C"`. The split is `["A", "B", "C"]` — none match the original zone names `"A + B"` and `"C"`. The first existing match (`"C"`) wins, even though `"A + B"` was the first constituent.

**Why it's HIGH, not CRITICAL:** the URA install today has 5 well-named house zones; none of them contain `+`. The trigger probability is low. But Option C v4.7.5 *guarantees* siblings carry identical data, so the wrong-pick still produces correct DPM behavior **only because every sibling has the same data**. If for any reason the mirror is incomplete (see H1 / M4), the wrong-zone fallback silently propagates stale data.

**Suggested fixes (any one):**

a. **Reject `+` in zone names at config-flow validate time.** Cleanest. Add to the zone-name validator: `if "+" in zone_name: raise vol.Invalid("zone name must not contain '+'")`. Document in PLANNING and release notes.

b. **Use a non-ambiguous separator.** Change the canonical merge in `hvac_zones.py:788-790` from `" + "` to something a zone name realistically can't contain (e.g., `" ⧸ "` U+29F8 BIG SOLIDUS, or a control character). Then update the energy.py read-side accordingly. **WARNING:** this changes the user-visible canonical label (`sensor.ura_hvac_zone_*` friendly_names, log lines). Coordinate with Reviewer B's deploy-side validation.

c. **Add a guard to the canonical merge that asserts no constituent name contains the separator.** Fail loudly during `iter_canonical_hvac_zones` if a violation is found, so the install operator notices.

d. **Iterate constituents in reverse order** in the energy.py split-fallback so the most-recently-added zone wins — and add a comment that this is a temporary patch until (a)/(b) lands. Weakest mitigation but minimal blast radius.

I recommend (a) for v4.7.5 (smallest fix, narrows a real bug class for the future). Add a regression test:

```python
def test_v475_d3_zone_name_validator_rejects_plus():
    """Zone name with '+' is rejected so canonical merge separator stays unambiguous."""
```

### M3 — `_zone_id_from_thermostat_pure` allows `zone_id == zone_name` collisions that bypass the split fallback in energy.py

**Bug class:** Lazy Canonical Resolution — read-side robustness.
**File:** `custom_components/universal_room_automation/domain_coordinators/energy.py:2591`.

```python
zone_data = zm_zones.get(zone_name, zm_zones.get(zone_id, {}))
```

When `iter_canonical_hvac_zones` returns a merged label like `"Entertainment + Master Suite"` AND the user has — accidentally or otherwise — a single house zone literally named `"zone_2"` (matching the synthesized `zone_id`), the fallback `zm_zones.get(zone_id)` will hit the wrong zone if `zone_name` isn't a real key.

Today the chance is low (`zone_id` follows the `zone_N` or `zone_<num>` pattern; users typically pick descriptive names) but the codepath isn't defended against it.

**Suggested fix.** Tighten the lookup ordering and intent:
```python
# 1) Direct match on raw house-zone name (covers solo zones)
zone_data = zm_zones.get(zone_name)
# 2) Merged label — split and resolve to a constituent
if not zone_data and " + " in zone_name:
    for _part in zone_name.split(" + "):
        _part = _part.strip()
        if _part and _part in zm_zones:
            zone_data = zm_zones[_part]
            break
# 3) Last-resort zone_id match (legacy / migration paths only)
if not zone_data:
    zone_data = zm_zones.get(zone_id, {})
```

This makes the intent explicit and eliminates the cross-key collision. Bonus: the `_part and ...` guard hardens against the degenerate `" + "` standalone edge.

### M6 — `test_v475_d5_mutation_proves_coverage` does NOT prove runtime coverage; it only proves the AST grep mechanism works

**Bug class:** Test fixture / coverage hole.
**File:** `quality/tests/test_v475_d5_config_flow_runtime_smoke.py:330-353`.

The test as written:
```python
mutated_modes = {"LIST"}  # DROPDOWN intentionally removed
refs = _collect_selector_attribute_refs("SelectSelectorMode")
missing = refs - mutated_modes
assert "DROPDOWN" in missing
```

This proves the set-difference math works — but it doesn't prove that calling `_load_config_flow(select_modes={"LIST"}, …)` would raise on the **runtime** path. The body comment at lines 348-353 admits this: "this part is conservative — we don't expect _load_config_flow to raise just by importing the module."

The whole point of D5 is to catch **runtime** ImportError/AttributeError that source-grep can't see. The mutation test should:

1. Call `_load_config_flow(select_modes={"LIST"}, …)` (DROPDOWN omitted from the stub).
2. Then call `flow.async_step_<some_step_that_uses_DROPDOWN>(user_input=None)`.
3. Assert `AttributeError` is raised.

As-is, the test name (`mutation_proves_coverage`) overstates what it actually proves.

**Suggested fix.** Strengthen the mutation test to actually run a method that references `SelectSelectorMode.DROPDOWN`:

```python
def test_v475_d5_mutation_actually_catches_missing_dropdown_at_runtime():
    cf = _load_config_flow({"LIST"}, _DEFAULT_TEXT_TYPES)
    # Many existing async_step_* methods use SelectSelectorMode.DROPDOWN in
    # their schema build (e.g., async_step_zone_rooms). Calling one of those
    # should raise AttributeError now that DROPDOWN is missing.
    OptionsFlow = cf.UniversalRoomAutomationOptionsFlow
    flow = OptionsFlow.__new__(OptionsFlow)
    flow.hass = _stub_hass()
    flow._config_entry = _stub_entry_with_zm()
    flow._selected_zone_name = "Office"
    flow._selected_zone_entry_id = None
    with pytest.raises(AttributeError) as exc:
        asyncio.get_event_loop().run_until_complete(
            flow.async_step_zone_rooms(user_input=None)
        )
    assert "DROPDOWN" in str(exc.value), (
        "Without this raise, D5 would not have caught v4.7.4.2 in CI."
    )
```

Keep the existing set-difference test as a separate `test_v475_d5_select_mode_set_difference_logic` — useful but properly scoped.

### L6 — `test_v475_d4_auto_mirror.py` module-load uses the "save/restore sys.modules" pattern but `_CF_MOD = _load_config_flow_module()` runs at import time

**Bug class:** Bug Class #44 — Cross-File sys.modules Pollution.
**File:** `quality/tests/test_v475_d4_auto_mirror.py:233`.

The test loads `config_flow` lazily at import (module-level `_CF_MOD = _load_config_flow_module()`). The helper saves/restores sys.modules — good — but the loaded `_CF_MOD` retains references to imports that resolved against the stubs (e.g., `const` module loaded into the stubbed namespace). If a *later* test module (or the same module under pytest's `--forked=no`) attempts to load config_flow again with different stubs, it may pick up cached state.

The helper docstring (lines 174-179) acknowledges this and claims the restoration is sufficient because cf_mod retains its own references. That's true for the module under test in isolation — but the D5 test in the same suite also loads config_flow with its own stubs. If tests run in the same Python process, there's no isolation between D4's `_CF_MOD` (loaded at module import) and D5's `_load_config_flow(...)` calls.

**Verification.** Run:
```
PYTHONPATH=quality python3 -m pytest quality/tests/test_v475_d4_auto_mirror.py quality/tests/test_v475_d5_config_flow_runtime_smoke.py -v
```
…in **both** orders (d4 first vs d5 first). If results differ, Bug Class #44 is back.

**Suggested fix.** Either (a) move the `_load_config_flow_module()` call into a session-scoped fixture rather than module-import-time so the order is explicit, or (b) defer module loading to test-function scope. Option (a) is cleanest.

### L7 — `_get_shared_thermostat_siblings` catches `Exception` broadly

**Bug class:** Bug Class #14 — Config snapshot staleness / over-broad exception swallow.
**File:** `config_flow.py:2057-2063`.

```python
except Exception:  # noqa: BLE001 — siblings discovery is best-effort
    _LOGGER.debug(...)
    return []
```

The intent is "never block the menu render." Fair. But a silent empty-list return means:
1. The banner won't render on the next call — masking the bug.
2. The mirror won't fire either (callers will see "no siblings" and skip the mirror loop).

If `zm_entry.data` or `.options` is malformed (e.g., `zones` is a list instead of a dict), silently dropping back to "no siblings" means saves silently stop mirroring. The bug surfaces only at the user-visible level ("why didn't my sibling zone update?") long after the malformed state was introduced.

**Suggested fix.** Narrow the catch to specific failure modes:
```python
except (AttributeError, TypeError, KeyError):  # noqa: BLE001
    _LOGGER.warning(  # WARNING, not debug — silent fallback to no-mirror is load-bearing.
        "v4.7.5 sibling lookup failed for zone=%s — auto-mirror skipped",
        zone_name, exc_info=True,
    )
    return []
```

WARNING-level surfacing makes the silent-mirror-off mode visible in `ha_get_logs`.
