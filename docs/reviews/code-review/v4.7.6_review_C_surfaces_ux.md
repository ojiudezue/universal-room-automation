### C-H2 — Single L1 plug `self_modulates` checkbox vs per-plug helper text (HIGH)
**File:** `custom_components/universal_room_automation/__init__.py:1807-1815`
```python
plug_self_modulates = bool(cm_config.get("l1_plug_self_modulates", False))
plug_config = {
    plug_id: {"self_modulates": plug_self_modulates}
    for plug_id in (smart_plug_entities or [])
}
```
The config flow exposes ONE `l1_plug_self_modulates` boolean (`config_flow.py:3527-3530`). At setup time, the value is broadcast to every configured L1 plug. Plan D3.4 / D6.4 specified per-plug semantics ("Mirror for plugs: per-plug checkbox `plug_self_modulates` in the smart-plug step"). The builder downgraded to a single bool. That is *acceptable* per the planning-doc allowance ("most installs have 0-1 L1 plugs"), but:

- The translations / strings helper text reads as if it's per-plug: `"Check when L1 plugs have native solar/schedule modes."` — plural "plugs" implies they're all governed together; OK there.

The sensor surface lies about the source.
- A future user with 2 L1 plugs in different garages who wants asymmetric behavior has **no escape hatch** other than reconfiguring all plugs identically.

**Fix options:**
1. Keep the single bool but mark `source` as `"explicit-broadcast"` so the user sees that all plugs are governed together.
2. Promote to per-plug at v4.7.7 and add the per-plug checkbox loop in config_flow.py.

**Bug class:** none yet — admin-UI granularity mismatch.

### C-M5 — L1 plug `idle` plug renders as `charging: True` (MEDIUM)
**File:** `energy_pool.py:1644`
```python
charging = is_on and not paused
```
For an L1 plug with no power sensor (the common case for dumb Moes plugs), URA has no way to know whether the plug is currently drawing power. The plan's D6.3 says:
> `charging: boolean: is_on AND power > threshold OR is_on AND not paused`

The implementation went with `is_on AND not paused` — meaning a plug switched ON with nothing plugged in (a stove plug always-on, a lamp on a smart plug used as "L1 charger") will show `charging: True` in the dashboard. That is wrong for the UX promise of the sensor.

**Fix options:**
1. Accept the limitation, rename `charging` to `armed` for L1 plugs to make the semantic difference explicit.
2. Make `charging` always equal `is_on` for L1 plugs, and require the user to read `power_source: "switch_status"` to know it's switch-only inference (currently already true).
3. Try to infer via a power-sensor lookup if one is configured (out-of-scope for v4.7.6 because the per-plug config flow doesn't accept a power sensor).

Pick (1) — minimal code churn. Communicate the limitation in the L1 helper text.

### C-M6 — `_v476_alias_migrated` flag may not survive entry reload, migration re-runs (MEDIUM)
**File:** `custom_components/universal_room_automation/switch.py:55-83`
```python
runtime = getattr(entry, "runtime_data", None)
if isinstance(runtime, dict) and runtime.get("_v476_alias_migrated"):
    return
...
try:
    if isinstance(runtime, dict):
        runtime["_v476_alias_migrated"] = True
    else:
        entry.runtime_data = {"_v476_alias_migrated": True}
```
HA's `ConfigEntry.runtime_data` is documented as a per-runtime cache — it is **reset on every entry reload**. After v4.7.6 ships and the user does ANY config change that bounces the CM entry, `runtime_data` is reinitialized, the flag is cleared, and `_migrate_excess_solar_entity_id()` runs again. Idempotent because (a) the legacy entity_id will no longer exist after first migration, so the registry lookup at `er.async_get(legacy_entity_id)` returns None; (b) the early-out at line 70 (`if registry.async_get(new_entity_id) is None`) ensures no collision.

**So the bug is benign** but the *guard is structurally wrong* — it doesn't actually guard anything because the real guard is the registry state, not the flag. The flag adds complexity (a try/except wrapping a write to `entry.runtime_data` because the builder wasn't sure of the runtime_data shape) without doing the job claimed in the comment ("ensure this runs at most once per entry setup").

**Fix:** drop the flag entirely; comment that the migration is idempotent because the registry lookup itself is the guard.

### C-L4 — `cooldowns.expires` `%Z` blank on naïve datetimes (LOW)
**File:** `energy_pool.py:1167`
```python
"expires": expires_local.strftime("%H:%M %Z").strip(),
```
`dt_util.now()` returns a tz-aware datetime in URA on HA. `now_local + timedelta(...)` preserves tz-aware. `%Z` will populate ("CDT"). However: on some test harnesses and CI environments where `dt_util.now()` is monkey-patched to `datetime.now()` (naïve), `%Z` is blank → the string renders as `"18:23 "` with a trailing space already stripped. Confirmed via inspection of `quality/tests/test_evse_solar_aware_ux.py:48-53`:
```python
"homeassistant.util.dt": {
    "utcnow": __import__("datetime").datetime.utcnow,
    "now": __import__("datetime").datetime.now,  # NAIVE!
    "as_local": lambda dt: dt,
}
```
The test surface uses naïve datetime — so the `%Z` is empty under test, but `dt_util.now()` in production is tz-aware. No production bug; minor test-fixture authority concern (test surface doesn't match production behavior, but it's not a wrong test, just a less-exercised path).

### C-L5 — Legacy entity_id "alias" is actually a one-shot rename (LOW)

### Reviewer C's findings from the matrix:

**Matrix-1 (LOW):** The `excess_solar` turn-ON path at `energy_pool.py:472-498` does NOT exclude EVSEs in `_paused_by_fill_priority` from being turned ON. **Matrix-2 (LOW):** Multiple rules dispatching `switch.turn_off` in the same tick is HA-idempotent (no double-toggle).
