## HIGH Findings

### C3 — No AST regression test prevents reintroduction of the lambda + async_create_task anti-pattern (HIGH)

The v4.6.3.2 cycle created a SOURCE-GREP test (`test_v463_anomaly_migration.py:1055`) that pins the fix for ONE specific site. But there is no codebase-wide guard. Any future developer adding a timer callback could reintroduce the pattern.

**Proposed test** (add to `quality/tests/test_v4615_threadsafety.py`):

```python
"""Bug Class #42: lambda + async_create_task in HA scheduler callbacks.

This AST regression test prevents reintroduction of the pattern:
    lambda _now: self.hass.async_create_task(self._async_refresh())
passed to async_track_time_interval / async_track_time_change.

HA's frame helper flags this as a thread-safety violation; the coroutine
is silently never awaited. Fixed in v4.6.15.
"""
import ast
import pathlib

URA_ROOT = (
    pathlib.Path(__file__).parents[2]
    / "custom_components"
    / "universal_room_automation"
)


def test_no_lambda_wrapping_async_create_task():
    """Bug Class #42: no lambda body may call async_create_task.

    Pattern: lambda ...: <expr>.async_create_task(...)
    This is always wrong when passed to HA scheduler APIs because:
    1. HA's HassJob doesn't recognize lambdas as coroutine functions
    2. The frame helper flags the thread-safety violation
    3. The created coroutine is silently never awaited
    """
    violations = []
    for py_file in sorted(URA_ROOT.rglob("*.py")):
        try:
            tree = ast.parse(py_file.read_text())
        except SyntaxError:
            continue
        for node in ast.walk(tree):
            if not isinstance(node, ast.Lambda):
                continue
            for inner in ast.walk(node.body):
                if (
                    isinstance(inner, ast.Call)
                    and isinstance(inner.func, ast.Attribute)
                    and inner.func.attr == "async_create_task"
                ):
                    violations.append(
                        f"{py_file.relative_to(URA_ROOT.parent.parent)}"
                        f":{node.lineno} — lambda wraps async_create_task "
                        f"(Bug Class #42)"
                    )
    assert not violations, (
        "lambda + async_create_task anti-pattern found "
        f"({len(violations)} site(s)):\n" + "\n".join(violations)
    )
```

This test would have caught all 5 original bug sites and will permanently prevent reintroduction.

### C4 — Test infrastructure gap: no HA frame-helper warning capture (HIGH)

All URA tests mock `homeassistant.helpers.event` with `MagicMock()` or thin lambdas that discard the callback. The test harness never creates a real HA event loop context, which means:
1. HA's frame helper (`homeassistant.helpers.frame`) is never active
2. Thread-safety violations are never detected at test time
3. The live symptom (the warning) would never surface in tests

Structural limitation of the URA test architecture (module-level mock injection rather than HA test harness `hass` fixture). Fully fixing requires migrating to `pytest-homeassistant-custom-component` — a large infrastructure project.

**Recommendation:** Accept as known gap. AST regression test (C3) provides static prevention. Document in QUALITY_CONTEXT.md.

## Bug Class #42 — Ready to Insert into QUALITY_CONTEXT.md

```markdown
### Bug Class #42: Lambda + async_create_task in HA Scheduler Callback

**Shape:** A lambda wrapping `self.hass.async_create_task(self._some_coroutine())` is passed to an HA scheduler API (`async_track_time_interval`, `async_track_time_change`, `async_call_later`). HA's `HassJob` machinery inspects the callable to determine if it is a coroutine function, but lambdas are never recognized as coroutine functions. HA's frame helper then flags a thread-safety violation ("calls async_create_task from a thread other than the event loop, which may cause crash or data corruption"). **The coroutine returned by the inner `async_create_task` call is silently never awaited** — scheduled work simply does not run. Sensors show stale data; digests never fire.

**v4.6.15 example:** 5 sites used `lambda _now: self.hass.async_create_task(self._async_refresh())` as the callback for `async_track_time_interval` (3 telemetry sensors added in v4.6.13) and `async_track_time_change` (2 NM digest schedulers added in v3.6.29). All 5 silently stopped refreshing. Correlated with multiple HA-core crashes on 2026-05-26.

**Sibling pattern (v4.6.3.1):** `async_create_task` called from a dispatcher signal handler fired by a non-event-loop thread. Same frame-helper violation but different entry point. Fixed in v4.6.3.2 by switching to `hass.add_job`. The root cause is the same: calling `async_create_task` outside the event loop contract.

**Prevention:**
- Pass coroutine functions directly to HA scheduler APIs: `async_track_time_interval(hass, self._async_method, interval)`. HA's `HassJob` wraps them correctly.
- For closures that need bound arguments, use `functools.partial(self._async_method, arg1, arg2)`.
- NEVER wrap in `lambda: self.hass.async_create_task(...)` — this pattern is always wrong for scheduler callbacks.
- For dispatcher signal handlers that may fire from non-event-loop threads, use `self.hass.add_job(coroutine)` instead of `self.hass.async_create_task(coroutine)`.
- AST regression test `test_no_lambda_wrapping_async_create_task` in `quality/tests/test_v4615_threadsafety.py` catches reintroduction at CI time.

**Detection:** AST grep for `lambda` nodes containing `async_create_task` attribute calls. Live: `ha_get_logs` search for "calls async_create_task from a thread other than the event loop".

**Discovered:** v4.6.15 (thread-safety hotfix, 2026-05-26)
**Severity:** CRITICAL — silent data staleness + correlated HA-core crashes
```
