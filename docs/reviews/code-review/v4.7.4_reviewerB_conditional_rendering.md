## D3: Runtime Fallback Correctness

**Question:** When `customize_buckets=False`, does `dynamic_preset.py` derive bucket values from baseline + offset, or does it crash / use wrong defaults?

**Finding: PASS -- fallback is present and structurally correct.**

`_build_overrides()` at dynamic_preset.py:449-476 implements the fallback:

1. Reads `home_low` / `home_high` from zone_data using per-bucket CONF keys (line 452-453).
2. If either is `None` AND `customize_buckets` is `False` (line 454-456), enters the derivation path.
3. Derivation calls `PresetManager(self.hass).get_seasonal_setpoints("home")` (line 464), which returns `(cool_setpoint, heat_setpoint)` for the current season from `SEASONAL_DEFAULTS` (or CM entry.options overrides per v4.7.3 D2).
4. Sets `home_high = cool_setpoint`, `home_low = cool_setpoint - 7.0` (standard 7F spread, line 465-466).

**Seasonal baseline values (from hvac_const.py:278):**
- Summer home: cool=77, so derived range = (70, 77)
- Shoulder home: cool=74, so derived range = (67, 74)
- Winter home: cool=72, so derived range = (65, 72)

The derivation produces identical home_high values to what the original Cycle B defaults used for the Cool bucket in summer (70-77). The formula is bucket-agnostic -- all buckets get the same baseline range when `customize_buckets=False`, which is the correct design intent: without customization, the override is just "apply the seasonal home setpoints + zone offset" regardless of thermal bucket.

**Offset application** (line 486): `effective_home_high = float(home_high) + zone_offset` -- correctly applied post-derivation.

**Sleep derivation** (line 511-514): When sleep cells are also absent, falls back to `compute_sleep_high(home_high, zone_offset)` which applies the `max(74, home_high - 1) + offset` floor rule. Correct.

**Edge case -- `get_seasonal_setpoints` returns None:** If the preset is not in seasonal defaults (line 464-466 wrapped in try/except), the method falls through to the `home_low is None or home_high is None` guard at line 478 and returns `[]` (no override). This is safe -- no crash.

**One MEDIUM observation:** The derivation always uses the "home" preset's seasonal baseline regardless of which bucket is active. This means that with `customize_buckets=False`, a zone in the EXTREME bucket gets the same setpoints as one in the COOL bucket. This is by design (the plan says "derive from baseline + offset" not "derive per-bucket differentials"), but it does mean DPM is effectively a no-op for preset range adjustment when customization is off -- it still transitions buckets and emits signals, but the override values don't vary by bucket. The user can enable `customize_buckets` to get differentiated ranges. Not a bug, just a design note.

**Classification:** PASS (no finding)

## D5: `__` Prefix Regression Test Effectiveness

**Question:** Does the test actually catch `vol.Optional("Back Hallway__zone_dynamic_preset_offset")` in a schema?

**Finding: PASS -- the regression test would catch the bug.**

`test_v474_translation_coverage.py` class `TestD5NoPrefixedFieldKeys` (line 55-124) has four tests:

1. **test_d5_no_prefixed_field_keys_in_surface1_schema** (line 73): Regex `vol\.Optional\(\s*["\']([^"\']*__[^"\']*)["\']` scans the Surface 1 schema builder body for any `vol.Optional("....__...")` pattern. A key like `"Back Hallway__zone_dynamic_preset_offset"` contains `__` and would be captured by `[^"\']*__[^"\']*`. **Would catch the bug.**

2. **test_d5_no_prefixed_field_keys_in_surface2_schema** (line 87): Same regex on Surface 2 schema builder. **Would catch it.**

3. **test_d5_no_prefixed_field_keys_in_baseline_schema** (line 98): Same regex on baseline presets step. **Would catch it.**

4. **test_d5_no_double_underscore_anywhere_in_schema_builders** (line 108): Broader canary -- scans the entire config_flow.py for `vol.Optional("...__zone_dynamic_preset...")`. This is the belt-and-suspenders catch for any future schema builder. **Would catch it.**

The tests scan source text (not translation files), which is the correct approach -- the bug originates in schema field key construction, not in translation file contents. The regex correctly matches `__` anywhere in the key string, not just as a prefix.

**One LOW observation:** Tests 1-3 use a fixed character window (3000/5000/12000 chars from the function signature). If the schema builder grows beyond this window, new keys at the end would escape detection. Test 4 (the whole-file canary) mitigates this for DPM-specific keys but not for arbitrary `__` in non-DPM schemas. This is acceptable for now -- the window sizes are generous relative to current function sizes.

**Classification:** PASS (no finding)
