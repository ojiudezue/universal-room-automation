## Findings

### MEDIUM-1 — `_no_coord_warned_zones` is not cleared on integration- or coordinator-manager-only unloads (latent leak)

**File / location:** `custom_components/universal_room_automation/__init__.py`, the three branches of `async_unload_entry`:
- `ENTRY_TYPE_INTEGRATION` branch begins line 2811
- `ENTRY_TYPE_ZONE_MANAGER` branch begins line 2957 (the one the diff touched)
- `ENTRY_TYPE_COORDINATOR_MANAGER` branch begins line 2969

**Issue:** The dedup set lives in integration-scoped state at
`hass.data[DOMAIN]["_no_coord_warned_zones"]`. The clear added at line
2965 fires only on Zone Manager unload. That is correct for the
"reload should re-warn" requirement because zone sensors are created
under the Zone Manager entry (forward_entry_setups at line 2397) and
the user-visible reload is the Zone Manager reload.

However, the integration-entry unload path at lines 2811–2954 does
NOT clear the key. After integration unload, `hass.data[DOMAIN]` is
NOT torn down — only individual sub-keys are deleted (lines 2829,
2860, 2895, 2901, 2907, 2912, 2918, 2952 etc.). The DOMAIN dict itself
survives. So:

- **Scenario A — full integration removal/reload:** if the user reloads
  the *integration* entry (not the ZM entry), `_no_coord_warned_zones`
  carries over. Zone sensors still exist (their entry, ZM, did not
  unload), so they continue running. Practically: harmless — those
  same entities already warned once during this boot, so suppressing a
  repeat on integration-reload is arguably *correct* (still a single
  boot lifetime). But this is implicit, not documented.
- **Scenario B — ZM-loaded-then-integration-reloaded ordering:** the
  set persists after integration reload; the ZM entry was never
  unloaded so its zone sensors keep firing into the same set with no
  re-warn. Same conclusion as A: harmless because nothing new is
  retried.
- **Scenario C — ZM unload happens first, integration unload runs
  later in the same teardown:** the ZM branch clears the set at line
  2965, then the integration branch is a no-op for this key. Fine.

**Why this is MEDIUM, not LOW or INFO:**
The dedup set is *integration-scoped state* but the clear lives on a
*sibling entry's* unload path. That's a deliberate-but-fragile
coupling. If a future cycle introduces another reason to populate the
set from a non-ZM code path (e.g. coordinator-manager-owned zone
mirror sensors, planned in `docs/planning/PLANNING_v4.7.18_census_service_shared_refactor.md`),
or if the ZM entry is removed without being re-added (current code
allows this — line 477 reuses an existing ZM entry but does not
mandate one), the set leaks indefinitely until the next HA restart.
That's not a user-visible defect today, but it is a Bug Class #20
("Concurrent Config Entry Reload Race") shaped trap — shared
`hass.data[DOMAIN]` state cleared on one entry's unload path, where
the lifecycle contract between entries is implicit. QUALITY_CONTEXT.md
line 801 specifically warns: *"In `async_unload_entry()`, set shared
keys to `None` instead of deleting them"* — the current code uses
`pop(..., None)` which is closer to the recommended pattern (no
KeyError on missing), but the bug class wants a single-owner contract
that doesn't exist here.

**Recommended fix (cheap, ~3 LoC):**
Also clear the set in the integration-entry unload branch. Either:

```python
# Add near line 2952 (just before `del hass.data[DOMAIN]["integration"]`)
hass.data.get(DOMAIN, {}).pop("_no_coord_warned_zones", None)
```

Or, equivalently and more robustly, clear it on `async_will_remove_from_hass`
of *any* `ZoneSensorBase` whose retry timer has already fired and
populated the set — but that complicates the entity teardown for no
real gain. The single extra `pop` in the integration unload branch is
the cleaner answer. Worth also adding a 1-line comment at the ZM
branch reminding the next person that this key is integration-scoped
and the ZM-branch clear is intentional (reload-re-warn semantics).

**Severity rationale:** MEDIUM, not HIGH, because:
1. No user-visible defect *today* — the worst case is "warning not
   re-emitted on integration reload," which is arguably the correct
   behavior anyway (single warn per HA process lifetime).
2. No memory leak risk: bounded by `len(zones)`, which is a small
   integer (operator's house has ~6–8 zones).
3. Not a HIGH because no realistic user action today produces a wrong
   outcome. The risk is *future-cycle fragility*, not present
   incorrectness.

### LOW-1 — `hass.data[DOMAIN]` could in principle be the literal sentinel from `hass.data.get(DOMAIN, {})` rather than the live dict

**File / location:** `__init__.py:2965`

```python
hass.data.get(DOMAIN, {}).pop("_no_coord_warned_zones", None)
```

If `hass.data[DOMAIN]` is absent at unload time, `.get(DOMAIN, {})`
returns a fresh empty dict, and `.pop(..., None)` is a no-op on that
throwaway dict. So the line is safe under absence.

But the pattern is identical for the more-defensive case AND for a
*bug case* where someone refactors this to `setdefault(DOMAIN, {})`
and then tries to write a key — at which point the fresh dict would
be discarded, not stored.

This is purely a hardening note: replace with the more readable

```python
domain_data = hass.data.get(DOMAIN)
if domain_data is not None:
    domain_data.pop("_no_coord_warned_zones", None)
```

so the intent ("only touch live state") is explicit. Optional.

**Severity:** LOW. Code is correct as written.

### LOW-2 — Retry timer could fire one extra time after `async_will_remove_from_hass` cancels its unsub, racing with a populated `_no_coord_warned_zones` set

**File / location:** `aggregation.py:2925–2969` (`_check_coordinators`
callback + `async_track_time_interval` registration) and `aggregation.py:2971–2975` (`async_will_remove_from_hass`).

**Background:** `async_track_time_interval` is a hass-bound helper. Its
unsub is stored on `self._retry_unsub` and called in
`async_will_remove_from_hass`. Per the HA pattern (verified by
inspection — the same pattern is used throughout this file at every
prior `_retry_unsub` site, e.g. line 2939), calling the returned unsub
cancels the next scheduled fire.

**Question raised by Reviewer B framing:** *"Could entities call
`_check_coordinators` AFTER the Zone Manager entry's `async_unload_entry`
has run but before their own timer is cancelled?"*

Trace:
1. `hass.config_entries.async_unload_entry` for ZM invokes
   `hass.config_entries.async_unload_platforms(entry, INTEGRATION_PLATFORMS)`
   at line 2958.
2. That awaits each platform's unload, which removes each entity via
   `async_remove`, which awaits `async_will_remove_from_hass` at line 2971.
3. `async_will_remove_from_hass` cancels `_retry_unsub` (lines 2973–2975).
4. Only AFTER `async_unload_platforms` returns does line 2965 run
   (the dedup-set clear).

So the ordering is: **all entity timers are cancelled BEFORE the dedup
set is cleared.** No use-after-clear from the per-entity timer.

But there is a narrow timing window worth flagging:

**Scenario:** Between the `async_track_time_interval` callback being
scheduled (e.g. at t=60s, in flight on the event loop's ready queue)
and the actual call to `_check_coordinators`, if `async_will_remove_from_hass`
runs and calls `_retry_unsub()`, the HA helper *should* cancel the
scheduled fire. Confirmed by reading
`homeassistant/helpers/event.py::async_track_time_interval` — it
schedules via `async_call_later` and returns a `remove_listener`
callable that does cancel pending fires.

**However**, the callback body itself does:
```python
warned_zones = self.hass.data.setdefault(DOMAIN, {}).setdefault(
    "_no_coord_warned_zones", set()
)
```

If the integration is mid-shutdown and `hass.data[DOMAIN]` has been
fully deleted (it isn't today — see MEDIUM-1 — but could be in a
future cycle), `setdefault(DOMAIN, {})` would *resurrect* the DOMAIN
key with an empty dict, which would then linger after teardown. This
is not a bug in v4.7.18.2 (the DOMAIN dict is never deleted in
`async_unload_entry` — only its sub-keys are popped), but
`setdefault` is a sharp edge: it *writes* to `hass.data` from a
callback that might in principle run during teardown.

**Recommendation (optional, defer if not in scope):** narrow the write
to a non-writing form, since the callback's job is "log if not yet
warned." If `hass.data[DOMAIN]` is gone, the warning is meaningless:

```python
domain_data = self.hass.data.get(DOMAIN)
if domain_data is None:
    # Integration torn down mid-retry; skip warn silently.
    return
warned_zones = domain_data.setdefault("_no_coord_warned_zones", set())
```

This avoids resurrecting DOMAIN. Strictly defensive — no real defect
in the current shape of `async_unload_entry`.

**Severity:** LOW. Defensive hardening; the resurrection risk is
hypothetical given today's unload code.

### INFO-1 — Restart resilience: confirmed clean

**File / location:** `__init__.py:600–601`:
```python
if DOMAIN not in hass.data:
    hass.data[DOMAIN] = {}
```

On fresh HA boot, `hass.data` is empty, so `hass.data[DOMAIN]` is
created as a new dict, and `_no_coord_warned_zones` is absent. The
first zone sensor whose retry timer expires creates the set via
`setdefault`, and the first warn per zone fires. This is exactly the
"warn once per boot" behavior the operator wanted.

There is no persistence path (no `RestoreEntity.async_get_last_state`,
no DB store, no `Store` save) for this key, which is correct — it
should be in-memory only. Cross-restart carryover impossible.

**Disposition:** No action. Confirmed correct.

### INFO-2 — The clear is on the correct unload branch

The branch at `__init__.py:2957` is the Zone Manager branch (verified
by reading `if entry_type == ENTRY_TYPE_ZONE_MANAGER:` at that line).
Zone sensors are forwarded from the Zone Manager entry via
`async_forward_entry_setups(entry, INTEGRATION_PLATFORMS)` at
`__init__.py:2397`. So a Zone Manager reload unloads exactly the
entities that populate the dedup set. Clearing the set in this same
branch is the correct coupling for "ZM reload → re-warn" semantics.

The Coordinator Manager unload branch (line 2969) and the room-entry
unload branch (line 2975+) do not forward zone sensor platforms, so
clearing the set there would either be wrong (re-warns on unrelated
reload) or no-op. Correctly left untouched.

**Disposition:** Confirmed correct.

### INFO-3 — Cross-entry / multi-entry interaction: clean for current entry topology

URA's installed-entry topology is: one ENTRY_TYPE_INTEGRATION, one
ENTRY_TYPE_ZONE_MANAGER, one ENTRY_TYPE_COORDINATOR_MANAGER, plus N
room entries. There is exactly one Zone Manager per HA instance
(enforced by `__init__.py:477`'s "reuse existing ZM entry" logic).
Zones across the system are owned by that single ZM entry. So a single
shared `_no_coord_warned_zones` set has a single owner, no ownership
ambiguity.

The "what if a second Zone Manager entry existed?" concern is moot
because the integration prevents that. If a future cycle changes that
invariant, the dedup design would need to become per-entry. Not in
scope today.

**Disposition:** Confirmed correct under current topology. Worth a 1-
line comment near the dedup-set creation noting the single-ZM
assumption for future maintainers.

### INFO-5 — Event-loop serialization renders the read-check-then-add safe without a lock

The code comment at `aggregation.py:2950–2952` correctly identifies
this. `async_track_time_interval` callbacks run on the single HA event
loop thread. Even if 20 zone-sensor timers fire at the "same" tick,
they are serialized into the loop's ready queue and each
`_check_coordinators` body runs to completion before the next starts.
So:

```python
if self.zone not in warned_zones:
    warned_zones.add(self.zone)
    _LOGGER.warning(...)
```

cannot interleave between entities. No `asyncio.Lock` needed. The
comment explicitly says so; reviewer concurs.

**Disposition:** Confirmed correct.
