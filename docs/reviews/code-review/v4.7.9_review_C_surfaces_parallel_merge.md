## Detail

### C-M1 — MEDIUM — Helper text in `strings.json` is unreachable from the entity registry

**File:** `custom_components/universal_room_automation/button.py:706-755` (`_ACRampButton.__init__`)
**Plus:** `custom_components/universal_room_automation/strings.json:1665-1670` and `translations/en.json:1665-1670`

**Finding.** The plan §D1 specifies a translation block:

```json
"button": {
  "hvac_force_ac_reset": {
    "name": "Force AC Reset",
    "description": "Manually trigger a hard AC reset for this zone. ..."
  }
}
```

This block landed in both `strings.json` and `translations/en.json` verbatim — exact-match against the planning spec. **However:** `_ACRampButton` (the class registering all four per-zone actions including `force_ac_reset`) does NOT set `self._attr_translation_key`. Instead, the entity name is computed at construction time as `self._attr_name = f"{label} ({zone_name})"`, where `label` is `"24 · Force AC Reset"` etc. HA's translation pipeline keys off `_attr_translation_key`; without it, the `entity.button.hvac_force_ac_reset` block is **never looked up**. The friendly name still renders correctly (from `_attr_name`), but the **`description` field is dropped on the floor** — the helper text the user wrote will never appear in the HA frontend.

**Cross-check.** This is **not a regression introduced by v4.7.9** — the existing `force_nudge`, `cancel_nudge`, and `clear_lockout` buttons follow the same `_attr_name`-only pattern and have no entries in `strings.json` either. The new translation block in v4.7.9 is the FIRST `entity.button.*` block to land in the file (verified: `grep` shows `hvac_force_ac_reset` is the sole key under `entity.button`).

**Implication.** The plan's intent (a user reading the entity-info card sees helper text describing the gates) is unmet, even though the work was done correctly per spec. The mismatch is between the planner-spec (assumed translation works) and the codebase reality (per-zone buttons don't use translation_keys).

**Suggested fix (small).** In `_ACRampButton.__init__` (`button.py:743`-area), conditionally set `self._attr_translation_key = f"hvac_{action}"` (or similar) for actions that have a strings.json entry. This unlocks the helper text. Out-of-scope for v4.7.9 hygiene if the user prefers to ship the translation block as documentation-only (it's discoverable by anyone reading the file even if not surfaced in UI).

**Recommendation.** ACCEPT for ship as-is OR add a one-liner `_attr_translation_key` assignment before deploy. User-call. Either way, no blocker.

### C-L1 — LOW — Parallel-merge audit guardrail counts markers without confirming locality

**File:** `quality/tests/test_v479_hygiene_bundle.py:857-870` (`test_sensor_edit_localized_to_dpm_sensor_method`)

**Finding.** The test asserts `sensor_src.count("v4.7.9 D2") == 3`. This catches:
- A future agent adding a stray `# v4.7.9 D2` comment elsewhere in sensor.py (count = 4, fails) — confirmed by mutation simulation.
- A future agent removing one of the three intended markers (count = 2, fails).

**It does NOT catch:** a future agent **moving** one of the three markers OUT of `DynamicPresetOverridesAppliedSensor.async_added_to_hass` into a different method — as long as the total stays at 3, the test passes. The "localized" name in the test docstring overstates its strength: it's a count-based proxy for localization, not a localization assertion.

**Suggested hardening.** Replace the count check with an AST-walk that:
1. Locates the class `DynamicPresetOverridesAppliedSensor` node.
2. Locates the method `async_added_to_hass` within that class.
3. Asserts all three "v4.7.9 D2" markers are inside the method node's line range.

That's the literal "localized" check the test's name implies. Not blocking; ship as-is.
