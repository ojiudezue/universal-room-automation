### HIGH-A1 — Winter gate fail-open default is silent when `current_season == ""` (uninitialised PM)

**Bug class:** #22 (enum-style mismatch — empty string is not `SEASON_WINTER`, gate falls through)
**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:419-436`

**Observed.**
```python
resolved_pm = getattr(_hvac, "_preset_manager", None)
if resolved_pm is not None:
    _season = getattr(resolved_pm, "current_season", "")
    if _season == SEASON_WINTER:
        return [], "winter_season"
```

**Why this matters.** `PresetManager.current_season` is the `@property` for `self._current_season`, which is initialised to `""` at `hvac_preset.py:88` and is only populated by `determine_season()`. `determine_season()` is called at HVAC setup (`hvac.py:421`) and once per day from a tick path (`hvac.py:672`). During cold-start window between the EC tick first firing and HVAC bringing up (or in a degraded-HVAC scenario), `current_season` is `""` and the winter check silently misses. DPM proceeds and would emit a cool-ceiling override in January.

Worse: this is **invisible by design** (the gate is a fail-open contract per the planning doc §7) so a real winter mis-emission and a degraded-HVAC fail-open look identical at the operator surface — both manifest as "DPM emitted in winter" with no log distinction.

**Acceptance hypothesis impact.** The acceptance hypothesis `dpm_v4_7_17_2_winter_gate` ("DPM emits zero overrides during SEASON_WINTER, regardless of forecast") becomes **non-falsifiable** during the HVAC-cold-start window because the gate fails open and the acceptance criterion does not distinguish "winter, gate honoured" from "winter, gate skipped due to PM not yet warm".

**Fix.**

1. Treat empty-string season as "not yet known" and explicitly call `determine_season()` once (it's cheap — just reads `dt_util.now().month`) before comparing. Either:
   - `_season = resolved_pm.current_season or resolved_pm.determine_season()`, OR
   - Compute season independently of PM in DPM via the calendar (the only thing `determine_season` does is bucket `now.month` into SUMMER/WINTER/SHOULDER — DPM does not need the PM to be warm).
2. Emit a single WARNING (rate-limited or boot-only) the first time DPM observes `current_season == ""` so a degraded HVAC bringup is loud, not silent.

**Recommend option (1) sub-option B (calendar-direct).** It removes the cross-coordinator coupling entirely for this gate and makes the test for `winter_season` trivial — `with patch("dt_util.now") returning a January date, assert skip_reason == 'winter_season'`. This is also the more honest signature: the winter gate is a calendar fact, not a PM-state fact.

**Severity:** HIGH. Operator-visible misbehaviour (DPM running in winter, the explicit thing the gate exists to prevent) during a known startup window. Documented as fail-open in the plan but the plan did not consider the empty-string transient.

### HIGH-A2 — `_record_daily_apparent_high` keys ring on **local** date but `_hydrate_rolling_window_from_store` uses **local** date for cutoff with no DST/timezone discipline

**Bug class:** #7 (date-keyed staleness with mixed time origins)
**Files:**
- `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:484` (record uses `dt_util.now().date().isoformat()` — local)
- `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:649` (hydrate cutoff uses `dt_util.now().date()` — local)
- `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:476` (forecast `fetched_at` uses `dt_util.utcnow()` — UTC)
- `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:227, 317` (other WPM datetime sites use `dt_util.utcnow()` — UTC)

**Observed.** The rolling window is the ONLY WPM surface that uses local time. Every other datetime in WPM is UTC. The date key for ring entries is the operator's local date.

**Why this matters.**

1. **DST transitions.** On a spring-forward day, the user's local calendar advances over a "missing hour" (e.g., 02:00 → 03:00). A forecast refresh that lands at 02:30 UTC after a HA restart could read `dt_util.now().date()` and disagree with another refresh from a previous run by one calendar day. This is a small risk — at worst, one day's entry is mislabelled and dedupe creates a same-day duplicate or skipped entry — but it interacts with the cap-at-14 eviction in a way that's hard to reason about because the ring is now keyed by a non-monotonic ordering.

2. **Cross-installation portability.** If the operator's HA timezone changes (e.g., relocation, configuration fix), already-persisted ring entries become dated against the OLD zone. The 21-day staleness cutoff at `:649` is computed against the NEW zone. The drop-stale logic is robust against the worst case (purge), but there's no `_LOGGER.info` or operator-visible signal when this happens.

3. **Test fragility.** The new test file `test_v4_7_17_2_dpm_simplified_frame.py` asserts source-grep patterns but does not pin the time origin (local vs UTC) of the date key. A future refactor that swaps `dt_util.now()` → `dt_util.utcnow()` would leave existing rings half-keyed.

**Fix.**

1. Pick ONE time origin and pin it. Recommend `dt_util.utcnow().date().isoformat()` for the ring (matches the rest of WPM's UTC discipline; the user-visible "what day was that?" frame is irrelevant to a 14-day median calculation).
2. Add an explicit comment at the record + hydrate sites documenting the choice ("DPM ring keys are UTC ISO dates — local-time observers may see a same-day forecast attributed to yesterday near midnight; this is fine because the 14-day median is invariant to single-day relabelling").
3. Add a behavioral test that calls `_record_daily_apparent_high` twice in close succession across a faked UTC midnight and asserts the ring contains exactly two entries (today + tomorrow), not three or one. The current source-grep tests cannot catch a time-origin regression.

**Severity:** HIGH. Will not produce a runtime error, but the 14-day rolling median is the central correctness anchor for the entire v4.7.17.2 cycle and its date-keying discipline is currently informal. Worth pinning now.

### MEDIUM-A1 — `apparent_high_f` sensor attribute exposes `raw_high` fallback values without disclosing the apparent-confidence flag

**Bug class:** #7-adjacent (stale/degraded data exposed without provenance label)
**File:** `custom_components/universal_room_automation/sensor.py:6998, 7039`

**Observed.** The sensor surfaces `apparent_high_f` directly from `WeatherProviderManager.current_apparent_forecast_high()`. In degraded mode (no provider exposes apparent_temp), WPM falls back to `raw_high` and tags the cached forecast with `confidence="fallback_raw"` or `"apparent_unavailable_fallback_raw"` (`weather_manager.py:448-453`). The sensor does not surface this confidence label.

**Why this matters.** The operator reads `apparent_high_f` on the diagnostic sensor as the literal "apparent high the forecast says today is" — but on a degraded day they may be reading raw_high without any indication. Combined with the rolling median (which was computed from previous-day apparent values during good days), the resulting `relative_delta_f` is comparing raw apples to apparent oranges. The DPM math will run correctly against `relative_delta_f` but the operator's *interpretation* of why DPM did what it did becomes wrong.

**Fix.**

Either:
1. Add an `apparent_confidence` attribute to the sensor's `extra_state_attributes` dict so operators can see when a fallback is in play, OR
2. Stop recording into the ring when `confidence != "high"` — i.e., reject fallback-raw days from the median entirely.

Option 2 is the cleaner semantic but introduces a new no-record path (and a new way the ring stays small forever in degraded environments). Option 1 is the minimum-surface fix.

**Severity:** MEDIUM. Doesn't cause wrong DPM behavior, but degrades the diagnostic story and obscures Bug Class #7 ("stale/wrong source labelled as authoritative") which has bitten URA before.

### MEDIUM-A3 — `_build_overrides_with_reason` falls back to constructing a fresh `PresetManager` when `resolved_pm` is None, but the fresh PM has `_current_season == ""` so the seasonal lookup uses `determine_season()` from now.month

**Bug class:** #46-adjacent (lazy derivation in a path that was supposed to be canonical-only)
**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:630-635`

**Observed.**
```python
_pm = resolved_pm
if _pm is None:
    from .hvac_preset import PresetManager
    _pm = PresetManager(self.hass)
_season_pair = _pm.get_seasonal_setpoints("home")
```

When `resolved_pm` is None (test path, or pre-HVAC-bringup tick), a fresh PM is constructed. The fresh PM has `_current_season == ""`. `get_seasonal_setpoints("home")` at `hvac_preset.py:132-133` then calls `self.determine_season()` lazily. The lazy call WORKS (it just reads `dt_util.now().month`), but it has a side effect — it mutates the throw-away PM's `_current_season` field. That mutation does nothing because the throw-away PM is GC'd. Functionally fine.

**Why this matters anyway.** The cycle's pre-deploy Tier 1 H1 was about NOT constructing a fresh PM per tick because it "loses `_current_season` continuity and bypasses any CM override caching the resolved PM holds." The fix was to pass `resolved_pm` in. But the fallback path still constructs one. Two problems:

1. The fallback is silent — there's no log line saying "DPM had to construct a fresh PM, HVAC coordinator wasn't ready." If this happens in production, the operator has no visibility.
2. The fresh PM's `get_seasonal_setpoints` DOES read CM entry.options for per-CONF overrides (`hvac_preset.py:148-164`), so the values are correct, but **only if** the CM entry is registered before DPM ticks. In a pre-CM-registration startup tick, the fresh PM's `get_seasonal_setpoints` reads default SEASONAL_DEFAULTS — which may not match the operator's overrides. The result is DPM emits a baseline that disagrees with HVAC's by 1-5°F.

**Fix.**

1. When `resolved_pm` is None, log at INFO once per zone-per-boot to surface the cold-start fallback.
2. Consider skipping the fallback entirely — return `[], "preset_manager_not_ready"` as a new skip reason. This is honest ("we don't know what the seasonal baseline is yet") and matches the v4.7.16.4 design philosophy of "if the canonical accessor isn't ready, skip rather than guess."

The current `home_range_not_configured` skip reason at `:651` partially handles this, but only when the throw-away PM returns None — not when it returns the default baseline that disagrees with the operator's override.

**Severity:** MEDIUM. Production risk is small (CM entry is registered long before DPM ticks in normal flow), but the silent disagreement during cold start could surface as a 1-tick override that the operator can't explain.

### MEDIUM-A4 — `sensor.py` re-derives `cool_high_adjustment_f` from a separate options read instead of reading what DPM actually emitted

**Bug class:** #7 (two views of the same truth that can drift)
**File:** `custom_components/universal_room_automation/sensor.py:7007-7033`

**Observed.** The sensor recomputes `cool_high_adjustment_f` by re-reading the CM options' `relax_f` / `tighten_f` values and re-calling `_compute_cool_high_adjustment(relative_delta_f, ...)`. This is parallel to what DPM did at the last tick — but the two computations can disagree if:

1. The operator changes the knob between DPM's tick and the sensor's render (the sensor reads "now's" knob, DPM emitted with "5 minutes ago's" knob).
2. The sensor reads `mgr.baseline_delta_for_zone(self._zone_id, "home")` which is the **current** delta, but DPM emitted overrides off the **delta at tick time**. Between ticks, the rolling median doesn't change (it's a daily-cadence update), so this is mostly safe. BUT if `_refresh_all_providers` ran between DPM's tick and the sensor's render and a new daily entry landed, the median can shift by a sample.

**Why this matters.** The sensor advertises `cool_high_adjustment_f` as "what DPM did today." If it's actually "what DPM would do RIGHT NOW," the operator's mental model of "this attribute should match the override on the climate entity" breaks silently. There's no exception, no warning — just confused diagnostics.

**Fix.**

Read the adjustment from `DynamicPresetOverrideSource.get_zone_state()` (already returns bucket + last_transition_iso). Extend that dict to include `last_cool_high_adjustment_f` so the sensor exposes the value DPM emitted, not a fresh recomputation. This keeps the sensor a passive observer of the source-of-truth (the DPM coordinator) per the URA "no parallel truth" architecture rule.

**Severity:** MEDIUM. Small operator-confusion window; no incorrect HVAC behavior.

### MEDIUM-A5 — Boundary inclusivity of dead zone: `relative_delta == ±DEADZONE_F` falls outside the dead zone

**Bug class:** edge-case correctness
**File:** `custom_components/universal_room_automation/domain_coordinators/dynamic_preset.py:119-123`

**Observed.**
```python
if relative_delta <= -DPM_RELATIVE_DELTA_DEADZONE_F:
    return float(relax_f)
if relative_delta >= DPM_RELATIVE_DELTA_DEADZONE_F:
    return -float(tighten_f)
return 0.0
```

Planning doc §3 specifies:
- `relative_delta ≤ -2.0°F` → cool day → apply +relax_f
- `-2.0°F < relative_delta < +2.0°F` → typical day → no override
- `relative_delta ≥ +2.0°F` → hot day → apply −tighten_f

The implementation matches the plan exactly. **No bug.** Logging this as a correctness-check pass rather than a finding.

However, the new test file's `test_dead_zone_boundary_inclusive_uses_le_and_ge` asserts only that the comparators `<=` and `>=` are present in the source. It does NOT assert the math at the boundary: e.g., that `_compute_cool_high_adjustment(-2.0, 1.0, 1.0) == 1.0` (cool day side, inclusive) and that `_compute_cool_high_adjustment(-1.999, 1.0, 1.0) == 0.0` (just-inside dead zone). Add behavioral coverage for both boundary points.

**Severity:** MEDIUM (test gap, not a code bug).

### LOW-A2 — `_hydrate_rolling_window_from_store` `datetime.fromisoformat(date_iso).date()` is fragile to formats like `2026-06-02T00:00:00+00:00`

**Bug class:** parsing
**File:** `custom_components/universal_room_automation/domain_coordinators/weather_manager.py:655-657`

**Observed.**
```python
date_iso, value = entry[0], entry[1]
entry_date = datetime.fromisoformat(date_iso).date()
```

The recorder writes `dt_util.now().date().isoformat()` which produces `YYYY-MM-DD` (no time component). `datetime.fromisoformat("2026-06-02")` works on Python 3.11+. On Python 3.10 (which HAOS still supports in some lanes per HA's stated minimum), `datetime.fromisoformat` does NOT accept date-only strings — only full datetime strings. The `except (ValueError, TypeError, IndexError)` catches this, so the row is silently dropped, but the ring becomes effectively empty after a Python 3.10 → 3.11 hop with persisted v1 data.

**Fix.** Use `date.fromisoformat(date_iso)` instead of `datetime.fromisoformat(date_iso).date()`. `date.fromisoformat` accepts `YYYY-MM-DD` from Python 3.7+ and is the semantically-correct parser here.

**Severity:** LOW. HA's stated minimum is Python 3.13 as of 2026 (per HA dev docs); HAOS ships 3.13. This is a defensive correction.
