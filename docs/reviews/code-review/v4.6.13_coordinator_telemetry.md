## Findings

### MEDIUM — fixed

**B.B1 ≡ C.M2 — D2/D3 missing `SIGNAL_DATABASE_READY` fallback**
`CoordinatorOverrideFrequencySensor` and `CoordinatorComplianceRateSensor` only check `hass.data["database"]` for initial refresh. If the DB initializes after `async_added_to_hass`, D2 stays at 0 for up to 5 minutes and D3 stays at "unknown" for up to 30 minutes (until next poll). D1 and D5 already have the SIGNAL_DATABASE_READY fallback (from v4.6.5.3 M2 pattern).

**Fix:** Added `SIGNAL_DATABASE_READY` one-shot subscription to D2 and D3, mirroring D1/D5. Closes the startup race so first-load latency is bounded by DB-ready time, not the poll interval.

**C.M1 — Hardcoded UI coordinator tuples ×4 instead of importing constant**
`async_setup_entry` had `("presence", "hvac", "energy", "safety", "security")` repeated four times. `coordinator_telemetry_const.py` defines `UI_COORDINATORS` as a `Final` tuple for exactly this purpose. Adding a 6th coordinator would require remembering all four sites.

**Fix:** Imported `UI_COORDINATORS as _UI_COORDINATORS` in `async_setup_entry` (CM branch only), replaced all four tuple literals with the single name.

### MEDIUM — deferred

**A.M1 — D2/D3 JOIN missing compound index for scale**
`compliance_log JOIN decision_log` filtered by `c.timestamp` and `d.coordinator_id`. SQLite picks one index per table-scan; with ~50k compliance_log rows the current single-column indexes are fine. Past ~200k rows the planner could lose the index race.

**Deferred:** Out of v4.6.13 scope (no schema changes this cycle — `database.py` diff is empty). Filed for a future schema cycle. Recommended: `CREATE INDEX IF NOT EXISTS idx_compliance_decision_ts ON compliance_log(decision_id, timestamp)`.

**A.L1 — `hass.add_job` vs `hass.async_create_task` style consistency**
Reviewer A's L1 suggested switching D1/D5 signal-handler scheduling from `hass.add_job` to `hass.async_create_task` for consistency with the polling sensors. **DECLINED.**

Reviewer B explicitly validated `hass.add_job` as **correct** for signal handlers. The v4.6.3.2 lesson at `sensor.py:10373-10380` documents: SIGNAL_ACTIVITY_LOGGED can fire from a sync worker thread; `async_create_task` from a non-event-loop thread raises `RuntimeError` under `ReportBehavior.ERROR` for custom integrations. Switching would re-introduce the v4.6.3.1 wedge that caused 3× dispatcher exceptions + orphaned coroutines + "coroutine never awaited" GC warnings.

The polling sensors (D2/D3/D4) use `async_create_task` correctly because `async_track_time_interval` fires from the event loop, not a worker thread. Different contexts, different choices, by design.

### LOW — deferred

**A.L2** — D5 passes `labels` as bare tuple to `execute()` while D1/D2/D3 use `(*labels, cutoff)` unpacked. Functionally identical (D5 has no extra args). Cosmetic, no fix.

**C.L1** — D4 makes up to 3 sequential `executor_job` calls per refresh (main + WAL + SHM). Could be consolidated into one helper with a single executor hop. At 5-min intervals: negligible. Defer to a future polish cycle.

**C.L2** — D2/D3 perform module-level `from .coordinator_telemetry_const import ...` inside `extra_state_attributes`. Python caches the import so it's effectively free after first call, but conventional style is module-level imports. Defer.

**A.L3** — staleness pattern documented for cache-based sensors (n/a here, no caches).
