### C2-H1 — HIGH — Cross-room camera contamination in `_has_camera`

**Location:** `sensor.py:2090-2123` (`RoomSignalInventorySensor._has_camera`).

**The issue:** The function intends to return True iff a camera registered for THIS room's `area_id` exists in some zone tracker. The actual implementation reads:

```python
for tracker in zone_trackers.values():
    if room_name not in getattr(tracker, "room_names", []):
        continue
    if room_area_ids.get(room_name) != room_area:
        continue
    cam_ids = getattr(tracker, "_camera_entity_ids", set()) or set()
    if cam_ids:
        return True
return False
```

`cam_ids` is the FULL set of cameras the zone tracker has registered. A zone composed of rooms A (area_a, has cameras) and B (area_b, no cameras) shares one tracker → `tracker._camera_entity_ids = {camera_a}`. Querying `_has_camera()` for room B walks the loop: room B is in `tracker.room_names`, `room_area_ids["room_b"] == area_b` matches `room_area=area_b`, then `cam_ids = {camera_a}` is non-empty → returns True.

**Consequence:**
1. Room B's `signal_inventory.has_camera` reports `True` even though no camera covers area_b. Operator sees `state="sparse_no_fallback"` with `has_camera=True` → reasonable interpretation: "this room has a camera". Actually false.
2. State labels degrade. The `native_value` branch at `sensor.py:2144` is `if has_camera and not has_pir and not has_mmwave: return "camera_only"` — a room B with no sensors and a sibling-room's camera would report `camera_only`. Wrong.
3. **D4 acceptance criterion is partially broken across zone-siblings.** Plan §D4 AC: "The signal inventory sensor (D2) `has_camera` attribute reflects opt-out". The opt-out CHECK (line 2095-2098) correctly short-circuits to False when the room opts out, so opt-out's own room is fine. But sibling rooms in the same zone misrepresent regardless of opt-out.

**Fix (≤ 15 LoC):** Filter `cam_ids` by area_id at registration time OR query the CameraIntegrationManager for cameras actually-in this specific area:

```python
camera_manager = self.hass.data.get(DOMAIN, {}).get("camera_manager")
if camera_manager is None:
    return False
cameras_in_area = camera_manager.get_cameras_for_area(room_area)
if not cameras_in_area:
    return False
# Check at least one of them is actually registered in any tracker.
registered = set()
for tracker in zone_trackers.values():
    registered.update(getattr(tracker, "_camera_entity_ids", set()) or set())
return any(
    c.person_binary_sensor in registered for c in cameras_in_area
    if c.person_binary_sensor
)
```

Or equivalently: do not look at zone trackers at all — just ask `camera_manager.get_cameras_for_area(room_area)` and short-circuit opt-out before. (Opt-out is already short-circuited at line 2095, so the lookup answers "would a camera have been registered for this room's area".)

**Severity rationale:** HIGH because the attribute is in the documented Live Validation checklist (README §6 D4 row) and a wrong value will be observed and reported as a real bug by the operator on day one.

### C3-H1 — HIGH — README §5 false rollback timeline for D4

**README §5 "Clear the camera-presence opt-out for a room"** says (line 173-178):

> 1. Settings → Devices & Services → URA → [Room] → Configure.
> 2. Toggle **Disable Camera Presence (Opt-Out)** to OFF (or clear it).
> 3. Save. URA reloads; cameras for the room's area re-register on next
>    discovery cycle. The room's `has_camera` attribute on its
>    signal_inventory sensor returns to its pre-opt-out value within 30 s.

This is incorrect. The room's config-entry reload (`__init__.py:3336-3349` `_async_update_listener` → `async_reload(entry.entry_id)`) reloads ONLY the room's own coordinator. The `PresenceCoordinator` is attached to a different entry (`ENTRY_TYPE_COORDINATOR_MANAGER`) and is NOT reloaded by a room-entry options change. `_discover_zone_cameras` therefore does not re-run, and `tracker._camera_entity_ids` is unchanged.

**On a clear-opt-out:**
- The room's `signal_inventory.has_camera` will continue to read `False` until the next HA restart (or until a Coordinator Manager reload), because once cleared the short-circuit at `sensor.py:2095-2098` no longer returns False, but the `_has_camera` body then walks zone trackers where no camera was *registered* for that area (because boot-time opt-out skipped registration).

**On a set-opt-out:**
- The cameras *previously registered* for the room's area remain in `tracker._camera_entity_ids` (there is no `deregister_camera` method — confirmed by `grep deregister_camera` returning nothing). The Tier 2 camera signal continues to fire for that zone. The opt-out has zero immediate effect; only after HA restart.

This breaks both rollback procedure §5 AND the live-validation checklist §6 D4 row (which says "the 'v4.7.16 D4' INFO log line lists the expected opted-out rooms at boot" — true on restart, but operators following §4 opt-out setup are NOT told they need to restart).

**Fix options:**
1. **Documentation-only (cheapest):** Amend §4 "Opt-out setup" step 3 and §5 rollback step 3 to say "Save. **Restart Home Assistant** to apply the change to the presence coordinator's camera registration." Add a line at end of each section: "v4.7.16 does not deregister cameras at runtime; full integration reload or HA restart is required for opt-out toggles to take effect mid-flight."
2. **Code (correct but heavier):** add a `tracker.deregister_camera(entity_id)` method on `ZonePresenceTracker` and wire the room update-listener to call it. Out of v4.7.16 scope; would belong in v4.7.16.x.

**Severity rationale:** HIGH because the operator-facing documentation states an outcome that won't happen. The first operator who toggles this field will conclude URA is broken. CLAUDE.md "No Fabrication" applies to docs as much as to code claims.
