## File-by-File Analysis

### weather_manager.py (NEW, ~620 LoC)

**Changes:** New WeatherProviderManager singleton. Ranked-list failover, staleness detection, divergence computation, apparent-temp probing, state-change-driven refresh.

**Classification:** ADOPT WITH MODIFICATIONS (2 CRITICAL, 1 HIGH, 2 MEDIUM findings)

**Data Integrity Assessment:**
- **EnergyConstraint back-compat (Bug #37):** The WPM correctly sources `raw_high` for `forecast_high_temp` and `apparent_high` for the new `apparent_forecast_high_temp` field. The two values flow through independent paths in `energy.py` (lines 2422-2426, 2572-2575). No existing consumer is broken.
- **No DB writes:** WPM has zero interaction with `database.py`. All data is in-memory only, re-derived from entity states on every refresh (Bug #10 compliance -- no cross-restart state loss possible because there's nothing to lose).
- **Config round-trip:** The 5 new CONF keys are read correctly via `self._options.get()` with proper defaults. Config survives reload because `_async_update_listener` triggers full teardown+setup, which reconstructs the WPM from fresh `entry.options`.

**Specific findings:**

1. **A1 (CRITICAL):** `_handle_provider_state_change` (line 529) calls `self.hass.async_create_task(self._refresh_all_providers(), name="ura_weather_manager_refresh")`. This task is NOT tracked. The plan explicitly says Bug #19 prevention: "all service calls awaited inline within event handlers; no fire-and-forget." The state-change callback is `@callback`-decorated (cannot await), so the `async_create_task` approach is architecturally correct. However, the task must be tracked in a `_pending_tasks` set with `add_done_callback(discard)`, and `async_teardown` must await pending tasks before returning. Without this, HA may log "Detected that custom integration 'universal_room_automation' does not cancel or await long running tasks" warnings.

2. **A2 (CRITICAL):** `_refresh_all_providers` fetches the active provider's forecast TWICE. First in the per-provider loop (line 342: `forecast_data = await self._fetch_provider_forecast(eid)`), and again after active election (line 371: `forecast_data = await self._fetch_provider_forecast(new_active)`). Each `_fetch_provider_forecast` is a full `hass.services.async_call("weather", "get_forecasts", ...)`. With 3 providers, a single refresh does 3+1 = 4 service calls instead of 3. On state-change events (which fire frequently -- every forecast update from every provider), this adds up. Fix: cache the forecast_data from the loop iteration for each provider and reuse it when building the cached forecast.

3. **A3 (HIGH):** `baseline_delta_for_zone` (lines 216-222) has dead imports: `__import__("custom_components.universal_room_automation", fromlist=["__init__"])` and `from homeassistant.const import DOMAIN as _`. Neither is used. This looks like leftover scaffolding from an earlier approach to resolving the coordinator_manager. The actual resolution happens in `_get_zone_baseline_high` (line 479) which correctly imports `..const.DOMAIN`. The dead code should be removed.

4. **A7 (MEDIUM):** Divergence-median calculation (lines 388-391) uses `provider_highs` (raw temperatures) but assigns the result to `apparent_high`. The `provider_apparent_highs` dict (populated at line 353) is never consumed anywhere. This means under divergence conditions, the sensor reports a median of RAW highs as "apparent" temperature, which is semantically wrong. The divergence should operate on apparent values when available.

### test_v47x_weather_manager.py (NEW, ~968 LoC)

**Changes:** 52 tests covering helpers, enum, provider list, health checks, failover scenarios, forecast shape, divergence, apparent fallback, unsub teardown, source-contract, AST regression, EnergyConstraint field, signal constants, config defaults.

**Classification:** ADOPT AS-IS (review of test quality is Reviewer C's charter, but noting one cross-test issue per the heads-up)

**Test-Infra Defect (CONFIRMED):** The `test_v47x_ev_tou_hardening.py` file installs a module-level `_FIXED_NOW` mock for `homeassistant.util.dt` at import time (line 48-55, 93-96). It uses `sys.modules.setdefault("homeassistant.util.dt", ...)` which means if EV TOU tests run FIRST, they install the fixed-time mock, and the weather manager tests inherit it. The weather manager's `_utcnow()` helper (line 46-47 of test file) calls `datetime.now(_UTC)` (real time), but the production code's `dt_util.utcnow()` would resolve to the EV TOU mock's `_fixed_utcnow()` returning `2026-05-27T14:00:00Z` forever. This corrupts staleness calculations: `_check_provider_health` compares `dt_util.utcnow()` against `state.last_changed`, and with a frozen clock, staleness checks become unpredictable depending on test ordering. Both test files use `sys.modules.setdefault` (not `sys.modules[...] = ...`) for the dt_util mock, so whichever test file loads first wins. This is a real test-infra defect that should be addressed (likely by having both test files use the same `setdefault` pattern AND by making the weather manager tests explicitly set their own dt_util mock using `sys.modules[...] = ...` to override any prior registration).
