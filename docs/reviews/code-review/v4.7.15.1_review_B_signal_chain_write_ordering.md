**Confirmed.** Operator's mandate ("house_inference is the AUTHORITATIVE LAST writer of `self._last_veto_decision` per cycle") holds for the steady-state code path:

2. The GUEST exit gate at `:2604-2645` writes `_last_veto_decision = exit_decision` THEN may set `new_state = None`. **No `return` statement.** Execution continues.
3. The Pattern A house_inference consolidated call at `:2647-2701` writes `_last_veto_decision = house_inference_decision` **unconditionally** inside `try` (`presence.py:2693-2699` comment explicitly says "Write UNCONDITIONALLY").

### B1-M1 (MEDIUM) — Exception path silently violates the "last writer" invariant

**File:line:** `presence.py:2700-2701`
**Bug class:** None directly — adjacent to #22 (silent failure) and the new sentinel-only payload-shape risk pattern from v4.6.1.1.
**Finding:** The Pattern A helper call is wrapped:

```python
try:
    ...
    self._last_veto_decision = house_inference_decision
except Exception:  # noqa: BLE001 — defensive: diagnostic-only path
    pass
```

If the helper raises mid-cycle (e.g., `state_context["house_state"]` is a freshly-introduced enum value the helper doesn't know how to lower-case, or some future caller wires bad signal kinds), the write is silently skipped. The sensor diagnostic surface then reflects the WAKING or GUEST exit decision from earlier in the tick — NOT the house_inference decision — and there is no log to indicate the divergence happened. Operators reading `sensor.ura_presence_house_state.last_veto_decision.scope` cannot tell whether the surface reflects a real house_inference result, a real WAKING/GUEST decision, or a fallback after an exception.

**Why MEDIUM not HIGH:** the helper is currently exception-safe in steady state — Pattern A's only failure modes are bad enum (defended at `:751-752`) and missing signal kinds (defaults to 0 / empty). I could not construct a runtime input that raises today. The risk is regressive — a future Pattern F or signal kind that throws would tear this open silently.

**Suggested fix:**
- Replace `pass` with `_LOGGER.warning("v4.7.15.1: Pattern A helper raised; _last_veto_decision NOT updated this tick", exc_info=True)`.
- Optionally write a sentinel `VetoDecision(False, 0.0, f"helper_raised:{type(exc).__name__}", "house_inference_exception")` so operators can spot the condition in the diagnostic surface.

**Owner:** B (this review) — write-ordering invariant is mine.

### B1-L1 (LOW) — Diagnostic surface ambiguity

**File:line:** `sensor.py:3665-3676`
**Finding:** `attrs["last_veto_decision"]` reflects whichever scope was the LAST writer. Because house_inference writes every tick, the surface is effectively pinned to `scope="house_inference"` whenever no exception fires. The WAKING and GUEST exit decisions ARE written to the field at `:2589` and `:2632` but those writes are overwritten ~100 lines later in the same tick. From the operator's perspective, the surface NEVER shows scope="waking_transition" or scope="guest_exit".

The plan §"CRITICAL RISK PREMIUM" item 4 calls this out as desired ("the surface always shows house_inference's decision"), but the WAKING/GUEST writes are now dead-ink — they cost a CPU cycle and produce nothing visible. If the design intent is "surface always shows house_inference," the WAKING and GUEST gate writes can be deleted entirely (they're write-then-overwrite within the same tick).

**Why LOW:** the dead writes are harmless. The risk is a future refactor moving `_last_veto_decision = wake_decision` to a meaningful place (e.g., a per-scope dict) without realizing it was never observable — wasting hours.

**Suggested fix:** delete `presence.py:2589` and `:2632` (they have no observable effect), OR introduce a per-scope dict `self._last_veto_decisions: dict[str, VetoDecision]` so operators can see what each scope decided this tick. Either way, document the choice.

**Owner:** B (this review).

## B3 — D3 helper test mechanics

### `_RUN_INFERENCE_WINDOW = 30000` correctness

`test_v4715_universalize_veto.py:740` sets `_RUN_INFERENCE_WINDOW = 30000`. The window is sliced from the start of `async def _run_inference` (located at `presence.py:2266`, not `:2212` as the brief states — I confirmed via `grep -n "async def _run_inference" presence.py` which returned exactly one match at `:2266`).

Math:
- WAKING gate at `presence.py:2540-2566` — offset `(2566 - 2266) * ~50 chars/line ≈ 15 KB` from `_run_inference` start. Inside window.
- GUEST exit gate at `:2574-2615` — offset ~17.5 KB. Inside window.
- Consolidated house_inference at `:2647-2701` — offset ~21.7 KB. Inside window.
- End of `_run_inference` body (next `async def`) — `_check_zone_anomalies` is invoked at `:2915` but `_run_inference` continues past that and ends before the next `async def`. I ran `grep -n "async def" presence.py` and the next sibling `async def` after `_run_inference` (at `:2266`) is at `:2934`. So `_run_inference` body spans `~2266-2934` = ~668 lines = ~33.4 KB at average line width.

A 30000-char (~30 KB) window from `:2266` covers approximately lines `:2266-:2870`, which **includes** the WAKING gate, GUEST exit gate, and Pattern A consolidated call. **It does NOT include the D5 signal_consensus calc at `:2865-2886`** — but no D3 assertion targets that block. The window is correct for D3 purposes.

**One sharp edge:** the next `async def` after `_run_inference` is at `:2934` (~33.4 KB into the body). The 30000-char window leaves a ~3.4 KB margin before bleeding into the next function. The `test_run_inference_only_defined_once` guard catches the "two functions named the same" case but does NOT catch the "window slides into the next function body" case — see B3-H1 below.

### B3-H1 (HIGH) — `test_run_inference_only_defined_once` is a substring match, not an AST parse

**File:line:** `test_v4715_universalize_veto.py:794-799`
**Bug class:** Test-authority degradation (Reviewer C's frame; flagged here because it directly weakens the B3 invariant I am verifying).
**Finding:** The brief asks whether the AST regression "actually parses the AST and counts FunctionDef/AsyncFunctionDef nodes named `_run_inference`." It does not. The body is:

```python
def test_run_inference_only_defined_once(self):
    assert PRESENCE_SRC.count("async def _run_inference") == 1, ...
```

This is `str.count`, not an `ast.parse + walk`. Three failure modes the substring test does NOT catch:

1. **Comment match.** A future commit adds `# the helper async def _run_inference uses ...` somewhere in `presence.py`. Substring count becomes 2 — test fails — but no real function duplication occurred. **False positive.**
2. **Name reuse in docstring.** A docstring line containing `async def _run_inference` flips the count. **False positive.**
3. **Window slides past EOF / into a different function body.** Substring count still equals 1, but the 30000-char window from `:2266` could span into `:2934`'s function body if `_run_inference` shrinks (e.g., a refactor extracts the consensus block out). Source-grep assertions targeting `_run_inference` content (`test_signal_consensus_calc_block_exists` uses `find(...async def _check_zone_anomalies)` to bound — D3 tests use the fixed-window slice and would silently match against the WRONG function body). **False negative.**

The brief calls out this exact risk: "Did widening accidentally make the assertion trivially true?" The substring guard does not protect against the false-negative case. The window can shift such that `body[idx:idx+30000]` straddles `_run_inference` and `_check_zone_anomalies`, and an assertion like `"waking_transition" in body` could pass against the wrong function — if a future refactor moves the WAKING handler to `_check_zone_anomalies`, the test would silently still pass.

**Why HIGH:** test authority is the foundation of Tier 2-DB confidence. A guard that doesn't actually guard is worse than no guard — it gives a false signal of safety. Operator-coined rule from CLAUDE.md: "Behavioral test fixtures extract schema from production source (never hand-copy DDL). Tests drive production code paths, not their own ...".

**Suggested fix:**

```python
import ast

def test_run_inference_only_defined_once(self):
    tree = ast.parse(PRESENCE_SRC)
    matches = [
        node for node in ast.walk(tree)
        if isinstance(node, (ast.AsyncFunctionDef, ast.FunctionDef))
        and node.name == "_run_inference"
    ]
    assert len(matches) == 1, (
        f"v4.7.15.1 D3: expected exactly 1 _run_inference definition, "
        f"found {len(matches)}; the 30 KB source-grep window cannot span "
        f"multiple bodies"
    )
    # Additionally bound the window — the body should be < 30 KB.
    body_start = matches[0].body[0].lineno if matches[0].body else matches[0].lineno
    body_end = (
        matches[0].end_lineno if matches[0].end_lineno is not None
        else len(PRESENCE_SRC.splitlines())
    )
    body_size = sum(
        len(line) + 1
        for line in PRESENCE_SRC.splitlines()[body_start - 1: body_end]
    )
    assert _RUN_INFERENCE_WINDOW <= body_size + 1000, (
        f"v4.7.15.1 D3: window {_RUN_INFERENCE_WINDOW} exceeds body size "
        f"{body_size} + 1 KB headroom — assertions may match adjacent functions"
    )
```

The second assertion catches the false-negative case (window > body) that the substring guard misses.

**Owner:** Reviewer C in spirit (test fixture authority is C's frame), but B raises it because the substring guard's failure modes directly weaken the D3 mechanics I am tasked to verify. Defer the fix to C if both reviewers land it; otherwise B owns it.
