## Focus-Area Findings (the five risk areas)

### 1. Fan-noise / wake correctness during sleep — VERIFIED SAFE

Traced `infer()` end-to-end (`presence.py:462-587`):

- `now = dt_util.now()` (local TZ) at `:487`, then `hour = now.hour` at `:489`.
- `_is_sleep_hour(hour)` at `:538` handles the overnight-window correctly
  (`:606-609`): `hour >= 23 or hour < 6` for the shipped default.
- Inside the sleep-hour branch, `current_state in (SLEEP, WAKING) → return None`
  (`:539-542`). **The engine does not propose WAKING at any hour ≥23 or <6.**
- WAKING is proposed only at `:545-547` under `current_state == SLEEP`, which
  is reachable only AFTER the `_is_sleep_hour` branch returned without taking
  it — i.e. only when `hour >= 6` (and `< 23`).
- The WAKING gate at `:2855` requires `new_state == HouseState.WAKING and
  current_state == HouseState.SLEEP` — only reachable when the engine proposed
  WAKING, which (by the above) cannot happen during sleep hours.

**Therefore:** a 3 AM mmwave fan blip cannot wake the house. `raw_occupied`
feeding the wake timer during sleep hours only accumulates `_first_positive_
zone_occupied_since`; it does not by itself flip state. The 90s sustained
threshold is incidental at that point — even a zero-second threshold would not
wake the house at 3 AM because the gate is never consulted.

**Residual (documented, accepted):** a fan running continuously across the
sleep_end boundary holds `_first_positive_zone_occupied_since` at e.g.
04:00:00, so at 06:00:00 when the engine first proposes WAKING the gate sees
≥120 minutes of sustained signal and passes immediately. This is "eager 6 AM
wake," not a false wake — it is a *latency* issue compared to the operator's
intent that someone has to physically be up. Plan acknowledges this and defers
mmwave fan-noise rejection to a future cycle. **No change requested.**

### 2. Backstop blast radius — VERIFIED CORRECT

The backstop is nested THREE levels deep:

1. `if new_state == HouseState.WAKING and current_state == HouseState.SLEEP:`
   (`:2855-2858`)
2. `if wake_decision.fired:` (`:2875`)
3. `if _backstop:` (`:2893`)

It can ONLY mutate behavior on SLEEP→WAKING. No other transition path
(SLEEP→AWAY, WAKING→HOME_DAY, GUEST→HOME_*, etc.) sees this code. **Confirmed
by reading `:2855-2910` end-to-end.**

**Hour-window math (default 6/23):** `_backstop_hour = 6 + 3 = 9`. Window
`9 <= local_hour < 23`. At exactly local_hour=9 the backstop is eligible; at
local_hour=8 the normal D3 veto suppresses. This is "eager at +3:00:00.000" by
one tick, but consistent with the documented "well past sleep_end_hour"
intent. **Accept.**

**`sleep_end_hour + 3 >= 24` case (M2):** if a future operator sets
`sleep_end=22` (e.g., a 20:00–22:00 nap window), `_backstop_hour=25`, and the
condition `25 <= local_hour` never holds → backstop silently dead. Not a
fire-incorrectly bug, but the silence is surprising. **Fix-in-cycle suggestion
(LOW-effort, ~6 LoC):**

```python
_backstop_hour_raw = engine.sleep_end_hour + _WAKE_BACKSTOP_HOURS_AFTER_SLEEP_END
if _backstop_hour_raw >= 24:
    _LOGGER.debug(
        "v4.7.18.1: backstop unreachable (sleep_end_hour=%d + %d >= 24); "
        "relying on D3 veto only",
        engine.sleep_end_hour, _WAKE_BACKSTOP_HOURS_AFTER_SLEEP_END,
    )
    _backstop = False
else:
    _backstop = (
        self._census_count > 0
        and _backstop_hour_raw <= _local_hour < engine.sleep_start_hour
    )
```

**Daytime-sleep window (`sleep_end > sleep_start`, e.g., 14→6):** the
engine's `_is_sleep_hour` correctly inverts (`:606-609`), so SLEEP is proposed
only between 14 and 6 — and the backstop window
`(sleep_end+3=17) <= hour < (sleep_start=6)` is empty in normal integer
comparison → backstop never fires. **Inert, not dangerous.** L3 covers the
test gap.

### 3. `raw_occupied` correctness — VERIFIED CORRECT

`_derived_mode` (`:247-275`) is evaluated in tier order:

- Tier 3 (BLE): if `_ble_occupied → OCCUPIED`. **BLE-only zone returns
  OCCUPIED correctly.**
- Tier 1 (`_room_occupied.values()`): requires `_has_sensors`. **Camera-only
  zone with no rooms: skips Tier 1.**
- Tier 2 (`_any_camera_occupied()`): requires `_has_sensors`. **Camera-only
  zone returns OCCUPIED when any camera fires within timeout.**
- Tier-1/2 fallthrough returns AWAY (`:268`). **`raw_occupied` returns False —
  correct.**
- No-sensor zone with no BLE history: returns UNKNOWN (`:275`). **`raw_occupied
  = (UNKNOWN == OCCUPIED) = False` — correct.**

No `None`/AttributeError risk: `_derived_mode` always returns one of three
`ZonePresenceMode` constants. `raw_occupied` is a pure equality check.

### 4. Override interaction — DOCUMENT BUT ACCEPT (M3)

`raw_occupied` returns `True` for a zone whose operator has set
`override = AWAY` if the underlying sensors fire. This means:

- **Operator manually overrides Master Suite to AWAY** because they're using
  it for a party and want HVAC to skip it.
- **During sleep**, party hasn't ended, mmwave still fires.
- **At sleep_end + 3**, the wake timer would have been accumulating from the
  raw signal → backstop or sustained-signal gate could pass.

This is a subtle change in semantics. Pre-v4.7.18.1, an operator AWAY override
on a zone hid that zone from the wake timer; post-fix it does not.

**Verdict: accept** — the override is "ignore this zone's sensors for
auto-derivation," not "this zone never has movement." The wake timer's purpose
is to detect real human activity in the house, and an overridden zone with
firing sensors is real activity. Single-install pragma applies. **Document in
review doc (this entry) for future audit; no code change requested.**

For the operator OCCUPIED override case, it's even cleaner: the operator has
explicitly said "this zone is occupied," which is consistent with feeding the
wake timer. No issue.

### 5. Standard hotfix checks

**Timezone (Bug Class #11) — M1:**
The backstop reads `dt_util.now()` (local) at `:2884` for the hour comparison;
the timer reads `dt_util.utcnow()` at `:2562, :2862` for the duration delta.
**This is correct by design.** The hour window is a "wall clock" concept
(9 AM local), and the duration is an interval (90 seconds). Mixing local-hour
for window-checks vs UTC for monotonic durations is the right pattern. DST
edge: in spring-forward, local_hour jumps 02→03, so the window check
`9 <= local_hour` is unaffected. In fall-back, local_hour replays 01→01, but
the window starts at 9 not 1, so no double-fire risk. **Accept.**

**Log levels — L4:** the backstop log is `_LOGGER.warning(...)`. Each
inference tick during the backstop window with insufficient sustained signal
re-fires the warning. With `_run_inference` triggered by census updates,
camera detections, periodic ticks (`:1999`), and zone changes, this could
hit journald several times in a row before WAKING is accepted. Operator
journals will see e.g. 5-10 WARNINGs over a few seconds. **Fix-in-cycle:**
guard with a "first-fire-only" flag or downgrade subsequent fires to INFO.
~5 LoC. Not a correctness issue.

**Counter restoration — L2:** `_wake_backstop_fires` is a plain int, reset to
0 on every coordinator init. `_wake_blocked_ticks` (its sibling counter
shipped in v4.7.15) follows the same pattern. The sensor surfaces it via
`getattr(presence, "_wake_backstop_fires", 0)` so an HA restart shows 0 until
the first fire. **Accept** — these are diagnostic counters for the current
session; persistence isn't load-bearing.

**None handling — L1:** `engine = self._inference_engine` at `:2883` —
`_inference_engine` is set unconditionally in `__init__` (`:645-648`), so
None is structurally impossible at this point. The whole inference cycle
already dereferences `self._inference_engine` upstream (e.g. `:2795`,
`:2850`) without guarding. **Accept** — local invariant.
