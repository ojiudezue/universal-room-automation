# Review D — Freeze-Floor CHOKEPOINT (Adversarial Completeness Backstop)

**Cycle:** v5.5.4 freeze-floor chokepoint
**Branch:** `feature/freeze-floor` (`git diff develop..HEAD`)
**Framing:** Tier-3 Reviewer D — hunt the missed path A/B/C don't cover.
**Invariant under test:** During a freeze (outdoor ≤35°F), no URA code path causes a
thermostat's effective `target_temp_low` to end below `FREEZE_FLOOR` (50°F).

---

## LEAD VERDICT

**LEAK FOUND: YES (2) — one staleness leak (in-scope) + one preset-side leak (boundary).**

- **D-HIGH-1 (in-scope staleness leak):** `_freeze_active` is refreshed in EXACTLY ONE
  place — `_update_freeze_active()` called only at `hvac.py:1479`, inside
  `_async_apply_preset_overrides`. That method is **double-gated** and early-returns
  before the refresh when EITHER `self._observation_mode` is True (`hvac.py:1385`) OR
  `self._guest_mode_actuation_enabled` is False (`hvac.py:1456`). The predictor
  banking-release emitters (`hvac_predict.py:855/924/1061`) and the override-arrester
  nudge/restore emitters (`hvac_override.py:890/1492/1568/2016/2234`) read the latched
  field lazily via the `freeze_active` property (`hvac.py:332`, returns the RAM field
  WITHOUT calling `_update_freeze_active`). These emitters fire on **independent
  signal-dispatched triggers**, not as a continuation of `_async_apply_preset_overrides`.
  **Therefore, with guest-mode actuation disabled (or in observation mode), the field
  is NEVER refreshed and stays at its boot default `False` (`hvac.py:242`) while a real
  freeze is ongoing** — every emitter then passes `freeze_active=False` and the chokepoint
  floor is a NO-OP. A banking-release that writes a sub-50 baseline low would not be
  floored. The freeze refresh and the setpoint emitters are decoupled.

- **D-HIGH-2 (boundary leak — thermostat-side preset):** `hvac.py:1303` selects
  thermostat-side presets (`away`, `home`, `sleep`) via `climate.set_preset_mode`.
  URA actively flips zones to the **`away` preset during vacancy/runtime overrides**
  (`hvac.py:1152/1200/1214`), which is exactly the freeze-concurrent path (empty/vacant
  house in cold weather). The `away` preset's heat_low is defined **on the thermostat
  device**, not by URA. If a homeowner's `away` preset has heat_low < 50, URA *selecting*
  that preset lowers the effective heat_low below the floor, and the chokepoint —
  which governs only `set_temperature`, never `set_preset_mode` — cannot catch it.
  No follow-up `set_temperature` re-floors the zone after the preset flip.

## 2. Does every caller pass the LIVE freeze_active? — YES (none default to False)

All 9 sites pass an explicit `freeze_active=`; none rely on the `=False` default
(`hvac_setpoint.py:67`). hvac_covers.py async_calls are covers, not climate. The
predictor fan turn_on (`hvac_predict.py:1002`) is a fan, not a setpoint — out of scope.

## 3. Is freeze_active CURRENT at each call? — **NO (D-HIGH-1)**

The value is *passed* live, but the *latched RAM field it reads* is only refreshed inside
the double-gated `_async_apply_preset_overrides` (`hvac.py:1479`). The property
(`hvac.py:332`, `hvac_override.py:269`, `hvac_predict.py:173`) returns the field WITHOUT
forcing a re-derive. Two staleness windows:
- **Boot / first-cycle:** field defaults `False` (`hvac.py:242`); a predictor banking
  release or override nudge that fires before the first successful
  `_async_apply_preset_overrides` reads stale-`False` during an actual freeze.
- **Steady state with actuation disabled:** if `_guest_mode_actuation_enabled=False` or
  `_observation_mode=True`, the refresh NEVER runs, so the field is permanently the boot
  default while independent emitters keep writing.

**Fix direction (no code edit here):** call `_update_freeze_active()` unconditionally
once per HC update tick BEFORE any emitter can fire (outside the actuation gate), or have
the `freeze_active` property itself re-derive (cache-on-read) so lazy readers can't see a
stale value. The defaults (`obs=False`, `guest=True`) make the leak latent, not universal
— but it is real for any house running observation mode or guest-actuation-off.

## 4. Non-set_temperature paths lowering effective heat_low

- **`climate.set_preset_mode` → `away` (D-HIGH-2):** in-scope trigger, OUT-OF-SCOPE floor.
  URA selects `away` during freeze-concurrent vacancy (`hvac.py:1152/1200/1214/1303`).
  The chokepoint cannot floor a thermostat-defined preset range. **Boundary:** URA does
  not author the `away` range, but it DOES select it during a freeze — so the invariant
  ("no URA code path causes <50") is technically violable via preset selection on a
  thermostat whose `away` preset is sub-50. Recommend: documented out-of-scope OR a
  follow-up `emit_set_temperature` after a freeze-time `away` flip to re-assert the floor.
- **`number.set_value` on a heat setpoint:** none found — `grep number.*set_value` on a
  climate/thermostat heat setpoint returned nothing in hvac*. Not a vector.
- **Direct attribute write:** none found.

## 5. Banking / override passthrough — chokepoint catches stale sub-50 lows: YES

Sites 6-9 pass `zone.target_temp_low` / resolved baseline lows. The chokepoint floors
**whatever is passed** (`hvac_setpoint.py:50-51`) — a stale sub-50 attr read upstream is
still floored AT THE WIRE, provided `freeze_active` is true at that call. So passthrough
lows are safe **only when D-HIGH-1 is fixed**; the floor logic itself is correct. The
deadband transform (`hvac_setpoint.py:55-56`) correctly prevents the raised low from
inverting the band (fixes A-HIGH-1).

## Summary (<300 words)

The chokepoint refactor is structurally sound: exactly one `climate.set_temperature`
service call exists (`hvac_setpoint.py:91`), all 9 emitters route through it, and every
caller passes an explicit live `freeze_active` (none default to False). The freeze-floor
+ deadband transforms are correct and floor passthrough lows at the wire.

But two completeness leaks survive A/B/C's framing:

**D-HIGH-1 (in-scope, staleness):** `_freeze_active` is refreshed in only one place
(`hvac.py:1479`), double-gated behind `_observation_mode` and
`_guest_mode_actuation_enabled`. The predictor and override-arrester emitters read the
latched field lazily and fire on independent triggers. With actuation disabled or in
observation mode — or on the first boot cycle — the field stays at its `False` default
during a real freeze, making the floor a silent NO-OP for those emitters. Fix: re-derive
freeze unconditionally per tick (or cache-on-read in the property).

**D-HIGH-2 (boundary, preset-side):** URA flips zones to the thermostat `away` preset
during freeze-concurrent vacancy (`hvac.py:1303`). The chokepoint governs
`set_temperature` only, not `set_preset_mode`, so a thermostat whose `away` preset has
heat_low < 50 ends below the floor with no URA re-assert. Out-of-scope for the chokepoint
mechanism, but in-scope for the invariant as stated.

**Verdict:** The single-service-call / all-emitters-routed invariant HOLDS. The
"no path ends <50 during a freeze" invariant **does NOT fully hold** — D-HIGH-1 (latent,
config-dependent) and D-HIGH-2 (preset boundary) are concurrent-freeze paths that can land
below 50. Recommend addressing D-HIGH-1 before close; classify/document D-HIGH-2 explicitly.
