## Summary

**Verdict: SHIP** — no CRITICAL or HIGH issues found.

The implementation correctly addresses the three failure modes identified in the planning doc:
1. **Persistence guard** — `_unidentified_first_seen` is captured on first qualifying tick; gate fires only after the window elapses.
2. **Confidence guard** — uses a documented integer rank map (`_CONFIDENCE_RANK`), not lexicographic string compare.
3. **Existence-only threshold** — `min_unidentified` cleanly dropped; effective threshold is `unidentified_count > 0` (single visitor still triggers).

Mental execution across the seven required starting states (a–g) is clean:
- Cold start: in-memory state is None; first qualifying census tick arms; periodic re-eval and recheck timer both function.
- Sustained unidentified for 5 min: persistence + recheck timer drives fire.
- Transient blip: existence-gate failure on next tick disarms cleanly.
- Confidence regression mid-arm: confidence-gate failure disarms cleanly.
- House transitions OUT of HOME_* during pending arm: `_run_inference` line 1574 disarms; recheck timer fallback also catches it (with up to a 5-min stale-state window that is harmless).
- HA restart while armed: in-memory state lost; HA cancels the timer at shutdown; fail-safe direction (window restarts).
- Coordinator unload while handle scheduled: `async_teardown` calls `_disarm_guest_gate` (line 1920) which cancels the handle.

The `async_call_later` handle is created, tracked on `self._guest_persistence_check_handle`, and cancelled on every exit path: gate fire, disarm (count drops / confidence regresses), house-state leaves HOME_*, coordinator unload. Bug Class #19 (Untracked Background Tasks) does not apply to the timer handle itself — it is tracked.

Findings below are all MEDIUM, LOW, or informational and do not block deploy. The MEDIUM is a reactivity gap that the 60s periodic inference covers, but is worth tightening in a follow-up.

## Recommendations for QUALITY_CONTEXT.md

No new bug classes required. Finding #1 (signal-reactivity gap — handler only refires on subset of payload changes) is a minor variant of "stale-data driving decisions" already covered by existing patterns. If it recurs (i.e., we see another case where a signal handler trigger-condition omits a payload key that's subsequently consumed), promote to a new class:

**Proposed class (deferred until a second instance is observed):**
> **Bug Class #39: Signal Handler Trigger Subset Omits Consumed Payload Key.** A signal handler computes a `should_run_inference` decision based on a subset of payload keys, but downstream logic consumes additional keys. Updates to those additional keys arrive without triggering re-evaluation, causing decisions to lag the actual signal state.
> **Prevention:** When extending a signal payload, audit the handler's trigger condition: every payload key consumed downstream must appear in the trigger-changed set, OR a fallback periodic re-eval must bound the lag.
