### A5 — MEDIUM — `native_value` "dense" branch is dead-letter

`sensor.py:2137-2138`:

```python
if ble_tier == 1:
    return "dense" if (has_mmwave or has_pir) else "dense"
```

The ternary's true and false arms are identical. This **always returns "dense"** for any `ble_tier=1` room, regardless of whether mmWave/PIR are present.

Per plan §2 D2 table, the intent was:
- `dense` = `ble_tier=1 AND at least mmWave OR PIR present`
- (some other label) = `ble_tier=1` BUT no mmwave/PIR

Two valid resolutions:
1. **Drop the requirement** — Tier 1 = "dense" period, mmWave/PIR absence is rare and visible in attributes anyway. Then simplify to `if ble_tier == 1: return "dense"`. This is the actually-shipped behavior — recommend codifying this in the docstring and removing the dead ternary.
2. **Honor the plan** — introduce a fall-through label like `ble_only` for `ble_tier=1 + no PIR/mmWave`. Then the ternary actually branches.

**Recommendation:** Option 1 (drop). Reasoning: a `ble_tier=1` room without mmWave/PIR is structurally "dense BLE coverage, no occupancy sensors" — still genuinely dense from the *scanner* perspective. The state label is a scanner-coverage rollup; sensor presence is in `has_mmwave`/`has_pir` attrs.

**Fix-up:**
```python
if ble_tier == 1:
    return "dense"
```

## D3 — Per-room weighted veto: **THE CONTENTIOUS DELIVERABLE**

`presence.py:2057-2168`.

### A1 — HIGH — Aggregation rule: **recommend `max`**, not `sum`

The builder explicitly delegated this to Reviewer A. Current code at `presence.py:2105`:

```python
aggregate_weight = sum(weights.values())
```

**Decision: change to `max(weights.values())` (or `0.0` if empty).** Reasoning:

1. **The semantic question is "how confident are we the zone is empty?"** The v4.7.15 helper is a *veto* against accepting OCCUPIED. The signal we care about is "the strongest BLE evidence the zone has." A zone with one Tier-1 room (weight 1.0) and four Tier-0 rooms (weight 0.0 each) has `sum=1.0`, `max=1.0` — same. A zone with five Tier-2 rooms (`sum=3.0`, `max=0.6`) under `sum` semantics **looks more confident than a single Tier-1 zone**, which is wrong — Tier-1 is by definition more reliable than Tier-2 by the v3.8.9 design rationale that motivated this whole feature.

2. **Sum invites BLE-tier ganging:** five borrowed-scanner rooms outweigh one own-scanner room. That contradicts the v3.8.9 README's explicit framing that direct-coverage rooms get BLE-as-primary while borrowed-coverage rooms require confirmatory sensors. With `sum`, the aggregate can mask weak per-room signals behind quantity.

3. **Max preserves the v3.8.9 invariant in aggregate form:** `max(weights)=1.0` ⟺ at least one Tier-1 room exists. `max(weights)=BLE_TIER_2_WEIGHT` ⟺ only Tier-2 rooms (the zone is genuinely sparse). `max(weights)=0.0` ⟺ Tier-0 only (no BLE at all). These three cases map cleanly to the three plan §6 acceptance criteria for D3:
   - "A zone composed entirely of `ble_tier=1` rooms produces `accept_occupied`" → `max=1.0`
   - "A zone composed entirely of `ble_tier=2` rooms needs corroborating Tier 1/2 (mmWave or camera)" → `max=0.6` (helper defers)
   - "A zone composed entirely of `ble_tier=0` rooms ignores BLE entirely" → `max=0.0`

4. **The mixed-zone plan §6 acceptance criterion** ("one Tier 1 + one Tier 2 sums to 1.6, helper accepts") is the only one that explicitly expects `sum`. **This criterion should be REWRITTEN** to "mixed zone where any room is Tier 1 → helper accepts (`max=1.0`)". The semantic intent (mixed zones with one strong room accept occupancy) is preserved; only the arithmetic changes.

5. **Operator-tunability under `max` is cleaner:** `BLE_TIER_2_WEIGHT=0.6` directly controls "how much do I trust a borrowed-scanner-only zone" without scaling by room count. Under `sum`, tuning the constant has a count-dependent multiplier the operator has to mentally apply.

**Counter-considered:** "But sum captures consensus across rooms." Counter-counter: the v4.7.15 helper takes the entire `weights` dict in `state_context` (`presence.py:2124` — `"room_weights": dict(weights)`). The helper itself can implement any aggregation it wants from the raw map. The aggregate value passed at `:2125` is for *URA's* diagnostic; it should be the value most consistent with the v3.8.9 design, which is `max`.

**Fix-up:**
```python
# v4.7.16 D3 (post-review A): max preserves the v3.8.9 "Tier 1 dominates"
# invariant in aggregate form. Per-room weights are still available to
# the helper via state_context["room_weights"] for any aggregation it
# wants to perform internally.
aggregate_weight = max(weights.values()) if weights else 0.0
```

**Side-effect:** the plan §6 D3 acceptance criterion "mixed-tier zone weight sums correctly" needs to be updated in the README to reflect `max` semantics. Reviewer A flags this for the README pass.

But the plan §0.7 and §2 D3 describe the v4.7.15 helper as **a pure function / module-level helper** that v4.7.16 imports and calls. ### Tier-0-only zone fallback (per A3 framing in task brief)

Plan §2 D3 boundary case says: "For a zone where every constituent room is Tier 0, the BLE channel contributes nothing. Current Tier 1 (mmWave/PIR) and Tier 2 (camera) signal classes in `_derived_mode` still apply. The zone falls back to multi-tier sensor agreement, exactly as today, without BLE input."

**Verified.** The D3 block at `presence.py:2074-2168` runs **alongside** the existing `_derived_mode` evaluation (which happens upstream in each `ZonePresenceTracker.mode` access at `:1990-1993` — `any_zone_occupied` is computed from `tracker.mode`, not from D3's verdict). The D3 verdicts are written to `self._v4716_zone_verdicts` and **not** wired into `infer()` (which still receives `any_zone_occupied` from the pre-existing tracker.mode path). So for a Tier-0-only zone:

1. `tracker.mode` is computed from `_derived_mode` using mmWave/PIR/camera signals — **unchanged from pre-v4.7.16**
2. D3 records `aggregate_weight=0.0` and (if helper exists) gets a verdict — **but the verdict is unused** (per A6)
3. `any_zone_occupied` is True/False based on the *unchanged* tracker.mode

**The fallback is correct because the new path is not yet wired.** Once the helper is hooked into `infer()` in the follow-up cycle, this guarantee needs to be re-verified — a Tier-0-only zone's verdict must NOT veto an OCCUPIED reading derived from non-BLE signals.

### A2 sum-vs-max — explicit recommendation summary (per task brief)

**Recommendation: `max`.** Reasoning consolidated:

| Aspect | sum | max |
|---|---|---|
| v3.8.9 invariant preservation (Tier 1 > Tier 2) | Broken — 5×Tier-2 > 1×Tier-1 | **Preserved** — `max=1.0` only when Tier-1 present |
| Operator tunability | Count-dependent; `BLE_TIER_2_WEIGHT` scales by room count | Direct; constant controls Tier-2-only zone confidence floor |
| Plan §6 D3 acceptance criteria compatibility | All-Tier-1 ✓, All-Tier-2 ✓, All-Tier-0 ✓, Mixed (needs README rewrite to "max-based") | All-Tier-1 ✓, All-Tier-2 ✓, All-Tier-0 ✓, Mixed (max=1.0 — same outcome, cleaner reasoning) |
| Defensibility under v4.7.15's helper contract | Aggregate is one number; helper has to back-derive | Aggregate is the dominant signal; helper still gets full `room_weights` for its own aggregation |
| Confidence semantics | "Total BLE weight" — fuzzy meaning | "Strongest BLE evidence" — crisp |

**Apply fix to `presence.py:2105` + update README/plan acceptance criterion for mixed zones to reflect max semantics.**

### A7 — LOW — Shared-area edge case

`presence.py:1173-1182`:

```python
area_to_zone: Dict[str, str] = {}
opted_out_area_ids: Set[str] = set()
opted_out_rooms = self._rooms_opting_out_of_camera_presence()
for zone_name, tracker in self._zone_trackers.items():
    for room_name in tracker.room_names:
        area_id = self._room_area_ids.get(room_name)
        if area_id:
            area_to_zone[area_id] = zone_name
            if room_name in opted_out_rooms:
                opted_out_area_ids.add(area_id)
```

**Edge case:** if two rooms (rooms A and B) share the same `area_id` (operator misconfig — e.g., assigning both "Reading Nook" and "Master Bedroom" to area `master_bedroom`), and only room A opts out, then `opted_out_area_ids` includes `master_bedroom`, and the camera registration is skipped **for both rooms' zone** because the discovery loop iterates `area_to_zone.items()` keyed on `area_id`, not on `(room, area_id)` pairs.

Concretely: room A opts out → its area_id added to `opted_out_area_ids`. Room B does not opt out, but its zone uses the same area_id (last write wins at `:1180`). The zone that "wins" the dict has its cameras skipped entirely.

**Probability:** Low — operators rarely assign two URA rooms to the same HA area. But the task brief A4 framing explicitly asked: "What if a camera is registered with multiple zones — does opt-out for one room remove the camera from all zones it covers?" The answer is: **the camera's area is the key, so yes — opt-out is by area, not by room.** This matches the design intent (cameras live in HA areas, opt-out is by physical area), but it's worth documenting because the operator-facing surface is `CONF_DISABLE_CAMERA_PRESENCE` on a *room*, not on an area.

**Recommendation:** Document in `docs/readmes/README_v4.7.16.md` operator runbook: "Opt-out applies at the HA area level. If two URA rooms share an HA area, opting out either one suppresses cameras for the entire area." Not a code change.

## A5 — `BLE_TIER_2_WEIGHT` operator-tunability

`const.py:334`: `BLE_TIER_2_WEIGHT: Final = 0.6`. Documented as operator-tunable (`const.py:328-333`).

### Sensitivity sweep

| Value | Behavior |
|---|---|
| `0.0` | Tier 2 rooms contribute nothing to `aggregate_weight`. Under `sum` semantics: identical to all-Tier-0 zone. Under recommended `max` semantics: same — `max(0, 0, …)=0`. **Functionally identical to demoting all Tier 2 rooms to Tier 0.** | OK |
| `0.3` | Conservative weight for noisy borrowed scanners. Under `max`: zone with only Tier 2 rooms gets aggregate_weight=0.3, well below any reasonable helper threshold. | OK |
| `0.6` | Default. Tier-2-only zone gets max=0.6 — likely below helper's "accept" threshold, so helper would defer. | Reasonable default |
| `1.0` | Tier 2 == Tier 1. Operator says "I trust my borrowed scanners as much as direct ones." | OK |

**A5 verdict:** Default and tunability range are reasonable. Constant-only (no per-room override) matches plan §6 explicit deferral. No change needed.
