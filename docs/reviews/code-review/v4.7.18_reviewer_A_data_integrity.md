### LOW

#### A-L1 — Test 2 (`test_hydrate_caps_to_max_days`) does not assert ordering preserves newest-90

**Bug class:** Test fixture authority (sibling of Bug Class #49 — shape-preservation tests must actually verify the shape).

**File:** `quality/tests/test_v4_7_18_dpm_drift_guard.py:159-198`

**Issue:** The test builds 95 entries with values `80.0 + i*0.01` where i=0..94, but constructs them with i=0 = today and i=94 = today-94 days. The list is **reverse-chronological** (newest first). The hydrate path's `cleaned[-90:]` slice then keeps the **oldest 90** of that input list (i=5..94, values 80.05..80.94) because the input is reverse-chronological. The test passes because the value assertion (`all(80.0 <= v <= 82.0)`) is satisfied either way.

**Why it doesn't break production:** In production, `_record_daily_apparent_high` always appends today's value to the ring (line 661), so the persisted Store payload is **chronologically ascending** (oldest first, newest last). `cleaned[-90:]` then correctly retains the newest 90. The bug only surfaces if a future change writes the Store in a different order (e.g., from a manual restore or a refactor).

**Suggested fix (optional, can defer to v4.7.19):** Strengthen the test to:
1. Build entries in chronological-ascending order matching the production write order.
2. Assert that the **first** retained entry's date is `today - 89 days` (not `today - 94 days`).
3. Add a second test that explicitly seeds a reverse-chronological list and asserts the hydrate is order-sensitive (locks the contract).

**Status:** LOW — defer. Production behavior is correct. The test gap is not a regression risk for v4.7.18; it could mask a future regression.

#### A-L2 — `restore_blocked_counter` does not clamp future timestamps

**Bug class:** Restart-resilience hygiene (sibling of Bug Class #11 timezone, but for value range).

**File:** `domain_coordinators/dynamic_preset.py:403-433`

**Issue:** `restore_blocked_counter` accepts `last_blocked_at` and coerces naive datetimes to UTC, but does not validate that the timestamp is in the past. A corrupted `last_state.attributes` payload (e.g., from a clock-skew incident or manual edit) could persist a future timestamp. The downstream consumer (`get_zone_state` → sensor attribute) would render that future timestamp unchanged.

**Blast radius:** Telemetry-only. The counter increment logic at `dynamic_preset.py:661` always uses `now` (UTC, from `dt_util.utcnow()` at line 540), so a future restored timestamp gets overwritten on the next gate fire. Until the next gate fire, the sensor shows a misleading "last blocked at" attribute.

**Suggested fix:** In `restore_blocked_counter`, after the tzinfo coercion:
```python
now = dt_util.utcnow()
if last_blocked_at > now:
    _LOGGER.debug(
        "DynamicPreset: discarding future last_blocked_at=%s (now=%s)",
        last_blocked_at.isoformat(), now.isoformat(),
    )
    last_blocked_at = None
```

**Status:** LOW — defer. Self-healing on next gate fire; no operator-visible regression risk.

#### A-L3 — Sensor renders `relax_ceiling_f` even when gate is effectively inactive (no `today_apparent_high`)

**Bug class:** Telemetry consistency / UX clarity.

**File:** `domain_coordinators/dynamic_preset.py:639-644`

**Issue:** When DPM evaluates with `today_apparent_high is None` (WPM cold-start or provider down), the resolver still snapshots a ceiling value at lines 643-644:
```python
ceiling_f, ceiling_source = _resolve_relax_ceiling(
    today_apparent_high, p25_apparent_high, ceiling_mode,
)
self._relax_ceiling_last_value[zone_id] = ceiling_f
self._relax_ceiling_last_source[zone_id] = ceiling_source
```

The gate itself correctly fail-opens (lines 652-657 require `today_apparent_high is not None`), so no spurious increment. But the sensor exposes `relax_ceiling_f = 90.0` (auto fallback) while the gate is effectively disabled. Operator looking at the sensor would think the gate is armed when it cannot fire.

**Suggested fix:** Set `_relax_ceiling_last_value` / `_relax_ceiling_last_source` only inside the gate-can-fire branch (i.e., when `today_apparent_high is not None`). Or expose a separate `relax_ceiling_active` boolean attribute that reflects whether the gate is presently armable.

**Status:** LOW — defer to v4.7.19 if operator finds the telemetry confusing. Functionally correct.

#### A-L4 — `restore_blocked_counter` accepts `count=0 + last_blocked_at=<value>` without warning

**Bug class:** State-shape coherence.

**File:** `domain_coordinators/dynamic_preset.py:415-428`

**Issue:** The two state fields (`_relax_ceiling_blocked_count` and `_relax_ceiling_last_blocked_at`) are independent in `restore_blocked_counter`. A corrupted state where `count=0` but `last_blocked_at` is set will restore `last_blocked_at` only. The sensor then renders `blocked_count=0` (correct — dict empty so `get_zone_state` returns 0 default) and `last_blocked_at=<value>` — a logically inconsistent pair (you can't have a "last blocked at" without ever being blocked).

**Suggested fix:** If `count <= 0`, also skip restoring `last_blocked_at`. This pairs the two fields tightly. Add a debug log noting the discarded value.

**Status:** LOW — defer. Self-heals on first gate fire post-restart.
