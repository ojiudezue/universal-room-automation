# v4.6.3 — Targeted Review B: Migration Correctness + Signal Chain Integrity

**Scope:** 10 emit-site migrations (D2–D6) and integration with existing
signal/dispatch/NM chains, plus D7 legacy `store_anomaly()` deletion. Sibling
Review A covers data integrity / DB architecture; Review C covers new
surfaces.

**Commit:** `84326ca` on `feature/v4.6.3-anomaly-migration-all-in-one`
(single commit, ~2,925 LoC across 20 files).

**Reviewer mode:** Staff-engineer mental execution. Walked each emit
end-to-end from signal source through DAO write, traced concurrency and
re-entry risk, cross-checked against legacy `store_anomaly()` semantics.

---

## Verdict: **HOLD — one CRITICAL data-loss regression must be fixed**

The migration plumbing is correct in terms of "rows still get written" and
"signals still fire," but the canonical-payload abstraction (`build_context_json`)
and the DAO's column-extraction logic disagree on where the metric values
live. The result is that every legacy emit site that previously landed
real values in the `observed_value` / `expected_mean` / `expected_std` /
`z_score` / `sample_size` columns now lands `0.0` / `0` sentinels for those
columns — values are preserved only inside `context_json.extra`. This is
silent data corruption visible to any analytics query or sensor that reads
those columns.

Three additional MEDIUM-severity items below; the rest of the migration is
sound.

### B1 — CRITICAL: Metric columns regress to sentinels

**Mental execution.** Smoke alarm fires → `safety._handle_hazard` →
`anomaly_detector.record_observation("hazard_trigger_frequency", ...)` →
returns `AnomalyRecord(observed_value=1.0, expected_mean=0.05, z_score=4.5, sample_size=720, ...)`.

Code builds payload via:

```python
_ctx = build_context_json(
    room_id=scope if scope != "house" else None,
    source_signal="SIGNAL_SAFETY_HAZARD",
    extra={
        "observed_value": anomaly.observed_value,
        "expected_mean": anomaly.expected_mean,
        ...
        "z_score": round(anomaly.z_score, 3),
        "sample_size": anomaly.sample_size,
    },
)
_event = AnomalyEvent(..., payload=_ctx)
await self.anomaly_detector.store_event(_event)
```

`build_context_json` (`anomaly_event.py:112–125`) places these under
`ctx["extra"]`, not at `ctx` top level. So the actual `payload` dict is:

```python
{
  "room_id": "kitchen",
  "source_signal": "SIGNAL_SAFETY_HAZARD",
  "extra": {"observed_value": 1.0, "z_score": 4.5, "sample_size": 720, ...}
}
```

Now look at `database.save_anomaly_event` (`database.py:4346–4351`):

```python
payload_dict = event.payload if isinstance(event.payload, dict) else {}
observed_value = payload_dict.get("observed_value", 0.0)
expected_mean  = payload_dict.get("expected_mean", 0.0)
expected_std   = payload_dict.get("expected_std", 0.0)
z_score        = payload_dict.get("z_score", 0.0)
sample_size    = payload_dict.get("sample_size", 0)
```

`payload_dict.get("observed_value", 0.0)` → **returns 0.0** (the value is one
level deeper under `extra`). All five metric columns receive their NOT-NULL
sentinels even though real data was passed in.

**Why this matters.**

1. The deleted legacy `store_anomaly()` wrapper (visible in the diff, top
   half of `coordinator_diagnostics.py:850–893` before deletion) packed
   these fields at the TOP level of `payload`. So previously, smoke /
   census / zone-occupancy emits landed real `observed_value` / `z_score`
   etc. in their proper columns. After v4.6.3, the same emits land
   sentinels. **Pure regression versus v4.6.2.**
2. Any sensor / analytics query that filters or aggregates on
   `anomaly_log.z_score`, `observed_value`, or `sample_size` will see
   zeros. Specifically: `sensor.ura_coordinator_manager_recent_anomalies`
   reads `severity` and `metric_name` only, so the new D12 sensor
   accidentally avoids the bug. But the existing per-coordinator anomaly
   sensors (e.g. anomaly score / score derivation in
   `coordinator_diagnostics.py`'s `get_recent_anomalies`, plus any
   downstream Bayesian / hvac anomaly accuracy queries) will degrade.
3. **The behavioral DAO tests miss this** because they call `_insert_anomaly`
   with payload-at-top-level shape (test_v463_behavioral_dao.py:121–151,
   178–185). They exercise the DAO contract in isolation, not the
   end-to-end production payload shape.
4. The new tests in `test_v463_anomaly_migration.py` are source-grep
   (D5/D6 tests check for substring presence). None walk a real
   write-read of a *migrated emit-site shape*.

**Sites affected by B1** (have real metric values that are lost):

- `safety.py:1672` — hazard_trigger_frequency emit
- `safety.py:1723` — active_hazard_count emit
- `presence.py:1737` — census_count emit
- `presence.py:1858` — zone_occupancy emit

Circuit (energy), NM dispatch, transit, compliance violation: these
emitters do **not** carry meaningful metric values (they're hazard /
correlation rows), so sentinels are semantically OK for them.

**Fix options (pick one):**

- **(A) Fix at the emit site.** Each affected emit lifts metric values out of
  `extra` into top-level payload alongside `source_signal`. Keeps the
  helper unchanged but requires touching 4 emit blocks. Removes the
  `extra` indirection for the metric subset.
- **(B) Fix in the helper.** Add a `metric_fields` kwarg to
  `build_context_json` that places the 5 canonical metric keys at top level
  (so the DAO's `.get("observed_value", 0.0)` resolves). This is the
  minimum-surface fix and preserves the per-coordinator `extra` slot for
  truly coordinator-specific keys.
- **(C) Fix in the DAO.** Change `database.save_anomaly_event` to look in
  `payload.get("extra", {}).get("observed_value", payload.get("observed_value", 0.0))`.
  Risk: silently double-meaning of the payload structure.

**Recommend (B)** — single touchpoint, doesn't require revisiting every
emit site, and clarifies the canonical schema. Add a behavioral test that
walks an end-to-end emit-site call (using a real `AnomalyDetector` + DAO +
`real_schema_db`) and asserts the column values match the
`AnomalyRecord` values, not 0.0.

This bug shape is a near-direct sibling of v4.6.1.1 (NOT NULL mismatch),
which was supposed to be addressed by D1/D8. The behavioral DAO tests
caught a different shape of the same bug class but missed this one
because they bypass the helper used in production.

### B2 — MEDIUM: `linked_event_id` not threaded into NM correlation

**Mental execution.** Energy detects circuit anomaly →
`_send_nm_alert(severity="high", title="Tripped Breaker: ...")` →
`nm.async_notify(coordinator_id="energy", severity=HIGH, ...)` → channels
fire → `_emit_nm_dispatch_anomaly(coordinator_id="energy", ...)`.

Now check `_emit_nm_dispatch_anomaly` (`notification_manager.py:916–926`).
It calls `build_context_json(source_signal="nm_alert_dispatched", extra={
"source_coordinator": coordinator_id, "title": title, ...})`. No
`linked_event_id` passed in.

**Why this matters.** Plan D5 acceptance criteria (line 133) explicitly
requires `payload.source_anomaly_id` for correlation; plan D11 canonical
context_json keys (line 269) define `linked_event_id` as "FK into
anomaly_log for correlations (D5)". The whole point of the NM
correlation row is to enable a join like:

```sql
SELECT a.*, b.metric_name AS source_metric
FROM anomaly_log a
JOIN anomaly_log b ON b.id = json_extract(a.context_json, '$.linked_event_id')
WHERE a.metric_name = 'nm.alert_dispatched';
```

Without `linked_event_id`, the only way to correlate is fuzzy
`(coordinator + severity + title + timestamp_window)` — defeating the
documented purpose of the canonical key.

**Why it's not CRITICAL.** No code currently consumes `linked_event_id`,
so nothing breaks today. But the v4.6.3 cycle is supposed to *establish*
the canonical shape so future cycles can rely on it. Shipping the
correlation row without the correlation key is half-built.

**Fix.** The emit path needs the source anomaly's row id. The cleanest
plumbing: `async_notify` takes an optional `source_anomaly_id: int | None`
kwarg, threaded through `_send_nm_alert` / `_critical_response` callers.
Where the dispatching coordinator just-now-wrote an anomaly, it passes the
returned row id. Where it doesn't (legacy paths), the field stays None.

Same omission applies to D4 (circuit emit) — if a circuit anomaly's NM
dispatch happens, the D4 row and D5 row both exist but neither references
the other.

### B3 — MEDIUM: D12 inconsistency — second safety emit skips ActivityLogger

**Location.** `safety.py:1711–1735`, the `active_hazard_count` emit block
after the primary hazard emit.

Plan D12 (line 320): "Every migrated emit site fires
`activity_logger.log(action='anomaly', ...)`."

This emit writes the AnomalyEvent (line 1731) and emits `_LOGGER.info`
(1732–1735) but does not call `activity_logger.log(...)`. The preceding
emit (hazard_trigger_frequency, lines 1685–1704) does. Inconsistency.

Impact: anomaly rows for `safety.active_hazard_count` exist in
`anomaly_log` but do NOT show up in the activity stream / HA Logbook /
`SIGNAL_ACTIVITY_LOGGED` cascade. The new `recent_anomalies` sensor will
pick them up on its next refresh cycle, but the dedicated Logbook trail
and the per-emit dispatch event are missing.

**Fix.** Add the missing `activity_logger.log` block, mirroring the
hazard_trigger_frequency emit. ~15 lines.

### B5 — LOW: `source_signal` value semantics

`notification_manager.py:917`:

```python
_ctx = build_context_json(source_signal="nm_alert_dispatched", ...)
```

The D11 docstring (`anomaly_event.py:106–107`) defines `source_signal` as
"HA dispatcher signal that triggered this emit, e.g.
`SIGNAL_SAFETY_HAZARD`". `"nm_alert_dispatched"` is not an HA dispatcher
signal — it's the new event's own type-tag. The actual source signal that
caused the NM dispatch was upstream (SIGNAL_SAFETY_HAZARD for hazards,
nothing for direct programmatic calls).

Two options:
- Store the upstream signal name (requires plumbing — same change as B2).
- Rename the field at the call site (e.g., `extra={"event_kind": ...}`
  and `source_signal=None`).

Either works; pick whichever fits the B2 fix.

1. Binary_sensor.smoke_kitchen → on.
2. `SafetyCoordinator._handle_hazard(hazard)` runs.
3. **Branch 1 (signal):** `async_dispatcher_send(SIGNAL_SAFETY_HAZARD, payload)`

the prevention is different: not just "test DAO writes against real
schema" but "test DAO writes against the actual production helper output

Suggested addition (paraphrase):
> **Bug Class #25 — Helper/DAO Shape Contract Mismatch.** Any helper that
> normalizes payload structure must have a behavioral test that walks

> `payload[*]` directly. Both passed isolated tests; the integration

## Reviewer notes

This review walked the migrated paths in mental execution rather than
checklist mode. The B1 finding emerged from comparing the deleted legacy
wrapper's payload shape (which packed metric fields at the top level)
against the new `build_context_json` shape (which puts them under
`extra`). Both halves are locally reasonable; the bug is in the seam.
The behavioral DAO tests were designed to catch exactly this class of
bug (per the v4.6.1.1 lesson) but exercise the DAO in isolation with a
hand-rolled payload that matches the DAO's reader assumptions, missing
the helper-produced shape that actually ships.

Recommend Review A and Review C confirm no other helper produces a
similarly mis-aligned shape (sensor reads, config flow saves, etc.).
