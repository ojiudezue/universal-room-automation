## Reviewer A — Data Integrity + Restart Resilience (4 LOWs)

### A-L1 — Test 2 ordering assertion does not lock newest-90 contract
- **Summary:** `test_hydrate_caps_to_max_days` builds entries in reverse-chronological order but asserts only value range, not ordering. The test passes but doesn't lock the contract "hydrate preserves newest 90 entries."
- **Why deferred:** Production code IS correct (`_record_daily_apparent_high` always appends today's value, so persisted ring is chronological ascending; `cleaned[-90:]` retains newest 90). The test gap masks future regressions, not present ones. Strengthening would add a 2nd test asserting `[-90:]` is order-sensitive against a chronologically-ascending input.
- **Target version:** v4.7.19 hygiene sweep.

### A-L2 — `restore_blocked_counter` does not clamp future timestamps
- **Summary:** A corrupted `last_state.attributes` payload (clock-skew or manual edit) could persist a future timestamp. Counter logic at `dynamic_preset.py:661` always uses `dt_util.utcnow()` so it self-heals on next gate fire.
- **Why deferred:** Self-healing on next fire; telemetry-only. Sensor would show a misleading "last blocked at" briefly until the next gate fire overwrites.
- **Target version:** v4.7.19 — add `if last_blocked_at > dt_util.utcnow(): last_blocked_at = None` after tz coercion.

### A-L3 — Sensor renders `relax_ceiling_f` even when gate is effectively inactive (no `today_apparent_high`)
- **Summary:** When DPM evaluates with `today_apparent_high is None` (WPM cold-start), the resolver still snapshots a ceiling value (90.0 fallback) on `_relax_ceiling_last_value`. Operator looking at the sensor sees `relax_ceiling_f=90.0` while the gate cannot actually fire (gate guard at lines 652-657 requires non-None apparent_high).
- **Why deferred:** Functionally correct (gate doesn't fire); only UX-confusing telemetry. Fix would add a `relax_ceiling_active` boolean attr or only snapshot inside the gate-can-fire branch.
- **Target version:** v4.7.19 if operator finds the telemetry confusing.

### A-L4 — `restore_blocked_counter` accepts count=0 + last_blocked_at=<value> without warning (LOW version)
- **Summary:** Two-field independence. count=0 with non-None last_blocked_at restores the timestamp orphan.
- **Status:** **PARTIALLY FIXED via C-M3.** C-M3 was the MEDIUM ratchet of this same hygiene issue; the fix at `dynamic_preset.py:419-428` now pairs the two fields. A-L4's only remaining ask is a debug log noting the discarded value, which is the diagnostic-gap class shared with C-L5.
- **Target version:** v4.7.19 — add `_LOGGER.debug("DynamicPreset: rejected last_blocked_at=%s because count=0", ...)`.

## Reviewer B — Migration + Cross-Coordinator + Signal Chain (4 LOWs)

### B-L1 — Dead `async_show_form` branch in Surface 2 save handler
- **Summary:** After D1 stripped inline bucket validation, the `if user_input is not None: errors = {}` block has no path that adds anything to errors. Voluptuous-level coercion failures still surface via HA's normal flow plumbing.
- **Why deferred:** Hygiene-only. No functional bug. Trim alongside the trailing 17 conf_keys in `_build_dynamic_preset_schema` (C-L3 sibling).
- **Target version:** v4.7.19 hygiene sweep.

### B-L2 — Restart-time race: counter restore can clobber freshly-incremented in-memory value
- **Summary:** Sensor subscribes to signals BEFORE `async_get_last_state` completes. If an EC tick fires the gate inside this microsecond window for a cold-start zone (0→1), the subsequent restore unconditionally overwrites with the stored value. Net: a single increment can be lost on first-tick-after-restart.
- **Why deferred:** EC tick is 5-min cadence; restore completes in microseconds. Vanishing window. Counter is observational (not load-bearing on actuation). Fix is `max(restored, current)` semantics.
- **Target version:** v4.7.19.

### B-L3 — Orphaned translation keys `dynamic_preset_range_invalid` + `dynamic_preset_sleep_below_floor`
- **Summary:** D2 deleted the producer (`_validate_dynamic_preset_input`) but two error strings remain in strings.json + en.json.
- **Why deferred:** No harm — HA will simply not surface them. Drift risk only if a future cycle resurrects validation under a different name. Already covered by the broader v4.7.19 string audit (planning §14 #3) + the new §14 #6 from C-M2.
- **Target version:** v4.7.19 string audit.

### B-L4 — D4 dropdown labels bypass HA i18n machinery (single-locale workaround)
- **Summary:** Option labels are Python literals in `SelectSelectorConfig(options=[...])` rather than `translation_key=` + selector.options.* entries in strings.json.
- **Why deferred:** URA is single-install single-locale (en). Practical i18n impact is nil. Convention-divergent but acceptable per URA's "Single User No Back-Compat" memo.
- **Target version:** Acceptable as-is. Track for v5.0 if multi-locale ever materializes.
