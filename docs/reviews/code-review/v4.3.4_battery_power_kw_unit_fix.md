# v4.3.4 Code Review — battery_power kW/W Unit Fix

**Tier:** 1 (Hotfix — latent unit-mismatch bug; ~30 LoC + 5 regression tests)
**Date:** 2026-05-06
**Predecessor:** v4.3.3

## Scope

Fix latent unit-mismatch in EV / smart-plug battery-drain protection that has been silently disabled since v4.2.17 on Envoy installs reporting power in kW.

## Bug summary

Discovered immediately after v4.3.3 shipped. User set the new EV battery drain SOC slider to 80, battery at 62%, EV charging at 7.4 kW, battery discharging at 210W → URA didn't pause the EV.

Root cause:
- `BatteryStrategy.battery_power` returns the underlying Envoy entity value with sign flipped. The user's `sensor.envoy_*_current_battery_discharge` reports `0.208` with `unit_of_measurement: "kW"`. So `battery_power = -0.208`.
- `energy.py:1870, 1895` passes this value to `determine_battery_drain_actions(battery_power_w=...)`.
- The callee's threshold check is `battery_power_w < -100` — assuming W.
- `-0.208 < -100` = False. Drain protection skipped.
- Latent since v4.2.17 when the protection was added; only exposed now because the user just changed the threshold from default 50% to 80% expecting the rule to fire.

## Fix

1. Add `BatteryStrategy.battery_power_w` property that reads the entity's `unit_of_measurement` attribute and multiplies by 1000 if kW. Always returns W (or None if unavailable).
2. Update `energy.py:1869` (EV drain) and `:1894` (smart plug drain) callsites to pass `self._battery.battery_power_w` instead of `self._battery.battery_power`.
3. Drain logic in `energy_pool.py` unchanged — the `< -100` (W) threshold is now correctly fed W.
4. `BatteryStrategy.battery_power` left as-is (still returns whatever-units, used by strategy sensor display for backward compat).

## Recommendation for QUALITY_CONTEXT.md

Add a new bug class:

**Bug Class candidate: "Unit-Mismatch Without UoM Check"**

Pattern: code reads a Home Assistant entity's `state` value and uses it in a numeric comparison without checking the entity's `unit_of_measurement` attribute. HA entities of the same `device_class` (e.g., `power`) can be in W, kW, mW depending on integration version or vendor. A threshold hardcoded for one unit silently fails when the entity is in another.

Detection rule: any code path that reads `state.state` for a numeric comparison should either (a) assert/normalize the UoM at the read site, or (b) read via a helper that normalizes (e.g., `battery_power_w` returning W regardless of source UoM).

Worth adding to `docs/QUALITY_CONTEXT.md`. Same shape was caught in v4.2.0 for `_get_net_power` (Emporia W vs Envoy kW) — fix there normalizes via UoM check at the read site. v4.2.17 missed applying the same pattern to `battery_power`.
