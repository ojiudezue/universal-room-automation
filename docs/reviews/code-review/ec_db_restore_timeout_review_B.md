## Cleared (holds because)
- **Task tracking / reload:** the reload path stores `task.cancel` on `_unsub_listeners`, and teardown cancels it (base.py:294-299). A cancel in the middle of a step lands in `wait_for`. `CancelledError` is a BaseException, so the `except Exception` in each restore lets it propagate (verified for accuracy, consumption, profiles, temp_regression). It does not get swallowed into a false "ok".
- **Parent reload during retry:** after cancel, the old instance can only finish closing its connection. Reads overlap safely under WAL. If `energy_baselines` was mid-write, close rolls back the uncommitted transaction.
- **Retry vs live ticks:** each retry restore does its awaited read first and then assigns state synchronously, so a tick cannot interleave partway through an assignment. `_reseed_cycle_after_boot` reads and then calls `reseed_cycle` synchronously (it adds today's in-memory accrual, energy_billing.py:582) and keys `_cycle_start_date`. The `peak_import` and `bill_forecast_ledger` guards prevent clobbering. `energy_baselines` save skips `sample_count == 0` (10696), so default baselines are not written over the DB before the retry.
- **Shutdown save:** the stop-save job and a concurrent retry use separate connections. busy_timeout serialises them, and the retry writes only during the baselines migration transaction.
- **Write queue:** the retry steps do not go through `_write_queue`. They use the same direct connections as at boot, so this branch adds no new queue interaction.
- **No-op path:** when nothing is skipped, `_schedule_restore_retry` returns early and no listener or task is registered.
