## DB Schema Integrity Trace

### `_create_table_safe` Isolation

`database.py:260-289` defines `_create_table_safe`. Behavior:
- Wraps statements in try/except.
- On success: commit + return True; `_last_table_error=None`.
- On failure: log error, store exception in `_last_table_error`, attempt rollback, return False.
- **Connection stays usable** — rollback restores transaction state.

`egress_state` block at `database.py:1098-1116`:
```python
if not await self._create_table_safe(db, "egress_state", [
    """CREATE TABLE IF NOT EXISTS egress_state (
        zone_id TEXT NOT NULL,
        state TEXT NOT NULL,
        ...
        PRIMARY KEY (zone_id)
    )""",
    """CREATE INDEX IF NOT EXISTS idx_egress_state_state
    ON egress_state(state)""",
]):
    failed_tables.append("egress_state")
```

**Cascade isolation: GOOD.** A CREATE failure on `egress_state` does NOT prevent `ac_ramp_events` (next table, line 1121) from creating. Mirrors the established `ac_reset_state` pattern.

### PRIMARY KEY discipline

PRIMARY KEY is `(zone_id)` — single column, not `(zone_id, date)` like `ac_reset_state`. This is per planner spec (egress is per-zone lifecycle, not daily counter). `INSERT OR REPLACE` semantics give upsert-by-zone — exactly what `save_egress_state` needs. Schema test `test_v478_db_egress_state_primary_key_zone_id_alone` extracts and asserts.

### Index coverage

Index is `egress_state(state)`. The `get_all_egress_state` DAO does `SELECT * FROM egress_state` — full table scan; index is unused there. The intent (per planner) was that future "in-flight scan" queries filter `WHERE state IN ('paused', 'counting', 'resume_countdown', 'cooldown')` — the index helps when there are many `idle` rows or post-prune residue. With one row per zone (~3 rows), the index is effectively decorative. Acceptable; not a defect.

### DAO write integrity (`save_egress_state`)

`database.py:5505-5538`. Uses `INSERT OR REPLACE` over all 11 columns. Caveats:
- `last_update_ts` falls back to `dt_util.now().isoformat()` if caller didn't supply (line 5534). All callers DO supply, so the fallback is defensive — fine.
- Wraps in try/except → graceful degrade on transient SQLite errors.
- Uses `self._db()` (write context) — appropriate for INSERT OR REPLACE.

### Schema fixture authority (Bug Class #44 boundary)

`test_v478_egress_db_schema.py:34-45` defines `_extract_ddl_for(table_name)` which regex-scans `database.py` for triple-quoted strings containing the CREATE TABLE / CREATE INDEX markers for the given table. The fixture is built from the EXTRACTED DDL, never hand-copied. Per Tier 2-DB doctrine, this satisfies "fixtures must extract from production source." **PASSES.**

The "cascade isolation" test (`test_v478_db_egress_state_create_failure_does_not_cascade`, line 189-197) only verifies the SOURCE CONTAINS the `_create_table_safe` call and `failed_tables.append` line. ## Detailed Findings

### B1 — HIGH — Bug Class #27 — `prune_stale_egress_state` not wired into nightly maintenance

**File:** `custom_components/universal_room_automation/__init__.py:811-822` AND `912-922`.

There are TWO `_cleanup_ops` lists (the primary path at L811 and the deferred path at L912 — both must list the new prune to be safe). Neither contains an `("egress_state", "prune_stale_egress_state", {...})` entry.

The DAO docstring at `database.py:5572-5575` explicitly claims:
> "Wired into the existing nightly maintenance hook (paired-cleanup per Bug Class #27)."

But no wiring exists. The DAO is callable from code but never scheduled. Mirror of the build report's flagged item.

**Real-world impact:**
- PK is `zone_id` → table bounded by zone count (~3 zones on this install). No unbounded growth.
- But `idle` rows are written defensively (the DAO docstring says they shouldn't exist; the rehydrate skips them) — if they ever get written by a future code change, they accumulate.
- More importantly: rows for **removed zones** (user deletes a zone via OptionsFlow) live in `egress_state` forever. The prune handles this case.
- Stale `paused` rows from a zone that was paused then deleted-from-config will rehydrate on every boot indefinitely, attempting to re-pause a non-existent zone. The `iter_canonical_hvac_zones` will silently not enumerate it, and the in-memory dict has an orphan entry. Minor leak.

**Severity:** HIGH because (a) planner explicitly required wiring, (b) docstring lies to future maintainers, (c) one-line fix.

**Suggested fix:**
```python
# In __init__.py, both _cleanup_ops lists (L811 + L912):
("egress_state", "prune_stale_egress_state", {"cutoff_days": 7}),
```

Append after `("anomaly_log", ...)` to preserve ordering convention.

### B2 — HIGH — Bug Class #14 / lifecycle — Number `_value` rehydrated AFTER EgressManager seeded

**Files:** `number.py:2010` (Threshold `__init__` reads from `entry.options`), `number.py:2034-2071` (Threshold `async_added_to_hass` calls `_push_to_coordinator()` on restore). Same shape in `HVACEgressResumeDelayNumber`.

**Sequence:**
1. `__init__.py:2043-2047` constructs `HVACCoordinator(... egress_threshold_min=cm_config.get("hvac_egress_threshold_min", 3))`. CM entry default = 3.
2. `HVACCoordinator.__init__` constructs `EgressManager(threshold_min=3)`.
3. Async setup runs, rehydrate runs, initial decision cycle runs at `await self._async_decision_cycle()` (`hvac.py:539`).
4. Number platform setup runs (independent timing — async parallel platform setup). `async_added_to_hass` calls `await self.async_get_last_state()` (line 2036) → restores the *user-configured* value, e.g., 5.
5. `_push_to_coordinator()` calls `hvac.egress_manager.set_threshold_min(5)`.

**The race:** Steps 3 (initial tick) and 4 (Number restore) can interleave. If the initial tick fires BEFORE the Number's restore push, the tick uses the seeded threshold (3) instead of the user's saved value (5). On HA, platform setup and integration setup are concurrent — there is no documented ordering guarantee that all platform restores complete before the integration's initial decision cycle.

**Real-world impact:** For one tick (5 min cycle), the threshold/resume_delay run at default values instead of user-saved values. Functional impact LOW; conceptual correctness concern HIGH because it violates the "RestoreEntity is canonical runtime store; entry.options seeds only" rule the project enforces elsewhere.

**Mitigation (one of):**
- Defer the initial decision cycle (`hvac.py:539`) until after `SIGNAL_HVAC_COORDINATOR_READY` has been processed by the Numbers (move it into a one-shot callback on the signal). The Numbers' deferred-restore branch (lines 2049-2070) already subscribes to this signal — they push when ready.
- Or: have `async_setup` re-read from `entry.options` AFTER the rehydrate (mirrors the seeding done in `__init__`) for the threshold/resume_delay so at least the saved-in-entry value is used. (Not as good — `entry.options` is the seed not the runtime store.)
- Cheapest acceptable fix: document that the first tick uses seeded values; entity-level RestoreEntity catches up on the next tick (≤5 min). Add a one-line comment near the initial-tick call.

### B3 — MEDIUM — Bug Class #5 / lifecycle — Master switch's deferred restore can flip `enabled` AFTER first tick already ran

**Files:** `hvac.py:539` (initial cycle) + `hvac.py:546-554` (signal dispatch) + `switch.py:3216-3260` (deferred restore handler).

**Sequence:**
1. `HVACCoordinator.__init__` seeds `egress_pause_enabled=True` (default).
2. `EgressManager.__init__` stores `_enabled=True`.
3. `async_setup` rehydrates, registers timer, then runs `await self._async_decision_cycle()`. First tick reads `enabled = bool(self._enabled)` → True.
4. After the initial cycle returns, `SIGNAL_HVAC_COORDINATOR_READY` is dispatched.
5. `HVACEgressWindowPauseSwitch._handle_hvac_ready` fires → reads `_deferred_value` (set in `async_added_to_hass` line 3231 when HVAC wasn't yet ready) → sets `hvac.egress_manager.enabled = self._deferred_value`.

If the user had the switch OFF before restart, the first tick may already have started pause-counting for an open egress window. Once the deferred restore lands, future ticks skip the pause logic (`enabled=False`), but the in-memory counters keep ticking until the disabled-path branch (line 361) clears them.

**Real impact:**
- If a window was already open at restart with switch=OFF, the first tick records `_egress_first_open_at[zone_id] = now`. Once switch flips OFF, line 364-367 clears the counter. No pause is engaged because `threshold_s` is 180+ seconds. Net: counter blip, no false pause.
- If the window has been open long enough to trigger pause on the first tick (e.g., R3 scenario rehydrated `_egress_first_open_at` from 2.5min ago, threshold=3min), the first tick could `_engage_pause` BEFORE the switch's restore lands. The switch then disabling does NOT auto-resume (per design). User sees an unexpected pause.

**Mitigation:** Same as B2 — defer the initial cycle to run on `SIGNAL_HVAC_COORDINATOR_READY`. Or: have `HVACEgressWindowPauseSwitch.async_added_to_hass` write directly to `egress_manager.enabled` synchronously when HVAC IS ready (line 3225 — already does), and ONLY defer when not. The current code does this. The race window is genuinely narrow but real. Document or fix.

### B4 — MEDIUM — Mixed tz primitives across modules

`hvac_zones.update_room_conditions` line 496: `now = dt_util.utcnow()` (used internally for timestamp on the data dict).
`hvac_egress.async_tick` line 310: `now = now or dt_util.now()` (local tz).
`hvac_egress._engage_pause` and friends: `dt_util.now()` throughout.

Both `dt_util.utcnow()` and `dt_util.now()` return tz-aware datetimes (per HA convention), so arithmetic between them works. But the convention split is fragile — a future refactor that compares a `utcnow`-derived timestamp to a `now`-derived one without paying attention could break.

**Mitigation:** Standardize on `dt_util.utcnow()` for all DB-bound timestamps + cross-module passing. Use `dt_util.now()` only for user-facing display strings. (Project-wide doctrine candidate — flag for QUALITY_CONTEXT.)

### B5 — MEDIUM — Empty preset on restore

`_engage_pause` reads `prior_preset = st.attributes.get("preset_mode") or ""`. Saves `""` if preset is missing. `_engage_resume` line 567: `if saved_preset:` skips restore for empty string. Correct for the case where the thermostat has no preset concept; correct for the case where pre-pause preset was empty. But it's also correct for "the attribute was present but its value was None" — those become "" too. The user can't distinguish.

**Real impact:** None today. Documented to ensure the next reviewer knows that "preset wasn't restored" can mean either "wasn't set originally" or "ha state was incomplete on capture."

### B6 — MEDIUM — `_safe_unsub` closure boundary

`number.py:2049-2070` (and parallel block at 2147-2168). The pattern:

```python
unsub_holder: list = []
unsubbed = [False]

def _safe_unsub() -> None:
    if unsubbed[0]:
        return
    if unsub_holder:
        unsubbed[0] = True
        unsub_holder[0]()

@callback
def _on_hvac_ready(*_a, **_kw):
    if self._push_to_coordinator() and unsub_holder and not unsubbed[0]:
        _safe_unsub()

unsub_holder.append(
    async_dispatcher_connect(self.hass, SIGNAL_HVAC_COORDINATOR_READY, _on_hvac_ready)
)
self.async_on_remove(_safe_unsub)
```

Walk-through:
- `_safe_unsub` registered BEFORE `unsub_holder` populated. If `async_on_remove` callback ever fires BEFORE `async_dispatcher_connect` returns (impossible in practice — `async_dispatcher_connect` is sync), `_safe_unsub` would find `unsub_holder == []` → no-op silently. Acceptable: signal subscription never happened in that hypothetical, so no leak.
- `unsubbed[0] = True` set BEFORE `unsub_holder[0]()` invoked. If `unsub_holder[0]` raises, `unsubbed` is already True → subsequent calls no-op. Good.
- If `_on_hvac_ready` fires and successfully calls `_safe_unsub`, then later removal fires `_safe_unsub` again → `unsubbed[0]` is True → no-op. Good.

Double-unsub guard works. No defect. **Documented only as boundary review.**

### B7 — LOW — `_handle_hvac_ready` and entity-lifecycle

`switch.py:3220-3260`. The `@callback` decorator marks the function as synchronous + event-loop-safe. It calls `self.async_write_ha_state()` directly — if the entity has been removed but the callback still fires (HA cleans up dispatcher subscriptions on `async_will_remove_from_hass` via `async_on_remove`), this would write state on a defunct entity. In practice safe because `async_on_remove(async_dispatcher_connect(...))` ensures the unsub fires before `async_write_ha_state` is called on a removed entity. **Code is correct; documented as a boundary trace.**
