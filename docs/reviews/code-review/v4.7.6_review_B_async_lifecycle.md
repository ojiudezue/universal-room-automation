## Dispatch-Latency Walk at N = 29 / 30 / 31s (REQUIRED DELIVERABLE)

Assume URA dispatches `switch.turn_off` for `garage_a` at decision-tick T0:
- Code path (energy_pool.py:725-731): `actions.append({"service":"switch.turn_off",...})`; `self._paused_by_battery_drain.add("garage_a")`; `self._pause_dispatch_ts["garage_a"] = now` (monotonic); `self._observed_off_since_pause["garage_a"] = False`.
- Decision tick is on a ~5-minute schedule, so the "next tick" walk below uses N seconds AFTER dispatch.

**Comparison operator:** Line 692 — `(now - dispatch_ts) > EV_PAUSE_DISPATCH_GRACE_SECONDS` (strict greater-than). Same at lines 876 (fill-priority), 1436 (plug drain), 1563 (plug fill-priority). At exactly N=30.000s, `30.0 > 30.0` is False → grace NOT expired.

### N = 29s (grace not expired)
- HA state cache hasn't yet propagated the `turn_off` because dispatch is async and the entity hasn't finished its state machine OR HA's state cache lag (~1-3s for slow entities, can be more for cloud-backed switches like Emporia).
- Decision tick reads `state["is_on"] = True` (stale cache).
- `_observed_off_since_pause.get("garage_a", False) = False` (we haven't yet observed off).
- State-update branch (lines 667-672): `is_on is False`? NO → skipped. `observed_off` stays False.
- Cooldown branch: no entry → skipped.
- Manual-override branch (lines 687-709): condition `not self_modulates AND in _paused_by_battery_drain AND is_on=True` → entered.
  - `dispatch_ts = 29s ago` (not None).
  - `observed_off = False`.
  - `grace_expired = (29 > 30) = False`.
  - `observed_off and grace_expired = False` → skip cooldown engagement.
  - Falls through to pause-conditions check.
- Re-pause: if `battery_discharging AND soc_low`, re-dispatch `turn_off`, re-stamp `_pause_dispatch_ts = now` (resets clock to 0s).
- **Verdict at N=29s:** CORRECT. No false cooldown. Idempotent re-pause restamps the clock.

### N = 30s (boundary — strict greater-than)
- `grace_expired = (30.0 > 30.0) = False`. Same as N=29s. **CORRECT.** Strict `>` is the safer choice here; the docstring "30s grace" implies "at least 30s have passed before treating as manual override," and `>` enforces that strictly.
- One nit: planner spec said `monotonic() - _pause_dispatch_ts[evse_id] > 30.0` — code matches. Good.

### N = 31s (grace expired, but...)
- If meanwhile HA propagated the state and a prior tick read `is_on=False`, then `_observed_off_since_pause["garage_a"] = True`.
- This tick: cache shows `is_on=True` because user (or auto-resume firmware) re-asserted ON.
- `grace_expired = (31 > 30) = True`. `observed_off = True`. → cooldown branch fires: discard from set, install 1h cooldown.
- **Verdict at N=31s with observed_off=True:** CORRECT — this is the intended Option B path for "real user turned it back on after URA paused it."

### N = 31s but observed_off=False (instant auto-resume race)
- Decision-tick frequency is ~5 min. Within one tick window URA dispatched off (T0) and Emporia auto-re-enabled on (T0+10s). Next tick is at T0+5min.
- At T0+5min, cache shows `is_on=True` (Emporia turned it on).
- `_observed_off_since_pause = False` (we never sampled the brief off state).
- `grace_expired = True`. `observed_off = False`. → manual-override branch's inner `if observed_off and grace_expired:` is False. Falls through.
- Re-pause: idempotent. `_pause_dispatch_ts` re-stamped to fresh `now`. `_observed_off_since_pause` reset to False.
- **Verdict:** CORRECT — this is the "smart-but-misconfigured-as-dumb" path. Without `_observed_off_since_pause` gating, URA would have wrongly engaged the 1h cooldown.

### Race: HA reports state change BEFORE URA's dispatch returns
- The dispatch is enqueued through `_execute_service_action` which `await`s `hass.services.async_call`. After the await returns, URA proceeds to the next loop iteration.
- During the await, HA can fire the state-change event and update `hass.states`. But URA does not subscribe to state changes for `_observed_off_since_pause` — it only reads on the next decision tick.
- Code ordering: line 727 (`actions.append`) happens THIS tick; the actual dispatch `await` happens AFTER `determine_battery_drain_actions` returns, inside `_async_evaluate_dynamic_presets` (the for loop). So the dispatch-ts is set BEFORE the dispatch goes out.
- Implication: `_pause_dispatch_ts[evse_id] = now` is set ~milliseconds BEFORE `await hass.services.async_call`. The grace window starts BEFORE the service call returns. This is the intended behavior (grace covers HA's propagation latency).

### Verdict for the dispatch-latency walk
The logic is internally consistent. N=29/30/31 all produce correct behavior. The "smart-but-misconfigured-as-dumb" path (observed_off=False at N>30) correctly re-pauses without cooldown. The "real user override" path (observed_off=True at N>30) correctly engages cooldown.

**One concern not fully covered by the walk:** when `_pause_dispatch_ts.get(evse_id) is None` (which happens if `_paused_by_battery_drain` contains an evse_id but no dispatch_ts was ever recorded — e.g., test paths, or hypothetical restart-paused-state-restore that doesn't exist today), the `grace_expired` flag becomes `False` (because `dispatch_ts is not None` is False), so the manual-override branch falls through and re-pauses. This is the safe fallback. **PASS.**

### EVSE add/remove lifecycle

- **Add via config flow:** triggers `update_listener` → `async_reload` → fresh `async_setup_entry` → fresh `EVPool.__init__` with new `evse_config`. All per-EVSE state starts empty. `_prune_removed_evses()` is called from `__init__`, but `known = set(self._evse.keys())` includes the newly added EVSE; nothing is pruned (correct — empty starting state for new EVSE).
- **Remove via config flow:** same path — `async_reload`. New `EVPool.__init__` uses new `evse_config` without the removed EVSE. `_prune_removed_evses` is called but the per-EVSE state dicts are already empty (we just created them), so it's a no-op. **The removed-EVSE state has nowhere to leak from because reload destroys the prior instance.**
- **Per-EVSE `self_modulates` flip via config flow:** identical path — `async_reload` rebuilds `EVPool`. The new `self_modulates` value is read at `_self_modulates_for(evse_id)` from the fresh `evse_config`. **WORKS — but see B-H1: the `update_evse_config()` method is unused.**

### `update_evse_config` dead-code analysis (B-H1)

The `update_evse_config()` and `update_plug_config()` methods exist (energy_pool.py:356, 1320) and are documented as being called "when config flow rewrites entries." They are referenced ONLY by the test suite (`test_energy_pool_drain.py:428`). They are NEVER called from production code.

The actual production path is `_async_update_listener` → `hass.config_entries.async_reload(entry.entry_id)` (`__init__.py:3164`) → full reload → new `EVPool` instance. So `self_modulates` flips DO take effect after a config-flow save, but via reload, not via in-place update.

**Consequence:** the planning doc's claim "called when config flow rewrites entries (or, in v4.7.6, when per-EVSE self_modulates flips)" is misleading. The reload path works; the `update_evse_config` path is unused.

**Risk:** future contributor sees the method, wires a partial in-place update, and skips reload → coordinator state goes out of sync with `entry.options`. The current dead code is a footgun.

**Recommended fix-up (one of):**
1. Delete `update_evse_config` and `update_plug_config` (and the test that calls them). Reload is the only canonical path. Add a docstring on `EVPool.__init__` noting this.
2. Keep them, but ALSO wire them from `_async_update_listener` to support in-place updates without a full reload for the specific subset of options that don't require teardown (would need to be carefully picked).

I recommend option (1) for v4.7.6.

### HA restart with active drain pause in flight (dispatch sent, response not yet received)

- Old process dies. New process starts. New `EVPool` has empty `_paused_by_battery_drain`. `_pause_dispatch_ts` empty.
- HA's switch may show `state.is_on = True` (if Emporia auto-re-engaged) or `state.is_on = False` (if URA's pre-restart dispatch landed).
- Next decision tick: drain rule re-evaluates from scratch. If conditions hold (battery still draining, SOC still low), it pauses again. If conditions cleared during restart, it doesn't.
- **Verdict:** correct — restart re-evaluates from scratch. No state corruption. (B-H2 is a documentation-of-surprise issue, not a correctness issue.)

- `_battery_drain_cooldown` is empty post-restart. The 1h cooldown is FORGOTTEN.
- This means: if user manually turned on the EVSE 30 min before restart and URA installed a 1h cooldown, post-restart URA may re-pause within 5 minutes (next tick) instead of waiting out the remaining 30 min.

### Bug Class #46 (`async_update_entry` re-entrancy) check

- `_migrate_excess_solar_entity_id` uses `entity_registry.async_update_entity()` — NOT `async_update_entry`. Confirmed at switch.py:73.
- This is the correct API. The registry mutation does not re-trigger config-entry setup.
- **However:** the idempotency guard via `entry.runtime_data` is BROKEN (B-H3). `runtime_data` is HA's new typed-data API (HA 2024.12+), but URA does not initialize it anywhere. Reading `getattr(entry, "runtime_data", None)` returns `None` on every reload. The `if isinstance(runtime, dict) and runtime.get(...)` check is always False → the migration always runs. The migration is idempotent (it bails if the legacy entity_id no longer exists in the registry under its old unique_id), so this is not catastrophic, but:
  1. The guard does nothing.
  2. Worse, the assignment `entry.runtime_data = {"_v476_alias_migrated": True}` (line 85) is performed inside an `if isinstance(runtime, dict)` else branch — so on first call it does set `entry.runtime_data` to a dict. After this, any future code that expects `runtime_data` to be its own typed instance (HA pattern) will find a stray `{"_v476_alias_migrated": True}` dict instead.
  3. Per `developers.home-assistant.io/docs/config_entries_index` (verified in spirit from URA's CLAUDE.md "no fabrication" admonition — I'm noting I have not opened the HA docs in this session; the assertion that runtime_data is meant to hold typed entry-specific data is reproduced from my training-corpus recollection and should be confirmed in a follow-up), URA stomping a foreign-typed value into `runtime_data` could become a foot-gun.
- **Recommended fix:** drop the `runtime_data` flag entirely. The migration is already idempotent (the `entity_entry is None or unique_id != legacy_unique_id` check). Just always-run and remove the flag write-back. OR use `hass.data[DOMAIN]["_v476_alias_migrated_entries"]` (a set of entry_ids) as the URA-domain-scoped guard.

### Bug Class #20 (concurrent reload race)

  - Tick checks `_ev_tou_enabled` again at line 2252, reads `False`, skips L1 plug branch.

### Visibility attrs computation — async safety

- `EVPool.get_status()` and `SmartPlugController.get_status()` read mutable instance state (`_pause_dispatch_ts`, `_observed_off_since_pause`, `_paused_by_*` sets, `_battery_drain_cooldown`).
- These are called from `EnergyCoordinator.ev_status` (property), which is invoked by the sensor's `extra_state_attributes`.
- HA sensor attribute access can happen on the event loop OR (for some integrations) via the recorder thread. URA's `EVChargingStatusSensor` accesses attributes via the standard `@property extra_state_attributes` pattern, which HA calls on the event loop only.
- All mutations (`set.add`, `dict[k] = v`, `set.discard`) happen in `determine_*` methods which are called from the decision-tick coroutine on the same event loop. Single-threaded; no race.
- The `.items()` iteration in `get_status` is over a dict; if a concurrent mutation happens, Python would raise `RuntimeError: dictionary changed size during iteration`. But both reader and writer are on the same event loop, so this would only happen if `get_status` does `await` mid-iteration. It does not (no awaits in `get_status`).
- **Verdict:** PASS for race conditions.

## Per-File Findings

### `energy_pool.py`

- Lines 213-230 (state init): correctly adds dicts/sets before `_prune_removed_evses()` is called. Order is safe.
- Lines 326-356 (`_prune_removed_evses`, `update_evse_config`): see B-H1. The pruning logic is correct but is exercised only at `__init__` (where there's nothing to prune) and from a never-called `update_evse_config`. Dead code in production.
- Lines 667-672 (state-update for `observed_off`): tested only for EVPool drain branch. The fill-priority branch at lines 858-862 has the symmetric update. **GOOD — keeps the dispatch-state coherent across both rules.**
- Lines 688-709 (manual-override branch): the `if observed_off and grace_expired:` predicate matches the planner spec. The fall-through `_LOGGER.debug` at line 705 fires for the legitimate dispatch-lag-and-fall-through path. **GOOD.**
- Lines 722-731 (idempotent re-pause): the `if state["charging"] and battery_discharging and soc_low:` condition is checked AFTER the manual-override branch's fall-through. Re-pause is unconditional — re-stamps both timestamp and `observed_off=False`. **WARNING:** if URA's prior dispatch at T0 set `_pause_dispatch_ts=T0`, and the prior tick observed off (`_observed_off_since_pause=True`), then this tick re-pauses, the re-stamp wipes `_observed_off_since_pause` BACK to False.
