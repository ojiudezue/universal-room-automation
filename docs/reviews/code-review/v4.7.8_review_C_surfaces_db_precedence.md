## C-H1 — HIGH: DPM `_async_apply_preset_overrides` does not skip egress-paused zones

**File:** `custom_components/universal_room_automation/domain_coordinators/hvac.py:985-1090`
**Bug class:** Cross-rule precedence violation (per Plan §D8)

### Finding

Plan §D8 precedence matrix declared explicitly:

> **DPM range update — SUPPRESSED while zone paused.** Don't apply ranges to an off compressor.

The build added `is_paused()` guards in three places:
1. `hvac.py:753` (`_apply_house_state_presets` "ensure thermostats active" loop) — correctly skips.
2. `hvac.py:805` (`_apply_house_state_presets` preset-iteration loop) — correctly skips.
3. `hvac_override.py:943` (`check_ac_reset`) — correctly skips.
4. `hvac_predict.py:504, 647` (predictor pre-cool / pre-heat) — correctly skips.

But the DPM apply path itself — `_async_apply_preset_overrides` at `hvac.py:985`, called from `hvac.py:983` after the preset loop — iterates `self._zone_manager.zones.items()` at line 1028 with **no `is_paused()` check**, and dispatches `climate.set_temperature` at line 1059. While the zone is in egress pause (`hvac_mode=off`), DPM will keep re-emitting `set_temperature` calls every 5-minute tick. Some thermostat firmwares (Ecobee notably) re-engage mode when receiving target-temp updates after an explicit `off`, which would silently defeat the pause.

The cycle's test for this (`test_v478_paused_zone_skipped_in_dpm_apply` at `quality/tests/test_v478_egress_window.py:756`) inspects `hvac_predict.py` instead of `hvac.py:_async_apply_preset_overrides`, so it passes despite the real DPM apply being unguarded. The test name is misleading — it covers the predictor (pre-cool/pre-heat), not the v4.7.1 DPM `OverrideEngine.set_temperature` apply.

### Recommendation

Add to the `_async_apply_preset_overrides` per-zone loop at `hvac.py:1028`:

```python
for zone_id, zone in self._zone_manager.zones.items():
    # v4.7.8 D8: Skip DPM apply for egress-paused zones.
    if self._egress_manager.is_paused(zone_id):
        continue
    zone_overrides = all_overrides.get(zone_id, [])
    ...
```

Update `test_v478_paused_zone_skipped_in_dpm_apply` to ALSO verify the guard exists in `hvac.py`, e.g.:

```python
def test_v478_paused_zone_skipped_in_dpm_apply(hvac_src, predict_src):
    # Predictor pre-cool/pre-heat: already guarded.
    assert "def set_egress_manager(self, egress_manager)" in predict_src
    # DPM OverrideEngine apply also needs the guard.
    apply_start = hvac_src.find("async def _async_apply_preset_overrides")
    apply_end = hvac_src.find("async def ", apply_start + 1)
    apply_body = hvac_src[apply_start:apply_end]
    assert "self._egress_manager.is_paused(zone_id)" in apply_body
```

## C-H2 — HIGH: `prune_stale_egress_state` is dead code (no schedule wiring)

**File:** `custom_components/universal_room_automation/__init__.py:811-821, 912-922`
**Bug class:** #27 (orphaned cleanup) — every INSERT table must have a paired cleanup that is actually scheduled.

### Finding

Plan §D4 explicitly required:

> `prune_stale_egress_state` runs from the existing nightly maintenance hook (Bug Class #27 — every INSERT table must have a paired cleanup that is actually scheduled). The prune deletes rows in state = 'idle' (defensive) and rows where `last_update_ts < now - cutoff_days`.

The DAO is implemented (`database.py:5560`) and tested behaviorally, but the method name is **not** added to either of the nightly-maintenance `_cleanup_ops` lists:

- `__init__.py:811-821` (primary maintenance path)
- `__init__.py:912-922` (deferred maintenance path — same race-recovery shape)

Result: `prune_stale_egress_state` is never called by the running integration. Rows accumulate in `egress_state` under three realistic failure modes:

1. HA crashes while a zone is in `cooldown` state — cooldown sweep at `hvac_egress.py:319-324` never runs to clear the row.
2. User disables `is_egress_window` for a room mid-pause — the disabled-path at `hvac_egress.py:360-368` clears in-memory state but does NOT write to the DB, leaving the `counting` row stale (separate LOW finding C-L4).
3. Zone is removed from canonical iteration (zone-manager reconfigure) — row never gets `clear_egress_state()`.

### Recommendation

Add to BOTH `_cleanup_ops` lists in `__init__.py`:

```python
("egress_state", "prune_stale_egress_state", {"cutoff_days": 7}),
```

Place it adjacent to `("ac_reset_state", "cleanup_ac_reset_state", ...)` if that entry exists; otherwise at the end of the list. The list order doesn't matter functionally (the rotating `_nightly_start_idx` gives every entry fair access), but co-locating with the closest sibling (`ac_reset_state`) keeps the list scannable.

Add a regression test in `test_v478_egress_window.py`:

```python
def test_v478_prune_egress_state_wired_into_nightly_maintenance():
    src = _read(os.path.join(ROOT_REL, "__init__.py"))
    assert src.count('"prune_stale_egress_state"') >= 2, \
        "prune must be in both _cleanup_ops + _cleanup_ops_d"
```

## C-M2 — MEDIUM: `RoomEgressWindowOpenSensor` diverges from `UniversalRoomEntity` pattern

**File:** `custom_components/universal_room_automation/binary_sensor.py:2071-2185`
**Bug class:** Device-info pattern divergence

### Finding

Every other room-bound binary sensor in `binary_sensor.py` inherits from `UniversalRoomEntity` (lines 179, 382, 398, 417, 432, 453, 477, 504, 539, 574, 698, 735). `RoomEgressWindowOpenSensor` (added line ~2071) does NOT inherit from it — it inherits from `BinarySensorEntity` directly and:

1. Hand-rolls the `_attr_unique_id` (`f"{DOMAIN}_room_{slug}_egress_window_open"`) instead of using the coordinator helper.
2. Overrides `device_info` as a `@property` returning a plain dict, rather than setting `_attr_device_info = DeviceInfo(...)` in `__init__`.
3. Bypasses the base entity's name-prefixing, `available` chain, and `extra_state_attributes` chain.

- Naming: `_attr_has_entity_name = True` is not set, so `_attr_name = "Egress Window Open"` will display as a bare entity name (not "Room Name Egress Window Open").
- The room-slug for `unique_id` comes from `entry.data.get("room_name", "unknown")` and is lowered + space-replaced. Other UniversalRoomEntity entities get their unique_id from `entity_id`-shaped slugs computed centrally — drift is possible if room renames happen.

### Recommendation

Either:

(a) Refactor to inherit `UniversalRoomEntity`:

```python
class RoomEgressWindowOpenSensor(UniversalRoomEntity, BinarySensorEntity):

    _attr_icon = "mdi:window-open-variant"

    _attr_has_entity_name = True
    _attr_name = "Egress Window Open"

    def __init__(self, coordinator):
        super().__init__(coordinator)
        self._attr_unique_id = f"{coordinator.entry.entry_id}_egress_window_open"
        ...
```

(b) Document explicitly why the pattern diverges, and add a regression-test in `test_v478_egress_window.py` that asserts the entity lands on the correct per-room device.

Option (a) is preferred — it's the same line-count and avoids latent device-association drift.

### Finding

The per-canonical-zone egress sensor (`HVACZoneEgressWindowOpenSensor`) is enumerated inside `async_setup_entry` for the CM entry path:

try:

### Recommendation

## C-L1 — LOW: NM dedup key uses local-date midnight rollover

**File:** `custom_components/universal_room_automation/domain_coordinators/hvac_egress.py:615-619`

### Finding

The build report flagged this; framing item #7 asked me to explicitly assess.

Scenario:

1. 23:55 local — zone enters paused state. `_maybe_dispatch_nm("egress_paused")` fires.
   - `today = now.date().isoformat()` = `"2026-05-30"`.
   - `_nm_emitted_today[(zone_id, "egress_paused")] = "2026-05-30"`. Notification fires.
2. 00:02 — user closes window. Resume countdown starts.
3. 00:05 — resume fires. Notification "Upstairs HVAC resumed" goes out (no dedup hit).
4. 00:10 — user re-opens window. After 3 min, pause fires again.
   - `today = "2026-05-31"` (different day).
   - `_nm_emitted_today.get((zone_id, "egress_paused"))` is `"2026-05-30"` — mismatch.
   - Notification fires a second time, ~15 minutes apart.

User receives "Upstairs HVAC paused" twice in under 20 minutes for what is functionally one egress event spanning midnight. Annoying but not data-corrupting.

### Recommendation

Either:

(a) Use a sliding 4-hour dedup window instead of date-bucket:
```python
last_emit = self._nm_emitted_today.get(key)
if last_emit and (now - last_emit).total_seconds() < 4 * 3600:
    return
self._nm_emitted_today[key] = now  # datetime, not str
```

(b) Document this as a known minor issue and ship.

Per build report: severity LOW. Per my framing: LOW — confirmed.

## C-L2 — LOW: Cooldown expiry → immediate re-counting flap possible

**File:** `custom_components/universal_room_automation/domain_coordinators/hvac_egress.py:320, 410`

### Finding

The cooldown sweep at line 320 runs BEFORE the per-zone loop. If a zone exits cooldown on a given tick AND an egress window is still open, the per-zone loop at line 410 immediately starts a fresh `_egress_first_open_at[zone_id]` count. Within `threshold_s` after cooldown expiry, the zone will re-pause.

If the user manually overrode at 12:00 and didn't close the window, then walked away — at 13:00 cooldown expires, at 13:03 zone is paused again (assuming default 3-min threshold). The user comes back at 14:00 to find HVAC paused again. Behavior is per-spec, but worth flagging because the original manual override implied "user wants HVAC on for this window-open condition."

### Recommendation

No code change required — behavior is per Plan §D8. Consider documenting in the live-validation §11 expectation that "after cooldown expires + window still open → URA will re-pause."

def _extract_ddl_for(table_name: str) -> list[str]:
    src = _read_source()                                   # reads database.py
    triple_pattern = re.compile(r'"""(.*?)"""', re.DOTALL)
    table_marker = f"CREATE TABLE IF NOT EXISTS {table_name}"
    index_marker = f"ON {table_name}("
    for m in triple_pattern.finditer(src):
        stmt = m.group(1).strip()
        if table_marker in stmt or index_marker in stmt:
