## State machine, flap, cadence

- **No intra-day flap.** The latch is written only by the walk (`presence.py:6334`, plus the press at `:6405`). The walk is scheduled once per newly completed night (`_maybe_schedule_guest_stay_refresh`, `:6123`) or after the 900 s error backoff (`:6125-6127`). The veto adds no trigger.
- **No day-to-day toggle from the veto alone.** Past `idx` decisions read only fixed past windows. The day paired with night j is the completed day BEFORE night j (`days[j]`, `:6176`), and today's partial day is never read. So the walk agrees with yesterday's walk over the shared span. A veto-held stay ends monotonically once x consecutive paired days read < 0.10. An off -> on edge still needs a qualifying night.
- **Precedence.** The veto is ANDed into the exit only (`:6323-6327`). It cannot affect entry, grace entry, `n`, or the press. The no-filter press proof in Review A holds; I re-traced it against `_after_press` (`:6262-6263`) and the `q` count (`:6290-6293`).
- **Cadence / DB cost.** No new DB read and no new state. The day fractions come from the same span call (`:6183-6187`). Added CPU is O(x * guest rooms) per walked night. That is negligible once per day.
- **Kill switch.** `veto_min = 2.0` when not scaled (`:6269-6272`) and fractions are at most 1.0, so off is byte-identical.

## Restart

- Deterministic in DB contents + the stored press (`_guest_left_load`, `:6366-6389`). No new RAM state, so a restart reproduces the verdict (`test_day_veto_restart_same_verdict`).
- D4's RAM `_guest_stay_long_nm_fired` re-pages at most once per restart-day. Unchanged and accepted.
- The DB-error path keeps the prior latch (`:6200-6203`). A vetoed stay therefore survives a transient error exactly as a normal one does.

## Findings

**LOW-1 (Bug class: horizon-dependent verdict / hidden discharge; extends Review A LOW-1), `presence.py:6169-6170`, `:6241`, `:6254`, `:6296-6303`.** The walk starts with the latch False at the replay horizon, and it starts with `ended_on = None`. Before the veto, a span of empty nights longer than 2 could not sit inside a stay. Now a veto-held span of empty-night/high-day nights can be arbitrarily long. When the original entry night slides past the horizon, the walk can no longer enter that stay. It then also loses the `ended_on` anchor, which a later grace re-entry depended on. Legal repro: entry at night S; days high, nights empty for 25 nights (vetoed); stay ends at E = S+27; grace re-entry at R = E+3 on a night with day < 0.10 (guest out all day, sleeps in the room). About 6 nights later S leaves the 35-night window. The walk then sees no ended stay, so R has no grace and fails the day test, and the latch drops with no new evidence. A restart is still deterministic, but the day-to-day verdict changes. This needs a phantom-shaped daytime hold to reach, the D4 page at 28 days fires first, and the result fails toward no GUEST. Fix: document the horizon as the effective release for a veto-only hold, in the same sentence Review A LOW-1 asks for. No code change.

**LOW-2 (observability, "diagnose on ground truth"), `presence.py:6336-6346`; README L3.** Nothing published says that a veto is what is holding the latch. `guest_stay_basis[*].day_fraction` is the day fraction of the room with the highest NIGHT fraction (`:6235-6237`), but the veto reads ANY guest room (`:6281-6284`). On a vetoed morning the basis can show `day_fraction < 0.10` for every listed night while the other room's day holds the stay. README L3 says "or the other guest room", but that room's value is not on the entity, so L3 can only be checked against the DB. The stated residual (phantom daytime hold) is exactly what an operator will need to tell apart from a real guest. Fix (small, in-cycle per the fix-LOWs rule): add `exit_vetoed: bool` (and the vetoing room) to the walk output, e.g. a `guest_stay_exit_veto` attribute or a per-row `day_veto_room`, plus one INFO line when the veto blocks an exit that would otherwise fire.

**LOW-3 (ripple naming), README "Residual".** The residual lists only the GUEST hold. A veto-extended or phantom-held stay also (a) keeps exterior-person NM severity at the GUEST row (MEDIUM, delivered nowhere) for perimeter approach / first_sighting cases that are HIGH in HOME_DAY with no resident home (`const.py:2846-2851` vs `:2877-2883`), (b) re-arms security ARMED_HOME each morning when auto-follow is on, and (c) pauses Bayesian learning / dwell-anomaly evaluation. All of these are pre-existing GUEST semantics; only the exposure grows. Fix: one README sentence naming the consumers. No code change.
