## Findings

### MEDIUM-1 — Stale planning/code-comment line citation; precedent is at line 897, not 1502
**Location:** `hvac.py:917-918` (comment); planning doc section 2.
**Description:** Both the in-source comment and the planning doc cite `hvac.py:1502` as the "duty-cycle / D6 stale-failsafe sleep-skip pattern." Line 1502 is actually the assignment `self._last_runtime_accumulation = now` inside `_accumulate_zone_runtime` — a window-reset line, not a sleep skip. The real D5 sleep-skip is at **line 897**: `if zone.runtime_exceeded and self._house_state != "sleep":`. The D6 stale-failsafe sleep-skip is at line 865 (`and self._house_state != "sleep"`). This is the "no fabrication" rule from CLAUDE.md: comments referencing concrete file:line citations must be verified. A reader following the citation hits dead code.
**Bug class:** No-fabrication discipline (project rule, not a numbered class).
**Fix:** Update the comment in `hvac.py:917-918` to cite the real precedents: lines 865 + 897. Update planning doc section 2 line 55 similarly.
**Must fix pre-deploy:** Yes (cheap doc fix, prevents future readers from chasing a phantom precedent).

### MEDIUM-2 — D1 fallback uses private `_zone_manager` traversal across coordinator boundary; brittle to refactor and to boot-order race (Bug Class #5 surface)
**Location:** `aggregation.py:3221-3225` (`_sleep_person_fallback_occupied`).
**Description:** The fallback reaches across coordinator boundary into private state:
```python
hvac = manager.coordinators.get("hvac") ...
zone = hvac._zone_manager.zones.get(self.zone)
zone_persons = getattr(zone, "zone_persons", None) or []
```
This has two real-world risks:
1. **Bug Class #5 (deferred restore via signal):** If `ZoneAnyoneBinarySensor.is_on` is read after `coordinator_manager` exists but the HVAC coordinator hasn't yet finished its first refresh (boot race window), `hvac` is non-None but `hvac._zone_manager.zones` may be empty. `zone is None` → returns False → falls back to Layer 1 only. **During the boot-race window at 3am while degraded sensors are off, this means the fallback silently fails** — exactly the wrong fallback. The try/except masks the error case silently.
2. **Private-attribute coupling:** `_zone_manager` is a single-underscore private. If a future refactor renames or moves it (very plausible — Tier 2 zone-manager refactor is a known direction), the fallback returns False with only a DEBUG-level log. Silent regression.

**Bug class:** Touches #5 (deferred restore) and #26 (in-memory reads of public surface preferred).
**Fix (recommended, not blocking):** Add a public accessor like `manager.get_zone(zone_name)` or `manager.get_zone_persons(zone_name) -> list[str]`, and have D1 call that. Keeps the boot-race semantics explicit and decouples from the private name.
**Fix (cheap interim, must-do):** Promote the silent-fail DEBUG to a one-shot WARN logged at most once per boot, so a stuck fallback during overnight degradation gets surfaced in logs the next morning.
**Must fix pre-deploy:** The interim one-shot WARN. The public accessor can defer.

### LOW-1 — `person.state` comparison hardcoded to `"home"`; misses zone-arrival edge state and may treat boot-time `"unknown"` as not-home
**Location:** `aggregation.py:3222`, `hvac.py:927`, `hvac_fans.py:353`.
**Description:** All three locations compare `state.state == "home"`. HA `person` entity state can be `"home"`, `"not_home"`, `"unknown"`, `"unavailable"`, or the name of a configured HA `zone.*` (e.g., `"work"`, `"gym"`). For this cycle's intent — "is the person physically here, asleep" — `"home"` is the correct positive. But `"unknown"` and `"unavailable"` during a stale Bluetooth/GPS reading mid-night would NOT match, so the fallback silently fails. This is arguably correct (don't fabricate occupancy from unknowns), but worth a comment so future readers don't "fix" this and break the safety property.
**Bug class:** #22 (enum mismatch, weak form).
**Fix:** Add a one-line comment at each comparison site: `# Strict "home" only — unknown/unavailable intentionally not trusted.`
**Defer:** Yes — behavior is correct, this is doc-only.

### LOW-2 — D3 indefinite hold ignores `room_fan.speed_pct == 0`; could hold an "off-speed" fan as on
**Location:** `hvac_fans.py:359` — `return True, room_fan.trigger, room_fan.speed_pct`.
**Description:** If the fan was already turned down to 0% speed at vacancy-hold entry (some prior tick set speed_pct to 0 but is_on stayed True), the D3 branch returns `(True, "", 0)` style — holding "on at speed 0". Downstream service-call logic for fans treats speed=0 as off in some integrations, on at minimum in others. The vacancy-hold semantics for the indefinite-hold-during-sleep should likely floor to the prior on-speed, not 0.
**Bug class:** None — edge-case correctness.
**Fix:** Either (a) guard `if room_fan.speed_pct > 0:` before the return, falling through to normal expiry if speed=0; or (b) floor to a small minimum (e.g., 20%) when entering indefinite hold. Likely (a) is safest — don't transmit zero-speed RF.
**Defer:** Yes, low real-world risk (vacancy state implies the fan was at a non-zero hold speed when it became vacant).

### LOW-3 — Test fixture authority weakness for D1: helper is `exec()`'d from source rather than imported (Bug Class #44 partial)
**Location:** `test_v4713_sleep_state_zone_presence_trust.py:193-225` (`_invoke_fallback`).
**Description:** The behavioral D1 tests parse `aggregation.py`, extract the helper function via AST, `exec()` it in an isolated namespace, then invoke. This DRIVES the production source text — better than re-coding the logic in the test — but it does NOT drive the production import / class binding. A regression that renames the helper, changes its method signature, or moves it to a different class would still pass these tests as long as the function body parses.
Trade-off: the D3 tests properly import `FanController` (the gold-standard pattern per Bug Class #44). D1/D2 tests fall back to AST-extract + exec because the full aggregation.py import requires a heavier HA mock harness.
**Bug class:** #44 (test fixture authority — partial compliance).
**Fix:** Add at least one test that imports `ZoneAnyoneBinarySensor` from the production module under the heavy mock harness already established for D3, and calls `instance._sleep_person_fallback_occupied()` directly. This would catch a missed binding regression.
**Defer:** Yes for v4.7.13; track as test-infra hardening backlog. Current tests are net additive over zero.

### NIT-1 — D2 `home_persons = []` then loop-append-then-check
**Location:** `hvac.py:923-935`.
**Description:** Build a list to check non-empty. Idiomatic Python is `any(...)`. The list serves dual purpose (logging the matching entities), so keep — but reset to `[]` inside the except is redundant since it's already `[]`. Cosmetic.
**Fix:** Optional. Drop the `home_persons = []` in the except branch.

### NIT-2 — D1 `_LOGGER.info` may be noisy at INFO level
**Location:** `aggregation.py:3231-3234`.
**Description:** Logging "sleep-state person fallback engaged" at INFO every refresh tick (default 30s) for every active fallback zone would generate ~2 messages/min × 8h sleep × N zones each night. Even one zone produces ~960 lines/night. The first-engagement-only or once-per-zone-state-transition would be more idiomatic.
**Fix:** Either (a) change to DEBUG; or (b) gate to log only on transition from "not engaged" to "engaged." (b) requires per-instance state.
**Defer:** Yes — verify in first-night live validation; downgrade in a follow-up patch if confirmed noisy.
