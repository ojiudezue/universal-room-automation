# v4.6.15 Thread-Safety Hotfix -- Review A: Correctness + Thread-Safety Integrity

**Reviewer:** A (Correctness + thread-safety framing)
**Cycle:** v4.6.15 -- Scheduler callback thread-safety hotfix
**Date:** 2026-05-26
**Baseline tag:** `pre-review-v4.6.15-threadsafety`
**Verdict:** PASS WITH FIXES (2 CRITICAL, 1 HIGH, 1 MEDIUM -- all addressable before deploy)

## Summary

The v4.6.15 fix addresses 5 sites where `lambda _now: self.hass.async_create_task(self._async_refresh())` was passed to HA scheduler helpers (`async_track_time_interval`, `async_track_time_change`). HA's frame helper flagged these 18 times per boot as "calls async_create_task from a thread other than the event loop". The fix replaces each lambda with either the bound coroutine method directly (sensor.py) or a `functools.partial`-wrapped coroutine method (notification_manager.py), and adds a `_now=None` parameter to absorb the datetime argument HA passes to timer callbacks.

The 5 targeted fixes are **mechanically correct** for the scheduler callback sites. However, the review surfaces 2 CRITICAL findings: (1) the identical `_handle_db_ready` pattern using `async_create_task` remains unfixed in 2 of the 3 changed sensors, and (2) three additional sensors elsewhere in sensor.py use `async_create_task` in their `_refresh_pending` follow-up path, which runs inside a `finally` block after the refresh -- this is on the event loop and is safe per se, but the `_handle_db_ready` sites in the fixed sensors are inconsistent with the established `hass.add_job` pattern used by the v4.6.3.2-era sensors.

## Findings

### CRITICAL-A1: `_handle_db_ready` in CoordinatorOverrideFrequencySensor and CoordinatorComplianceRateSensor still uses `async_create_task`

**Location:** `sensor.py:11425-11426` (OverrideFrequency), `sensor.py:11551-11552` (ComplianceRate)

**Bug class:** #42 (proposed: Lambda/async_create_task in Scheduler or Dispatcher Callback)

**Description:**
The two sensors that were fixed for the `async_track_time_interval` callback retain a `_handle_db_ready` inner function that calls `self.hass.async_create_task(self._async_refresh())`. This is a sync function registered via `async_dispatcher_connect` to `SIGNAL_DATABASE_READY`.

While `SIGNAL_DATABASE_READY` is dispatched from `async_setup_entry` (confirmed at `__init__.py:766` and `__init__.py:2378`), which runs on the event loop, this is still fragile: if the signal dispatch site ever moves to a worker thread, the same frame-helper warning will reappear. More importantly, it is **inconsistent** with the established fix pattern from v4.6.3.2, where the equivalent `_handle_db_ready` in `URARecentAnomaliesSensor` (sensor.py:10818-10819) and `CoordinatorDecisionsTodaySensor` (sensor.py:11308-11309) and `CoordinatorLastDecisionSensor` (sensor.py:11782-11783) all use `self.hass.add_job(self._async_refresh())` -- which is thread-safe regardless of calling context.

**Recommendation:** Change `self.hass.async_create_task(self._async_refresh())` to `self.hass.add_job(self._async_refresh())` in both `_handle_db_ready` closures at sensor.py:11426 and sensor.py:11552, matching the v4.6.3.2 pattern established in the sibling sensors.

**Severity rationale:** CRITICAL because the inconsistency creates a latent thread-safety bug that will trigger when/if the dispatcher context changes, and the fix is trivial (2-line change, copy existing pattern). The whole point of this cycle is to eliminate thread-safety warnings; leaving 2 instances of the same structural pattern unfixed in the same sensors being changed is a regression waiting to happen.

### CRITICAL-A2: `functools.partial` of async method -- Python version sensitivity for HassJob classification

**Location:** `notification_manager.py:1989, 2008` (both `partial(self._fire_digest, ...)`)

**Bug class:** #42 (proposed)

**Description:**
The fix wraps `self._fire_digest` in `functools.partial(self._fire_digest, person_id, person_cfg)` and passes it to `async_track_time_change`. HA's `HassJob` constructor uses `inspect.iscoroutinefunction()` to classify the callback as `Coroutinefunction` (will be awaited) vs `Callback` (will be called synchronously).

**Python version behavior verified empirically:**

| Python Version | `inspect.iscoroutinefunction(partial(async_method))` |
|---|---|
| 3.9 | **False** -- partial is misclassified as sync |
| 3.12+ | **True** -- CPython bpo-46073 propagates coroutine flag through partial |
| 3.14 | **True** -- confirmed on Python 3.14.5 |

HA 2026.5.x requires Python 3.13+ (HAOS ships 3.14.x). On Python 3.14, `inspect.iscoroutinefunction(partial(...))` returns `True`, so `HassJob` correctly classifies the partial as a coroutine function and awaits it. **This fix is correct for the target runtime.**

However, if anyone runs an older Python (e.g., 3.11 in a venv install), `HassJob` would classify the partial as a sync `Callback`, call it without `await`, and the returned coroutine would be silently discarded -- the same "coroutine never awaited" bug the fix intends to solve. This is not a production risk (HAOS enforces Python 3.14), but it is a **portability trap** for development/testing environments.

**Recommendation:** Add a defensive comment at the `partial(...)` site documenting the Python 3.12+ requirement. Alternatively, for maximum safety, wrap with explicit `HassJob`:
```python
from homeassistant.core import HassJob, HassJobType
unsub = async_track_time_change(
    self.hass,
    HassJob(
        partial(self._fire_digest, person_id, person_cfg),
        job_type=HassJobType.Coroutinefunction,
    ),
    hour=hour, minute=minute, second=0,
)
```

However, `async_track_time_change` may not accept a raw `HassJob` as its `action` parameter in all HA versions. The simpler defensive alternative: keep the `partial` approach but add an assertion at module load or `_setup_digest_timers` entry:
```python
assert inspect.iscoroutinefunction(partial(self._fire_digest, "", {})), \
    "Python >= 3.12 required for partial(async) to be detected as coroutine"
```

**Severity rationale:** CRITICAL because if the assumption is wrong, the digest callback becomes completely dead code (fire-and-forget coroutine), with no error logged. Downgraded to HIGH if a comment or runtime assertion is added. The production target (HAOS Python 3.14) is safe, but the risk of silent failure without any guard warrants flagging.

**UPDATE after verification:** Since HAOS 2026.5.x ships Python 3.14 and `inspect.iscoroutinefunction(partial(async_method))` returns True on 3.14, this is SAFE for production. Downgrade to HIGH if a comment is added documenting the Python 3.12+ dependency; remains CRITICAL only if no guard or documentation is present.

### HIGH-A3: Missed scope -- 3 sensors' `_refresh_pending` follow-up path uses `async_create_task`

**Location:**
- `sensor.py:10924` -- `URARecentAnomaliesSensor._async_refresh` finally block
- `sensor.py:11363` -- `CoordinatorDecisionsTodaySensor._async_refresh` finally block
- `sensor.py:11849` -- `CoordinatorLastDecisionSensor._async_refresh` finally block

**Bug class:** Tangential to #42 (not the same anti-pattern but same API)

**Description:**
Three sensors that were NOT part of the 5-site fix use `self.hass.async_create_task(self._async_refresh())` in their `finally` block to handle a "pending refresh" burst. This code runs inside `_async_refresh`, which is an `async def` -- so the `async_create_task` call executes on the event loop and is **safe**. It will not trigger the frame-helper warning because the calling context is already the event loop thread.

However, this creates a **consistency problem**: if a future developer sees `async_create_task` used for follow-up refresh in one sensor and `add_job` used for initial refresh in another, they may not understand the distinction. The comment at sensor.py:10789-10795 explains the `add_job` rationale for dispatcher callbacks but there is no equivalent comment explaining why `async_create_task` is safe in the `finally` block.

**Recommendation:** Add a one-line comment at each site: `# Safe: already on event loop (inside async_refresh)`. No code change needed -- this is a documentation gap, not a bug.

**Severity rationale:** HIGH for maintenance risk, not runtime risk. The code is functionally correct but the inconsistency will confuse future reviewers and may lead to incorrect "fixes" that break things.

### MEDIUM-A4: `_flush_regime_weekly_digest` uses `@callback` + `async_create_background_task` -- same structural pattern as the fixed sites

**Location:** `notification_manager.py:2455-2500`

**Bug class:** Not the same anti-pattern (this is `@callback` correctly used with `async_create_background_task`, not `async_create_task`)

**Description:**
`_flush_regime_weekly_digest` is a `@callback`-decorated sync function passed to `async_track_time_change` at line 563. It creates a background task via `cm_entry.async_create_background_task(self.hass, self._send_regime_weekly_digest(), ...)`. This is structurally different from the fixed pattern because:

1. The `@callback` decorator tells `HassJob` this is a sync callback -- so it will be called, not awaited. Correct.
2. `async_create_background_task` is the HA-sanctioned way to launch async work from a sync `@callback`. Correct.
3. The task is tracked against the config entry, so it will be cancelled on unload. Correct (Bug Class #19 fix from v4.6.2).

This is **not** the same anti-pattern. No fix needed.

**Recommendation:** No action required. Documenting here for completeness -- this was audited and confirmed safe.

**Severity rationale:** MEDIUM (informational -- no bug, but worth auditing given the scope of this cycle).

### Pass-A7: Dispatcher callback context for `_handle_db_ready` (6th potential site)

**Question from review spec:** Is `_handle_db_ready` at sensor.py:11419-11427 also off-loop?

**Answer:** No. `SIGNAL_DATABASE_READY` is dispatched exclusively from `async_setup_entry` in `__init__.py` (lines 766 and 2378), which is an `async def` running on the event loop. The dispatcher's `async_dispatcher_send` delivers callbacks synchronously on the same thread. Therefore `_handle_db_ready` runs on the event loop, and `async_create_task` is technically safe.

However, per CRITICAL-A1, the pattern is still fragile and inconsistent with sibling sensors. The recommendation stands: change to `hass.add_job` for defensive consistency.

## QUALITY_CONTEXT.md Bug Class Proposal

**Ready-to-insert text for Bug Class #42:**

```markdown
### Bug Class #42: Lambda/async_create_task in Scheduler or Dispatcher Callback

**Pattern:** A lambda (or sync function) passed to `async_track_time_interval`,
`async_track_time_change`, `async_call_later`, or `async_dispatcher_connect`
wraps a coroutine call in `hass.async_create_task()`. HA's scheduler runs the
callback via `HassJob`, which expects either:
(a) a sync `@callback` function (called directly), or
(b) an `async def` coroutine function (awaited automatically by the scheduler).

When a lambda wrapping `async_create_task` is used, `HassJob` classifies it as
a sync callback (correct), but `async_create_task` is called from whichever
thread the scheduler fires on. In HA 2026+, this triggers the frame helper
warning "calls async_create_task from a thread other than the event loop" and
may leave the inner coroutine never-awaited (the `create_task` call returns
a future that is immediately discarded by the lambda).

**Impact:** Frame helper warnings (18 per boot in v4.6.14), potential coroutine
never-awaited, potential crash or data corruption if `async_create_task` is
called from a non-event-loop thread.

**The Fix:**
```python
# WRONG -- lambda + async_create_task
async_track_time_interval(
    hass,
    lambda _now: hass.async_create_task(self._async_refresh()),
    timedelta(seconds=300),
)

# CORRECT -- pass the coroutine function directly; add _now parameter
async_track_time_interval(
    hass,
    self._async_refresh,  # HassJob detects async, awaits it
    timedelta(seconds=300),
)

async def _async_refresh(self, _now=None) -> None:
    # _now absorbs the datetime arg from the scheduler
    ...

# CORRECT (with partial for pre-bound args) -- Python 3.12+ required
from functools import partial
async_track_time_change(
    hass,
    partial(self._fire_digest, person_id, person_cfg),
    hour=8, minute=0, second=0,
)

async def _fire_digest(self, person_id, person_cfg, _now=None) -> None:
    ...
```

**Prevention:**
- [ ] Never wrap `async_create_task(coro())` inside a lambda passed to HA scheduler helpers
- [ ] For async callbacks: pass the coroutine function directly (HA's `HassJob` will await it)
- [ ] Add `_now=None` parameter to absorb the datetime argument from schedulers
- [ ] For partial-bound async: requires Python 3.12+ for `inspect.iscoroutinefunction` to detect the partial correctly
- [ ] For sync callbacks that must launch async work: use `@callback` + `entry.async_create_background_task()`
- [ ] Grep guard: `grep -rn 'lambda.*async_create_task' custom_components/` should return zero results (comments excluded)

**Historical Example:** v4.6.15 -- 5 sites across sensor.py and notification_manager.py
triggered HA frame helper warnings 18 times per boot. Three sensor timer callbacks
and two digest timer callbacks used the lambda + async_create_task pattern.

**Discovered:** v4.6.15
**Impact:** Frame helper warnings, potential never-awaited coroutines, potential crash
**Severity:** HIGH
```
