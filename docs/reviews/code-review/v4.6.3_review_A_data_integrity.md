# v4.6.3 Targeted Review A — Data Integrity + DB Architecture Preservation

**Reviewer scope:** Safety-of-existing-data + DB write/read architecture preservation.
**Commit reviewed:** `84326ca` on branch `feature/v4.6.3-anomaly-migration-all-in-one`.
**Sibling reviews:** B (migration correctness), C (new surfaces) — not duplicated here.

---

## Verdict

**Ship with fixes.**

No CRITICAL data-loss or schema-destruction risk. Existing `anomaly_log` rows are preserved, no DDL changes, no DROP/ALTER. The legacy `store_anomaly()` wrapper is replaced by equivalent calls to `save_anomaly_event()` via the same write queue, on the same table, with the same columns.

However, three meaningful issues warrant attention before deploy:

1. **HIGH — conftest_db.py schema is a hand-mirrored copy of the production DDL, not extracted or imported.** This is the exact bug-class shape v4.6.3's Piece B was meant to prevent.
2. **HIGH — Activity-logger dedup may silently coalesce distinct anomaly emits for `compliance` and `nm.alert_dispatched`** because the `description` field lacks a numeric distinguisher.
3. **MEDIUM — `URARecentAnomaliesSensor._async_refresh` has no in-flight or debounce guard;** a burst of anomalies triggers N concurrent untracked tasks each running 5 read queries.

Additional MEDIUM/LOW/INFO listed below.

## Findings

| # | Severity | Bug class | Location | Description |
|---|---|---|---|---|
| A1 | HIGH | Schema mirror drift | `quality/tests/conftest_db.py:24-55` | Hand-copied DDL, not imported from `database.py`. Defeats the stated purpose of v4.6.3's Piece B ("prevent v4.6.1.1 from recurring"). If `database.py` adds a NOT NULL column tomorrow, `conftest_db.py` won't change, behavioral tests will pass against the stale fixture, and production will fail the same way. |
| A2 | HIGH | Dedup-mask | `activity_logger.py:147` + `coordinator_diagnostics.py:578-587`, `notification_manager.py:946-947` | Dedup key = `coordinator:action:room:description`. For `compliance.override_detected` description = `f"Compliance violation: {device_type} {device_id} overridden at {scope}"` — no numeric distinguisher; two distinct violations of the same device within the 60s `notable` window silently dedup. Same shape for `nm.alert_dispatched` (`f"NM alert dispatched: {severity} from {coordinator} via {channels}"`). The anomaly_log INSERT still happens (different code path), but the ActivityLogger event drops, so `SIGNAL_ACTIVITY_LOGGED` does NOT fire, so `URARecentAnomaliesSensor` does NOT refresh. UI under-counts violations during bursts. |
| A3 | MEDIUM | Untracked background tasks + read-storm | `sensor.py:10310` | `self.hass.async_create_task(self._async_refresh())` fires unbounded. A 10-anomaly burst → 10 concurrent refresh tasks → 50 concurrent read queries opening 10 fresh SQLite connections. None tracked. Add an in-flight guard (`if self._refresh_in_flight: self._refresh_pending = True; return`) or debounce. |
| A4 | MEDIUM | Field-shape drift in context_json | All new emit sites (`safety.py:1656-1668`, `presence.py:1729-1741`, `transitions.py:399-410`, `energy.py:2718-2721`, `coordinator_diagnostics.py:534-547`, `notification_manager.py:931-940`) | New emit sites pack `z_score`/`observed_value`/`expected_mean`/`expected_std`/`sample_size` under `payload["extra"][...]` via `build_context_json(extra=...)`. The legacy `store_anomaly()` wrapper packed them as **top-level** keys. Net effect: `save_anomaly_event` `payload_dict.get("observed_value", 0.0)` (`database.py:4347-4351`) returns 0.0 sentinels for ALL post-v4.6.3 rows, and the metric columns (`observed_value`, `expected_mean`, `expected_std`, `z_score`, `sample_size` — all NOT NULL) are filled with 0.0/0 sentinels instead of the real values. Pre-v4.6.3 rows have real values; post-v4.6.3 rows do not. No in-process reader depends on these columns today (verified — no `payload.get("z_score")` in production code), so this is silent data degradation, not a runtime regression. Future SQL analytics will see a discontinuity at the upgrade boundary. **Fix:** either also pass the metric values as top-level payload keys (alongside `extra`), or refactor `build_context_json` to surface them at top-level. |
| A5 | MEDIUM | Cross-table queue pressure | `safety.py:1655-1709` (and 5 other emit sites) | Each emit fires (a) `save_anomaly_event` (1 queue write), then (b) `async_create_task(activity_logger.log(...))` (a second queue write to `ura_activity_log`). The activity log task is untracked — it may complete during HA shutdown after the write worker is cancelled, causing `RuntimeError("DB write worker not running...")` per `database.py:204-207`. `activity_logger.log` already swallows the exception (line 100), so observable impact is bounded to "lost activity log row" — but worth flagging. |
| A6 | LOW | Field name drift between `_database` access patterns | `transitions.py:421`, `energy.py:2733`, `notification_manager.py:953`, `coordinator_diagnostics.py:558` | New emit helpers fetch the database via `self.hass.data.get(DOMAIN, {}).get("database")` rather than the `self._database` property that `AnomalyDetector` and `ComplianceTracker` use. Functionally equivalent; minor consistency drift. |
| A7 | LOW | severity column type mismatch (legacy) | `database.py:676` declares `severity TEXT NOT NULL`; `save_anomaly_event` line 4374 passes `int(event.severity)`. | SQLite is dynamically typed so this stores INTEGER affinity in a TEXT-declared column. ## Mental execution log

### Scenario (a) — Startup with 100+ existing `anomaly_log` rows

Trace:
1. `__init__.py` boots, instantiates `database`, starts write worker.
2. `PresenceAnomalySensor` (etc.) read from coordinator status dicts — no DB query at startup.
3. `PersonRoutineStatusSensor.async_update` runs on its update schedule; queries `coordinator_id='bayesian'` rows. Pre-v4.6.3 may have these rows from v4.6.2; their context_json shape was set by v4.6.2 D6's regime detector, NOT by the legacy wrapper. So `context_json` parsing path is the same as before. ✓
4. `URARecentAnomaliesSensor.async_added_to_hass` runs `_async_refresh()`: COUNT, top-10, GROUP BY coordinator_id, GROUP BY severity, GROUP BY event_class. All four queries filtered by `timestamp >= ?` → planner uses `idx_anomaly_timestamp`. Pre-v4.6.3 rows have a `severity` column; the result map uses `str(r[0])` so any value works. `event_class` may be NULL for pre-v4.6.1 rows; the `COALESCE(event_class, 'point_in_time')` handles that. ✓

**Result:** No corruption, no exception, results returned. PASS.

### Scenario (b) — Burst of 20 anomaly emits in 1 minute across 5 coordinators

Trace:
1. 20 emits → 20 × `save_anomaly_event` queue submissions + 20 × `async_create_task(activity_logger.log(...))`.
2. Each `activity_logger.log` enqueues 1 more queue submission (40 queue entries total). Write worker processes them sequentially.
3. Each successful activity-logger call fires `SIGNAL_ACTIVITY_LOGGED` with `action="anomaly"`.
4. `URARecentAnomaliesSensor._handle_activity_logged` matches → fires `async_create_task(_async_refresh())`. **20 concurrent refresh tasks queued** with no in-flight guard.
5. Each refresh task opens its own `aiosqlite.connect` via `_db_read()`, runs 5 queries, closes.
6. SQLite + WAL handles concurrent reads, BUT 20 connections is wasteful + each connection setup includes `PRAGMA busy_timeout` + `PRAGMA query_only`. ~100 PRAGMA writes for 20 refreshes.
7. Dedup interaction: 5 of the 20 might be `compliance.override_detected` with the same description (same device repeated). 4 of them silently drop at the activity_logger layer (within the 60s `notable` window). So only 16 refreshes fire — but the anomaly_log rows are intact.

**Result:** No data loss, but read-side amplification + activity-log under-emission. Finding A2 + A3.

### Scenario (c) — Options-flow entry reload while anomaly emits are mid-flight

Trace:
1. User saves new sensitivity bucket in coordinator manager entry options.
2. CM entry reloads — coordinators get torn down + re-created.
3. In-flight `save_anomaly_event` calls hold `self.hass.data[DOMAIN]["database"]` which is at the **integration** level, not entry level. Database is NOT torn down on entry reload. ✓
4. In-flight `async_create_task(activity_logger.log(...))` from a torn-down coordinator continues to run; `activity_logger` is also integration-level. ✓
5. `AnomalyDetector` instances are torn down. Their `Z_SCORE_*` thresholds are instance attributes, mutated at init from the sensitivity multiplier. On reload the new instance has new thresholds. ✓
6. RACE: between coordinator teardown and re-creation, a transitional dispatcher signal could trigger code that touches `self.anomaly_detector` which is None or stale. This is BaseCoordinator territory and not v4.6.3-specific — but the new D10 sensitivity-init pattern reads `_ce.data + _ce.options` synchronously inside `_setup_internal` which means the read happens AFTER teardown — no stale value. ✓

**Result:** No new race introduced by v4.6.3. PASS.

### Scenario (d) — Malformed JSON write to context_json

Trace:
1. `save_anomaly_event` line 4377: `_json.dumps(event.payload)` — no `default=`.
2. Audited all new emit sites' `extra` dicts:
   - Safety: `hazard.type.value` (str), `hazard.severity.name` (str), floats, ints. ✓
   - Presence: floats, ints. ✓
   - Transit: floats, strings, ints. ✓
   - Energy circuit: spread from `_circuits.check_anomalies()` — all str/float/int (verified `energy_circuits.py:195-204`). ✓
   - Compliance: `record.deviation_details` — `_compare_states` returns plain dict (verified). ✓
   - NM: `channels_fired: list[str]`, severity_str: str, etc. ✓

**Result:** No path identified that would write malformed JSON today. Finding A9 is preventive only.

### Scenario (e) — Reader-side handling of pre-v4.6.3 rows

Trace for `URARecentAnomaliesSensor`:
1. COUNT query — column-shape-agnostic. ✓
2. Top-10 — selects `timestamp, coordinator_id, severity, metric_name`. All four columns exist in pre-v4.6.3 schema. `severity` is read as the raw value (no `int()` cast). ✓
3. By coordinator — same. ✓
4. By severity — same. ✓
5. By event_class — `COALESCE(event_class, 'point_in_time')` handles NULL gracefully. ✓

Trace for `PersonRoutineStatusSensor`:
- Filtered to `coordinator_id='bayesian'` AND `metric_name='bayesian.routine_shift'` — these only exist from v4.6.2. ✓
- `int(r[0])` for severity — works on rows written by v4.6.2 D6 (integer-shaped severity since the unification migration). ✓

**Result:** Existing readers handle pre-v4.6.3 rows correctly. PASS.

## Recommendations for the orchestrator before deploy

**Must-fix (HIGH):**

1. **A1 — Make `conftest_db.py` extract DDL from `database.py`.** Options:
   - Refactor `database.py` to expose a `_get_anomaly_log_ddl()` or module-level constants the conftest imports.
   - Or add a behavioral test that AST-walks `database.py`'s `CREATE TABLE anomaly_log` and asserts column-by-column equality with the conftest DDL.
   - Without this, v4.6.3's stated Piece B value is voided.

2. **A2 — Include a distinguisher in compliance + NM dedup descriptions.** Add the timestamp (microsecond precision), z_score, or a counter to the description. Example: `f"Compliance violation: {device_type} {device_id} overridden at {scope} t={timestamp_iso}"`. Without this, burst violations and dispatch storms silently drop activity_logger events and the new sensor mis-counts.

**Should-fix (MEDIUM):**

3. **A3 — Add in-flight guard to `URARecentAnomaliesSensor._async_refresh`.**
4. **A4 — Surface metric values at top-level of payload** (or refactor `save_anomaly_event` to look under `payload["extra"]` for them). Otherwise post-v4.6.3 rows write 0.0 sentinels into the NOT NULL metric columns — silent data degradation.

**Nice-to-have (LOW/INFO):** A5–A11 can defer to a hardening cycle.

## Recommendations for QUALITY_CONTEXT.md

Propose two new bug classes:

- **Schema mirror drift in test fixtures** — test infrastructure that hand-copies production DDL silently rots when production DDL changes. Mitigation: extract or AST-couple the schema, never hand-copy.
- **Dedup-mask via low-cardinality description** — ActivityLogger-style dedup with a `coordinator:action:room:description` key silently coalesces distinct events when the `description` field lacks an event-unique distinguisher (timestamp, z_score, ID). Mitigation: every description that is a candidate for dedup must include a numeric/ID component that differs between event instances.
