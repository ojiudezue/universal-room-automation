## Verdict: **HOLD**

Two CRITICAL defects in the test-infra layer (D1/D8) defeat the stated purpose of the v4.6.3 plan — the "behavioral test against real schema" pattern that was supposed to prevent the v4.6.1.1 bug class. The user-visible surfaces (D10/D12/D13) are mostly correct, but D10 has a HIGH defect: the energy coordinator dropdown is a no-op because the energy coordinator has no AnomalyDetector to receive the multiplier.

These are not "ship with fixes" defects — they are foundation problems. Fix D1, D8, and the energy dropdown wiring (or surface it as out-of-scope), then re-review.

## Mental-execution traces

### Trace (a) — User picks "sensitive" in HVAC options flow

1. User opens CM device → Configure → step `coordinator_hvac`.
2. `_show_coordinator_hvac_form` includes the dropdown (config_flow.py:3585). Default = `_get_current(CONF_HVAC_ANOMALY_SENSITIVITY, DEFAULT_ANOMALY_SENSITIVITY)` → `"normal"` on first open.
3. User selects `sensitive` → form submit → options saved to `entry.options[CONF_HVAC_ANOMALY_SENSITIVITY] = "sensitive"`.
4. CM entry reload triggered automatically by HA.
5. On reload, HVACCoordinator setup runs `_setup_diagnostics` (hvac.py:487). It iterates `hass.config_entries.async_entries(DOMAIN)` looking for CM entry (line 507). Merges `{**ce.data, **ce.options}` (line 509) so options-saved value wins. Reads `"sensitive"`.
6. `ANOMALY_SENSITIVITY_MULTIPLIERS["sensitive"]` = 0.75. Passed as kwarg to `AnomalyDetector(...)`.
7. `AnomalyDetector.__init__` (coordinator_diagnostics.py:738-740) computes `self.Z_SCORE_ADVISORY = 2.0 * 0.75 = 1.5`, similarly ALERT=2.25, CRITICAL=3.0. Matches plan.
8. On re-open of options flow: `_get_current` reads from `entry.options` first → returns `"sensitive"` → dropdown pre-selects it. ✓

**Result: PASS for HVAC. Same trace fails for Energy (no AnomalyDetector, Finding #6).**

### Trace (b) — Smoke alarm fires

1. SafetyCoordinator detects smoke hazard (safety.py).
2. Hazard handler dispatches `SIGNAL_SAFETY_HAZARD`, fires activity_logger `action="hazard_detected"`.
3. Hazard handler then calls `anomaly_detector.record_observation` (safety.py:1652). If returns anomaly:
4. Builds `AnomalyEvent` with `event_class=EVENT_CLASS_HAZARD`, calls `anomaly_detector.store_event(_event)` → `database.save_anomaly_event` → INSERT into anomaly_log, committed. ✓
5. Fires activity_logger via `async_create_task(...log(action="anomaly", description=f"... z={z_score:.2f}", importance="critical"))`.
6. ActivityLogger.log: dedup-check passes (z_score in description), writes `ura_activity_log` row, fires `ura_action` event, dispatches `SIGNAL_ACTIVITY_LOGGED` with payload including `"action": "anomaly"`.
7. `URARecentAnomaliesSensor._handle_activity_logged`: payload action == "anomaly" → schedules `_async_refresh`.
8. `_async_refresh` queries anomaly_log; the row from step 4 is already committed → count increments, top_10 includes new row. ✓

**Result: PASS. Sequencing OK because store_event awaits commit before dispatching activity log.**

### Trace (c) — Diagnostic dump button press

1. User presses button → `async_press`.
2. Reads `database = hass.data[DOMAIN]["database"]`. Available check passes (`available` property at button.py:1010).
3. Opens `_db_read()` context, fetches last 50 anomaly_log rows, per-coordinator counts. ✓
4. Reads `database._write_queue.qsize()`, `_db_stats`. ✓
5. Reads activity_logger dedup cache size. ✓
6. Looks up `coordinator_manager` in `hass.data[DOMAIN]` — calls `manager.get_anomaly_summary()` if present. Wrapped in try/except so missing method does not break dump.
7. Emits single `_LOGGER.error("URA ANOMALY DIAGNOSTIC DUMP: %s", json.dumps(dump, default=str))`.

**Result: PASS. One caveat: accesses `database._write_queue`, `database._db_stats`, `activity_logger._dedup_cache` — private attributes. Acceptable for a diagnostic button but ideally exposed via a public method.**

### Trace (d) — Behavioral test catches a malformed save_anomaly_event call

This trace is **the central failure**. The test fixture is hand-typed and drifted from production. A test that writes a row via the test's inline `_insert_anomaly()` validates that the inline SQL matches the inline fixture schema — both written by the same author in the same commit. There is **no** test that calls `database.save_anomaly_event(_FakeAnomalyEvent(...))` against the real schema. Therefore: if `database.py` adds a new NOT NULL column tomorrow, no test in v4.6.3's test suite will fail at build time. This is the exact bug class v4.6.3 was supposed to solve.

**Result: FAIL.**

## Recommendations for `docs/QUALITY_CONTEXT.md`

Propose new bug class **"Test Fidelity by Schema Drift"**: When test fixtures hand-copy the production schema rather than importing it, behavioral tests degenerate into self-consistency checks that pass while production diverges. Detection: `grep -L "from .*\.database import" quality/tests/conftest*.py` — if conftest defines DDL inline, flag. Mitigation: tests must import the production schema-application function directly, or the fixture must be regenerated from production each test session and the diff asserted to be empty.

This is mechanistically distinct from existing bug class #7 (stale data source) — that one is about runtime/MCP data; this one is about test-time schema authority.
