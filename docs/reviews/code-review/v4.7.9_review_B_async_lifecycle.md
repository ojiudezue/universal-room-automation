### Framing 4 — Prev-snapshot survives reload

**Verdict: PASS (deliberate design — confirmed via inline doc).**

`_dynamic_preset_skip_reasons_prev: dict[str, str] = {}` is initialized in `EnergyCoordinator.__init__` at `energy.py:454`. On config-entry reload:

1. `async_unload_entry` tears down the CM entry → old `EnergyCoordinator` is GC'd → old `_dynamic_preset_skip_reasons_prev` dict is GC'd with it.
2. `async_setup_entry` constructs a new `EnergyCoordinator` → `__init__` runs → `self._dynamic_preset_skip_reasons_prev = {}` (fresh empty dict).
3. First tick post-reload:
   - `updated_skip_reasons` is whatever the eval produces (could be `{}` or non-empty).
   - `_reasons_changed = ({} != updated_skip_reasons)` → `True` if non-empty, `False` if empty.
   - If `True`: signal fires; sensor refreshes once → renders the post-reload state.
   - If `False`: no spurious dispatch.

The inline comment at `energy.py:452-457` documents the expected first-tick semantics ("first tick against empty dict does NOT spuriously fire; first tick with non-empty reasons WILL fire — correct, real state change"). This matches what a downstream consumer of "DPM skip reasons changed" needs: the post-reload state IS a state change from the consumer's perspective (the consumer's subscription was also reset).

**No finding on correctness.** Framing 4's open question ("is first-post-reload tick the desired emit semantic, or should it skip?") resolves to **emit is correct** — the sensor's attribute is fed by a getter that reads the EC's live `_dynamic_preset_skip_reasons` dict; if that dict is non-empty after a fresh start, the sensor's old cached HA state (from before unload) would be stale until the next genuine reasons-change. The first-tick fire ensures the sensor renders the live state without waiting for a real transition.

### Framing 6 — Button press during config-entry reload

**Finding B-L3 — LOW. Race window: button press during `OverrideArrester` swap.**

**Bug Class:** #20 (Concurrent Config Entry Reload Race) + Bug Class adjacency to v4.7.7 AC Nudge concurrent-reload-race finding.

**Trace:** User presses the new Force AC Reset button. The button's `_get_arrester()` re-resolves via `hass.data[DOMAIN]["coordinator_manager"].coordinators["hvac"]._override_arrester` on every press (`button.py:757-762`). Two windows exist:

1. **CM reload mid-press race:** If the CM is reloading concurrently, the `coordinator_manager` key may be `None` or `dict-missing` for a microsecond between `async_unload_entry` and `async_setup_entry`. `_get_arrester` returns `None` → `async_press` logs `"OverrideArrester not available"` and returns. **This is the desired behavior** — user-visible "press did nothing, retry" is better than calling into a half-torn-down arrester.

2. **In-flight escalation across swap:** A more interesting window — `_get_arrester` returns the OLD arrester instance (CM teardown in progress, swap not yet completed). The user's `await method(...)` begins executing on the OLD arrester. Mid-await, the OLD arrester's DB handle (`self._db`) could be torn down by the CM unload, causing a partial `_perform_hard_reset_escalation` (e.g., `state = await self._db.get_ac_reset_state(zone_id)` succeeds, but the subsequent `await self._db.save_ac_reset_state(state)` fails because the connection is closed).

**Likelihood:** Very low. Requires the user to press the button in the exact ~milliseconds the CM is reloading. The existing v4.7.7 AC Nudge/Reset code already lives with this race (force_nudge, cancel_nudge, clear_lockout). The v4.7.9 button does not introduce a new failure mode beyond what already exists. Mirror of the LOW finding from v4.7.7 Reviewer B.

**Recommendation (defer):** Track for a future v4.7.x cycle that wraps `OverrideArrester` mutator entry points in a "swap fence" (e.g., a per-arrester `asyncio.Event` cleared during unload). NOT a blocker for v4.7.9 deploy.

**File:line:** `button.py:800-827` and `hvac_override.py:1758-1812`.

### Framing 7 — Signal handler GIL atomicity

**Verdict: PASS.**

The signal handler `_on_signal` reads no shared state directly — it just calls `async_write_ha_state()`. State is re-pulled inside the property accessor `extra_state_attributes` (`sensor.py:6867-6918`):

```python
reasons_by_zone = _get_dynamic_preset_skip_reasons(self.hass)
```

`_get_dynamic_preset_skip_reasons` (`sensor.py:6527-6542`) returns `getattr(energy, "_dynamic_preset_skip_reasons", {}) or {}`. This is a single GIL-atomic attribute read of a dict reference.

The decision tick writes the dict via wholesale assignment: `self._dynamic_preset_skip_reasons = updated_skip_reasons` (`energy.py:2792`). Python attribute assignment is GIL-atomic for the binding itself. The sensor cannot observe a "partial write" of the dict — it either sees the prior dict or the new dict.

Critically, the prev-snapshot dance does NOT introduce a non-atomic window for the sensor:

```python
# Order of operations in energy.py:
self._dynamic_preset_skip_reasons = updated_skip_reasons       # L2792 — sensor reads this
... (overrides edge-detection + dispatch) ...                  # L2794-2815
_reasons_changed = self._dynamic_preset_skip_reasons_prev != updated_skip_reasons  # L2825-2827
self._dynamic_preset_skip_reasons_prev = dict(updated_skip_reasons)  # L2831 — internal only
if _reasons_changed:
    async_dispatcher_send(self.hass, SIGNAL_DPM_SKIP_REASONS_UPDATED)  # L2836
```

By the time the signal is dispatched, the sensor-visible `_dynamic_preset_skip_reasons` has been updated for >40 lines of synchronous code. The handler's subsequent read of `_dynamic_preset_skip_reasons` reflects the same `updated_skip_reasons` dict that drove the edge detection. **No torn read possible.**

**No finding on atomicity.** See B-M1 below for a separate, lower-stakes concern about the `dict() copy` cost.

## Additional Findings (MEDIUM + LOW — not blockers)

### B-M1 — MEDIUM — `dict()` copy on every tick for unchanged reasons

**File:** `energy.py:2831`
**Risk:** Minor CPU + GC churn — `self._dynamic_preset_skip_reasons_prev = dict(updated_skip_reasons)` runs on every DPM tick (~every 5 minutes), even when nothing changed. The copy is O(zones); typical small (≤6 zones).
**Why MEDIUM not LOW:** The copy is correct (prevents prev-snapshot from aliasing the live dict — see the inline rationale at `energy.py:2828-2830`). But it could be skipped when `_reasons_changed=False` by comparing AT THE OBJECT-IDENTITY level first. As written, every tick allocates a new dict object. Negligible at 6 zones; would matter at hundreds.
**Fix sketch:**
```python
_reasons_changed = (
    self._dynamic_preset_skip_reasons_prev != updated_skip_reasons
)
if _reasons_changed:
    self._dynamic_preset_skip_reasons_prev = dict(updated_skip_reasons)
    async_dispatcher_send(self.hass, SIGNAL_DPM_SKIP_REASONS_UPDATED)
```
**Recommendation:** Defer to a future micro-optimization pass. Not worth a fix-up commit in v4.7.9.

### B-L1 — LOW — Imports inside the dispatch try-block re-import on every tick

**File:** `energy.py:2811-2813`, `energy.py:2834-2836`
**Risk:** Two `from ... import ...` statements live inside the per-tick code path:
```python
from homeassistant.helpers.dispatcher import async_dispatcher_send
from .signals import SIGNAL_DPM_SKIP_REASONS_UPDATED
async_dispatcher_send(self.hass, SIGNAL_DPM_SKIP_REASONS_UPDATED)
```
Python caches successful imports in `sys.modules`, so subsequent imports are dict-lookups — not free, but cheap. Mirrors the existing pattern for `SIGNAL_DYNAMIC_PRESET_OVERRIDES_UPDATED` (`energy.py:2811-2813`).
**Why LOW:** Negligible CPU. Pattern matches existing v4.7.7 code.
**Recommendation:** Defer. If a future cycle hoists these to module-level imports, audit for the original reason they were inlined (likely to avoid circular-import risk at module load).

### B-L2 — LOW — Bare `except Exception: pass` on dispatch site

**File:** `energy.py:2837-2838` (and the pre-existing `energy.py:2814-2815` for the overrides signal)
**Risk:** Silently swallows any exception during signal dispatch. If `signals.py` is malformed or the dispatcher helper raises, the failure is invisible. The pre-existing overrides emit has the same pattern, so this is a consistency match — not a regression.
**Mitigation:** The outer `try/except Exception` at `energy.py:2840-2841` already logs the broader eval failure with `exc_info=True`. A `_LOGGER.debug("DPM skip-reasons signal dispatch failed", exc_info=True)` inside the inner except would be cheap and aid debug.
**Recommendation:** Defer. Captured for the next hygiene cycle.

### B-L4 — LOW — `_on_signal` ignores `_payload`; signal sent payload-less

**File:** `sensor.py:6848-6850` + `energy.py:2836`
**Risk:** The dispatcher sends `async_dispatcher_send(self.hass, SIGNAL_DPM_SKIP_REASONS_UPDATED)` with NO payload. `_on_signal(self, _payload=None)` accepts an optional payload. Internally consistent. The signal acts as a pure "refresh hint" — the sensor re-reads `_dynamic_preset_skip_reasons` from the EC after refresh.
**Why LOW:** No bug. Risk note: if a future cycle ever wants to send the diff in the payload (so the sensor can avoid re-reading the EC dict), the existing handler signature is forward-compatible. Document the intentional payload-less contract somewhere — currently only the dispatch-site comment hints at it ("Sensor recomputes from latest state; idempotent re-fire is safe" — `signals.py:103`).
**Recommendation:** Defer. Add a one-liner to the `_on_signal` docstring in a future cycle: `"""Signal carries no payload by design — sensor re-reads live EC state."""`
