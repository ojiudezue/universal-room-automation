### CRITICAL-B1: D5 guest_room_gate not evaluated in GUEST state -- sustained occupancy cannot hold GUEST mode

**Bug Class:** #5 (Startup Race -- generalized to "execution path skip"), NEW potential class (Exit-path gate skip)
**Severity:** CRITICAL
**File:** `presence.py:1897-1913`

**Problem:** `_run_inference()` only evaluates `_guest_room_gate_armed()` when `current_state in _home_like_states` (HOME_DAY, HOME_EVENING, HOME_NIGHT). When `current_state == HouseState.GUEST`, lines 1910-1913 hardcode `guest_room_gate_armed = False` and `guest_armed = False`.

The D5 change to the inference engine exit condition at line 449:
```python
if current_state == HouseState.GUEST and unidentified_count == 0 and not guest_gate_armed:
```
depends on `guest_gate_armed` being truthful even in GUEST state. But because `guest_armed` is always False when in GUEST, the exit condition reduces to `unidentified_count == 0`, which means:

- If a guest enters via the D5 guest_room path (census unidentified_count may be 0), the system exits GUEST on the VERY NEXT inference cycle.
- The sustained-occupancy signal cannot hold GUEST state.
- Result: rapid oscillation between GUEST and HOME_* every inference cycle.

The pre-existing `_guest_gate_armed()` (unid path) was correctly skipped in GUEST state because it has side effects (`_disarm_guest_gate()` calls). But `_guest_room_gate_armed()` is a **pure predicate** -- safe to evaluate in any state.

**Fix:** When `current_state == HouseState.GUEST`, also evaluate `_guest_room_gate_armed()` and pass it into the combined `guest_gate_armed`:

```python
if current_state in _home_like_states:
    unid_gate_armed = self._guest_gate_armed(...)
    guest_room_gate_armed = self._guest_room_gate_armed(now=dt_util.utcnow())
    guest_armed = unid_gate_armed or guest_room_gate_armed
elif current_state == HouseState.GUEST:
    # Don't re-evaluate unid gate (has side effects), but DO check guest_room gate
    # (pure predicate) so the exit condition at infer() line 449 gets a truthful value.
    unid_gate_armed = False
    guest_room_gate_armed = self._guest_room_gate_armed(now=dt_util.utcnow())
    guest_armed = guest_room_gate_armed
else:
    unid_gate_armed = False
    guest_room_gate_armed = False
    guest_armed = False
```

**Status:** MUST FIX before deploy.

### MEDIUM-B3: Misleading comment -- dt_util.now() does NOT return UTC

**Bug Class:** #11 (UTC vs Local)
**Severity:** MEDIUM
**File:** `presence.py:1907`

**Problem:** Comment reads: `"Bug Class #11: now is already UTC-aware (dt_util.now() returns UTC)."`

This is factually incorrect. `dt_util.now()` returns the **local timezone-aware** datetime (e.g., America/Chicago), not UTC. `dt_util.utcnow()` returns UTC.

The code at line 1908 correctly uses `dt_util.utcnow()` for the `_guest_room_gate_armed()` call, and `first_seen` in `_handle_guest_room_occupancy_change` is also set via `dt_util.utcnow()`. So the subtraction is UTC-vs-UTC, which is correct. The bug is in the comment, not the code.

Meanwhile, the existing unid gate at line 1882 uses `now = dt_util.now()` (local) and `_unidentified_first_seen` is also set from `now` (local), so that subtraction is local-vs-local, also correct.

**Fix:** Change comment to: `"Bug Class #11: D5 timestamps are UTC-aware (dt_util.utcnow())."`

**Status:** Fix before deploy (prevents future confusion).

### MEDIUM-B5: D5 docstring contradicts implementation -- "no async_create_task" but code calls async_create_task

**Bug Class:** #42 (Lambda + async_create_task -- documentation inconsistency)
**Severity:** MEDIUM
**File:** `presence.py:1641`

**Problem:** Docstring reads: `"Bug Class #19: no async_create_task in this callback -- schedules inference."`

But line 1698 calls: `self.hass.async_create_task(self._run_inference("guest_room_occupancy"))`

The docstring is misleading. The actual pattern is safe: `async_create_task` is called from a `@callback`-decorated method that runs on the event loop (not from a background thread), and the callback is a bound method (not a lambda). This matches the established pattern at lines 1263, 1308, 1347.

The docstring appears to have been trying to say "no Bug Class #19 violation (untracked background tasks)" but the phrasing implies no `async_create_task` call exists.

**Fix:** Change to: `"Bug Class #19: async_create_task used for inference scheduling -- safe because @callback runs on event loop."` or simply remove the misleading claim.

**Status:** Fix before deploy.

## Recommendations for QUALITY_CONTEXT.md

Consider adding a new bug class:

**Bug Class #46: Exit-Path Gate Skip** -- When a state machine has separate entry and exit conditions that both depend on gate evaluation, but the gate is only evaluated on the entry path (e.g., because the original exit path used a simpler condition), adding a new gate source that must also hold the exit path will fail silently unless the gate is also evaluated when the system is already in the gated state. Pattern: the exit condition references a variable that the caller hardcodes to a default when in the "already entered" state.
