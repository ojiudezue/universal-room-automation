## 1. `set -e` / `set +e` leak prevention trace (dedicated section)

This was the primary framing axis. Trace below covers every entry/exit edge between the two `set` states in `deploy.sh` step 4.

### Trace: `deploy.sh:74-104`

```bash
# Step 4 enters with `set -euo pipefail` active (from line 8).

step "4/7 ..."                                            # set -e ACTIVE
run git -C "$REPO_DIR" push origin develop                 # set -e ACTIVE
                                                           # ↑ fails here ⇒ deploy halts
                                                           #   (this is the desired behavior)

if git -C "$REPO_DIR" remote get-url gitea >/dev/null 2>&1; then
  if $DRY_RUN; then
    echo "  [dry-run] ..."                                 # set -e ACTIVE — fine
  else
    set +e                                                 # ⇐ set -e DISABLED
    bash "$REPO_DIR/scripts/dual-push.sh" --gitea-only develop
    rc=$?                                                  # capture exit code
    set -e                                                 # ⇐ set -e RESTORED
                                                           # All branches below run
                                                           # under restored set -e.
    if [ "$rc" -eq 0 ]; then :
    elif [ "$rc" -eq 1 ]; then echo "  [warn] ..." ; echo "  [warn] catch up ..."
    elif [ "$rc" -eq 2 ]; then echo ... >&2; exit 2
    elif [ "$rc" -eq 130 ]; then echo ... >&2; exit 130
    else echo ... >&2; exit "$rc"
    fi
  fi
fi

# Step 5 enters with `set -e` ACTIVE  ✓
```

**Verdict for the leak-prevention axis:** The `set +e` window is bounded to ONE command (`bash dual-push.sh ...`), `rc=$?` captures the exit code on the very next statement, and `set -e` is restored BEFORE any branching. The branches that explicitly `exit "$rc"` propagate the failure; the fall-through (`rc=0` or `rc=1`) leaves the script with `set -e` re-enabled. **Step 5 is guaranteed to run with `set -e` active.** No leak.

Empirical validation: I ran a faithful one-liner reproduction of this pattern with the wrapped command exiting rc=7. The wrapper exited rc=7 (i.e., the unexpected-rc branch propagated correctly, and `set -e` was active for the `exit "$rc"` call).

This is the cleanest bounded `set +e`/`set -e` window pattern I could have asked for. **No finding.**

## 3. Findings

### B-M1 (MEDIUM) — Indefinite hang on network drop never fires trap

**Bug class:** Untrapped Indefinite Wait / no upper bound on `git push` duration. (Not in QUALITY_CONTEXT.md — that's runtime-Python; this is a new shell-side class. Recommend adding "Shell push without timeout" as a new entry — see §6.)

**Surface:** `scripts/dual-push.sh:124-126`.

**Trace:** `git remote set-url` rewrites `.git/config` with `https://USER:TOKEN@host/...`. `git push gitea "$BRANCH"` then begins. If the network drops mid-push without TCP RST (e.g., NAT timeout, captive-portal silent drop, Verizon LTE handoff), `git` may block indefinitely on a socket waiting for ACK. Bash is blocked in `git push`. **No signal is delivered, so the trap NEVER fires.** The credentialed URL remains in `.git/config` until the operator notices and kills the process.

If the operator then SIGINT's, the trap fires and restores — but if the operator gives up and closes the terminal (HUP), the trap fires on SIGHUP (because EXIT covers all of HUP too in interactive bash) — but if the operator hibernates the laptop and the bash process eventually gets reaped by the kernel on next wake, SIGKILL semantics apply and the URL stays dirty.

**Verification I did:** None empirically (would need to simulate network blackhole). Reasoning from `git` socket-blocking semantics is documented across multiple HN/SE threads; I did not verify it for this specific git version.

**Recommendation (HIGH-value LOW-effort fix):** Wrap the push with a `timeout` command (GNU coreutils — but macOS ships it via `brew install coreutils` as `gtimeout`, or via `perl -e 'alarm…; exec…'` as a portable alternative). Suggested form:

```bash
# Cap each push at 60s to bound the trap-eligibility window.
PUSH_TIMEOUT="${URA_DUALPUSH_TIMEOUT:-60}"
_timeout_push() {
  if command -v gtimeout >/dev/null 2>&1; then
    gtimeout "$PUSH_TIMEOUT" "$@"
  elif command -v timeout >/dev/null 2>&1; then
    timeout "$PUSH_TIMEOUT" "$@"
  else
    # No timeout available — fall back to direct call; document residual risk.
    "$@"
  fi
}
_timeout_push git push gitea "$BRANCH"
```

If timeout fires, the wrapped command receives SIGTERM, the trap fires, the URL is restored. Exit code is 124 (timeout), which should be added to the deploy.sh dispatch as another HALT case (or mapped to rc=1 since gitea is mirror-only).

**Severity rationale:** MEDIUM because the credentialed URL is theoretically retrievable from `.git/config` by anyone with file-system read access, and the dev machine is single-user, so the practical blast radius is small. But this is exactly the failure class that the trap was designed to prevent — and the trap as designed has a measurable blind spot.

**Status:** DEFER to a follow-up cycle. v4.7.10 ships without the timeout wrapper. File as "shell-side residual: network-hang URL leak window."

### B-M2 (MEDIUM) — Origin push (lines 140-145) runs WITHOUT the URL-restoration trap covering it

**Bug class:** Trap-coverage gap on conditional branch.

**Surface:** `scripts/dual-push.sh:139-146`.

**Trace:** The origin push branch:

```bash
if ! $GITEA_ONLY; then
  echo "→ Pushing to GitHub origin/$BRANCH"
  if $DRY_RUN; then
    ...
  else
    git push origin "$BRANCH"     # ← can fail; trap covers this
    git push origin --tags         # ← can fail; trap covers this
  fi
fi
```

The trap IS registered (line 54) before this block, so technically it fires on failure. **But the trap's job is to restore `GITEA_CLEAN_URL` — at this point `GITEA_CLEAN_URL` is empty, so the trap body short-circuits.** That's correct behavior; no actual bug.

However, there is a subtle ordering issue: if `git push origin` fails under `set -e`, we exit before reaching `inject_gitea_creds` and the gitea URL was never rewritten — so nothing to clean up. **No bug.**

I am downgrading this finding to **LOW (B-L1)** below. Moving on.

Actually, re-reading: there IS a real concern. When `deploy.sh` step 4 invokes `dual-push.sh --gitea-only`, `$GITEA_ONLY=true` so the origin block is skipped — correct. But the planning doc allows `dual-push.sh develop` (no `--gitea-only`) to be invoked manually as a catch-up command. In that path, BOTH origin AND gitea push happen. If origin succeeds but gitea fails, the trap fires correctly and the URL is restored. If origin fails, we never reach the gitea path, so URL was never credentialed, trap-body short-circuits, OK.

**Net: No bug. Downgrading.** See B-L1 below for the residual observability concern.

### B-M3 (MEDIUM) — `deploy.sh` step 4 does NOT handle `rc=143` (SIGTERM) from `dual-push.sh`

**Bug class:** Incomplete signal-rc dispatch table.

**Surface:** `scripts/deploy.sh:87-103`.

**Trace:** The deploy.sh dispatch handles `rc=0`, `rc=1`, `rc=2`, `rc=130`, and `else` (catch-all). `dual-push.sh`'s exit-code contract documented in its header (lines 18-22) lists `143 SIGTERM` as a valid contract code that the caller should halt on. The `else` branch in deploy.sh does halt (`exit "$rc"`), so the operational behavior is correct.

However, the user-facing message in the `else` branch is `"gitea push exited with unexpected code $rc"`, which is misleading for a SIGTERM — that's not "unexpected", it's the contracted halt signal. A tired operator at 11pm parsing the error message would not infer "I (or another process) sent SIGTERM" from "unexpected code 143". They would think the script had a bug.

**Recommendation:**

```bash
elif [ "$rc" -eq 130 ]; then
  echo "  [error] gitea push interrupted by user (SIGINT)" >&2
  exit 130
elif [ "$rc" -eq 143 ]; then
  echo "  [error] gitea push terminated by signal (SIGTERM)" >&2
  exit 143
```

**Severity rationale:** MEDIUM not LOW because the planning doc's failure-state matrix (§6 row 4) explicitly lists SIGTERM as a halt case AND the `dual-push.sh` exit-code contract documents 143 as a first-class code — so the dispatch table is genuinely incomplete relative to the contract. The current behavior (catch-all halts correctly) is not broken, but the message is misleading and any future regression that quietly downgrades 143 to "swallow" would slip past the existing tests.

**Status:** DEFER to fix-up — 4-line change, no test churn required. Could be folded into v4.7.10 fix-up if reviewer C agrees, or v4.7.11.

### B-M4 (MEDIUM) — Test #8 (`test_v4710_trap_restores_clean_url_on_sigint`) has a real-leak risk on slow CI

**Bug class:** Test fixture introduces credential leak under timing skew.

**Surface:** `quality/tests/test_deploy_scripts.py:344-460` (test 8).

**Trace:** Test 8 spawns `dual-push.sh` with a shim `git` that sleeps 5s on `push gitea`, then SIGINT's the process group. The pre-SIGINT phase calls the REAL `git remote set-url gitea` (forwarded by the shim, lines 374-377) to actually mutate `.git/config` — the test wants to verify the trap restored it.

The shim:
```bash
if [[ "$1" == "remote" && "$2" == "set-url" ]]; then
  exec "{real_git}" "$@"
fi
```

This means the test's `.git/config` will, for the duration of the 5-second sleep, contain `https://DECOY_USER_DO_NOT_LEAK:DECOY_TOKEN_DO_NOT_LEAK_12345@gitea.phalanxmadrone.com/example/repo.git`. The DECOY values are fake, but **the URL points at the real gitea host**. If, by some quirk of the shim's exec ordering, `git push gitea` were ever run against the REAL git binary against the REAL `.git/config` before the shim intercepts it, the test could attempt a network push (with fake creds) to the real gitea host. The shim does intercept `push` (lines 365-371), so this should not happen, but the safety margin is one-conditional-branch thin.

The deeper issue: test 8 is timing-dependent. It waits up to 5s for the `push gitea` log entry, then SIGINT's. On a slow CI runner, the SIGINT could land DURING the `git remote set-url` call (before the sleep starts) — in which case the trap fires, but the URL might be partially set or not yet set. The post-condition `re.search(r"://[^/]+:[^/@]+@", final_url) is None` would pass (correctly) but for the wrong reason (URL was never credentialed at all).

**Recommendation:** Either
- (a) Change `EXPECTED_GITEA_HOST` to `gitea.phalanxmadrone.com.invalid` for the test fixture (point at a non-routable host so even if the shim ever fails to intercept, the push hits DNS failure not a real server), OR
- (b) Add an explicit log-line assertion in the test confirming the `set-url` call DID happen before the SIGINT (so a passing test proves the trap was actually exercised, not just that nothing was credentialed).

**Severity rationale:** MEDIUM because the test sets up a real credential leak window (against the real gitea host) with synthetic creds. If a real gitea operator misconfigures CI auth, the test could in theory attempt to push to the real server. Single-line defensive change closes the risk.

**Status:** DEFER as a test-hardening fix-up. Not blocking for v4.7.10 deploy.

### B-L1 (LOW) — `dual-push.sh` origin-push failure under `set -e` exits with rc=1 but never logs the origin error

**Surface:** `dual-push.sh:144-145`.

**Trace:** Under `set -e`, a failed `git push origin "$BRANCH"` exits the script immediately with `rc=1`. The trap fires, which is correct. But there's no `|| echo "[dual-push] origin push failed: ..."` — the operator sees only the trap's silent restoration and the bash error. From the caller's (deploy.sh) point of view, in the manual catch-up flow `bash scripts/dual-push.sh develop` (no `--gitea-only`), an origin failure would be indistinguishable from a gitea failure.

**Recommendation:** Add `git push origin "$BRANCH" || { echo "[dual-push] origin push failed" >&2; exit 1; }` style logging. LOW because (a) `set -e` will already emit the offending command to stderr, (b) in normal deploy.sh use this branch is skipped (`--gitea-only`).

**Status:** DEFER.

### B-L2 (LOW) — Concurrent invocations race on `.git/config`

**Surface:** Whole script (no lockfile).

**Trace:** If the operator launches `deploy.sh` in two terminals simultaneously (mis-fire of muscle memory), both will eventually invoke `dual-push.sh --gitea-only`. The two processes can race on `git remote set-url gitea` calls. Possible outcomes:
- Run A rewrites URL to credentialed → Run B rewrites URL to credentialed (no change, same creds) → Run A pushes → Run B pushes (one will see "non-fast-forward") → Run A restores → Run B restores. End state: clean URL. Acceptable.
- Worse interleaving: Run A's trap fires BEFORE Run B starts pushing → Run B finds clean URL when it wants credentialed → Run B re-credentials → Run A's trap restores → Run B pushes against clean URL → push fails (no creds). Acceptable degradation, no leak.
- Pathological: Run A's trap fires DURING Run B's `git push gitea` → `.git/config` mutated mid-push → push behavior undefined (likely fails). No leak.

In all interleavings I can construct, no credentials are persisted past the slower trap's firing. **No leak, but observable confusion.**

**Recommendation:** Add a `flock`-based advisory lock around the URL-mutation block:

```bash
exec 9>".git/dualpush.lock"
flock 9 || { echo "[dual-push] another dual-push is running" >&2; exit 1; }
```

LOW because operationally near-impossible (the user does not launch deploy.sh twice in a single sitting) AND any race outcome is non-leak.

**Status:** DEFER. Acknowledged in planning doc §10 Reviewer B framing — explicitly accepted residual.

### B-L3 (LOW) — Trap does NOT use `set -E` (errtrace) — trap inheritance into functions

**Surface:** `dual-push.sh:54` `trap restore_gitea_url EXIT INT TERM`.

**Trace:** Without `set -E`, the EXIT trap is set on the top-level shell. Subshells (e.g., `$(...)` command substitution or `(...)` grouping) do NOT inherit the trap. The script does not use any subshells around the credential-bearing logic, so this is a non-issue in practice. But if a future maintainer wraps `inject_gitea_creds` in `$(inject_gitea_creds)` to capture its output, the trap would NOT fire in the subshell.

**Recommendation:** Add `set -E` near `set -euo pipefail` as a defense in depth. Documents intent.

**Status:** DEFER. Pure defense-in-depth, no current bug.

### B-L4 (LOW) — Bash 3.2 portability — script tested OK on local bash 3.2 but `printf '%s\n' "$*"` shim pattern is bash-4-ish in subtle ways

**Surface:** `quality/tests/test_deploy_scripts.py:103-128` (fake_git_bin) and `:354-372` (trap shim).

### B-L5 (LOW) — `_dualpush_preflight` `.env.local` check uses `grep -c` which counts blank-prefixed forms incorrectly

**Surface:** `scripts/dual-push.sh:85-95`.

**Trace:** Preflight checks key presence via:
```bash
user_count="$(grep -c '^GITEA_USER=' .env.local || true)"
```

If `.env.local` is `export GITEA_USER=...`, the grep regex `^GITEA_USER=` does NOT match — preflight fails with "missing GITEA_USER". This is a minor UX gap if the operator writes the file in `export FOO=bar` form (a common convention; `set -a; source .env.local; set +a` at line 107 DOES handle the `export` prefix via the `set -a` side effect, but only AFTER the preflight already rejected the file).

**Recommendation:** Relax the regex: `grep -c '^\(export[[:space:]]*\)\?GITEA_USER=' .env.local` or just `grep -cE '(^|^export[[:space:]]+)GITEA_USER='`. LOW because the current code's failure mode is "clear actionable error" not "silent leak."

**Status:** DEFER.

## 6. Recommended QUALITY_CONTEXT.md additions

Two new shell-side bug classes surface from this review:

1. **"Shell push without timeout"** — A `git push` invocation in a shell script that performs URL credentialing should be wrapped in a `timeout` command. Without it, a network blackhole creates an indefinite-hang window during which the trap that would restore a clean URL cannot fire. (B-M1)
2. **"Trap-coverage signal gap"** — A `trap ... EXIT INT TERM` does NOT cover SIGKILL or signals delivered to a stuck network syscall. Always pair credential-mutating shell scripts with a timeout AND document the SIGKILL residual. (B-M1 corollary)

These are shell-side, not Python-runtime, so they extend the current 47-class list into a new section. Defer the QUALITY_CONTEXT.md edit to a separate documentation pass (post-v4.7.10).
