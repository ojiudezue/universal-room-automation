### 1. `domain_coordinators/energy_pool.py` (D1 + D3)

#### Finding M1 -- `set_force_charge_override` does not validate timezone awareness (MEDIUM)

**Bug Class:** #11 (UTC vs local), #21 (naive/aware mix)

The docstring says "The caller is responsible for supplying a UTC-aware datetime" but the method performs no validation. If a caller passes a naive datetime (e.g., `datetime.now()` without tzinfo), the comparison `now_utc < self._force_charge_until` in `determine_actions()` will raise `TypeError` at runtime, crashing the entire energy decision cycle.

The current sole caller (`EVSEForceChargeButton.async_press`) correctly passes `dt_util.utcnow() + timedelta(...)`, so this is not exploitable today. But the API is public on the controller and any future caller could trigger it.

**Location:** `energy_pool.py` `set_force_charge_override()` (line ~364-371 post-patch)
**Action:** Add a defensive guard: `if until.tzinfo is None: raise ValueError("force_charge_until must be timezone-aware")`

#### Finding L1 -- Duplicate `from homeassistant.util import dt as dt_util` in `determine_actions` and `get_status` (LOW)

**Bug Class:** None (style)

The import `from homeassistant.util import dt as dt_util` appears as a deferred import inside both `determine_actions()` and `get_status()`. This is consistent with the existing deferred-import pattern in this file (imports inside methods to avoid circular import at module level), so it is correct but worth noting for future refactoring.

**Action:** No change needed.

#### D1 Strict Re-Pause: Correctness Verification

- The `_paused_by_us` guard is correctly removed ONLY from the enforcement path (`if state["is_on"]:`). The resume path (`if evse_id in self._paused_by_us:` in the off-peak branch) still uses the set correctly -- URA only resumes EVSEs it paused.
- `_paused_by_us.add(evse_id)` is still called after each turn_off action, maintaining correct bookkeeping for resume.
- The excess-solar exception (`if evse_id in self._excess_solar_active: continue`) fires BEFORE the D1/D3 checks, preserving the documented exception. Verified correct.
- The force-charge override check fires AFTER the excess-solar check but BEFORE the D1 strict re-pause. This ordering is correct: excess solar should not be interrupted even by an admin who forgot to cancel the override.
- **Strict policy verification:** During peak/mid_peak, with no override active and no excess solar, URA will issue `switch.turn_off` on every tick if the EVSE is on. Manual HA-side toggles are defeated within one decision cycle (<=5 min). Confirmed: the policy "all grid charging for EV should happen only during off-peak for every season" is enforced.

#### D3 Force-Charge Override: Edge Case Analysis

- **Midnight crossing:** If a user presses the button at 23:59 and the 30-min window crosses midnight into a different TOU period, the override persists correctly. The check is `now_utc < self._force_charge_until` -- pure datetime comparison, no date-boundary logic. If the TOU period transitions from mid_peak to off_peak at midnight, the force-charge override has no additional effect (off-peak doesn't pause anyway). If it transitions from off_peak to peak, the override correctly suppresses the new peak's pause. Working as designed.
- **Double-press within 1 second:** `set_force_charge_override` replaces (not stacks) the window. Two calls 1s apart: second wins, window is 30 min from second press. Correct.
- **Override expiry cleanup:** When `now_utc >= self._force_charge_until`, the field is set to `None` AND the log message fires. Next tick, `force_charge_active` will be False. Correct.
- **`get_status()` mirrors `determine_actions()` expiry logic:** Both check `now_utc < self._force_charge_until`. The status dict will show `None` for expired overrides. Correct.

### 4. `switch.py` (D2 sub-switch restore + D3 override attribute)

**Changes:** Adds `SIGNAL_ENERGY_COORDINATOR_READY` subscription in `async_added_to_hass`, new `_handle_ec_ready` callback, changes retry-exhaustion behavior to keep `_deferred_restore=True`, adds `async_write_ha_state()` calls on restore success, and creates `ECEvTouSwitch` subclass with `override_active_until_iso` attribute.

#### Finding M2 -- `ECEvTouSwitch.extra_state_attributes` accesses `energy.ev_controller` without None guard on the controller itself (MEDIUM)

**Bug Class:** #11 (None handling)

```python
ev = energy.ev_controller
until = ev.force_charge_until
```

The `_get_energy()` None check is present (returns `{}` if energy is None). But after that, the code trusts that `energy.ev_controller` is not None. The `ev_controller` property (energy.py:3527) returns `self._ev`, which is initialized in `__init__` as `self._ev = EVChargerController(hass, ...)`. So it cannot be None in normal operation. However, if EC is in a degraded state where `_ev` was never assigned (e.g., constructor exception caught partially), this could raise `AttributeError`.

**Likelihood:** Very low -- the `EVChargerController` constructor does not do I/O and cannot fail in practice.
**Action:** Consider wrapping in `try/except AttributeError: return {}` for defense-in-depth, or accept the risk.

#### D2 Sub-Switch Restore: Correctness Verification

- `async_on_remove(async_dispatcher_connect(...))` correctly tracks the unsub for Bug Class #38. Verified.
- `_handle_ec_ready` is decorated with `@callback` (synchronous). No `async_create_task` calls. Compliant with Bug Class #42 and #19.
- The retry-exhaustion path now keeps `_deferred_restore = True` instead of setting it to `False`. This is the key fix: the signal handler will still fire when EC eventually becomes available. Before this change, the retry chain's exhaustion was terminal. Correct.
- `async_write_ha_state()` is called in three places where restore succeeds: (a) immediate restore in `async_added_to_hass`, (b) `_handle_ec_ready`, (c) `_retry_restore`. This ensures the HA UI updates immediately on restore. Previously only the retry path was missing this call. Correct.
- The signal subscription is registered BEFORE `async_get_last_state()` is called. If EC init completes between subscription and the `_get_energy()` check, the signal fires but `_deferred_restore` is still False (not yet set), so `_handle_ec_ready` is a no-op. Then the fast-path in `async_added_to_hass` finds EC and restores immediately. No race condition. Correct.

### 5. `binary_sensor.py` (D2 synced sensor)

**Changes:** New `ECSubSwitchesSyncedSensor` class (diagnostic binary sensor, PROBLEM device class).

#### Finding H1 -- Synced sensor does not actually verify per-switch sync status (HIGH)

**Bug Class:** None (new -- see Recommendations)

The docstring and entity name claim to report "whether the 5 EC sub-switches have completed their saved-state restore." But the actual `is_on` property only checks whether `_get_energy()` returns None:

```python
@property
def is_on(self) -> bool | None:
    energy = self._get_energy()
    if energy is None:
        return True  # problem: not synced
    return False  # problem resolved: EC is registered, synced
```

This is a weaker guarantee than documented. EC being registered does NOT mean all 5 sub-switches have completed their deferred restore. The sub-switches restore independently via `_handle_ec_ready`, and the signal fires once (not per-switch). If a switch's `_handle_ec_ready` finds EC is still None in `hass.data` (the warning branch), that switch remains unsynced while this sensor reports "no problem."

The sensor's `extra_state_attributes` similarly only reports whether EC is registered and how long since `_ec_ready_at`, with a `mismatch_alert` flag for >10 min. But it never queries the actual switch entities to verify their `_deferred_restore` state.

**Impact:** The user may see the synced sensor as "no problem" while one or more sub-switches are actually stuck at constructor-seeded values. This defeats the purpose of D2's user-visible safeguard described in the planning doc.

**Action:** Either:
1. Rename the sensor to reflect what it actually checks ("EC Coordinator Registered" or "EC Init Completed"), or
2. Implement actual per-switch verification by querying the entity registry for the 5 sub-switch entities and checking their state matches the CM options values. This is the stronger fix but requires accessing switch entity state from within the binary sensor.

#### Finding M3 -- Type annotation `dt_util.dt.datetime` is fragile (MEDIUM)

**Bug Class:** None (type safety)

Line 1939:
```python
self._ec_ready_at: dt_util.dt.datetime | None = None
```

This references `dt_util.dt.datetime`, which assumes `dt_util` has already been imported at module level AND that `dt_util` re-exports `dt` from its internals. The correct type annotation would be `datetime` (imported from `datetime` module) or just use a string annotation `"datetime | None"`. If `dt_util` is not imported at the module level of binary_sensor.py, this annotation will fail at runtime when Python evaluates it (though `from __future__ import annotations` would defer evaluation).

**Location:** `binary_sensor.py` line 1939
**Action:** Change to `datetime | None` with a `from datetime import datetime` import, or verify that `from __future__ import annotations` is present at the top of the file.

#### Finding L2 -- `_SUB_SWITCH_SUFFIXES` tuple is defined but never used (LOW)

**Bug Class:** None (dead code)

The class defines:
```python
_SUB_SWITCH_SUFFIXES = (
    "grid_import_cap",
    "load_shedding",
    "excess_solar",
    "arbitrage",
    "ev_tou_management",
)
```

But this tuple is never referenced by any method. It appears to be scaffolding for a future per-switch verification that was not implemented (see H1).

**Action:** Either implement per-switch verification using this tuple, or remove it to avoid dead code confusion.

### 6. `button.py` (D3 force-charge button)

**Changes:** New `EVSEForceChargeButton` class with 30-min override window, NM notification, and observation mode gating.

#### Finding M4 -- Button accesses `energy._observation_mode` (private attribute) and `energy._send_nm_alert` (private method) (MEDIUM)

**Bug Class:** #23 (observation mode gating)

```python
if not energy._observation_mode:
    await energy._send_nm_alert(...)
```

The button reaches into two private members of `EnergyCoordinator`:
- `energy._observation_mode` -- there is a public property `energy.observation_mode` (line 3731 of energy.py) that should be used instead.
- `energy._send_nm_alert(...)` -- this is a private async method. The button is calling it correctly (await, proper args), and the observation mode gate is correctly checked BEFORE the call (Bug Class #23 compliant). But using private methods creates coupling that can break silently if the method signature changes.

The observation mode gating itself is correct: NM notification is suppressed when observation mode is on, and a debug log is emitted instead.

**Action:** Change `energy._observation_mode` to `energy.observation_mode` (use the public property). For `_send_nm_alert`, consider either promoting it to a semi-public method or having the button dispatch through a coordinator method like `energy.send_force_charge_notification(until_str)`.

#### D3 Edge Cases: Additional Verification

- **Envoy validation fails AFTER override opens:** The override is stored on `EVChargerController._force_charge_until`, which lives in memory on the EC instance. If Envoy validation fails and EC is torn down/reloaded, the override is lost (field reset to None in new instance's `__init__`). This means the override is NOT persistent across EC restarts. This is acceptable behavior -- an EC restart during a 30-min override window is an exceptional event, and silently reverting to strict enforcement is the safe default.
- **Observation mode toggled mid-override:** The force-charge override itself (`_force_charge_until`) is not gated by observation mode. The TOU pause bypass happens regardless. Only the NM notification is suppressed. This is correct: if an admin deliberately presses the button, the EVSE should charge regardless of observation mode. The observation mode gate only applies to the notification side-effect.
- **Button pressed when EC is None:** The `async_press` method checks `energy is None` and returns early with a warning log. Correct.

### 8. `quality/tests/test_v47x_ev_tou_hardening.py` (Test file)

**Changes:** 858-line test file with 33 tests covering all 4 deliverables.

#### Test Infrastructure Concern -- `sys.modules.setdefault` and `_FIXED_NOW` patching

**Confirmed:** The test file uses `sys.modules.setdefault(name, ...)` for all mocked HA modules (lines 59-117). The `setdefault` pattern means it only installs mocks if the module is not already loaded. This is safer than `sys.modules[name] = ...` (which would overwrite).

The `_FIXED_NOW = datetime(2026, 5, 27, 14, 0, 0, tzinfo=timezone.utc)` is installed as `homeassistant.util.dt.utcnow` via the mock module. Because `setdefault` is used, this mock only takes effect if no other test has already loaded `homeassistant.util.dt`. When run in the full suite, pytest collects and imports test files in alphabetical order. `test_v47x_ev_tou_hardening.py` runs after `test_v4_6_9_*` files, which also use the same `sys.modules.setdefault` pattern. The mock installed by whichever file is collected FIRST wins.

**Empirical result:** Running the full suite with and without this test file produces the same 58 failures and 14 errors. The test contamination is NOT manifesting in the current ordering. However, the risk is real if test collection order changes (e.g., via pytest-randomly plugin or file renaming).

**Practical mitigation already in place:** The D3 tests use far-future (2099) and far-past (2000) timestamps that are immune to any reasonable `_FIXED_NOW` value. The D1 tests do not use time at all. Only the integration test `test_override_does_not_affect_off_peak_resume` uses `_FIXED_NOW + timedelta(minutes=30)`, but this test only checks action generation, not time comparison.

**Assessment:** Low risk in practice. The test design (far-future/far-past timestamps) mitigates the contamination concern. No action required for this cycle, but the pattern should be noted for future test infrastructure improvements.

## Strict Policy Verification

**Policy:** "All grid charging for EV should happen only during off-peak for every season."

**Verified:**
1. D1 removes the `_paused_by_us` short-circuit. URA re-issues `switch.turn_off` on every decision tick during peak/mid_peak if the EVSE is on. Manual HA-side toggles are defeated within one cycle.
2. D3's force-charge override is the ONLY way to bypass the policy. It requires deliberate button press, fires NM notification, and auto-expires after 30 min.
3. The excess-solar exception (which allows EVSE charging during mid_peak when battery is full and solar is abundant) is preserved and fires BEFORE the D1/D3 checks.
4. There is a separate load-shedding path in `energy.py:2790` (`_execute_shed_action`) that still uses the `_paused_by_us not in` guard. This is a DIFFERENT code path (emergency load shedding, not TOU enforcement) and the guard is correct there -- load shedding should not double-pause an already-paused EVSE. The force-charge override does NOT apply to load-shedding-driven pauses, which is correct: load shedding is a safety/capacity concern that should override admin convenience.

**Result: Policy enforcement is correct and complete.**

## Recommendations for QUALITY_CONTEXT.md Updates

### Candidate New Bug Class: "Diagnostic Sensor Overpromises Scope"

**Pattern:** A diagnostic sensor's name/docstring claims it monitors a multi-component subsystem (e.g., "all 5 sub-switches synced") but its implementation only checks a proxy condition (e.g., "coordinator is registered"). The sensor passes all tests because the tests verify the proxy, not the claimed scope. Users trust the sensor's name and miss the actual failure mode.

**Recommendation:** Defer this bug class addition until H1 is resolved. If the sensor is renamed to match its actual scope, the class is not needed. If per-switch verification is implemented, the class serves as a reminder to verify diagnostic sensor claims match implementation.

### No changes needed to existing bug classes

Bug Classes #43, #23, #5, #11, #21, #38, #42, and #19 are all accurately described and the code correctly addresses them. No updates needed.
