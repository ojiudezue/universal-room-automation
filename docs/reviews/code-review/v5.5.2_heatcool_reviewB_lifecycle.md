the enforcer is idempotent, the new background task path is tracked, and the cross-writer

## #1 — suppress() handshake + feedback loop  ✅ PASS

**Trace.** Enforcer write path: `hvac.py:1083` `suppress(entity)` → `hvac.py:1085-1093`
`climate.set_hvac_mode: heat_cool` (blocking) → on success, log; on exception
`hvac.py:1099` `unsuppress(entity)`.

**Finding B-OK-1 (✅): except path restores state, no leaked suppression.**
The single write is the only awaited call inside the `try`. The `except` (`hvac.py:1098-1103`)
calls `unsuppress()` which pops the TTL entry (`hvac_override.py:516`). No partial-state /
double-suppress leak. Idempotent re-call of `suppress()` next tick just overwrites the
expiry — bounded.

**Finding B-OK-2 (✅): the set_hvac_mode write cannot register as an override — belt AND suspenders.**
Two independent reasons a suppressed `set_hvac_mode` is ignored by the arrester:

1. **TTL window (A-F5).** `suppress()` opens a `SUPPRESS_TTL_SECONDS = 5`s window
   (`hvac_override.py:73,506-508`). `_handle_climate_change` (`hvac_override.py:614-640`)
   checks `_suppressed_until` and `return`s while in-window — *except* it lets through a
   `preset_mode` transition INTO `"manual"` (`hvac_override.py:630-634`). A `set_hvac_mode`
   write changes `state`/`hvac_mode`, NOT `preset_mode`, so it never matches the
   manual-passthrough carve-out → stays suppressed. ✅
2. **Override detection doesn't key on hvac_mode at all.** Even with NO suppression,
   `is_override` is set only for `preset_mode == "manual"` (`hvac_override.py:659`) or a
   setpoint delta on a non-manual preset (`hvac_override.py:661`). A bare mode flip touches
   neither → not an override. This is exactly the gap the cycle is fixing, and it means
   **there is no feedback-loop risk even if the TTL expired early.** ✅

**Bug class:** Override Feedback Loop (the A-F5 class) — **not present**.

**Minor (B-LOW-1, ⚠️ tz-cosmetic, NOT a bug):** the arrester suppression clock uses
`dt_util.now()` (local, `hvac_override.py:507,616`) while the enforcer's emergency-hold clock
uses `dt_util.utcnow()` (`hvac.py:1075,1690`). Each comparison is **internally
self-consistent** (set and compared with the same function), so there is **no** Bug Class #11/#21
defect. Flagged only because mixing `now()`/`utcnow()` across the same feature invites a future
copy-paste error. No change required.

## #2 — runs EVERY cycle now (was gated to `off`)  ✅ PASS

**Idempotency (✅).** The guard is `zone.hvac_mode != "heat_cool"` (`hvac.py:1079`). When already
`heat_cool` the whole `if` is skipped → **no service call** → no 5-min spam. Confirmed by
`test_already_heat_cool_is_idempotent_no_write`. ✅

**Untracked background task / Bug Class #19 (✅).** The enforcer does NOT spawn a task — the write
is `await`ed inline under the held `_decision_cycle_lock` (`hvac.py:855-856`). The *emergency
heat* path that populates the hold IS a task, and it is correctly tracked:
`hvac.py:1625-1629` `async_create_task` → `_pending_tasks.add(task)` →
`task.add_done_callback(self._pending_tasks.discard)`. No Bug Class #19. ✅

**Async unsub leak / Bug Class #38 (✅).** The enforcer registers no new listeners or timers; it
reuses the existing 5-min `async_track_time_interval` (`hvac.py:668-671`) whose unsub is stored.
Nothing new to leak. ✅

**B-MED-1 (⚠️): per-cycle write-volume on a degraded thermostat.**
If a thermostat genuinely cannot hold `heat_cool` (advertises it but the underlying device
silently downgrades to `cool`/`heat` after each write — the exact failure
`_verify_restore` at `hvac_override.py:1265` was added to catch for AC-reset), the enforcer will
re-issue `set_hvac_mode: heat_cool` **every 5 minutes forever**, with no backoff and no
"gave up" counter. This is far gentler than the v5.0.0 write-flood (5-min cadence, one call per
drifted zone, not per-finding), so it is **not** a DB/write-queue hazard — but it is an
unbounded actuation loop against a misbehaving device and will spam the INFO log line at
`hvac.py:1094`. **Recommend:** a small per-zone consecutive-enforce counter that downgrades the
log to DEBUG after N (e.g. 3) and/or emits one diagnostic so a stuck zone is visible rather than
silently re-poked forever. Defer-acceptable for ship; track as follow-up.

## #3 — restart resilience of `_emergency_heat_zones`  ⚠️ HIGH (judgement call)

**B-HIGH-1: RAM-only hold lost on restart; enforcer can clobber `heat`→`heat_cool` before the
freeze hazard re-emits and re-populates the hold.**

**The dict is RAM-only** (`hvac.py:221`, `dict[str, Any]`), populated only on the
emergency-heat success path (`hvac.py:1689-1691`). It is **not** persisted (no RestoreEntity, no
DB). On HA restart during an active freeze, the hold is gone.

**Exposure window — quantified:**

- HVAC's **first** post-boot decision cycle is **suppressed** by the boot-settle gate until
  Predicate B releases (`EVENT_HOMEASSISTANT_STARTED` **or** `BOOT_SETTLE_TIMEOUT_SECONDS = 60`,
  `hvac.py:797,838-844`; const `1474`). So the enforcer does **not** run in the first ~0–60s.
  This is a meaningful mitigant. ✅
- The freeze re-emit, however, is **NOT** driven by the safety periodic check. `_async_periodic_check`
  (`safety.py:2066-2088`) only re-evaluates **flooding** escalation — it does **not** re-scan
  temperature sensors for freeze. Freeze is re-detected only via a **sensor state-change**
  (`safety.py:1099` → `_process_sensor` `safety.py:1209` → `_respond_to_hazard`
  `safety.py:1739` dispatches `SIGNAL_SAFETY_HAZARD`), gated by `is_new`
  (`safety.py:1698-1704`). After restart `_active_hazards` is also RAM-cleared, so the first
  post-boot below-threshold reading IS `is_new` → it **will** re-dispatch and re-populate the
  hold via `_set_emergency_heat`.
- **The race:** the freeze re-emit fires when the temp sensor publishes its first post-boot
  reading (typically an `unavailable→value` state change early in boot, also handled
  synchronously by `_evaluate_sensor_on_recovery` `safety.py:1122,1186` — though note that path
  updates `_active_hazards` but **discards** the returned hazards and does **not** itself
  dispatch the signal; dispatch still rides the async intent → `evaluate` →
  `_respond_to_hazard` path). If a slow/cloud temp sensor does not report until **after** the
  HVAC boot-settle gate releases (>60s), the enforcer's first real cycle can fire first and
  write `heat`→`heat_cool` on the still-freezing zone. Comfort/safety thermostats will keep
  *some* heating in `heat_cool`, so this is a partial-degradation (relaxed heating, possibly
  cooling allowed), not a hard heat-off — but it does **transiently fight the freeze response**
  for one decision cycle until the re-emit lands and re-arms the hold.

**Judgement.** The window is bounded (≤ one 5-min cycle, and only when the temp sensor is slower
to report than the 60s boot-settle gate). Pre-fix code left zones in `heat` indefinitely with no
recovery, so the feature does **not** regress freeze safety in steady state. But "enforcer can
momentarily undo an emergency-heat freeze response after a restart" is a safety-adjacent
behavior that deserves an explicit guard rather than relying on emit-ordering luck.

**Recommended mitigations (pick one, in order of preference):**
1. **Boot-guard:** on the first N post-boot decision cycles (or until `_startup_audit_done` +
   one settle), have the enforcer **skip `heat`-mode zones** specifically (only correct
   `off`/`cool`/`fan_only` drift at boot), since `heat` is the one drift that could be a live
   freeze response. Cheap, no persistence, closes the window.
2. **Persist the hold** (RestoreEntity attr or a small DB row) — heavier, and the 2h TTL makes a
   stale restored hold low-risk, but adds surface.
3. **Re-trigger freeze on boot from current readings:** have safety's startup do one synchronous
   temperature freeze scan that dispatches (today only `flooding` is periodic). Fixes the root
   "freeze only re-emits on state change" fragility for *all* consumers, not just this enforcer.

**Cleanup / unbounded growth (✅).** The dict is keyed by `zone_id` → bounded by zone count
(small, fixed). Expired entries are deleted lazily when the enforcer next visits the zone
(`hvac.py:1077`). A zone that is emergency-heat'd and then **removed** from the zone manager
would leave a stale key (the enforcer loop only iterates current zones, so it never revisits to
delete it) — but zone removal is rare, the value is a bounded 2h-expiry datetime, and the dict
can hold at most one entry per ever-seen zone. **B-LOW-2 (⚠️):** consider pruning
`_emergency_heat_zones` keys not in `self._zone_manager.zones` during the daily reset to be tidy.
Not a leak of consequence.

## #4 — cross-writer conflicts  ✅ PASS (no oscillation)

Enumerated every URA `set_hvac_mode` writer and checked it against the enforcer's gates:

| Writer | Target mode | Enforcer gate | Verdict |
|---|---|---|---|
| Enforcer (`hvac.py:1087`) | `heat_cool` | self | — |
| Emergency heat (`hvac.py:1679`) | `heat` | `_emergency_heat_zones` hold (`hvac.py:1073`) | ✅ gated, except the boot window in #3 |
| Egress pause (`hvac_egress.py:559`) | `off` | `is_paused` (`hvac.py:1069`) | ✅ skipped |
| Egress resume (`hvac_egress.py:631`) | `saved_mode` | `is_paused` clears only on resume completion | ✅ no overlap |
| Override revert (`hvac_override.py:938`) | `heat_cool` | converges (same target) | ✅ agree |
| AC reset OFF (`hvac_override.py:1172`) | `off` | `has_active_ac_reset` (`hvac.py:1081`) | ✅ skipped |
| AC reset restore (`hvac_override.py:1239/1274`) | `heat_cool` (when supported) | see B-OK-3 | ✅ converges |

**B-OK-3 (✅): the AC-reset-restore gap is benign.** `_reset_timers.pop(zone_id)` happens at
`hvac_override.py:1225`, **before** the restore write (`:1237`) and its 30s verify retries. So
`has_active_ac_reset` returns `False` during the restore window — the enforcer is **not** gated
there. BUT the AC-reset restore target is **also `heat_cool`** (`hvac_override.py:1221-1223`,
v4.7.32). So if the enforcer fires in that gap it writes the *same* `heat_cool` the restore is
already driving toward → idempotent collision, **no oscillation**. Worst case is one redundant
`set_hvac_mode: heat_cool` call. ✅

**D5 duty-cycle coast (✅ orthogonal).** Coast sets `preset` to `away`, not `hvac_mode`
(confirmed: no `set_hvac_mode` in the preset-apply path; the enforcer touches mode only). The
enforcer and preset-apply operate on **different attributes** of the same entity in the same
tick — `heat_cool` mode + `away` preset is a valid combined state. No conflict.

**No two writers drive the same entity to *different* modes in the same/next tick** except the
#3 boot-window emergency-heat case. ✅
