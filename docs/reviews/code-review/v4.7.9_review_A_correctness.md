### Cross-cell observations (HIGH and MEDIUM material)

**A-H1 — Press-while-mid-nudge timer collision.** The `force_ac_reset` method does NOT check `if zone_id in self._nudge_in_flight` before invoking the escalation, unlike `force_nudge` at L1748-1752 which explicitly refuses to overlap with an in-flight nudge. The hard-reset escalation path runs `_perform_ac_reset(zone)` which:
- Reads `original_mode = zone.hvac_mode` at L1033 (whatever it is **right now** — possibly mid-nudge state).
- Sets `set_hvac_mode → "off"`.
- Schedules `_on_reset_fire` after `AC_RESET_OFF_DURATION_SECONDS`.

Meanwhile, the in-flight nudge has TWO live `async_call_later` timers:
- `self._nudge_restore_timers[zone_id]` (set L1387) — will fire `_restore_after_nudge` which does `set_temperature(target_temp_high=original_target)` against a climate that is **currently off** because the reset set hvac_mode to off. The setpoint write may be accepted but won't actuate until the reset's restore re-enables the mode.
- `self._nudge_eval_timers[zone_id]` (set L1439 after restore) — fires `_evaluate_nudge_outcome` 10 minutes after nudge restore. By then, `kwh_rate_after` may be misleadingly low **because the AC is being force-cycled by the reset**, not because the soft-nudge succeeded. Could falsely classify the nudge as "effective" OR falsely escalate to another hard reset on noise.
- The hard-reset path L1180-1183 has a defensive `if zone_id in self._nudge_in_flight: self._nudge_in_flight.discard(zone_id)` inside `_restore_after_reset`, which fires AFTER reset completion. So the in-flight flag is eventually cleared, but the **restore and eval timers themselves are not cancelled**.

**Real-world consequence:** during a busy ramp-down (Cell 1 or Cell 3) with auto-nudge already running, a user presses Force Reset. The thermostat goes off → comes back to original mode (good), but the still-pending nudge restore timer writes a setpoint that may or may not be the user's actual target (because the nudge captured `original_target` from before the reset, and the user may have reset the nudge target manually in the interim).

**Why HIGH not CRITICAL:** the practical chance of this collision is low in steady-state — Cell 3 is the documented primary use case and it implies `_ac_nudge_enabled=False`, so there shouldn't BE a soft-nudge in flight to collide with. The collision matters only in Cell 1 (both enabled) where manual force-reset is fired while auto-nudge is already mid-window. Documentation of this limitation is acceptable, but a defensive check + timer-cancel in `force_ac_reset` is the higher-quality fix.

**Proposed fix (recommend for v4.7.9 before deploy):**
```python
async def force_ac_reset(self, zone_id_or_entity: str) -> None:
    if not self._ramp_master_enabled:
        ...
        return
    zone = self._resolve_zone(zone_id_or_entity)
    if zone is None:
        ...
        return
    # v4.7.9 A-H1: cancel any in-flight nudge timers/state before
    # stacking the hard-reset escalation. Mirrors cancel_nudge L1680-1686.
    if zone.zone_id in self._nudge_in_flight:
        cancel = self._nudge_restore_timers.pop(zone.zone_id, None)
        if cancel:
            cancel()
        cancel_eval = self._nudge_eval_timers.pop(zone.zone_id, None)
        if cancel_eval:
            cancel_eval()
        self._nudge_in_flight.discard(zone.zone_id)
        _LOGGER.info(
            "force_ac_reset: cancelled in-flight soft-nudge on %s before escalation",
            zone.zone_name,
        )
    ...
    await self._perform_hard_reset_escalation(zone, 0.0)
```

### Idempotency — re-press / button mash

User mashes the button 5 times in 2 seconds.

**Trace (Cell 1 baseline):**
- Press 1: gates pass; counter increments to 1; `_perform_ac_reset` schedules `_on_reset_fire` after `AC_RESET_OFF_DURATION_SECONDS` (e.g., 90s).
- Press 2 (< 1s later): gates pass again because `last_hard_reset_ts` was just written `now.isoformat()`, but the min-interval gate is `(now - last).total_seconds() / 60 < self._hard_reset_min_interval_min` — i.e., `< 1 minute` is virtually always < the default min-interval (look at production default below). If `_hard_reset_min_interval_min > 0`, Press 2 is correctly blocked with a warning log.
- Counter still gets to 1 only.

**Test sanity:** verify `_hard_reset_min_interval_min` defaults to a non-zero value. Search:
```
grep -n "_hard_reset_min_interval_min" hvac_override.py
```
The init reads from CM options at coordinator setup; if the user has explicitly set this to 0, mashing the button WILL bypass Gate B and rapidly fill the daily cap (after `_hard_reset_daily_limit` presses, Gate A fires lockout). That is correct behavior — user set min-interval to 0 explicitly.

**Verdict:** idempotency holds via existing Gate B for non-zero min-interval. No new finding; the existing protection covers force-button mashing.

### `_prev_tick_skip_reasons` snapshot lifecycle

**Initialization (`__init__` L443-452):**
```python
self._dynamic_preset_skip_reasons: dict[str, str] = {}
self._dynamic_preset_skip_reasons_prev: dict[str, str] = {}
```
Both initialized to empty `{}`. First-tick comparison is correct.

**Update site (L2792 + L2831):**
- `self._dynamic_preset_skip_reasons = updated_skip_reasons` — re-assigns to the new tick's dict. Note: this is a **reference assignment**, not a copy. If anything else mutates `updated_skip_reasons` after this line, both attributes change together. In the current code path, `updated_skip_reasons` is built locally within `_async_evaluate_dynamic_presets` and not exposed externally, so no real mutation risk — but defensive copy would be more robust.
- `self._dynamic_preset_skip_reasons_prev = dict(updated_skip_reasons)` — defensive copy on the prev side. Asymmetric vs the current-tick assignment.
- **Minor inconsistency (A-L1):** the comment claims "dict() copy ensures we don't capture the same reference we just assigned to self._dynamic_preset_skip_reasons above." This is technically correct but slightly misleading — it's the PREV side that gets the copy, not the current side. The current side does share a reference with `updated_skip_reasons`. No functional bug because the local goes out of scope at function return.

**Survives reload?** No — instance attribute on EnergyCoordinator. If EC reloads (e.g., via config-entry reload), the attr re-initializes to `{}`. First post-reload tick may double-fire (see Edge case above). Acceptable per plan.

**Update ordering — snapshot AFTER edge detection:**
- L2825: compare prev vs new.
- L2831: snapshot new into prev (after compare).
- L2832: fire if changed.
- **Order is correct.** Snapshot does NOT happen before compare. The test `test_snapshot_after_compare_for_next_tick` at L521 covers this.
