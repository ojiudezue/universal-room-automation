## A. Correctness of dedup mechanism

### A1 — Zone-identity key is correct  ✅
`aggregation.py:2956` checks `if self.zone not in warned_zones` and `:2957` does `warned_zones.add(self.zone)`. `self.zone` is the value passed by every Zone-Manager-driven entity constructor (`aggregation.py:434-458, 485` — `ZoneOccupiedSensor(hass, entry, zone_name)` etc., where `zone_name` is iterated from `merged.get("zones", {})`). Because all ~20 entities for a given URA-zone are constructed from the SAME `zone_name` string (same dict key), the dedup key is stable across the entity fan-out. Net behavior: 1 warning per URA-zone per setup, matching design.

### A2 — Zone-name collision risk  ✅ LOW
The dedup is keyed by raw zone-name string, not by config-entry id or canonical id. I considered:
- **Two URA-zones sharing one thermostat (Bug Class #36 territory):** these still have *distinct* URA-zone-name strings at the aggregation layer (the HVAC-zone-manager merge to `"X + Y"` happens downstream in `hvac_zones.py`). At ZoneSensorBase, `self.zone == "Master Suite"` and `self.zone == "Entertainment"` are distinct dict keys → distinct dedup entries → each warns once if coordinator-less. Correct.
- **Same zone presenting under two name spellings (e.g., trim/whitespace, casing drift):** `config_flow.py:732` strips whitespace at config-entry creation; `_get_zone_coordinators()` (`aggregation.py:2988`) does a raw `coord_zone == self.zone` compare with no normalization. If two callers somehow introduced `"Master Suite"` vs `"master_suite"` for what should be one URA-zone, the dedup would treat them as separate zones (correctly mirroring the rest of the codebase's case-sensitive treatment). Not a regression introduced here.

**Finding: LOW (info).** No collision risk introduced by this change.

### A3 — Empty / None zone-name edge case  ⚠️ LOW
`aggregation.py:343-346` and `:396-399` already short-circuit setup for an entry where `zone_name` is falsy (warning + return), so a ZoneSensorBase with `self.zone is None / ""` cannot reach `_check_coordinators` via the Zone-Manager setup path. The legacy `ENTRY_TYPE_ZONE` path (`:340`) has the same guard. The dedup set could in principle accept `None` or `""` as a key (Python sets don't mind), so there is no AttributeError risk if a future bypass path skips the guard. **Finding: LOW (info)** — no defect; documenting the invariant.

### A4 — `self.zone not in warned_zones` is a synchronous read-check-then-add  ✅
The dedup pattern executes:
```python
warned_zones = self.hass.data.setdefault(DOMAIN, {}).setdefault(
    "_no_coord_warned_zones", set()
)
if self.zone not in warned_zones:
    warned_zones.add(self.zone)
    _LOGGER.warning(...)
```
This is inside the `_check_coordinators` `@callback` body (`aggregation.py:2925`) registered with `async_track_time_interval`. HA dispatches scheduled callbacks on the event-loop thread, single-threaded; the `@callback` decorator at `:2925` enforces synchronous-on-loop execution. Between the membership check (`:2956`) and the `add` (`:2957`) there is **no `await`, no yield, no I/O**, so even if N entities' timers fire in the same loop tick they each execute the read-check-then-add atomically with respect to each other.

The comment in production code (`:2950-2952`) makes this reasoning explicit and accurate. Reviewer B owns the broader async-lifecycle audit; from a pure data-structure-correctness angle there is no TOCTOU here. **No finding.**

### A5 — `hass.data` shape robustness  ✅
`hass.data.setdefault(DOMAIN, {}).setdefault("_no_coord_warned_zones", set())` is the canonical HA-idiomatic seed. Risks I considered:
- **`hass.data[DOMAIN]` set to a non-dict by some other path:** I greped the codebase for direct writes to `hass.data[DOMAIN]` — every site treats it as a dict or sets it from `hass.data.setdefault(DOMAIN, {})`. No risk.
- **`_no_coord_warned_zones` pre-populated as a non-set:** the only writer is this one site (set) plus the `pop(...)` in `__init__.py:2965` (read-deletion). No risk of type drift.
- **Race against the `__init__.py:2965` `pop` during reload:** the `pop` happens inside an `async def async_unload_entry`, which during a reload runs *after* all platforms finish unloading. `async_will_remove_from_hass` (`aggregation.py:2971`) cancels every entity's timer before unload returns, so no `_check_coordinators` callback can fire concurrently with the pop. The new entities created after the pop call `setdefault` again, which creates a fresh empty set. Correct.

**No finding.**

### A6 — Coordinators appear after some entities already warned  ⚠️ MEDIUM
Scenario: zone `master_suite` enters `_check_coordinators` retry. At t≈55s, entity #1 fires its t=60s tick, sees `coords == []`, hits the elif branch, adds `master_suite` to `warned_zones`, emits the warning, cancels its timer. At t≈58s, a room coordinator for `master_suite` finishes setting up. At t≈60s, entity #2 fires, sees `coords != []`, hits the if branch at `:2930-2940` — marks itself ready, cancels its timer — **but never removes `master_suite` from `warned_zones`**. The warning was already emitted, and `master_suite` is now correctly served, but the dedup set retains a stale entry for the rest of the integration's lifetime.

**Behavioral impact:** zero. The dedup set is only read inside the elif branch that fires *when no coordinators are found* — and now there ARE coordinators, so subsequent retries (if any other zone hits this code path) are unaffected. There's no functional regression. The stale entry sits in `hass.data[DOMAIN]["_no_coord_warned_zones"]` until unload, occupies ~50 bytes, and is harmless.

**However:** if a future edit ever wires this set into a "is this zone unhealthy" check, the stale entry would create a false positive. Worth a one-line cleanup in the success branch.

**Finding: MEDIUM** — minor cleanliness. Recommendation: in the `if coords:` branch at `:2930-2940`, after marking ready, do `self.hass.data.get(DOMAIN, {}).get("_no_coord_warned_zones", set()).discard(self.zone)`. Defers cleanly if the set was never created. Not blocking.

## B. Test authority (the user-flagged concern)

### B/4 — Behavioral test replicates production rather than invoking it  🚩 HIGH
This is the most material correctness concern in the cycle.

`_drive_to_max_retries` (`test_v4_7_18_2_boot_warning_logonce.py:417-449`) literally re-implements the production elif-branch body:
```python
def _drive_to_max_retries(entity, max_retries: int = 12):
    ...
    for _ in range(max_retries):
        entity._retry_count += 1
        coords = entity._get_zone_coordinators()
        if coords:
            entity._coordinators_ready = True
            continue
        if entity._retry_count >= max_retries:
            warned_zones = entity.hass.data.setdefault(DOMAIN, {}).setdefault(
                "_no_coord_warned_zones", set()
            )
            if entity.zone not in warned_zones:
                warned_zones.add(entity.zone)
                _LOGGER.warning(...)
            ...
```
The behavioral test thus validates the test author's re-implementation against the test author's expectations. Per **Bug Class #40 (Self-Validating Behavioral Tests)** this is a known anti-pattern — production can drift in shape (e.g., the dedup key changes to `(zone, entry_id)`, or the membership check moves to a different branch, or the `setdefault` namespace key gets renamed) and the behavioral test will continue to pass green.

The author's docstring at `:421-426` acknowledges this and points at the AST canaries as the safety net. The AST canaries are:

1. `test_warned_zones_set_keyed_by_self_zone` (`:290-305`) — string-grep for `"_no_coord_warned_zones"`, `"warned_zones.add(self.zone)"`, `"if self.zone not in warned_zones"` in `aggregation.py`.
2. `test_no_per_entity_log_once_flag_remnant` (`:307-314`) — grep that `_coordinator_warning_logged` is absent.
3. `test_unload_clears_warned_zones` (`:316-322`) — grep that `_no_coord_warned_zones` appears in `__init__.py`.
4. `test_warning_call_inside_membership_guard` (`:324-374`) — real AST walk: finds `ZoneSensorBase.async_added_to_hass`, walks for an `if self.zone not in warned_zones` test, then walks INSIDE that node for a `_LOGGER.warning(...)` call whose first arg contains `"No room coordinators found after"`.

**How well do the canaries actually catch divergence?**

- **String renames of the dedup key** (e.g., `_no_coord_warned_zones` → `_no_coord_zones_warned`) — caught by #1 and #3.
- **Switching to `id(self)` / `self.entity_id`** as the dedup key — caught by #1 and #4 (the AST check verifies the guard is `self.zone not in <set>`).
- **Moving the dedup OUT of `async_added_to_hass`** entirely (e.g., into `async_will_remove_from_hass` by mistake) — caught by #4 (walks specifically inside `async_added_to_hass`).
- **Reintroducing the per-entity flag** — caught by #2.
- **Inverting the membership check** (`if self.zone IN warned_zones: warn` — the obvious regression) — **caught by #4** (the AST scan asserts the warning sits inside a `NotIn`-flavored `Compare`).

Gaps:
- **Dedup `set` replaced with a dict keyed on `self.zone`** with payload `{warned: True}` — production still works, AST `Compare` with `NotIn` still passes (`if self.zone not in warned_zones:` works against a dict too), but the behavioral test would silently diverge from production. Low likelihood; would need an intentional refactor.
- **Dedup window made TTL-based** (e.g., a `{zone: timestamp}` dict with re-warn after 1h) — AST canaries silent, behavioral test silent, behavior changed.
- **Future change to log at INFO instead of WARNING** — `caplog.at_level(logging.WARNING, ...)` in the behavioral test would simply not capture the INFO emit; the test would assert `len(warnings) == 1` against `[]` and FAIL — actually a correct failure, just not informative. (This is fine.)

**Assessment:** the canaries cover ~80% of plausible drift. The 20% gap is mostly intentional-refactor territory rather than honest-mistake territory. Given (a) the change is cosmetic-log-spam only, (b) Reviewer B will examine lifecycle / reload independently, and (c) the AST canaries are unusually thorough for a "small fix," this is **HIGH-not-CRITICAL** in my framing — meaning ship it, but note that this same pattern recurring in functionally-load-bearing code would be CRITICAL.

**Recommendation (non-blocking for ship):** the cheapest hardening is to monkeypatch `_check_coordinators` extraction. The author claims it "can't easily be extracted without running `async_added_to_hass`" — but `async_added_to_hass` is a coroutine that, mocked correctly, just calls `_get_zone_coordinators` once (returns `[]` because we stub it) and then `async_track_time_interval` (our capturing stub returns a MagicMock unsub). The captured timer callback IS the production closure. The test already has `_CAPTURED_TIMERS` (line 80) — it just never uses the captured callback. Replacing `_drive_to_max_retries` with `for _ in range(12): _CAPTURED_TIMERS[idx][1](None)` would invoke production exactly. About a 10-LoC fix-up for a meaningful integrity gain. Filing as HIGH because it removes the entire 20% drift gap; closing it inside this cycle would convert the verdict to unconditional SHIP.

## C. Edge cases

### C1 — Late-arriving coordinators (after some entities already warned)
Covered in A6 above. Stale-set-entry, no functional impact. MEDIUM cleanup recommendation.

### C2 — Entity re-add lifecycle  ✅
HA does not re-add an entity instance after `async_will_remove_from_hass`; on entity registry restoration after a restart, fresh ZoneSensorBase instances are constructed. `async_will_remove_from_hass` (`aggregation.py:2971-2975`) cancels the per-entity retry timer, so a remove during the retry window correctly stops the timer. The dedup set is *not* cleaned up on per-entity removal — only on Zone Manager unload — which is the design intent (the zone is still the same zone). Correct.

### C3 — Zone Manager unload-clear path  ✅
`__init__.py:2965` does `hass.data.get(DOMAIN, {}).pop("_no_coord_warned_zones", None)`. The `.get(DOMAIN, {})` defensive fallback handles the case where the integration entry already unloaded (popped `DOMAIN` itself). The trailing `, None)` default suppresses KeyError if the set was never created. Safe under all unload orderings I considered (integration-before-zm, zm-only, zm-only-with-no-prior-warns).

**Note (LOW, not a finding):** `hass.data.get(DOMAIN, {})` returns a *new empty dict* if `DOMAIN` is absent — and the `.pop` operates on that throwaway dict. Net effect: no-op, which is what we want. Correct.

### C4 — Reload semantics  ✅
After the unload-pop, a subsequent reload re-creates `ZoneSensorBase` instances; the first one to hit t=60s in a coordinator-less zone re-creates `_no_coord_warned_zones` via `setdefault` and re-warns. Live operator gets one warning per zone per reload — exactly the design intent per the operator memo ("track but ignore" pre-fix → "one warning per zone after fix").

### C5 — Bug Class #17 (Unbounded Retry Loops) reminder
The retry is correctly bounded (`max_retries = 12`, `:2923`) and the timer is cancelled in BOTH branches (success at `:2938-2940`, failure at `:2963-2965`). Not new in this cycle but worth noting that the change preserves the bounded-retry guarantee.

### C6 — Bug Class #19 (Untracked Background Tasks) ✅
The dedup-set write is synchronous; no `async_create_task` is spawned. Not in scope.
