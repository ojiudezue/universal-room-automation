### HIGH-1: `_zone_manager.zones[zone_id].room_conditions` skips rooms whose coordinators haven't booted (Bug Class #43 — Bookkeeping Short-Circuit Defeated by External State Change)

**Files:**
- `domain_coordinators/hvac_zones.py:494-495` (skip when room coordinator is None)
- `domain_coordinators/hvac_egress.py:347-353` (consumes room_conditions for egress aggregation)

**Issue.** `ZoneManager.update_room_conditions` skips any room whose coordinator hasn't yet registered in `hass.data[DOMAIN]` (line 495: `if coordinator is None: continue`). The `RoomCondition` for that room is never appended. EgressManager then iterates `zone_state.room_conditions` at L347 to determine `any_egress_open`. If the room with the open egress window is the *only* affected room AND its coordinator is briefly absent (boot ordering, reload mid-tick, room entry just-loaded), egress aggregation evaluates to False and:

- `counting` state does not engage even though the window is open
- a paused zone with that single room sees `any_egress_open = False` and starts resume_countdown prematurely

This is the v4.7.5 boot-ordering risk repeating — same class as Bug Class #43 (bookkeeping short-circuit defeated by external state change).

**Reproduction risk.** Low in practice (post-bootstrap ticks should have all rooms loaded) but the failure mode is silent — no log, no sensor evidence. After HA restart, the FIRST tick is most exposed.

**Recommended fix.** In `update_room_conditions`, when `coordinator is None` but `room_entry_meta[room_name]` IS present (i.e., the room entry exists but its coordinator hasn't booted), STILL append a `RoomCondition` with `temperature=None, humidity=None, occupied=False` but with the `window_sensor` and `is_egress_window` fields populated from `room_entry_meta`. Egress aggregation works from window state alone, not from coordinator-supplied data.

```python
# hvac_zones.py:493+
for room_name in zone.rooms:
    coordinator = room_coordinators.get(room_name)
    meta = room_entry_meta.get(room_name, {})
    # v4.7.8 — read window state even when coordinator absent (egress safety)
    window_sensor = meta.get("window_sensor")
    window_state = None
    if window_sensor:
        try:
            st = self.hass.states.get(window_sensor)
            if st is not None:
                window_state = st.state
        except Exception:
            window_state = None
    if coordinator is None:
        # Append a coordinator-less RoomCondition so EgressManager still sees
        # the window state. Other rules already tolerate occupied=False.
        zone.room_conditions.append(RoomCondition(
            room_name=room_name,
            window_sensor=window_sensor,
            window_state=window_state,
            is_egress_window=bool(meta.get("is_egress_window", True)),
            room_entry_id=meta.get("entry_id"),
        ))
        continue
    # ... existing body
```

### MEDIUM-2: Snapshot reads stale `preset_mode` mid-resume_countdown (Bug Class #14 — Config Snapshot Staleness, indirect)

**File:** `domain_coordinators/hvac_egress.py:454-498` (`_engage_pause`)

**Issue.** Snapshot of `prior_mode + prior_preset` from `hass.states.get(thermostat)` happens at the same tick as the `set_hvac_mode:off` dispatch. Plan task #2 framing: "the snapshot at T and dispatch at T+ε with state machine moves between is a meaningful representation of what the user wanted before egress fired?" Answer: snapshot is taken from HA's in-memory `state.state` — which reflects HA's last-known thermostat state, NOT necessarily the live thermostat. If a v4.7.7 AC Nudge had dispatched `set_temperature` 30s ago, the thermostat's mode and preset are stable; the prior_preset snapshot is correct.

But — if HA's state machine reports a TRANSITIONAL preset (e.g., the user JUST clicked a preset in the UI 1 second before egress threshold fires), `prior_preset` captures the new preset, not the user's original target. On resume, URA restores that new preset. **Net: URA preserves whatever HA's state machine says was "current" — which is the right intent.**

The only edge case that breaks: if the user mid-click is the trigger of an over-ridden preset that HA hasn't yet acknowledged. The race window is sub-second.

**Severity.** Documented for the reviewer's task #2 (snapshot/restore atomicity); not actionable. Plan §D6 acceptance for "Idempotent restore" covers the symmetric case (URA-set-off mode).

**Recommended fix.** None required. Add a code comment at L462-463 documenting the assumption: "Snapshot reflects HA's last-known state; brief mid-click races may snapshot a transient preset. Acceptable per planning §D3 — egress favors current intent."

## Snapshot/Restore Atomicity (Reviewer A's task #2)

The snapshot of `prior_mode + prior_preset` at `_engage_pause` L460-463:

```python
st = self._hass.states.get(thermostat)
if st is not None:
    prior_mode = st.state or ""
    prior_preset = st.attributes.get("preset_mode") or ""
```

Both fields come from a SINGLE `states.get()` call → atomic with respect to HA's state machine. Race window between the snapshot read and the subsequent `set_hvac_mode:off` dispatch:

- Snapshot at L460 (T=0)
- Dispatch at L479 (T+~100µs — interleaved code is pure dict ops)
- HA state update propagates: T+ε after dispatch returns

Between T+100µs and T+ε, no other URA code runs (we hold `_decision_cycle_lock`). External HA events (e.g., a separate automation firing `climate.set_preset_mode`) could fire between awaits, but the only `await` between snapshot and dispatch is the dispatch itself. Race window: zero.

**Verdict.** Atomic enough. Documented; no fix needed.
