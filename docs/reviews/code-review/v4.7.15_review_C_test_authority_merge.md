## C2 — Helper Relocation Refactor Risk (D4)

### C2.1 — Migration completeness

Cited sites:
- **Old location** (per builder report): `hvac.py:1350` — `_check_zone_occupancy_confidence`.
- **New location:** `presence.py:829-921` — `check_zone_occupancy_confidence` (public method).

- `grep "check_zone_occupancy_confidence" hvac.py` → 2 hits, both at the caller site at `:921` and `:923`.
- The deletion stub at `:1401-1408` is a clean marker (no leftover code).

### C2.2 — Caller rewire correctness

The caller at `hvac.py:911-925` properly fetches `presence` via the coordinator-manager:

```python
manager = self.hass.data.get(DOMAIN, {}).get("coordinator_manager")
presence = manager.coordinators.get("presence") if (
    manager is not None and hasattr(manager, "coordinators")
) else None
if presence is not None and hasattr(
    presence, "check_zone_occupancy_confidence",
):
    confirmed, possible = presence.check_zone_occupancy_confidence(zone)
else:
    confirmed, possible = 0, 0
```

This is well-defended:
- Manager-absent fallback: `(0, 0)`.
- `hasattr` guard against boot-race (presence not yet registered): `(0, 0)`.
- The downstream threshold logic at `:927-948` correctly handles `possible=0` (`threshold=1` per `:927`, `confirmed=0 < threshold` → "stale sensor" branch).

**Semantics preserved:** When the helper used to live on `HVACCoordinator`, the only difference at the call site was `self._check_zone_occupancy_confidence(zone)`. Now it's a 4-line guarded fetch + call. The "(confirmed, possible) tuple shape preserved" claim in the deletion comment is correct.

### C2.3 — Risk: lifecycle ordering

**MEDIUM finding:** `_run` lifecycle is not the concern here — the caller is in `_apply_house_state_presets` (`hvac.py:775`), which is invoked by `_run` (`:707`). The risk is that on a cold restart, `_apply_house_state_presets` could be reached BEFORE `PresenceCoordinator` is registered in `hass.data[DOMAIN]["coordinator_manager"].coordinators`. The `hasattr` guard handles this, but the *behavior* during the boot race is now different from v4.7.14:
- **v4.7.14:** the helper was an HVAC method, available immediately when the HVAC coordinator's `_apply_house_state_presets` was reachable. Multi-source confidence check fired correctly.
- **v4.7.15 D4:** during the brief boot window where HVAC is up but Presence is not yet wired to `coordinator_manager.coordinators`, the call returns `(0, 0)` → threshold becomes 1, confirmed is 0, **so the path falls to "stale sensor" → effective_preset='away'.** Until v4.7.14 this would have used the real multi-source confidence; now it conservatively forces away.

This is a subtle preset-application *behavior change* during boot race, not a correctness bug. The conservative direction (force away under uncertainty) is defensible but is not documented in the README §10 limitations.

**Recommendation:** Add to README §10 known limitations: *"During cold boot, if `_apply_house_state_presets` runs before PresenceCoordinator registers with coordinator_manager.coordinators, multi-source confidence falls back to (0, 0) and the failsafe forces effective_preset='away' for that one cycle. v4.7.14 behavior was to use HVAC's local helper synchronously. The 5-15 second boot window where this matters is bounded by the next `_run` tick."*

This costs nothing and prevents a "why did HVAC briefly force away on startup?" investigation in 3 months.

### C2 verdict

Relocation is purely additive on the presence side. Single caller rewired correctly. Deletion stub clean. No remaining `_check_zone_occupancy_confidence` references. **MEDIUM** finding on boot-race behavior change should be reflected in README §10.

## C3 — Parallel-Merge Risk with v4.7.14.1 (sibling)

### C3.1 — The shape of v4.7.14.1

Per `docs/planning/PLANNING_v4.7.14.1_forgotten_phone_hotfix.md:78`:

> "What v4.7.14.1 changes at the call site (`presence.py:1896-1923`): The `all_tracked_persons_away` computation gets two new filters (H2 phone-left-behind exclusion, H3 tracking_status exclusion) BEFORE the `all(...)` reduction."

v4.7.14.1 modifies `_run_inference` IN PLACE at lines 1896-1923 (per plan), adding `_phone_trustworthy()` and `_tracking_active()` local helpers, and tightening the `unidentified_count == 0` predicate to `unidentified_count == 0 AND census_count == 0` (H1).

Crucially, **v4.7.14.1 does NOT route through the v4.7.15 D1 helper** — it modifies the inline `_run_inference` block that v4.7.14 originally shipped. This is consistent with the v4.7.14.1 plan being authored before v4.7.15 D1 was even spec'd.

### C3.2 — The shape of v4.7.15 D1 Pattern A

The shipped Pattern A at `presence.py:734-751` re-implements the v4.7.14 logic **inline within the helper**, NOT by consuming H1/H2/H3 from the call site. Specifically:

```python
if scope == "house_inference":
    all_away = any(
        s.kind == "person_tracker_away" and s.value for s in reliable_signals
    )
    any_home = any(
        s.kind == "person_tracker_home" and s.value for s in reliable_signals
    )
    unid = next(
        (s.count for s in transient_signals
         if s.kind == "unidentified_person_count"),
        0,
    )
    if tracked_count > 0 and all_away and not any_home and unid == 0:
        return VetoDecision(...)
```

The helper:
- Expects the call site to pre-compute `all_away` and `any_home` for each person and emit them as `ReliableSignal("person_tracker_away", True)` + `ReliableSignal("person_tracker_home", True)`.
- Has no concept of `census_count`, `phone_left_behind`, or `tracking_status` (H1/H2/H3 surfaces).

### C3.3 — CRITICAL: Naive merge produces semantic divergence

**The risk:** if v4.7.14.1 ships first (per its plan, Reviewer C of that cycle), then v4.7.15 D1 lands as-built, the system has:
- **Two different "all_tracked_persons_away" predicates running in different places:**
  1. The v4.7.14.1 inline computation at `presence.py:~1896-1937` (which excludes phone-left-behind and STALE/LOST trackers, and requires `census_count == 0`).
  2. The v4.7.15 D1 Pattern A computation at `presence.py:734-751` (which uses only the raw `person_tracker_away` / `person_tracker_home` signals from whatever the caller passes).

If a **future caller** (e.g., v4.7.16 D3 room-level) consults the D1 helper with `scope="house_inference"`, it will get **v4.7.14 semantics, not v4.7.14.1's hardened semantics.** That is a CRITICAL bug class regression because the entire purpose of v4.7.14.1 is to prevent ghost-presence under STALE phone tracking, and any caller bypassing the inline call site loses that protection.

### C3.4 — Required merge order

This is the C3 recommendation, explicit:

1. **v4.7.14.1 lands first** (per its Reviewer C decision).
2. **v4.7.15 rebases** onto v4.7.14.1.
3. **v4.7.15 D1 fix-up (mandatory before deploy):** Pattern A in `presence.py:734-751` is **rewritten to consume v4.7.14.1's H1/H2/H3 surfaces** rather than re-implementing them inline. Concretely:
   - The Pattern A `state_context` accepts new keys `census_count`, `phone_left_behind_persons` (set), `stale_tracking_persons` (set).
   - The `tracked_count` already passed in is interpreted as the **post-H2/H3-filter denominator**, not the raw person-count.
   - The Pattern A predicate becomes: `tracked_count > 0 and all_away and not any_home and unid == 0 and census_count == 0`.
4. **v4.7.14.1's inline H1/H2/H3 logic is replaced by a single `should_veto_due_to_reliable_signals(scope="house_inference", state_context={... full H1/H2/H3 surfaces ...})` call.** The local helpers `_phone_trustworthy` and `_tracking_active` move into the call-site preparation block (NOT into the D1 helper itself — they read entity state, the D1 helper should remain pure).
5. **Tests updated:** every Pattern A test in v4.7.15 gets a `census_count=0` parameter in `state_context`; new tests for `census_count > 0` blocks the veto.

## C4 — Parallel-Merge Risk with v4.7.16 (successor)

### C4.1 — Reading the v4.7.16 plan

`PLANNING_v4.7.16_room_level_veto_density_weighting.md:287-291`:

> "The veto helper from v4.7.15 (signature pending — see §0.7) is expected to take:
> - `signals: list[RoomSignal]` where each `RoomSignal = (room_name, mode_tier, weight, source_kind)`
> - `inputs: VetoInputs` (all_tracked_persons_away, house_state, etc.)
> - returns: `VetoVerdict` — one of `accept_occupied`, `veto_to_away`, `defer_to_consensus`"

v4.7.16 expects:
- A `list[RoomSignal]` where each element carries a `weight: float`.
- A `VetoVerdict` enum return with **three** values: `accept_occupied | veto_to_away | defer_to_consensus`.

### C4.2 — What v4.7.15 actually shipped

`presence.py:707-824` ships:
- `reliable_signals: List[ReliableSignal]` where `ReliableSignal = (kind: str, value: bool)`. **No weight field.**
- `transient_signals: List[TransientSignal]` where `TransientSignal = (kind: str, count: int)`. **No weight field.**
- Returns `VetoDecision(fired: bool, confidence: float, reason: str, scope: str)`. **Binary fired/not-fired, no three-valued verdict.**

### C4.3 — CRITICAL: Contract drift between plan and ship

v4.7.15 shipped a **different signature** than v4.7.16's plan expects. This is exactly the kind of cross-cycle blind spot Reviewer A's A7 and Reviewer B's B6 flagged (per task brief), but with a more specific framing:

- v4.7.16 D3 cannot just add `scope="room_level_weighted"` to the existing helper — its weighted signals do not fit `ReliableSignal(kind, value)`.
- v4.7.16 D3 cannot consume the existing 3-valued verdict — it needs to express "defer to other consensus channels" which is not in `VetoDecision`.

If v4.7.16 lands naively, one of two bad things happens:
1. v4.7.16 **bypasses the D1 helper** and re-implements the room-level veto inline, **defeating the entire purpose of v4.7.15** (universalize Bug Class #48 patterns into a shared helper).
2. v4.7.16 **changes the D1 helper signature** breaking the v4.7.14 Pattern A test corpus and possibly the D2/D3 call sites.

### C4.4 — Required merge order with explicit fix-up location

Putting C3 and C4 together, the full sprint sequence is:

```
Step 1: v4.7.14.1 lands as-built (inline H1/H2/H3 at presence.py:1896-1937).
        Production behavior: hardened forgotten-phone veto.

Step 2: v4.7.15 lands as-built (D1 helper at presence.py:707-824 with current signature).
        Production behavior: zone aggregator non-sleep + WAKING + GUEST exit covered.
        Known dead spot: house_inference Pattern A doesn't consume H1/H2/H3.

Step 3a: v4.7.15.1 follow-up cycle (NEW — recommended).
         (a) Extend ReliableSignal/TransientSignal with optional `weight: float = 1.0`.
         (b) Extend VetoDecision with a third-state mode:
             VetoDecision(fired, confidence, reason, scope, defer_to_consensus: bool = False).
             OR introduce a sibling VerdictDecision class returned by a separate
             helper method `assess_room_consensus(...)` that v4.7.16 calls.
         (c) Refactor v4.7.14.1's inline H1/H2/H3 to flow through Pattern A via

         (d) Update Pattern A predicate to consume those new keys.
         (e) Update all D1 Pattern A tests to pass census_count=0 by default.

Step 3b: v4.7.16 lands AFTER 3a.
         (a) Adds Pattern F: scope="room_level_weighted" or "room_consensus".
         (b) Uses weighted ReliableSignal entries (now possible after step 3a.a).
         (c) Returns either VetoDecision with defer_to_consensus=True, OR

```

### C4.5 — Specifically what Pattern F needs

If we choose to extend the existing helper with `scope="room_level_weighted"` (instead of adding a sibling helper):

- **signal_set required:** list of `ReliableSignal(kind="room_occupied", value=bool, weight=float)` — one per room in the zone. Weight derived from `person_coord.get_ble_tier(room_name)` per v4.7.16 plan §D3.
- **Plus:** `transient_signals` carrying `TransientSignal(kind="camera_person_detected_room", count=int, weight=float)` for the Tier 2 camera channel.
- **state_context keys:** `scope="room_level_weighted"`, `house_state`, `total_weight_sum` (precomputed), `weight_threshold` (default 1.0, configurable).
- **Return:** `VetoDecision` with a new `defer: bool` field added (backward-compatible default `defer=False`). If `weighted_sum >= weight_threshold and not all_away` → `fired=False, defer=False` (accept occupied). If `all_away and weighted_sum < weight_threshold` → `fired=True` (veto to away). If `weighted_sum is borderline` → `fired=False, defer=True` (caller falls back to multi-tier consensus).

### C4.6 — Recommendation: v4.7.15 ships now, v4.7.16 owns the fix-up
