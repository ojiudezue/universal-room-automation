### C-M3 — `_try_restore_blocked_counter` does NOT defensively short-circuit when `last_state.attributes` is None

**Severity:** MEDIUM
**Bug class:** Lazy derivation / partial-restore safety (Bug Class #46 family)
**File:** `custom_components/universal_room_automation/sensor.py:6943-6970` (the new method)

**Evidence:**
Reading the new method at `sensor.py:6943-6970`:
```python
def _try_restore_blocked_counter(self, last_state) -> None:
    """v4.7.18 D5: hydrate the per-zone relax-ceiling counter ..."""
    from datetime import datetime, timezone
    try:
        source = _get_dynamic_preset_source(self.hass)
        if source is None:
            return
        attrs = last_state.attributes or {}
        raw_count = attrs.get("relax_ceiling_blocked_count")
        raw_last = attrs.get("relax_ceiling_last_blocked_at")
        ...
        source.restore_blocked_counter(self._zone_id, raw_count, last_blocked)
    except Exception:  # noqa: BLE001
        pass
```

The call site `sensor.py:6934` is:
```python
if last_state is not None:
    self._try_restore_blocked_counter(last_state)
```

This is technically correct, BUT the inner pattern `attrs = last_state.attributes or {}` is the only defensive layer. On a malformed `last_state` where `last_state.state` is a string like `"unknown"` but `last_state.attributes` is `None` or missing, the method gracefully no-ops via the `or {}` fallback. **However:**

1. `raw_count` may be a string (operator pasted "7" via Developer Tools), a float ("7.0"), a list, a dict, etc. The `restore_blocked_counter` callee at `dynamic_preset.py:412-414` coerces via `int(count)` inside `try/except (ValueError, TypeError)` → safe for scalars/strings, **but will crash with `TypeError` on a list and `ValueError` on `"7.5"`**. The except catches both — so it falls back to 0. **OK in practice but undocumented; add a 1-line comment to `restore_blocked_counter` documenting the defense for the next reader.**

2. `raw_last` parsing: `datetime.fromisoformat(raw_last)` — if raw_last is non-string (int/None/bool/dict), this raises `TypeError`, caught by the `except (ValueError, TypeError)` → safe.

3. **The real gap:** if `last_state.attributes` contains `relax_ceiling_blocked_count` but NOT `relax_ceiling_last_blocked_at` (one shipped, the other didn't because HA serialized only one), the restore correctly handles it (count restored, timestamp stays None). Also fine.

4. **What's actually missing:** the `Exception` swallow at the outer try has no `_LOGGER.debug(...)` for diagnostic purposes. Compare to `_try_restore_to_source` at `sensor.py:6968` which ALSO swallows silently — so this is a pre-existing pattern, not a v4.7.18 regression. **Reviewer-C-equivalent finding from v4.7.17.2 wasn't fixed and is not introduced by this cycle.** Defer.

5. **Genuine bug-shaped concern:** `restore_blocked_counter` at `dynamic_preset.py:419-424`:
```python
# Only set if we have a positive value — leave dict empty when
# restored count is 0 (matches the never-fired pattern).
if c > 0:
    self._relax_ceiling_blocked_count[zone_id] = c
if last_blocked_at is not None:
    if last_blocked_at.tzinfo is None:
        last_blocked_at = last_blocked_at.replace(tzinfo=timezone.utc)
    self._relax_ceiling_last_blocked_at[zone_id] = last_blocked_at
```
**This is the actual concern:** if `count == 0` but `last_blocked_at` is non-None (malformed/inconsistent pre-restart attrs OR a session that fired the gate then operator zeroed the counter via developer tools), the timestamp gets restored WITHOUT a corresponding counter. The next time the gate fires, `last_blocked_at` will be updated but `_relax_ceiling_blocked_count` starts fresh at 0 then increments to 1 — the timestamp will reflect "last time it fired" correctly. But during the gap between restart and first new fire, `get_zone_state` returns `relax_ceiling_blocked_count=0, relax_ceiling_last_blocked_at="2026-06-01..."` — an inconsistent shape ("never fired yet shows a last_blocked_at"). The bucket sensor surfaces this state. Shipwatch H4 (planning §12) reads both attrs.

**Fix (MEDIUM):**
At `dynamic_preset.py:419-428`, tighten the restore semantics: if `c == 0`, also reject the `last_blocked_at` (it has no meaning without a counter). Or alternatively, if `last_blocked_at` is None but c > 0, log a debug warning. The simplest correct fix:

```python
if c > 0:
    self._relax_ceiling_blocked_count[zone_id] = c
    if last_blocked_at is not None:
        if last_blocked_at.tzinfo is None:
            last_blocked_at = last_blocked_at.replace(tzinfo=timezone.utc)
        self._relax_ceiling_last_blocked_at[zone_id] = last_blocked_at
# else: count==0 → leave both dicts empty; the inconsistent
# "timestamp without counter" case is silently rejected.
```

This is a 3-line indent change. No test churn.
