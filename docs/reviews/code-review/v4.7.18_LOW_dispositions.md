# v4.7.18 LOW dispositions

After Tier 2-DB review, 14 LOWs were identified across three reviewers (A: 4, B: 4, C: 6). Eight were fixed in-cycle per the operator's "stop the deferment, don't pile up debt" rule (2026-06-02): **A-L1, A-L2, A-L3, B-L1, B-L2, B-L3, C-L1, C-M3-pair-check** (the latter actually fixed C-M3 directly + A-L4 by transitive coverage). The 6 below are deferred with explicit justification — each is either superseded by an in-cycle fix, intentional by design, or genuine v5.0+ scope.

## A-L4 — superseded by C-M3

C-M3 paired the `(count, last_blocked_at)` restoration so that `count=0` rejects the timestamp too (the exact incoherent shape A-L4 flagged). With the pairing in place, the warning A-L4 suggested adding (`count=0 + last_blocked_at=<value>`) is now unreachable as input — the shape can no longer hit the assignment path. A-L4 self-resolves; no further action needed.

## B-L4 — single-locale i18n

D4's `_ceiling_mode_options` list uses Python literal labels (`Auto (recommended)`, `Conservative — skip above 85°F`, …) inline in `SelectSelectorConfig(options=[...])`. HA's preferred pattern is `translation_key=...` + matching `selector.<key>.options.*` entries in strings.json. C-M2 was applied via the URA-precedent inline-label path (description strings landed via `data_description`, not via `selector.translation_key`), so the divergence persists. URA is single-install, single-locale (en) — practical impact is nil. Defer to v5.0 i18n sweep alongside any other selector that uses the inline pattern.

## C-L2 — intentional data preservation

`MIRROR_KEYS_ZONE_DPM` deliberately retains the 16 bucket-cell keys and `customize_buckets` so existing per-zone bucket data in `entry.options` continues to mirror between sibling HVAC zones across saves. Planning §6 D1 risk section explicitly called this out as "Bucket CONFs remain in `entry.options` untouched" — the data has to survive D1 strip until a future Bucket Editor surface re-exposes it. Trimming the mirror set now would cause data loss the moment the user saves on the stripped Surface 2.

## C-L3 — v5.0 schema-builder signature sweep

`_build_dynamic_preset_schema` still accepts 21 positional `*conf_keys` for a function that consumes 4. The signature is documented in code (`config_flow.py:6198-6202`) as intentional back-compat to avoid churning both call sites in-cycle. Trimming requires touching the two call sites (`:6133-6151`, `:6157-6175`) plus retiring the surrounding tests. Flagged for the v5.0 architectural-debt sweep alongside the other DPM signature tidies.

## C-L4 — live-validation covers schema-shape AST

There is no test that instantiates the options-flow handler, calls `_build_hvac_dynamic_preset_schema`, and asserts 5 options match `DPM_RELAX_CEILING_MODES`. Reviewer C explicitly preferred this gap over a fragile schema-shape AST test (the same pattern that retired `test_v474_dpm_ui.py` in commit `1b3d491`). The H1 acceptance criterion is covered by Shipwatch live validation post-deploy. If pre-deploy confidence becomes critical, the one-line fix is a `len(DPM_RELAX_CEILING_MODES) == 5` + set-equality assertion in the energy_const module — no schema-builder coupling. Defer until that need surfaces.

## C-L5 — matches existing `_try_restore_to_source` pattern

`_try_restore_blocked_counter` swallows its outer `Exception` silently (no debug log). The sibling method `_try_restore_to_source` (`sensor.py:6943-6944`) uses the same silent pattern. Improving the new method alone would create inconsistency; improving both is a separate hygiene cycle that touches all RestoreEntity helpers in the file. Defer to a focused logging sweep.

## C-L6 — `pytest.approx` not needed (bit-exact today)

All v4.7.18 float comparisons use ratio-controlled inputs (75.0, 90.0, 85.0, 92.0) where bit-exact equality holds (`statistics.median` is exact on these magnitudes; `statistics.quantiles` outputs aren't compared to hand-computed expectations in this file). Reviewer C confirmed acceptable as-is. If future tests compare p25 outputs against hand-computed expectations, the fix is a 1-line `pytest.approx(expected, abs=0.01)` swap — defer until that exposure exists.
