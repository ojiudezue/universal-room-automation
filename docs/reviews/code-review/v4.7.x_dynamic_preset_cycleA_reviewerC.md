### CRITICAL

#### C1: Cross-file test isolation -- EV TOU dt_util mock poisons weather staleness tests
**Severity:** CRITICAL
**Bug class:** NEW -- propose "Cross-file sys.modules pollution" as Bug Class #44
**File:** `quality/tests/test_v47x_ev_tou_hardening.py` (primary fault) + `quality/tests/test_v47x_weather_manager.py` (victim)

**Root cause:** Both test files use `sys.modules.setdefault("homeassistant.util.dt", ...)` at module-import time. When pytest loads EV TOU first (`test_v47x_ev` sorts before `test_v47x_weather`), the `setdefault` call wins because the module was not yet registered. EV TOU's mock freezes `dt_util.utcnow` to `_FIXED_NOW = datetime(2026, 5, 27, 14, 0, 0, tzinfo=timezone.utc)`. When `test_v47x_weather_manager.py` subsequently calls `_utcnow()`, it gets the LIVE `datetime.now(UTC)`, but the `_check_provider_health` code path imports `dt_util.utcnow` from the module that EV TOU already seeded -- the fixed time.

The state mock's `last_changed` is constructed via weather's `_utcnow()` (live time), but `_check_provider_health` computes age via the dt_util module (potentially the EV TOU frozen time). When run together in alphabetical order:

```
FAILED test_v47x_weather_manager.py::TestProviderHealth::test_stale_entity
assert healthy == stale  -- staleness check fails because utcnow is frozen
```

In reverse order, EV TOU's D2 sub-switch tests fail with `ImportError: cannot import name 'async_call_later'` because the weather test's `homeassistant.helpers.event` mock (which lacks `async_call_later`) wins the `setdefault` race.

**Evidence:** Reproduced:
- `pytest test_v47x_ev_tou_hardening.py test_v47x_weather_manager.py` -> 1 weather FAIL
- `pytest test_v47x_weather_manager.py test_v47x_ev_tou_hardening.py` -> 4 EV TOU FAIL

**Whose fault:** The design defect is SHARED but the PRIMARY fault is in EV TOU's test file:
1. EV TOU uses a fixed `_FIXED_NOW` at module scope and injects it into `sys.modules` unconditionally. Any test loaded afterward that relies on a live `dt_util.utcnow()` gets the wrong time.
2. Weather tests also use `sys.modules.setdefault` but with a LIVE `datetime.now(UTC)` function, which is less toxic because it doesn't freeze time.
3. Both files use `sys.modules.setdefault` rather than `sys.modules[name] = ...`, which means whichever file loads first wins. This is a fundamental isolation gap.

**Fix path:**
- SHORT TERM: Each test file should use `sys.modules[name] = ...` (force-set) rather than `setdefault` for the dt_util mock, so each file always gets its own mock regardless of import order. This is still fragile but eliminates the current cross-contamination.
- MEDIUM TERM: Extract the sys.modules mock setup into a shared conftest.py fixture that provides a factory (`make_dt_util_mock(utcnow_fn=...)`) and properly isolates/restores sys.modules per test session or per module. This prevents the N^2 interaction matrix from growing.
- LONG TERM: Move toward `pytest-homeassistant-custom-component` or an equivalent fixture framework that manages HA module mocking centrally.

**Status:** NOT FIXED (review-only pass)

#### C2: `threshold_f` in WeatherDivergenceBinarySensor.extra_state_attributes is hardcoded to None
**Severity:** CRITICAL
**Bug class:** #29 (sensor populator path -- every status branch must have a populator)
**File:** `binary_sensor.py:1720`

The plan spec (section A2) states the binary sensor should report `threshold_f` in its attributes. The current code:

```python
return {
    "divergence_f": mgr.divergence_f,
    "threshold_f": None,  # populated from options via manager
    "provider_high_map": mgr._provider_highs,
}
```

The comment says "populated from options via manager" but it is ALWAYS None. The WPM exposes `_divergence_threshold_f()` as a method. The sensor should call it:

```python
"threshold_f": mgr._divergence_threshold_f(),
```

Without this, the user cannot see what threshold is configured from the entity attributes, and any automation that reads `threshold_f` to compare against `divergence_f` gets a null.

**Status:** NOT FIXED

#### H2: No `available` property override on weather sensors -- always True even when WPM is absent
**Severity:** HIGH
**Bug class:** #5 (startup race)
**Files:** `sensor.py:6334` (WeatherActiveProviderSensor), `sensor.py:6382` (WeatherApparentForecastHighSensor), `binary_sensor.py:1672` (WeatherDivergenceBinarySensor)

All three new entities inherit from `AggregationEntity`, whose `available` property unconditionally returns `True` (aggregation.py:693-695). This means:

1. During startup, if the WPM setup fails (the `except Exception` block in `__init__.py:1497`), these sensors report `available=True` with `native_value="none"` or `None`. HA treats this as a valid state, not as unavailable. Automations triggering on state changes would fire on the placeholder values.

2. If WeatherProviderManager crashes or is torn down during a reload while entities are still registered, they continue to report `available=True`.

Sibling sensors like `EnergyEnvoyAvailableBinarySensor` do NOT override `available` either, so this is a pre-existing pattern gap. But the weather sensors are the first entities that access a singleton (`hass.data[DOMAIN]["weather_manager"]`) that is constructed OUTSIDE the coordinator_manager lifecycle. If WPM setup fails, `coordinator_manager` still exists but `weather_manager` does not.

**Recommended fix:** Add an `available` property to each weather entity:

```python
@property
def available(self) -> bool:
    return self.hass.data.get(DOMAIN, {}).get("weather_manager") is not None
```

**Status:** NOT FIXED

#### H3: WeatherApparentForecastHighSensor reads from Energy Coordinator, not WeatherProviderManager
**Severity:** HIGH
**Bug class:** Indirection coupling -- tight coupling to EC internals
**File:** `sensor.py:6403-6413`

The `native_value` property reads:

```python
manager = self.hass.data.get(DOMAIN, {}).get("coordinator_manager")
energy = manager.coordinators.get("energy")
return energy._cached_apparent_forecast_high
```

This reads from `EnergyCoordinator._cached_apparent_forecast_high`, a private attribute populated during EC's `_update_forecast_temps` method. Problems:

1. **Coupling:** The sensor bypasses the WeatherProviderManager API and reaches into EC's private cache. If EC hasn't run a decision cycle yet (startup race), this returns None even though WPM may already have valid data.
2. **Naming confusion:** The sensor is named "Weather Apparent Forecast High" and documented as a WPM sensor, but it actually reads EC's cached copy. The `extra_state_attributes` method (line 6421) reads from BOTH `coordinator_manager` and `weather_manager`, creating a mixed provenance.
3. **Staleness:** EC's cached value only updates during the EC decision cycle (every 5 min or on event). WPM's cache updates on every provider state-change event. The sensor lags behind WPM by up to 5 minutes.

The sensor should read directly from `WeatherProviderManager._cached_forecast.apparent_high` for both `native_value` and attributes, matching what `WeatherActiveProviderSensor` does.

**Status:** NOT FIXED

### MEDIUM

#### M1: `_provider_highs` dict exposed as raw dict reference in binary sensor attributes
**Severity:** MEDIUM
**Bug class:** #8 (type safety in dynamically-structured data)
**File:** `binary_sensor.py:1721`

```python
"provider_high_map": mgr._provider_highs,
```

This exposes the internal mutable dict directly. HA's state machine calls `json.dumps()` on extra_state_attributes. While `dict[str, float]` is JSON-serializable, the reference to the internal dict means:
1. If WPM mutates `_provider_highs` while HA is serializing, a `RuntimeError: dictionary changed size during iteration` is possible (though unlikely given the event loop model).
2. Any downstream code that modifies the returned dict would corrupt WPM's internal state.

Should be `dict(mgr._provider_highs)` (shallow copy) for defensive safety, consistent with how the WPM's own `provider_health_map` property (weather_manager.py:571) returns `{eid: str(h) for eid, h in ...}` -- a new dict each time.

**Status:** NOT FIXED

#### M2: WeatherDivergenceBinarySensor constructs DeviceInfo inline instead of using `_energy_device_info()` helper
**Severity:** MEDIUM
**Bug class:** Consistency / DRY violation
**File:** `binary_sensor.py:1689-1698`

The two weather sensor entities in `sensor.py` use `_energy_device_info()` (sensor.py:5969) to construct their DeviceInfo. The binary sensor in `binary_sensor.py` constructs an identical DeviceInfo inline:

```python
self._attr_device_info = DeviceInfo(
    identifiers={(DOMAIN, "energy_coordinator")},
    name="URA: Energy Coordinator",
    ...
)
```

The identifiers and parameters are identical to `_energy_device_info()`. Using the inline construction:
1. Creates a maintenance burden -- if the Energy Coordinator device name or identifiers change, this site would be missed.
2. The sibling `EnergyEnvoyAvailableBinarySensor` (binary_sensor.py:1592) uses the same inline pattern, so this is consistent with the binary_sensor.py convention, but inconsistent with the sensor.py convention.

Not a functional defect. The `_energy_device_info()` helper is in sensor.py and not importable from binary_sensor.py without a cross-module import. Could be extracted to a shared location in a future cleanup.

**Status:** NOT FIXED (cosmetic)

#### M3: `priority_rank` in WeatherActiveProviderSensor is hardcoded to 0
**Severity:** MEDIUM
**Bug class:** #29 (sensor populator path -- incomplete attribute)
**File:** `sensor.py:6371`

```python
"priority_rank": 0,
```

Per the plan spec (section A2), `priority_rank` should reflect the rank of the current active provider in the priority list (0 = primary, 1 = secondary, 2 = tertiary). Hardcoding to 0 means the sensor always reports the active provider as rank 0, even when failover has promoted the secondary or tertiary provider.

WPM does not expose a `priority_rank` property, so this would need to be added to WPM's public API.

**Status:** NOT FIXED

#### M4: Double fetch of active provider forecast in `_refresh_all_providers`
**Severity:** MEDIUM
**Bug class:** Performance / redundant I/O
**File:** `weather_manager.py:342 + 371`

In `_refresh_all_providers()`, the active provider's forecast is fetched twice:
1. Line 342: `forecast_data = await self._fetch_provider_forecast(eid)` -- during the health+election loop
2. Line 371: `forecast_data = await self._fetch_provider_forecast(new_active)` -- after election, to build the cached forecast

Each `_fetch_provider_forecast` call makes a `hass.services.async_call("weather", "get_forecasts", ...)` service call. This doubles the HA service call load for the active provider on every refresh cycle.

The first fetch's result should be cached and reused at line 371 instead of re-fetching.

**Status:** NOT FIXED

## QUALITY_CONTEXT.md Update Recommendation

Add **Bug Class #44: Cross-file sys.modules Pollution in Test Harness**.

**Pattern:** Test files that use `sys.modules.setdefault()` or `sys.modules[name] = ...` at module import time to mock HA dependencies. When pytest collects multiple such files in a single process, the first file loaded wins the `setdefault` race. Later files silently inherit the first file's mock, which may have frozen timestamps, missing attributes, or incompatible behavior.

**Prevention:**
- Each test file should force-set its own mocks (`sys.modules[name] = ...`) rather than using `setdefault`
- Extract shared HA mock setup into a conftest.py fixture that properly isolates and restores sys.modules per test module
- Tests that freeze time should do so within individual test functions or classes, not at module scope
- CI should run each test file in isolation (`pytest --forked` or per-file invocations) as a canary for cross-contamination
