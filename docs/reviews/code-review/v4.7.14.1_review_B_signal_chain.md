## B1 — Interaction with v4.7.14 veto plumbing

### B1.a — MEDIUM: v4.7.14 `_LOGGER.info` predicate diverges from the new gate

**Location:** `presence.py:2057-2064` (feature branch line numbers; corresponds to v4.7.14 NIT-1
fix at `presence.py:2007-2014` on master).

The veto-fired log site reads:
```python
if (
    all_tracked_persons_away
    and self._unidentified_count == 0
    and new_state == HouseState.AWAY
    and current_state != HouseState.AWAY
):
    _LOGGER.info(
        "v4.7.14: Person-tracker veto fired — all %d tracked persons "
        "away (%s), no unidentified people; forcing AWAY (was %s, "
        "any_zone_occupied=%s)",
        ...
    )
```

H1 added `census_count == 0` to the gate in `StateInferenceEngine.infer()`
(`presence.py:415-419`), but the log-site predicate at `presence.py:2057-2064` was NOT
updated to mirror the new condition. Two consequences:

1. **Functional:** the log gate is OUTCOME-driven (`new_state == HouseState.AWAY`), so the
   log won't actually fire when H1 blocks the veto (because `new_state` won't be AWAY when
   H1 short-circuits). Net behavior: correct.
2. **Operator-visible:** the log MESSAGE text still reads `"no unidentified people; forcing AWAY"`
   — it does NOT mention the new census-zero requirement. Operators reading the log will not
   understand why the veto fired vs didn't fire on adjacent days, because the printed
   conditions list is incomplete.

**Action:** update the log message to include census state. Suggested:
```
"v4.7.14.1: Person-tracker veto fired — all %d trusted persons away (%s), "
"unidentified=0, census=0; forcing AWAY (was %s, any_zone_occupied=%s)"
```

Note also that `tracked_count` and `away_person_ids` now reflect the H2/H3-FILTERED set, not
the raw configured set. The message says "all N tracked persons away" but the N is the
post-filter denominator. See B1.c for the recommended language.

### B1.b — LOW: confidence semantics under H1 short-circuit

**Location:** `presence.py:415-419` (the H1 block).

When H1's new `census_count == 0` clause blocks the veto branch, control falls through to:
- `presence.py:421` `has_people = census_count > 0 or any_zone_occupied`
- The subsequent has_people branch sets confidence per its own logic (e.g., the ARRIVING /
  HOME_DAY paths, generally 0.85 from camera-driven inference).

This is correct — the 0.95 setpoint is reserved for the "everyone definitively away" branch,
and falling out of that branch into the camera-driven path is the right behavior. The
inference engine does NOT carry a stale `self._confidence = 0.95` from a previous cycle
because the `_confidence` attribute is reassigned in every branch that returns a non-None
state.

**Action:** none — confirmed correct by inspection. Documenting for future reviewers.

### B1.c — MEDIUM: `tracked_persons_count` attribute semantics changed silently

**Location:** `sensor.py:3785-3795` (master; unchanged on feature branch).

The diagnostic exposure block in `PresenceHouseStateSensor.extra_state_attributes` says:
```python
# v4.7.14: Person-tracker veto diagnostics. tracked_persons_count
# is the number of configured person.* trackers seen by
# person_coordinator; all_tracked_persons_away True means every
# one is reporting away ...
attrs["tracked_persons_count"] = getattr(
    presence, "_tracked_persons_count", 0
)
```

Post-v4.7.14.1, `_tracked_persons_count` is set at `presence.py:1991` to
`len(trustworthy_persons)` — the H2 + H3 FILTERED count, not the raw configured count. An
operator with 4 configured persons but 1 with `phone_left_behind=on` will see
`tracked_persons_count: 3`. Without a docstring update they will reasonably conclude that
one person dropped out of `person_coordinator.data`, and may start investigating the wrong
problem (Bermuda glitch, Mobile App outage) rather than the trusted state of the
phone-left-behind diagnostic.

This is the same `silent filter` shape as Bug Class #43 (silent room drop): a filter
operation that reduces an exposed count without surfacing what was removed.

**Action (mandatory before deploy):** at least one of:

1. **Preferred** — expose both: `tracked_persons_count_raw` (pre-filter) AND
   `tracked_persons_count_trusted` (post-filter), plus a list attribute
   `excluded_persons` with reason strings (`"phone_left_behind"`, `"tracking_status=stale"`,
   `"tracking_status=lost"`). Cost: ~15 LoC in `_run_inference` + ~10 in sensor.py.
2. **Minimum acceptable** — keep `tracked_persons_count` semantics as today, but update the
   sensor.py docstring at `:3785-3789` to explicitly say "post-filter count (excludes
   phone-left-behind and STALE/LOST trackers)" and add a small `excluded_persons` attribute
   so the operator can see the count delta's cause without grepping logs.

If the second option is chosen, also update the README runbook (`docs/readmes/README_v4.7.14.1.md`)
to call out the operator-facing meaning of the attribute.

## B2 — `phone_left_behind` carve-out design intent

### B2.a — Design-intent match: PASS

**Locations:** `binary_sensor.py:973-1084` (sensor class), v3.5.2 design notes at
`docs/PLANNING_v3.5.2_CYCLE_6.md` §15.

Original v3.5.2 intent: detect "phone is at home but person isn't" (BLE places phone in a
room + no camera sighting in `PHONE_LEFT_BEHIND_HOURS=1.0`). The sensor fires when the
phone holder's `person.X` state would falsely report "home" because the BLE beacon is in the
house but the human isn't.

v4.7.14.1 H2 consumes the sensor as a "trust this phone's `location` field for veto-denominator
inclusion" signal. The semantic is a direct match: if the sensor is `on`, it is telling us
exactly that `person_data[name]["location"]` is currently meaningless — which is precisely
what H2 needs to know to exclude the entry from the away-veto computation.

The carve-out design intent is preserved.

### B2.b — Feedback-loop check: NO LOOP

Three potential paths examined:

1. **Sleep-hour suppression** (`binary_sensor.py:1014-1017`, local TZ via `dt_util.now()`):
   sensor returns `False` during 22:00-07:00 local. H2 sees `state != "on"` → person counted
   normally. No interaction with H2's behavior — the sleep window simply makes the diagnostic
   silent, which is the v3.5.2 intent. No loop.
2. **Census suppression** (`binary_sensor.py:1028-1034`): sensor returns `False` when
   `census.last_result.house.total_persons > 0`. Scenario: phone on counter, person actually
   away, another resident walks past camera → census detects them → sensor flips OFF →
   H2 stops filtering the phone-left-behind person → that person is now counted as "home" →
   `all_tracked_persons_away = False` → veto blocked by the `all()` reduction.

   This is the CORRECT outcome — someone IS home (the other resident), so the veto SHOULD
   be blocked. H1 also independently blocks the veto in this case (`census_count == 0`
   fails). Belt-and-suspenders; no conflict, no loop.
3. **H2 → sensor → H2 loop**: ruled out. H2 only READS sensor state; nothing H2 does
   feeds back into the sensor's inputs (sensor reads BLE location + transit_validator
   sightings + census, none of which H2 mutates).

### B2.c — NIT: new-consumer documentation

The sensor's `_attr_entity_registry_enabled_default = False` (`binary_sensor.py:988`) was
appropriate for a "rarely-needed diagnostic" — v3.5.2's original framing was that operators
would enable it case-by-case. v4.7.14.1 promotes it to a load-bearing veto-correctness
signal. The H2 fail-OPEN design correctly preserves v4.7.14 behavior for operators who
haven't enabled it, but the operational story has shifted: from now on, enabling the
sensor is the recommended way to gain correctness in the forgotten-phone scenario.

The runbook (`docs/readmes/README_v4.7.14.1.md`) does call this out (per quick scan). LOW —
no code action; consider a one-line comment at `binary_sensor.py:973` explaining that the
sensor is now a v4.7.14.1 veto-denominator input as well as its original v3.5.2 use.

### B3.b — `_tracking_active` helper default-direction: PASS

`presence.py` H3 helper:
```python
def _tracking_active(info: dict) -> bool:
    return info.get("tracking_status", TRACKING_STATUS_ACTIVE) == TRACKING_STATUS_ACTIVE
```

The missing-field default is `ACTIVE`, which is the **correct fail-OPEN direction** — older
in-memory entries from before `tracking_status` was added (pre-v3.2.8.1 per the file
comment) would be treated as ACTIVE rather than silently excluded. Symmetric with H2's
fail-OPEN: a missing signal preserves v4.7.14 baseline behavior.

`TRACKING_STATUS_ACTIVE` is properly imported from `..const` (`presence.py:40`).

### B3.c — STALE set-site (`:288`): PASS

The `STALE` set-site at `person_coordinator.py:288` is excluded by H3 as well. STALE means
"Bermuda data older than threshold but person was last seen somewhere real." Treating STALE
as not-confirmed-away is consistent with H3's framing ("only ACTIVE counts as confirmed
away for the high-confidence 0.95 veto").
