## HIGH

### H1 — `async_step_zone_config_menu` raises `NameError: name 'zone_name' is not defined` on the legacy (non-ZM) zone-entry path

**Bug class:** Lifecycle / control-flow correctness (not a numbered class — but indistinguishable to the user from Bug Class #46's "options form opens broken" symptom).

**Location:** `custom_components/universal_room_automation/config_flow.py:5231-5242`

**Issue.** The banner block reads `zone_name` from the function body, but `zone_name` is only assigned at line 5232:

```python
zone_name = getattr(self, "_selected_zone_name", None)
if not zone_name:
    zone_entry = self._get_zone_entry()
    if not zone_entry:
        return self.async_abort(reason="zone_not_found")

# v4.7.5 D4 banner: detect shared-thermostat siblings, build placeholders.
banner = ""
if zone_name:                                  # ← legacy zone-entry path: zone_name is None
    try:
        zm_entry = self._find_zone_manager_entry()
        ...
```

That part is actually OK — `zone_name` is set to `None` and the `if zone_name:` guard skips the banner block. **However**, the bigger issue: on the legacy zone-entry path, `zone_name` is `None` but `zone_entry` (the local from `_get_zone_entry()`) carries the real zone identity. The banner is silently skipped for legacy zone entries. URA's only install is the ZM-path, so this is benign today — but:

- The plan acceptance criteria (D4.c, D4.d) assume the banner renders for ANY zone with shared thermostat. The legacy-entry path silently drops the banner. Plan says "banner appears on `zone_config_menu` when the selected zone shares a thermostat" — for legacy entries this is broken.
- More important: the legacy path no longer reaches `async_abort(reason="zone_not_found")` even when intended. Pre-v4.7.5 logic was:
  ```python
  if not getattr(self, "_selected_zone_name", None):
      zone_entry = self._get_zone_entry()
      if not zone_entry:
          return self.async_abort(reason="zone_not_found")
  ```
  which is *fall through to render menu* if EITHER `_selected_zone_name` is set OR a legacy zone_entry was found. The v4.7.5 refactor preserves the abort, but `zone_entry` is now an UNUSED local — the menu renders the same way regardless of whether the legacy lookup actually found an entry, because the new control flow only checks `zone_name`. This is a **silent control-flow regression**.

**Fix:**
```python
zone_name = getattr(self, "_selected_zone_name", None)
zone_entry = None
if not zone_name:
    zone_entry = self._get_zone_entry()
    if not zone_entry:
        return self.async_abort(reason="zone_not_found")
    # v4.7.5 D4 single-user reality: legacy zone-entry path doesn't carry a
    # shared-thermostat-sibling concept; banner stays empty. If you ever add
    # legacy-entry banner support, derive zone_name from zone_entry here.
```

Make the legacy-path intent explicit. The current code's reliance on "`zone_name` happens to be falsy so the banner is skipped, and `zone_entry` happens to be unused so the abort-guard logic still works" is too clever for a build that just shipped a NameError-class regression in v4.7.4.2.

**Reload-chain concern (Bug Class #46 echo).** The banner-derivation block also reads `_find_zone_manager_entry()` and `self._get_shared_thermostat_siblings(zm_entry, zone_name)` — both pure reads, neither touches `async_update_entry`. Safe. But the `except Exception:` is too broad — see L1.

### H2 — `async_step_zone_rooms` does NOT route through `_auto_mirror_to_siblings`; comment lies about "single async_update_entry"

**Bug class:** Bug Class #46 echo (multiple `async_update_entry` calls per save → multiple `update_listener` fires → reload loop hazard).

**Location:** `config_flow.py:5355-5384` and the room-entry update at `5322-5343`.

**Issue.** The block at line 5355 carries an inline comment:

> "Use the auto-mirror helper anyway so the rename path stays atomic with the save (one `async_update_entry` total, even when the zone is renamed)."

But the body DOES NOT call `_auto_mirror_to_siblings`. It builds `zones` locally and calls `self.hass.config_entries.async_update_entry(zm_entry, ...)` directly. The "single `async_update_entry`" claim in the comment is technically true *for the ZM entry only*, but:

1. **The ROOM-entry updates at lines 5328 and 5341 ALSO fire `async_update_entry`** — each room added to or removed from the zone triggers a separate `async_update_entry` on a *room* entry. Each of those room entries has its own `_async_update_listener` registered (per `__init__.py:2231/2347/2424/2532` showing the listener is registered on every CM/Room setup), and each fires `hass.config_entries.async_reload(entry.entry_id)` per `__init__.py:3133-3146`.

2. **Reload chain.** If the user saves zone_rooms after adding 2 new rooms and removing 1, the save fires:
   - 2× `async_update_entry` for room entries (added rooms) → 2× reload schedule
   - 1× `async_update_entry` for room entry (removed room) → 1× reload schedule
   - 1× `async_update_entry` for ZM entry → 1× reload schedule
   - **Total: 4 reloads scheduled via `hass.async_create_task`** in the same options-flow save.

   The reloads are fire-and-forget background tasks (per the v4.0.5 comment at `__init__.py:3136`), so they don't block the response. But they DO race each other and each carries the full unload/setup cost. This was the pattern v4.0.5 worked around for the 30s aiohttp timeout — fine for room entries (no per-room budget pressure), but still a *lot* of churn per save.

3. **No bug — but plan promise broken.** The plan §D4 says "test_v475_d4_one_update_entry_per_save — instrument `async_update_entry`; assert exactly one call per save". The current build's `zone_rooms` path makes more than one `async_update_entry` call in the multi-room-edit case. The test exists in `test_v475_d4_auto_mirror.py:519` and ONLY tests the HVAC path through the helper. It does NOT cover `zone_rooms`. So a regression where someone adds a second `async_update_entry` to the helper itself would catch — but the existing pattern of N+1 calls in `zone_rooms` is invisible to the test.

**Fix (preferred):**
Make `zone_rooms` actually call `_auto_mirror_to_siblings` as the comment claims:

```python
if zm_result:
    # Rename: pop old key first
    payload = {CONF_ZONE_DESCRIPTION: user_input.get(CONF_ZONE_DESCRIPTION, ""),
               CONF_ZONE_ROOMS: selected_rooms}
    if old_zone_name != zone_name:
        # Pre-pop: helper will write to new key
        merged = {**zm_entry.data, **zm_entry.options}
        zones = {k: dict(v) for k, v in merged.get("zones", {}).items()}
        if old_zone_name in zones:
            zones[zone_name] = zones.pop(old_zone_name)
            # Persist the rename via a single update so helper's read sees new key
            self.hass.config_entries.async_update_entry(
                zm_entry, options={**zm_entry.options, "zones": zones},
            )
    self._auto_mirror_to_siblings(
        zm_entry, zone_name, payload, MIRROR_KEYS_ZONE_ROOMS,
    )
```

This still leaves the rename case at 2 `async_update_entry` calls (rename + payload). If you want truly atomic, fold the rename into the helper as an optional `old_name` param.

**Fix (acceptable minimum):** Update the comment to be accurate — *"single `async_update_entry` for the ZM entry; room-entry updates remain N per save."* Lying comments mislead future reviewers.

### H3 — DPM and energy save paths do NOT propagate `old_thermostat` → unlink loses old-sibling mirror for non-HVAC fields

**Bug class:** #33 (Partial fix — sibling helpers skipped).

**Location:** `config_flow.py:5945-5947` (DPM), `5650-5660` (energy).

**Issue.** Only `async_step_zone_hvac` (line 5581) passes `old_thermostat=current_thermostat` to `_auto_mirror_to_siblings`. The other 6 editor steps (rooms, media, hvac handled, energy, persons, cameras, dynamic_preset) do NOT pass `old_thermostat`. This makes sense for steps that don't write `CONF_ZONE_THERMOSTAT` — but the helper's unlink logic *relies* on knowing the old thermostat to mirror to old siblings one final time.

**Concrete failure mode:**
1. User opens Entertainment → HVAC, changes thermostat from `climate.t1` to `climate.t2`. Saves. `_auto_mirror_to_siblings` correctly mirrors to old siblings (Master Suite on t1) AND new siblings (Office on t2). ✓
2. **Same session**, user immediately opens Entertainment → DPM, edits a bucket cell. Saves. The helper computes `new_siblings` based on the *new* thermostat (t2 → Office), but `old_thermostat=None`, so no unlink branch fires. Master Suite (which was just unlinked from Entertainment via the HVAC save) gets ZERO mirror.

   That's actually the *correct* behavior — Master Suite is no longer a sibling.

3. **But:** Step 1 didn't mirror the DPM values to Master Suite. Step 1 only mirrors `MIRROR_KEYS_ZONE_HVAC` (thermostat + AC ramp). So Master Suite is left with whatever DPM cells it had before the unlink + the HVAC values from the final pre-unlink state. **Master Suite is now in a half-state**: HVAC says t1, DPM uses Entertainment's stale offsets and bucket cells.

The plan's "unlink path mirrors to OLD ONE LAST TIME (so siblings reflect any intermediate-edit state before the relationship breaks)" only mirrors *the saved step's* fields. It does NOT mirror the OTHER zone's fields (DPM cells, energy sensors) at the unlink moment.

**Why Reviewer B owns this:** This is a multi-step lifecycle race. Reviewer A may catch it under correctness ("Master Suite DPM is stale post-unlink"), but the underlying issue is *the unlink event happens at one tick (HVAC save), but the DPM/energy data the old sibling carries is from a different tick*. That's a lifecycle ordering bug, not a correctness bug per se.

**Fix.** Two options:
- **Option 1 (minimum):** Document in `_auto_mirror_to_siblings` and in `QUALITY_CONTEXT.md` Lazy Canonical Resolution: *"On thermostat reassignment, only HVAC mirror fields are propagated to the old sibling group. DPM and energy values for the old sibling retain their pre-unlink state — they were already in sync at the moment the user last saved DPM/energy on either zone."*
- **Option 2 (better):** At HVAC unlink time, additionally mirror DPM + energy fields from the saved zone to the OLD siblings. This requires reading current DPM/energy values from the saved zone (which are present in `zm_entry.options["zones"][saved_zone_name]` before the user's HVAC save) and including them in the helper's "final pre-unlink" mirror payload. Adds complexity; the plan doesn't ask for this.

Pick one. The current build does neither — there's no doc and no fix.

**Sub-issue:** `_auto_mirror_to_siblings` uses `if mirror_keys and old_thermostat and old_thermostat != new_thermostat:` to gate unlink. If a user saves zone_dpm via the helper, `mirror_keys` is non-empty (`MIRROR_KEYS_ZONE_DPM`), and `old_thermostat=None`, so unlink branch is skipped — fine. But what if a user changes `CONF_ZONE_THERMOSTAT` from `zone_hvac` AND `mirror_keys` happens not to include `CONF_ZONE_THERMOSTAT`? Today `MIRROR_KEYS_ZONE_HVAC` does include it, so no bug. If a future contributor removes `CONF_ZONE_THERMOSTAT` from the HVAC mirror set, the unlink branch breaks silently. Add an assertion in the helper:

```python
if old_thermostat and old_thermostat != new_thermostat:
    if CONF_ZONE_THERMOSTAT not in mirror_keys:
        _LOGGER.warning(
            "v4.7.5: thermostat reassignment without CONF_ZONE_THERMOSTAT in "
            "mirror_keys — unlink logic may not reflect to old siblings. "
            "Saved zone=%s mirror_keys=%s", saved_zone_name, sorted(mirror_keys),
        )
```

### M1 — `_auto_mirror_to_siblings` is declared `def`, not `async def`, but is called WITHOUT `await` in all 7 call sites; OK today but easy to break

**Bug class:** None numbered; HA lifecycle / async correctness.

**Location:** `config_flow.py:2086` (`def _auto_mirror_to_siblings`) and call sites at `5449, 5582, 5654, 5719, 5770, 5945`.

**Issue.** `_auto_mirror_to_siblings` is synchronous (`def`, not `async def`). It calls `self.hass.config_entries.async_update_entry(...)` — which despite its `async_` prefix is *not* a coroutine; it's a synchronous HA API that internally schedules the listener via `hass.async_create_task`. Verified by reading HA source: `config_entries.py:async_update_entry` returns `bool`, not `Coroutine`.

So the build is correct. **But** the symbol naming is misleading: a future contributor reading this from the `await self.async_step_zone_config_menu()` line just above will reasonably assume `_auto_mirror_to_siblings` is also a coroutine and add `await`. Today that would be `await <bool>` → `TypeError: object bool can't be used in 'await' expression`.

Also, the docstring says:
> "Caller has already constructed `saved_zone_data` for `saved_zone_name` but has NOT yet called `async_update_entry`."

That's wrong for the helper — the helper *does* call `async_update_entry` itself. Compare to the planning doc's helper signature, which was `async def`. The builder converted it to sync (correct for the API), but didn't update the call-site invocation pattern or update the helper's own docstring.

**Fix.** Either:
- Rename to `_mirror_save_to_siblings` (no `async_` semantic mismatch); update docstring; OR
- Make it `async def` (no functional change for now, but future-proofs against any helper that needs `await dispatcher_send` etc.).

Either way, fix the docstring.

### M2 — D5 smoke test uses `asyncio.get_event_loop()` which is deprecated in Python 3.12+

**Bug class:** Test fragility; HA targets Python 3.12+ (per HA 2026.5.x).

**Location:** `quality/tests/test_v475_d5_config_flow_runtime_smoke.py:386-388`.

```python
result = asyncio.get_event_loop().run_until_complete(
    flow.async_step_manage_zones(user_input=None)
)
```

**Issue.** `asyncio.get_event_loop()` emits `DeprecationWarning` on Python 3.12+ when there is no running loop. In some configurations it raises `RuntimeError: There is no current event loop in thread 'MainThread'`. CI environments running on Python 3.13 will start failing this test silently or noisily.

**Fix.** Use `asyncio.new_event_loop()` + `loop.run_until_complete()` + `loop.close()`, OR use `asyncio.run(...)`:

```python
result = asyncio.run(flow.async_step_manage_zones(user_input=None))
```

`asyncio.run()` is the canonical 3.7+ idiom and handles loop lifecycle correctly.

### M3 — `_find_zone_manager_entry()` may return the same `entry` instance the OptionsFlow is editing → read-after-write race within the same tick

**Bug class:** Stale Data Source / Bug Class #7 echo.

**Location:** `config_flow.py:2024-2026` and `_auto_mirror_to_siblings:2163`.

**Issue.** `_auto_mirror_to_siblings` calls:
```python
self.hass.config_entries.async_update_entry(
    zm_entry,
    options={**zm_entry.options, "zones": zones},
)
```

`async_update_entry` in HA: writes the new options to the entry object SYNCHRONOUSLY (it sets `entry.options = new_options` before scheduling the listener as a task). So immediately after this call, `zm_entry.options` is the new dict.

Now consider the call sequence in `async_step_zone_hvac` (line 5582):
1. `_auto_mirror_to_siblings(zm_entry, ...)` runs → entry now has new options, listener task scheduled (not yet running).
2. `await self.async_step_zone_config_menu()` → renders menu.
3. `async_step_zone_config_menu` calls `self._find_zone_manager_entry()` → returns the SAME `zm_entry` instance.
4. Banner derivation reads `zm_entry.data` + `zm_entry.options` → reads the NEW options (good — the user's save is reflected).

So the synchronous flow is correct. **BUT:** the `hass.async_create_task(hass.config_entries.async_reload(entry.entry_id))` scheduled by the update_listener may begin BEFORE the next options-flow step renders. If reload starts and the OptionsFlow handler is still holding a reference to the old `zm_entry` object via `self._config_entry`, the next step that reads `self._config_entry` may see torn state (the reload re-creates `ConfigEntry` objects in HA core, though the entry_id stays stable — verify).

In practice URA today survives this because:
- The reload is scheduled as `async_create_task` and runs on a future event loop iteration.
- The options-flow chain returns from `async_step_zone_config_menu` immediately, so the next user click triggers a NEW options-flow instance which reads `self._config_entry` afresh.

But this is brittle. **If** a future step adds an `await` between the mirror save and `async_step_zone_config_menu()`, the scheduled reload could begin during the await window, and the menu render could see partial state.

**Fix.** Document this in `_auto_mirror_to_siblings` docstring:

> "After this call returns, the scheduled reload task may begin at the next event-loop iteration. Callers MUST NOT `await` any unrelated work between this call and returning a menu/form render — the rendered state should reflect the user's save."

Also worth verifying via test: instrument `hass.config_entries.async_reload` and assert it has not been awaited synchronously within the helper.

### M4 — D5 `stub_hass` and D4 `_StubHass` don't simulate `async_create_task` — silent miss for code paths that schedule background work

**Bug class:** Test fixture authority (Tier 2-DB Reviewer C territory, but relevant to async).

**Location:** `test_v475_d4_auto_mirror.py:280-282` and `test_v475_d5_config_flow_runtime_smoke.py:375-378`.

**Issue.** Both stubs implement `config_entries.async_entries(...)` and `config_entries.async_update_entry(...)`. Neither implements `hass.async_create_task`. If a future contributor adds a `self.hass.async_create_task(...)` call into `_auto_mirror_to_siblings` or `async_step_zone_config_menu` (e.g., to fire a dispatcher signal), the tests will fail with `AttributeError`, NOT a clear "you added an untracked task" message.

For now this is fine because the current helper makes no `async_create_task` calls. But the planning doc § Bug Class #42 explicitly warns against `async_create_task` in scheduler callbacks — the test surface should fail loudly if someone introduces one.

**Fix.** Add to `_StubHass`:
```python
self.create_task_calls: list = []
def _record_create_task(coro, *a, **kw):
    # Eagerly drop the coroutine to avoid RuntimeWarning("coroutine never awaited").
    coro.close()
    self.create_task_calls.append(kw.get("name", "unnamed"))
self.async_create_task = _record_create_task
```

Then add a test:
```python
def test_v475_d4_helper_does_not_schedule_background_tasks(shared_thermostat_zm):
    flow = _make_flow_with_zm(shared_thermostat_zm, selected_zone="Entertainment")
    flow._auto_mirror_to_siblings(...)
    assert flow.hass.create_task_calls == [], (
        "v4.7.5 / Bug Class #42: _auto_mirror_to_siblings must not schedule "
        "background tasks — it runs synchronously inside the options-flow handler."
    )
```

## LOW

### L1 — `except Exception:` in banner derivation can mask `ImportError` / `AttributeError` regressions

**Bug class:** Bug Class #34/#22 echo (silent runtime errors).

**Location:** `config_flow.py:5262-5266`.

```python
except Exception:  # noqa: BLE001 — never fail menu render
    _LOGGER.debug(
        "v4.7.5 banner derivation failed for zone=%s",
        zone_name, exc_info=True,
    )
```

**Issue.** Logging at DEBUG only. A future regression where `_get_shared_thermostat_siblings` raises an `ImportError` (e.g., `CONF_ZONE_THERMOSTAT` import gets deleted) will be silently absorbed — banner just won't show, no INFO log, no anomaly. This is the v4.7.4.2 class of bug: silent failure invisible to the user UNTIL they notice the missing banner.

**Fix.** Log at WARNING the first time per session (use a class-level set to dedup), and explicitly narrow the except to expected exceptions:

```python
except (KeyError, AttributeError, TypeError) as exc:
    _LOGGER.warning(
        "v4.7.5 banner derivation failed for zone=%s: %s",
        zone_name, exc, exc_info=True,
    )
```

Or at minimum: keep the broad except but log at INFO not DEBUG.

## Async/Lifecycle Verifications That Passed

For the record, these specific concerns from the framing were verified and pass:

1. **Bug Class #42 (lambda+`async_create_task` in scheduler callbacks).** No new scheduler registrations in the diff. `_auto_mirror_to_siblings` does not call `async_create_task` directly or via lambda. ✓

2. **Bug Class #45 (lambda closure stale variable).** The diff adds no lambdas that capture mutable locals. The list comprehensions in `_get_shared_thermostat_siblings` and `_auto_mirror_to_siblings._siblings_for` capture `zones` / `saved_zone_name` by reference, but neither is mutated between comprehension construction and consumption. ✓

3. **Bug Class #46 single-`async_update_entry`-per-save claim.** Verified for `zone_hvac`, `zone_energy`, `zone_persons`, `zone_cameras`, `zone_media`, `zone_dynamic_preset` — exactly one `async_update_entry` per save flows through the helper. `zone_rooms` is the exception (see H2). The test `test_v475_d4_one_update_entry_per_save` covers the helper but not the editor-step orchestration end-to-end. ✓ with caveat.

4. **Bug Class #46 boundary (no `async_update_entry` from `async_setup_entry`).** All `async_update_entry` calls in the diff live in OptionsFlow methods → fired strictly from user save → post-bootstrap-2. Confirmed safe per QUALITY_CONTEXT.md §"When `async_update_entry` IS safe in `async_setup_entry`" condition 2. ✓
