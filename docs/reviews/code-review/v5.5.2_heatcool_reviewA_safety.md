**Reviewer framing:** Enforcer correctness + the freeze/emergency-heat safety

**Branch:** `feature/heatcool-enforcer-reason-fix` @ `13285cd2`
**Diff:** `git diff develop..HEAD`
**Scope:** `hvac.py` enforcer block (~1043-1104), `_set_emergency_heat`

## VERDICT ON THE CRITICAL SAFETY QUESTION

❌ **UNSAFE.** A sustained freeze does **NOT** re-arm the `_emergency_heat_zones`
hold before its 2h expiry. After 2h the continuous enforcer clobbers
`heat` → `heat_cool` **mid-freeze**, silently defeating freeze protection while
the freeze is still active. The 2h blind timer is the wrong design; the hold
must be cleared by an explicit freeze-cleared signal / live re-check, not by a
timer that assumes "the freeze event is over."

### End-to-end evidence (read both sides)

**Re-arm requires `SIGNAL_SAFETY_HAZARD` to re-fire.** The hold is populated
ONLY in `_set_emergency_heat` (`hvac.py:1689`), which runs ONLY from
`_handle_safety_hazard` (`hvac.py:1626`), which runs ONLY on
`SIGNAL_SAFETY_HAZARD`. There is no other re-arm/extend path
(grep: `_emergency_heat_zones` is written at exactly one site; removed at
exactly one site — the enforcer's expiry-drop at `hvac.py:1077`).

**The signal is gated by `is_new`, NOT by the dedup window.** In
`_respond_to_hazard` (`safety.py:1687`):
- `key = "{type}:{location}"`; `is_new = existing is None or existing.severity != hazard.severity` (`safety.py:1696-1698`).
- If `not is_new`: increments an occurrence counter and **`return []`** at
  `safety.py:1701-1704` — **before** the dispatch block. The
  `async_dispatcher_send(SIGNAL_SAFETY_HAZARD, …)` at `safety.py:1739` is only
  reached when `is_new` is True.
- `AlertDeduplicator.should_alert` (`safety.py:1782`) gates only the
  **NotificationAction**, not the signal. So the prompt's premise that the
  CRITICAL=1min / HIGH=5min dedup window governs re-emit is **incorrect** — the
  signal re-emit is governed by *severity transition*, and dedup is downstream
  of an already-skipped path.

**A steady freeze never changes severity → never re-fires.** Freeze re-detection
is purely **state-change driven** — `_respond_to_hazard` is reached only via
`_async_sensor_state_changed` → intent → `evaluate` → `_process_sensor`
(`safety.py:1100, 1209-1212`). `_async_periodic_check` (the 1-min timer,
`safety.py:2066`) handles **flooding only** — it does NOT re-evaluate freeze.
Even when the outdoor temp sensor reports fresh values every minute,
`_classify_severity(FREEZE_RISK, value)` (`safety.py:1481-1485`) returns the
worst matching band, so a reading held below 35°F stays `HIGH` indefinitely →
`is_new=False` → no re-dispatch → no re-arm. The hold therefore expires at the
hard 2h mark regardless of whether the freeze persists.

**There is no FREEZE_RISK CRITICAL band.** The prompt and the new code comment
("≤35°F = CRITICAL") are wrong: `NUMERIC_THRESHOLDS[FREEZE_RISK]`
(`safety.py:184-188`) defines only `HIGH=35`, `MEDIUM=40`, `LOW=45`. Emergency
heat fires on `severity in ("critical","high")` (`hvac.py:1620`), so in
practice freeze always arrives as **HIGH**. This does not change the verdict
(HIGH still gates on `is_new`), but it means there is exactly ONE severity band
in the sub-35°F regime — so the severity-transition re-arm path can never fire
for a deepening freeze either.

**Failure timeline (concrete):**
1. T+0: outdoor temp crosses ≤35°F → HIGH freeze → signal fires →
   `_set_emergency_heat` sets `heat`, hold = T+2h.
2. T+0…T+2h: temp stays sub-35°F. Sensor updates fire, but
   `_respond_to_hazard` sees `not is_new` → `return []`. Signal never re-fires.
   Hold is NOT refreshed.
3. T+2h: next 5-min decision cycle. `hold_until < utcnow()` → hold dropped
   (`hvac.py:1077`) → `zone.hvac_mode == "heat"` `!= "heat_cool"` →
   **enforcer commands `heat_cool`** while still freezing.
4. In a real cold snap, `heat_cool` with the operator's normal range can let
   indoor temp fall to the low end of the band — freeze protection defeated,
   pipe-burst risk re-introduced, with no alert (notification already
   deduplicated long ago).

### Required redesign (not a tuning change)

The hold must be cleared by **freeze-cleared truth**, not a blind timer. Options
(A preferred):
- **(A) Explicit clear + live re-check.** Keep the zone exempt until either
  (i) Safety routes a "freeze cleared" signal to HVAC (add a
  `clear_hazard(FREEZE_RISK, …)` → dispatch that HVAC subscribes to and which
  pops `_emergency_heat_zones`), or (ii) at hold-expiry the enforcer does a
  **live freeze re-check** (read the same outdoor-temp truth Safety uses) and
  RE-ARMS instead of clobbering if still ≤35°F. The timer then becomes a
  safety *ceiling*, not the primary release.
- **(B)** Make Safety re-dispatch `SIGNAL_SAFETY_HAZARD` on a heartbeat while a
  freeze hazard is active (or have HVAC re-arm on the occurrence-counter
  increment). This refreshes the hold every cycle and lets the 2h timer be a
  genuine staleness backstop. Larger blast radius (touches Safety's
  intentionally-quiet re-emit policy) — note Review B's lane.

The diff comment claims "the pre-fix code also left zones in 'heat'
indefinitely, so this only improves recovery, never worsens it." That is the
**wrong baseline for the safety axis**: pre-fix, a zone stranded in `heat`
during a freeze stayed protected. This change *removes* that protection at the
2h mark. For the freeze path specifically it is a **regression**, not a
strict improvement.

## Findings

### ❌ A-CRITICAL-1 — Enforcer clobbers freeze protection at 2h on a sustained freeze
**Bug class:** Safety-response defeat / blind-timer staleness assumption
(new class candidate: "Timer-released safety hold without truth re-check").
**File:** `hvac.py:1071-1097`, `hvac.py:1689`; chain via
`safety.py:1698-1704, 1739`.
**Reasoning:** see verdict above. Re-arm is impossible for a steady freeze
because the re-emit is gated by severity transition, not by time or dedup.
**Fix:** redesign per (A) — explicit clear or live re-check on expiry; do not
release on a blind timer alone.

### ⚠️ A-HIGH-1 — Incorrect provenance comment ("≤35°F = CRITICAL") + no CRITICAL freeze band
**Bug class:** Fabricated/stale spec in comment.
**File:** code comments around `hvac.py` enforcer + the cycle's framing;
ground truth `safety.py:184-188`.
**Reasoning:** Freeze maxes at HIGH. Anyone reasoning about the 2h hold from
"CRITICAL=1min dedup" (as the cycle framing did) reaches a false safety
conclusion. Correct the comment; if a true CRITICAL freeze tier is wanted
(e.g. ≤25°F), that is a separate Safety change.
**Fix:** correct comments; optionally add `FREEZE_RISK CRITICAL` threshold.

### ⚠️ A-MEDIUM-1 — `del` on expired hold is not concurrency-guarded
**Bug class:** Dict mutated during iteration / KeyError race.
**File:** `hvac.py:1073-1077`.
**Reasoning:** `_async_decision_cycle` is serialized by `_decision_cycle_lock`
(`hvac.py:264, 850`) so two enforcer passes won't overlap, and
`_set_emergency_heat` only ever *adds* keys — so a `del` of a key fetched the
same line is currently safe. But the safety of the `del` depends on that
single-writer invariant holding; if any future path pops the key, the
`del self._emergency_heat_zones[zone_id]` at 1077 would KeyError. Low
likelihood today.
**Fix:** use `self._emergency_heat_zones.pop(zone_id, None)` for defensiveness.

### ✅ A-PASS-1 — Enforcer only acts on heat_cool-capable zones
`_supports_heat_cool` (`hvac_override.py:894-905`) reads live
`hvac_modes` and returns False for heat-only/cool-only AND for
unavailable/None-state entities (modes=[]). A genuinely single-mode unit is
never forced into an unsupported mode, and an unavailable entity is skipped.
Correct and complete for this axis.

### ✅ A-PASS-2 — Egress-pause + AC-reset skips correct and complete
- Egress: `self._egress_manager.is_paused(zone_id)` → `continue`
  (`hvac.py:1069`). Egress sets `off` deliberately (`hvac_egress.py:524-559`);
  enforcer leaves it.
- AC-reset: `not has_active_ac_reset(zone_id)` in the act-guard
  (`hvac.py:1081`). AC-reset's own restore (`hvac_override.py:1172`) targets
  `heat_cool` when supported, so even after the reset window closes the zone
  is already heat_cool → idempotent skip.
No OTHER URA path was found that *intentionally* parks a zone in a single
mode (`cool`/`heat`/`fan_only`) and leaves it there: the remaining
`set_hvac_mode` writers are AC-reset (off→heat_cool restore) and
`_revert_override`/the existing override.py enforcer (`hvac_override.py:938`),
both of which target `heat_cool`. Emergency-heat (`heat`) is the only
single-mode parker, and it is the one this finding is about.

### ✅ A-PASS-3 — Idempotency
`zone.hvac_mode != "heat_cool"` guard (`hvac.py:1079`) → no write when already
heat_cool. Suppress/unsuppress handshake is correctly paired: `suppress` before
the call (1083), `unsuppress` on the failure path (1099); success path relies
on the suppress TTL window (A-F5) to self-clear — consistent with
`_set_emergency_heat`'s pattern. No unbounded suppression on success.

### ✅ A-PASS-4 — `away` preset vs `heat_cool` mode are orthogonal — no coast conflict
The enforcer writes `hvac_mode`; the D5 duty-cycle coast away-flip writes
`preset_mode` (`hvac.py:1284-1308`, `set_preset_mode`). Independent HA
attributes within the same `_apply_house_state_presets`. The enforcer
restoring `heat_cool` does not disturb the away/coast preset, and coast does
not push the mode off heat_cool. No bad interaction.

## Recommendation

**REDESIGN-then-ship.** The non-freeze enforcer behavior (capability gating,
egress/AC-reset skips, idempotency, coast orthogonality) is correct and shippable.
But A-CRITICAL-1 means the freeze-safety interaction — the single highest-risk
part of this cycle — is a **regression** as written: a real cold snap longer
than 2h loses freeze protection silently. Do not ship the
`_emergency_heat_zones` 2h-blind-timer release. Replace it with an explicit
freeze-cleared clear path or a live re-check-and-re-arm at expiry
(redesign option A). Re-review the freeze path after the redesign.
