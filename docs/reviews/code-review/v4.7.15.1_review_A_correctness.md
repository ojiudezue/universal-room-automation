## A1 — Pattern A refactor correctness

**Trace.** `custom_components/universal_room_automation/domain_coordinators/presence.py:755-826` (helper body, `scope == "house_inference"` branch).

### A1.a Per-person parallel-list contract — VERIFIED

`presence.py:768-791` extracts two lists by signal-kind filter:
- `phone_trust = [s.value for s in reliable_signals if s.kind == "person_phone_trustworthy"]`
- `track_active = [s.value for s in reliable_signals if s.kind == "person_tracking_active"]`

Length-parity guard at `:779-787`:
- If both non-empty AND `len(phone_trust) == len(track_active)` AND `len(phone_trust) > 0` → `trusted_count = sum(1 for p, t in zip(phone_trust, track_active) if p and t)`.
- Else → `trusted_count = 0`.

Then at `:810-826` the veto requires `trusted_count > 0 AND all_away AND not any_home AND unid == 0 AND census == 0`. With `trusted_count = 0`, the veto **cannot fire** — returns `VetoDecision(False, 0.0, "", scope)` at `:826`. **Fail-conservative confirmed.** Bug Class #43 (silent person drop) is neutralized: the canary triggers `False` rather than silently dropping the misaligned tail.

One subtlety worth flagging: the parity check is `len(phone_trust) == len(track_active) AND len(phone_trust) > 0`. If a caller supplies BOTH lists empty *and also* drops the back-compat path (e.g., omits `tracked_count` from `state_context`), we hit the else with `trusted_count = 0` and no veto. That's the intended fail-safe — not a bug.

### A1.b Reason string accuracy — VERIFIED

`presence.py:820-823`:
```
"all_tracked_persons_away (no guests, no census, trusted={trusted_count})"
```

`trusted_count` is the **post-filter** count derived from the zip at `:783-785`. It is not a copy of `tracked_count` (state_context) UNLESS the back-compat path fired (per-person lists empty). Tests verify:
- `test_pattern_a_fires_when_census_zero_and_unid_zero_and_all_trusted_away` asserts `"trusted=4"` (4 phone/4 track all True).
- `test_pattern_a_excludes_phone_left_behind_from_trusted` asserts `"trusted=3"` (1 phone False).
- `test_pattern_a_excludes_stale_lost_tracking_from_trusted` asserts `"trusted=2"` (1 track False).

`trusted=N` in the reason string genuinely reflects the post-filter computation.

### A1.c Backward-compat fallback — VERIFIED

`presence.py:788-791`: `if not (phone_trust or track_active): trusted_count = tracked_count` (state_context). This preserves pre-v4.7.14.1 semantic for callers that don't yet supply per-person trust signals (e.g., zone_aggregator scope or future external callers).

`test_pattern_a_falls_back_to_state_context_tracked_count_when_per_person_lists_empty` at `test_v4715_universalize_veto.py:401-415` covers this: `tracked_count=2` → reason includes `"trusted=2"`, decision fires. Equivalent to the v4.7.14 baseline behavior.

**Minor honesty concern (A-L1):** the comment at `:789-790` calls this "pre-v4.7.14.1 semantic." That's accurate for **counting**, but the H1 (census_count) and `unid == 0` clauses still apply in the fallback path — a back-compat caller still gets H1-tightened semantics. A reader could misread the docstring as "fallback restores pre-H1 behavior." Suggest tightening the comment.

### A1.d Veto math AND-gating — VERIFIED

`presence.py:810-816`:
```python

    trusted_count > 0
    and all_away
    and not any_home
    and unid == 0
```

All five components are independently AND-gated. Each is extracted in isolation:
- `all_away` from `person_tracker_away` reliable signal (`:793-795`)

Each component is correctly extracted, and the conjunction is short-circuit-safe (no side effects in `next()` defaults). **Math is correct.**
