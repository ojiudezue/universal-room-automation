### B2 — D5 `_signal_consensus` + D6 defer gate integration

**Files:** `presence.py:2417-2476` (consensus calc), `hvac.py:780-814` (HVAC defer), `coordinator_diagnostics.py:530-566` (compliance defer)

#### B2-HIGH — Read race: HVAC sees new-consensus + old-`_last_transition_time`

**Race trace:**

`_run_inference` writes:
1. `presence.py:2460` — `self._signal_consensus = max(0.0, consensus)` **(new value)**
2. `presence.py:2496` — `await self._count_transition()` **(yields)**
3. `presence.py:2820` — `self._last_transition_time = now` (inside `_record_transition_outcome`)

The HVAC decision cycle and presence `_run_inference` run as **separate tasks** on the event loop. Between steps 1 and 3, HVAC's `_apply_house_state_presets` at `hvac.py:780-814` can interleave and read:

```python
consensus = getattr(presence, "_signal_consensus", 1.0)              # NEW
last_transition = getattr(presence, "_last_transition_time", None)   # OLD (could be hours stale)
```

Then `secs_since_transition` is large (likely > 30), so the gate `consensus < 0.5 AND secs_since_transition < 30` evaluates FALSE → HVAC writes presets **despite the consensus drop** at the very tick the new state just landed.

The reverse error (consensus=old, transition=new) is impossible because the write order is consensus-first; the only inversion is "fresh disagreement + apparently-stale transition timestamp."

**Likelihood:** the consensus drop is usually CAUSED by the state transition (disagreement-1: phones-away + zones-occupied). So step-3 racing with HVAC's read is the most likely time for the gate to be wanted, and exactly the time the inversion occurs.

**Severity:** HIGH (silent correctness — D6's whole point is to suppress preset thrash during disagreement; the race ensures it doesn't trigger during the riskiest tick).

**Fix-up options (cheapest first):**

1. **Move `_signal_consensus =` write AFTER the transition record.** Specifically, push the entire D5 block (`presence.py:2417-2476`) below the `if new_state is not None:` block (`presence.py:2477-2547+`), so by the time consensus is updated, `_last_transition_time` is already current. This preserves "consensus tracks inputs, not output" semantics if computed-once-per-tick — the inputs are only re-checked once per `_run_inference` call anyway. Diff: move ~60 LoC down by ~150 LoC.

2. **Atomic-snapshot helper.** Add a `presence.snapshot_consensus_gate_inputs() -> (consensus, secs_since_transition)` method that captures both under a single sync code path. Callers use the snapshot. Costs an extra ~10 LoC, but generalizes for v4.7.16+ callers.

3. **WONTFIX with rationale.** The race window is ~milliseconds; D6 has asymmetric hysteresis (resume at 0.7) so even if one tick misses, the next will catch. Accept and document.

**Reviewer B recommendation:** Option 1. The cost is low, the fix is local, and "compute consensus after the transition is recorded" matches the documented intent of D5 ("consensus tracks INPUT agreement, not output transitions") more cleanly than the current placement.

#### B2-MED — Compliance defer reads `_consensus_low_since` correctly

Both are scalar/None attributes updated in the same code block at `presence.py:2471-2475` (no await between them), so the compliance reader sees consistent values. ### B5 — Two new D6 switches

**Files:** `switch.py:1808-1873` (HVAC), `switch.py:1876-1940` (Compliance), wired at `switch.py:206-208`

#### B5-MED-1 — RestoreEntity pattern correct, but default-ON semantics fragile

`switch.py:1862-1869` (HVAC) and `:1930-1936` (Compliance):
```python
async def async_added_to_hass(self) -> None:
    await super().async_added_to_hass()
    last_state = await self.async_get_last_state()
    if last_state is not None and last_state.state == "off":
        # ... set coord attribute False
```

This says "default ON; only flip OFF if explicitly restored OFF." The coord attribute itself defaults to True in `hvac.py:196` (`self._defer_gate_enabled: bool = True`) and `coordinator_diagnostics.py:345` (`self._compliance_defer_gate_enabled: bool = True`).

**The race:** between `_async_setup_entry` adding the switch entity and `async_added_to_hass` running the restore, the coordinator's own `_defer_gate_enabled` is `True` (default). If an HVAC tick fires before restore runs, the gate is ON regardless of what the user set. This is the **right** behavior on first install (default ON) but means **on every restart, the user's OFF setting only takes effect AFTER the switch's `async_added_to_hass` runs** — typically <1s but not guaranteed before the first HVAC tick.

**Bug Class #5 (deferred restore via signal):** the pre-restore window is short; HVAC ticks are not common (decision cycle interval typically 30-60s). This is **MUCH less risky** than the Bug Class #5 cases that motivated the rule. Acceptable.

**Recommendation:** add a `_LOGGER.debug` on restore-OFF so operators can see the timing in logs. Optional, not required.

### B6 — CRITICAL/HIGH cross-cycle handoff: `scope="room_level_weighted"`

**Files:**
- v4.7.15: `presence.py:707-824` — helper with patterns A/B/C/D/E
- v4.7.16 (already merged ahead on `develop`): `presence.py:2119` — caller passing `scope="room_level_weighted"`

#### The gap

- `"zone_aggregator"` (Patterns B + C) at `:754, 763`

#### Verdict (Reviewer B framing)

**This is NOT a v4.7.15 bug** because v4.7.16 D3 explicitly designs this block as **diagnostic-only** for this cycle (per v4.7.16 Review A line 208: "v4.7.16 records the verdict for diagnostics; downstream gating ties in once the helper API is stable"). The verdict being structurally `False` means **the diagnostic recorder is recording a constant-False signal**, which is misleading but not behaviorally broken.

**This IS a v4.7.16 latent risk** when a future cycle (v4.7.17?) wires `_v4716_zone_verdicts` into actual gating. At that point, the per-room weighted veto will silently no-op until a Pattern F is added.

**This IS a sprint sequencing gap** that should be tracked in QUALITY_CONTEXT.md as a new class candidate:
- "Caller passes a `scope=` value the dispatcher doesn't recognize → silent no-veto fall-through → diagnostic look fine, gating doesn't fire."

#### Recommendation (B6 explicit, per task brief)

**Option B (preferred for v4.7.15):** **Document as future cycle.** Add an inline comment at `presence.py:824` (the fall-through return):
```python
# v4.7.15 D1: unknown scope. v4.7.16 D3 passes "room_level_weighted" here;
# helper falls through. Diagnostic recorder records fired=False. When v4.7.17+
# wires room-weighted gating, add Pattern F BEFORE removing the diagnostic-only
# acceptance from v4.7.16's _v4716_zone_verdicts callers.

```

**Option A (lower-cost fix-up to v4.7.15):** add Pattern F NOW using v4.7.16's documented signature. Roughly:

if scope == "room_level_weighted":
    aggregate_weight = float(state_context.get("aggregate_weight", 0.0))

            True, 0.7,

But this REQUIRES coordinating with v4.7.16 Reviewer A's pending decision between `sum` vs `max` aggregation (A1 in their review). Don't ship Pattern F without that consensus or you'll ship the wrong threshold semantic.

**Option C (defer to v4.7.16 fix-up):** v4.7.16 changes its scope to fit an existing pattern. **No existing pattern fits** — Patterns A/B/C/D/E all carry house-state or transition-side semantics; `room_level_weighted` is fundamentally a per-zone calc. Don't try to retrofit.

**Reviewer B verdict on B6:** **Option B for this cycle.** Add the inline comment, ship v4.7.15 as-is. Pattern F belongs in the same cycle that flips `_v4716_zone_verdicts` from diagnostic to gating, because the threshold semantic (sum vs max, 1.0 vs 0.6 vs ...) needs the diagnostic data first. Track in QUALITY_CONTEXT.md as future Bug Class candidate: "scope-dispatcher silent no-op for unknown scope strings — caller's diagnostic look fine but gating never fires."
