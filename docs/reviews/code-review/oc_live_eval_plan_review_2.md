## Build-prediction: what the builder will get wrong
1. **Stale-mount check on the wrong file.** The URA DB runs in WAL mode, so the main `.db` mtime only moves at checkpoint and can legitimately be older than 600 s, which makes the run abort for no reason. Check the `-wal` mtime (or `max(rowid)` growth / a known-fresh table's newest timestamp).
2. **`mode=ro` over SMB with WAL.** A read-only WAL reader needs the `-shm`. Over Samba, locking is unreliable, so expect "unable to open database" or stale snapshots. Long readers also delay HA's checkpoints. The plan should say: one connection per query, close immediately, `sql_timeout_s` enforced by the progress handler. D1 acceptance should include a test of opening each DB over the mount.
3. **Judge rule appended, not replaced** (F3c).
4. **HA REST path regex applied to the full URL.** `history/period/<start>?filter_entity_id=…` includes a query string. The builder either matches the full URL (rejects valid calls) or matches the path only and passes through arbitrary query params (`minimal_response` is harmless, but the allowed params should be listed). Specify: match the path, then build the query from an allowlist of params.
5. **Double shell quoting for `ssh ha journalctl … | grep`.** The command passes through a local and a remote shell. `shlex.quote` once is not enough. Specify `subprocess.run(["ssh","ha", remote_cmd])` with `remote_cmd` built from `shlex.quote` once per remote token, and the `-u` unit pinned (the plan writes "…"; the builder will guess). Better: drop the grep and filter locally in Python.
6. **SQLite authorizer gaps.** Allowing FUNCTION also allows `load_extension()`. Assert `enable_load_extension(False)` and test it. `PRAGMA query_only=1` must run before the authorizer is set, or the authorizer blocks its own PRAGMA. Recursive CTEs need SQLITE_RECURSIVE allowed.
7. **Leak scan over all results** (F4). The builder will implement it literally and void every good run.
8. **`list_changes_since` from raw `git log`** (F1). The builder will return subjects.
9. **Judge transcript size.** Live results can be large (history up to 2000 rows), and the judge "reads stored results". The builder will hit context limits or silently truncate. Specify per-result truncation with a recorded marker, using the same truncation the model saw.
10. **Case denominators hard-coded to 7** (F5).
