## Findings

### A-H1 (HIGH): H2 phone_left_behind entity-ID slug is unverified — silent no-op risk

**File:** `presence.py:1932-1937`

```python
person_slug = person_name.lower().replace(" ", "_")
entity_id = f"binary_sensor.{person_slug}_phone_left_behind"
state = self.hass.states.get(entity_id)
```

**Problem.** `PersonPhoneLeftBehindSensor` (`binary_sensor.py:973-1006`) registers with:
- `_attr_has_entity_name = True` (`:989`)
- `_attr_unique_id = f"{DOMAIN}_person_{person_id.lower().replace(' ', '_')}_phone_left_behind"` (`:1000`)
- `_attr_name = f"{person_id} Phone Left Behind"` (`:1001`)
- `DeviceInfo(identifiers={(DOMAIN, "integration")}, name="Universal Room Automation", ...)` (`:1003-1008`)

Under HA's `has_entity_name=True` semantics, the entity_id is composed from the device name + entity name on first registration (HA dev docs: "Entity naming"), **not** from `unique_id`. The plan §0.2 conflates the two: "Entity ID pattern: `binary_sensor.<person_id_lowercased>_phone_left_behind` (unique_id at `binary_sensor.py:1000`)". The cited line is the unique_id formula. Unique_id and entity_id are independent.

Comparable case in the same file: `URAUnexpectedPersonSensor` (`binary_sensor.py:802-827`) uses identical DeviceInfo + `has_entity_name=True` + `_attr_name = "Unexpected Person Detected"` and lives as `binary_sensor.ura_unexpected_person_detected` per `docs/readmes/README_v3.5.0.md:30`. The device-name prefix collapses to `ura_` (likely via a name override or because of the unique_id legacy ID). Either way, the resulting entity_id is **not** what the slug-formula heuristic predicts from name alone.

For `PersonPhoneLeftBehindSensor`, the actual entity_id is likely one of:
- `binary_sensor.universal_room_automation_oji_phone_left_behind` (canonical HA composition)
- `binary_sensor.ura_oji_phone_left_behind` (if the URA shortening pattern applies)
- `binary_sensor.oji_phone_left_behind` (if the entity registered before `has_entity_name=True` was set, or via legacy unique_id path)

Only the last case matches H2's formula. The other two cause H2 to silently fail-OPEN for every person — `hass.states.get()` returns None → `_phone_trustworthy` returns True → no filtering → v4.7.14 baseline behavior. **Gap B remains unclosed and the cycle ships a silent no-op for H2.**

**Test gap (Bug Class #44).** `test_h2_entity_id_slug_matches_binary_sensor_format` (test file lines ~445-456) constructs `"binary_sensor.oji_udezue_phone_left_behind"` and asserts the production helper finds it. But the test fixture mirrors the production slug formula, so the test cannot catch a mismatch between either of those and the real registered entity_id.

**Suggested fix (one of):**

1. **Verify against live HA** (15 min) before deploy: ask HA MCP `ha_get_entity` for `binary_sensor.oji_phone_left_behind` and check whether it exists with the predicted slug. If yes, ship as-is and add a unit test that pins the formula explicitly with a comment "verified against live entity 2026-05-30." If no, switch to entity-registry lookup by unique_id (see option 2).
2. **Switch H2 to unique_id resolution.** Use `entity_registry.async_get(self.hass)` and resolve `unique_id = f"{DOMAIN}_person_{person_slug}_phone_left_behind"` → entity_id, then `hass.states.get(entity_id)`. This is slug-independent and robust to entity-registry renames.

**Severity rationale.** Not CRITICAL because fail-OPEN means no regression vs v4.7.14 baseline. But HIGH because the cycle ships claiming to close Gap B and may not actually close it — the live-validation runbook in the README assumes the entity exists at the predicted slug.

### A-M1 (MEDIUM): Veto-fired log condition does not match the v4.7.14.1 veto predicate

**File:** `presence.py:2057-2072`

```python
if (
    all_tracked_persons_away
    and self._unidentified_count == 0
    and new_state == HouseState.AWAY
    and current_state != HouseState.AWAY
):
    _LOGGER.info(
        "v4.7.14: Person-tracker veto fired — all %d tracked persons "
        "away ...",
```

**Problem.** The log condition does NOT include `self._census_count == 0`, so it also fires when the line-398 AND-gate (`census_count == 0 AND not any_zone_occupied`) drove the AWAY transition. That gate doesn't use `all_tracked_persons_away` at all — it would fire even with `all_tracked_persons_away=False` (just with the same end result here because the predicate is unrelated). When `all_tracked_persons_away=True` and the line-398 gate fires (confidence 0.9), the log claims "Person-tracker veto fired" — which is misleading; the AND-gate fired, not the veto.

This is a **pre-existing v4.7.14 defect** (not introduced by v4.7.14.1) but the cycle is the natural place to fix it because v4.7.14.1 already documents the precise veto predicate.

**Suggested fix.** Tighten the log condition:

```python
if (
    all_tracked_persons_away
    and self._unidentified_count == 0
    and self._census_count == 0          # mirror H1
    and any_zone_occupied                # only the veto path, not the AND-gate
    and new_state == HouseState.AWAY
    and current_state != HouseState.AWAY
):
```

Also: the log message should report `confidence` so the operator can distinguish 0.9 (AND-gate) from 0.95 (veto) in journald.

### A-M2 (MEDIUM): `tracked_persons_count` attribute semantics changed without sensor-doc update

**Files:**
- `sensor.py:3624-3634` (D3 attribute block)
- `presence.py:1977-1979` (where `_tracked_persons_count` is set)

**Problem.** Pre-v4.7.14.1, `tracked_persons_count` reflected `len(person_coordinator.data)` — the raw configured-person count. Post-H2+H3, it reflects the **filtered** count after phone_left_behind and STALE/LOST removal. Two consequences:

1. The sensor.py docstring (`:3622-3627`) says "tracked_persons_count is the number of configured person.* trackers seen by person_coordinator" — now wrong; it's the post-filter trustworthy subset.
2. Any operator dashboard or automation that reads this attribute (e.g., showing "4 of 4 configured persons away") will silently show smaller numbers without the operator understanding why. Memory body `project_v4714_live.md` cites `tracked_persons_count = 4` from the v4.7.14 verification — the v4.7.14.1 number could be 3 if oji's phone is BLE-stale.

**Suggested fix.** Either:
- Update the sensor.py comment to describe post-filter semantics; add explicit `configured_persons_count` attribute alongside for the raw count; document both in the README live-validation section, OR
- Keep `tracked_persons_count` as raw count, add a new `trustworthy_persons_count` attribute for the filtered denominator. (Cleaner — preserves backwards compatibility with anything reading the old attribute.)

I prefer the second option.

### A-M3 (MEDIUM): `away_person_ids` in INFO log enumerates only post-filter persons — operator-visibility regression

**File:** `presence.py:1969, 2068-2069`

**Problem.** After H2+H3, `away_person_ids` lists `sorted(trustworthy_persons.keys())` — the filtered subset. When the veto fires and the operator reads journald, they see e.g. `"v4.7.14: Person-tracker veto fired — all 3 tracked persons away (ada, jaya, kai)"` even though 4 persons are configured. The 4th (oji, phone-left-behind) is silently elided.

For an operator debugging "why didn't oji's home phone block the veto?" the log doesn't say. They'd have to know the post-filter shape mentally.

**Suggested fix.** In the veto-fired log, ALSO include the filtered-out persons and the reason. E.g.:

```
v4.7.14.1: Person-tracker veto fired — 3 trustworthy persons away (ada, jaya, kai);
1 excluded (oji: phone_left_behind=on); no unidentified; census=0
```

This is a single log-line change but materially improves diagnostic transparency. Mandatory once H2/H3 land because the operator runbook in the README depends on this log line for live validation.

### A-L2 (LOW): `_tracking_active` default-to-ACTIVE swallows future field-rename bugs

**File:** `presence.py:1939-1950`

```python
return info.get("tracking_status", TRACKING_STATUS_ACTIVE) == TRACKING_STATUS_ACTIVE
```

**Problem.** If `person_coordinator.py` ever renames the field (e.g., to `tracking_state`), the H3 filter silently defaults all persons to ACTIVE — no filtering, silent regression to v4.7.14 behavior. No log, no test failure.

**Suggested fix (defer or now).** Add a debug log when the field is missing AND `person_data` is non-empty:

```python
if "tracking_status" not in info:

    )
```

Or — stronger — add a one-line assertion test in this cycle:

```python
def test_h3_tracking_status_field_name_is_stable():
```
