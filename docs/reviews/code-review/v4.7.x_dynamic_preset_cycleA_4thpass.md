### WPM-C1: Double-fetch + re-entrancy (Reviewer A2 / B1 / B2 / C-M4)

**Reviewers' concern:** (a) Active provider forecast fetched twice per refresh (double service call), (b) no re-entrancy guard on `_refresh_all_providers` -- concurrent state-change events interleave writes to shared state.

**1. Was the fix applied at the right file:line?**
YES. `weather_manager.py:117` adds `self._refresh_lock: asyncio.Lock()`. Lines 323-333 split the method: `_refresh_all_providers` acquires the lock via `async with`, then delegates to `_refresh_all_providers_locked`. Line 349 introduces `fetched_forecasts: dict[str, dict] = {}` as a local cache. Line 370 populates it (`fetched_forecasts[eid] = forecast_data`). Line 397 reuses it (`forecast_data = fetched_forecasts.get(new_active)`) instead of re-fetching.

**2. Does the fix actually close the issue?**
YES -- both sub-issues:
- **Double-fetch eliminated:** The active provider's forecast data is fetched once in the per-provider loop (line 364) and cached in the local `fetched_forecasts` dict. The post-election code at line 397 does a `dict.get()` instead of `await self._fetch_provider_forecast()`. No second service call.
- **Re-entrancy guarded:** `asyncio.Lock` serializes concurrent calls. The lock is acquired in the public method and released after the inner method returns. The `async with` pattern is correct -- the lock IS held across `await` calls inside the locked method, which is the intended behavior (serialization, not deadlock risk, because no other code path tries to acquire the same lock re-entrantly from within `_refresh_all_providers_locked`).

**3. Does the fix introduce a new issue?**
MINOR NOTE (not a defect): `get_today_forecast()` (line 192) still calls `await self._refresh_all_providers()`, which acquires the lock. If EC calls `get_today_forecast()` while a state-change-driven refresh is in progress, the EC call will block until the state-change refresh completes, then run its own full refresh. This is correct behavior (serialized, not dropped), and the latency budget is acceptable -- each refresh completes in <100ms (2-3 weather service calls). No regression.

**Verdict: VERIFIED -- no regression.**

### WPM-C2: Untracked task tracking (Reviewer A1 / B5)

**Reviewers' concern:** `_handle_provider_state_change` calls `hass.async_create_task` but discards the return value. Tasks are not tracked for cancellation during teardown.

**1. Was the fix applied at the right file:line?**
YES. `weather_manager.py:118` adds `self._pending_refresh_tasks: set[asyncio.Task] = set()`. Lines 570-575 capture the task, add it to the set, and register `task.add_done_callback(self._pending_refresh_tasks.discard)`. Lines 163-169 in `async_teardown` cancel all pending tasks, await them with `return_exceptions=True`, and clear the set.

**2. Does the fix actually close the issue?**
YES. The pattern is:
```python
task = self.hass.async_create_task(...)
self._pending_refresh_tasks.add(task)
task.add_done_callback(self._pending_refresh_tasks.discard)
```
This is the canonical URA pattern for Bug #19 (matches `hvac.py:922-924` precedent). The `add_done_callback(discard)` fires when the task completes normally OR is cancelled, so the set stays clean.

**3. Does the fix introduce a new issue?**
NO. Race analysis: `add_done_callback` runs on the event loop, so there is no TOCTOU between `add(task)` and the callback being registered. If the task completes between `async_create_task` and `add`, the callback fires immediately on the next event-loop tick, which is fine -- `discard` on a set that does not contain the element is a no-op. The teardown path snapshots `list(self._pending_refresh_tasks)` before iterating, so concurrent discard callbacks do not cause `set changed size during iteration`.

**Verdict: VERIFIED -- no regression.**

### WPM-C3: Divergence transition (Reviewer B3)

**Reviewers' concern:** `SIGNAL_WEATHER_DIVERGENCE_DETECTED` fires on every refresh while divergent, causing unbounded log spam and signal flooding.

**1. Was the fix applied at the right file:line?**
YES. `weather_manager.py:114` adds `self._was_divergent: bool = False`. Lines 472-497 implement the transition logic.

**2. Does the fix actually close the issue?**
YES. The implementation:
```python
was_divergent = self._was_divergent        # read old value into local
self._was_divergent = is_divergent          # update instance state
if is_divergent and not was_divergent:      # enter-divergence transition
    ...signal fires + WARNING log...
elif was_divergent and not is_divergent:    # exit-divergence transition
    ...INFO log "cleared"...
```
The critical ordering is correct: `_was_divergent` is read BEFORE being updated, so the transition check uses the previous state. The signal fires only on `False -> True` transition. The exit path (`True -> False`) logs an INFO (not WARNING) and does NOT fire a signal, which is correct per the plan.

**3. Does the fix introduce a new issue?**
ANALYZED -- no issue:
- **First divergence event:** `_was_divergent` starts as `False` (constructor). First time `is_divergent=True`, the guard `is_divergent and not was_divergent` fires correctly. Signal dispatches once.
- **Reload during active divergence:** On reload, the new WPM instance starts with `_was_divergent = False`. The first refresh will re-derive divergence and fire the signal once (re-entry). This is acceptable -- the reload is a fresh lifecycle, and subscribers re-register on reload too, so they need the signal to get current state. Not a bug.
- **Exit + re-enter:** After divergence clears (`_was_divergent` set to `False`), if divergence recurs, the signal fires again. Correct behavior.

**Verdict: VERIFIED -- no regression.**

### WPM-H1: Signal subscribers (Reviewer B7)

**Reviewers' concern:** Three new entities lack signal-driven refresh -- dispatcher signals have zero subscribers.

**1. Was the fix applied at the right file:line?**
YES. Three entities modified:
- `sensor.py:6352-6366` -- `WeatherActiveProviderSensor.async_added_to_hass` subscribes to `SIGNAL_WEATHER_PROVIDER_CHANGED`
- `sensor.py:6424-6438` -- `WeatherApparentForecastHighSensor.async_added_to_hass` subscribes to `SIGNAL_WEATHER_PROVIDER_CHANGED`
- `binary_sensor.py:1700-1714` -- `WeatherDivergenceBinarySensor.async_added_to_hass` subscribes to `SIGNAL_WEATHER_DIVERGENCE_DETECTED`

**2. Does the fix actually close the issue?**
YES. Each entity:
- Calls `await super().async_added_to_hass()` first (preserves parent lifecycle)
- Uses `async_dispatcher_connect(self.hass, SIGNAL_*, self._on_*_signal)` for subscription
- Wraps the unsub in `self.async_on_remove(...)` for cleanup (Bug #38 compliance)
- The handler is `@callback`-decorated and calls `self.async_write_ha_state()` to push updated values to HA

Signal correctness:
- `WeatherActiveProviderSensor` subscribes to `SIGNAL_WEATHER_PROVIDER_CHANGED` -- CORRECT (updates on failover)
- `WeatherApparentForecastHighSensor` subscribes to `SIGNAL_WEATHER_PROVIDER_CHANGED` -- CORRECT (apparent high changes when provider changes)
- `WeatherDivergenceBinarySensor` subscribes to `SIGNAL_WEATHER_DIVERGENCE_DETECTED` -- CORRECT (updates on divergence entry)

**3. Does the fix introduce a new issue?**
MINOR NOTE: The `WeatherDivergenceBinarySensor` subscribes to the divergence signal, which now only fires on the enter-transition (per C3 fix). This means the binary sensor will update reactively when divergence starts, but will NOT get a reactive update when divergence clears -- it relies on the next `SIGNAL_WEATHER_PROVIDER_CHANGED` (if provider also changes) or the next HA poll. However, `WeatherDivergenceBinarySensor.is_on` reads `mgr.is_divergent` (which is `self._divergent`, updated on every refresh). Since every state-change event triggers a refresh that may change `_divergent`, and `SIGNAL_WEATHER_PROVIDER_CHANGED` fires on provider changes, the practical update latency for divergence-cleared is bounded by the next provider state-change event. Not a functional defect; merely a note that divergence-exit updates are indirect rather than signal-driven. The sensor will still converge to the correct state.

**Verdict: VERIFIED -- no regression.**
