### Specific cells flagged:

- **`fill_priority` vs `excess_solar` flapping (plan's hint):** The plan asked about SOC borderline 95±5 — does a single tick produce one action? **YES** — SOC < 80 and SOC ≥ 95 cannot simultaneously be true. The toggle's single switch (`_excess_solar_enabled`) gates BOTH the turn-ON path (excess_solar) and the pause path (FP), so an OFF state of the switch disables both consistently. **No flap.** ✅

- **`drain` vs `fill_priority` ordering:** Drain fires FIRST in the tick. If drain pauses, FP runs next. FP sees `is_on=False` (drain just dispatched off) and skips pause. FP does NOT add EVSE to `_paused_by_fill_priority`. Then next tick drain pauses again (idempotent), FP again skips. Result: only drain holds the set. **No double-pause-state.** ✅

- **`fill_priority` running first then drain (hypothetical reverse):** Not possible — code ordering fixes drain first.

- **Force-Charge override scope:** **The Force-Charge button bypasses ONLY TOU pause (`determine_actions` checks `_force_charge_until`). It does NOT bypass `determine_battery_drain_actions`, `determine_fill_priority_actions`, `determine_grid_cap_actions`, or `determine_arbitrage_actions`.** Plan + button helper text (D3.5) say "Override URA's solar-aware EV gating ... charge now regardless of solar or battery state." This is **A-H1** below — UX contract violation. Drain/FP/grid_cap continue paunsing during the force-charge window.

## Findings

### A-H1 — **HIGH** — Force-Charge helper-text vs implementation mismatch (plan + code)

**Where.** `button.py` EVSEForceChargeButton helper text (D3.5 update), `energy_pool.py:380-393` (force-charge check at TOU only).

**Symptom.** Helper text claims:
> "Override URA's solar-aware EV gating for the next 30 minutes. Use this when an EVSE is marked self-modulating (URA re-pauses every cycle) but you need it to charge now regardless of solar or battery state."

But `_force_charge_until` is consulted ONLY in `EVChargerController.determine_actions(tou_period)` (TOU pause). It is NOT consulted in:
- `determine_battery_drain_actions` (SOC < drain threshold + battery discharging)
- `determine_fill_priority_actions` (NEW — SOC < fill threshold + solar healthy)
- `determine_grid_cap_actions`
- `determine_arbitrage_actions`

**Failure mode.** User has fill-priority-paused EV (SOC 51%, soc_threshold=80, solar healthy). User reads button helper text, presses Force-Charge expecting EV to charge for 30 min. URA's next decision tick: TOU bypass fires → but FP STILL pauses → EV never starts. Same for drain. Same scenario the plan said this button would resolve: "you need it to charge now regardless of solar or battery state" — does not work.

**Material consequence.** Quietly defeats the documented admin escape hatch. User support burden when the "override" doesn't override.

**Fix options.**
1. **Code fix (preferred):** add `if self._force_charge_active: continue` to the top of the per-EVSE loop in `determine_battery_drain_actions` and `determine_fill_priority_actions`. Drain/FP/etc respect the same admin window. Then issue a turn-on dispatch when force-charge becomes active for any EVSE currently in `_paused_by_*`. The plan's #6 (cross-rule precedence matrix) demanded this be locked down; it isn't.
2. **Doc fix (minimal but lies to user):** narrow helper text to "Override URA's TOU pause for 30 min." Drop "solar or battery state" claim.

**Recommendation.** Option 1. The whole reason to add Force-Charge in v4.7.x D3 was the admin escape hatch — narrowing it to TOU-only neuters it for the most common new-cycle scenario (fill-priority pause). Pause-skip guards in drain+FP+grid_cap also need symmetric resume-on-entry behavior (turn the switch ON when force-charge engages and the EVSE is in any `_paused_by_*` set).

### A-H2 — **HIGH** — Drain resume clobbers fill-priority's dispatch state on handoff

**Where.** `energy_pool.py:778-791` (EV drain resume "other pause active" block) and `energy_pool.py:1481-1491` (plug mirror).

**Code:**
```python
if battery_out_of_capacity or soc_recovered:
    if (
        evse_id in self._paused_by_grid_cap
        or evse_id in self._paused_by_us
        or evse_id in self._paused_by_arbitrage
        or evse_id in self._paused_by_fill_priority   # NEW
    ):
        self._paused_by_battery_drain.discard(evse_id)
        self._clear_pause_dispatch_state(evse_id)     # ← clobbers FP's state!
```

**Problem.** `_pause_dispatch_ts` and `_observed_off_since_pause` are **shared** between drain and fill-priority (planner explicit decision — D2 "Shares `_pause_dispatch_ts` / `_observed_off_since_pause` with drain — only one URA dispatch is pending at a time per EVSE."). The handoff path here clears those dicts unconditionally — including when fill-priority is the one still holding the EVSE and owns the current dispatch tracking.

**Failure trace.** Tick 1: FP pauses garage_a; stamps `_pause_dispatch_ts[garage_a]=T1`, OF=False. Tick 2: drain ALSO meets conditions (SOC < drain threshold), pauses garage_a, re-stamps `_pause_dispatch_ts[garage_a]=T2`, OF=False, adds to `_paused_by_battery_drain` (drain runs before FP this tick). Tick 3: SOC recovers above drain threshold + 5 → drain wants to resume. FP still wants to pause (SOC still < fill_priority_soc=80). Drain's resume gate sees `_paused_by_fill_priority` holds → calls `_clear_pause_dispatch_state(garage_a)` → wipes `_pause_dispatch_ts` and OF. Tick 4: FP's manual-override branch reads `_pause_dispatch_ts.get(garage_a)` → None → `grace_expired` evaluates False → manual-override never fires for this EVSE until FP re-dispatches.

**Failure manifestation.** If the user toggles `switch.garage_a` ON between ticks 3 and 4, FP **cannot detect the manual override** (no dispatch_ts to compare grace against) until FP itself dispatches a new pause. The safety net works again on the next FP dispatch (line 910 re-stamps), so the window is at most one decision interval. But it means: a user who toggles the switch ON right after drain-to-FP handoff briefly escapes URA's manual-override detection.

**Fix.** Do not call `_clear_pause_dispatch_state(evse_id)` in the "other pause active" handoff branches. Drain's set membership is dropped; FP retains its dispatch state. Symmetric: same in plug version (line 1486).

```python
# Drain handoff to another pause reason
if (
    evse_id in self._paused_by_grid_cap
    or evse_id in self._paused_by_us
    or evse_id in self._paused_by_arbitrage
    or evse_id in self._paused_by_fill_priority
):
    self._paused_by_battery_drain.discard(evse_id)
    # Don't clear dispatch state — the receiving rule (FP) still uses it.
    _LOGGER.info(...)
    continue
```

Same fix in FP→drain handoff path (line 925-936 in EV, line 1480-1491 in plug). The terminal-resume path (turn_on dispatched) at lines 794 and 952 should still clear dispatch state because no rule holds the EVSE after that.

**Severity rationale.** Brief window of broken safety net, NOT data loss, NOT immediate failure — HIGH (silent defeat of override detection during a handoff), not CRITICAL.

### A-M2 — **MEDIUM** — `pause_reason_human` and `energy_status` precedence orderings disagree

**Where.** `energy_pool.py:1196-1213` (per-EVSE `energy_status`) vs `energy_pool.py:1227-1259` (`pause_reason_human`).

**Per-EVSE `energy_status` order:** drain → fill_priority → arbitrage → grid_cap → us(TOU) → excess_solar → charging → idle → off

**`pause_reason_human` order (per inline comment line 1228):** fill_priority → drain → grid_cap → arbitrage → TOU → excess_solar → activity

**Concrete failure.** EVSE in BOTH `_paused_by_battery_drain` AND `_paused_by_fill_priority` (this can happen — see A-H2 trace). Sensor surfaces:
- `evse_state.energy_status = "battery_drain_paused"`  ← drain wins
- `pause_reason_human.garage_a = "holding for battery fill (target 80%, solar healthy)"`  ← fill_priority wins

Same sensor, same EVSE, contradictory reasons. User dashboards / NM alerts that consume either become incoherent.

**Smart-plug version (`SmartPlugController.get_status()` lines 1097-1116)** uses yet a third order: drain → fill_priority → us(TOU) → activity. Mid-rule subset, but the drain-vs-fill-priority order matches the EVSE `energy_status` order — and DISagrees with the EVSE `pause_reason_human` order. So the L1 plug `pause_reason_human` is consistent with EVSE `energy_status`, neither is consistent with the EVSE `pause_reason_human`.

**Fix.** Pick ONE precedence order (the plan's documented order is fill_priority > drain > grid_cap > arbitrage > TOU > excess_solar) and use it for both `energy_status` and `pause_reason_human`, and at both the EV and the plug surfaces. Add a `_format_pause_reason(evse_id)` helper and have both branches call it.

### A-M3 — **MEDIUM** — Grace-window resets perpetually on idempotent re-pause

**Where.** `energy_pool.py:716-722` (drain re-pause body) and lines 902-911 (FP re-pause body).

**Code:**
```python
self._paused_by_battery_drain.add(evse_id)
self._pause_dispatch_ts[evse_id] = now          # ← re-stamped every tick
self._observed_off_since_pause[evse_id] = False # ← reset every tick
```

**Concern.** Every tick that drain re-pauses (idempotent), the grace window restarts from now. A user who toggles the switch ON within EVERY 30 seconds — perhaps via an external automation that fights URA — would NEVER trigger the cooldown branch (G never True). URA re-pauses, re-stamps grace, user re-toggles, repeat. This is technically the intent (idempotent re-pause is correct), but it weakens the cooldown safety valve.

**Impact.** Low in practice — a hostile/buggy external automation already loses against URA (the switch gets re-paused every 5 min). The grace-reset means we never engage the 1-hour cooldown to stop fighting, but in practice URA wins on tick frequency anyway.

**Recommendation.** Leave as-is for v4.7.6 (matches plan intent). Add a comment at line 720 documenting: *"Grace window resets every tick — by design. Idempotent re-pause beats grace expiry. The cooldown branch only fires if the user-side toggle stays ON across a full tick AFTER URA's last dispatch was observed-off. Hostile-automation fight is resolved by URA's tick-rate dominance, not by cooldown."*

### A-M4 — **MEDIUM** — FP peak-clear leaks shared dispatch state

**Where.** `energy_pool.py:836-841` (FP `tou_period == "peak"` early-return).

**Code:**
```python
if tou_period == "peak":
    for evse_id in list(self._paused_by_fill_priority):
        self._paused_by_fill_priority.discard(evse_id)
    return actions
```

**Problem.** When TOU transitions to peak, FP silently drops set membership but does NOT call `_clear_pause_dispatch_state(evse_id)`. If FP was the only rule holding the EVSE, the stale `_pause_dispatch_ts[evse_id]` and `_observed_off_since_pause[evse_id]` entries persist until something else writes them (drain may re-stamp on its own pause, but if drain doesn't fire, they're orphaned).

**Fix.** Inside the peak-clear loop, also call `self._clear_pause_dispatch_state(evse_id)`.

if tou_period == "peak":
    for evse_id in list(self._paused_by_fill_priority):

## Specific Edge Case Worth Noting

**SOC=12 at start of recharge cycle:** when SOC is exactly at `reserve_soc + 2` AND solar is actively recharging (e.g., battery_power_w = +3000 W, positive = charging), `battery_discharging=False` → `battery_ok=True`. `battery_out_of_capacity=True` → drain resumes EV. This is **the wrong moment** to resume — solar is just starting to recharge the battery. Resuming the EV at 7.4 kW will pull the battery back down.

In practice this is a narrow window — the user typically sets `reserve_soc` to a level where they accept grid fallback. But the rule conflates "not discharging this instant" with "no capacity," which the plan's intent (`capacity exhausted`) does not actually mean.

**Recommendation:** Tighten `battery_ok` to require `battery_power_w` between a small negative threshold and a small positive threshold (e.g., `-100 <= battery_power_w <= +500`) — i.e., the battery is genuinely at equilibrium, not actively recharging. Defer to v4.7.7 or capture in a follow-up.

**Severity:** documented in A-L1 family → **LOW-MEDIUM**, leaving as observation.
