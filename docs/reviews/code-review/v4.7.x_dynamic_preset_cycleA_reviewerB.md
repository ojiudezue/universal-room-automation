## Finding B1 -- CRITICAL: Double Fetch of Active Provider Forecast in `_refresh_all_providers`

**File:** `domain_coordinators/weather_manager.py:342,371`
**Bug class:** Performance + correctness (novel -- propose as new class)

The `_refresh_all_providers` method calls `await self._fetch_provider_forecast(eid)` for ALL usable providers in the loop (line 342), then calls `await self._fetch_provider_forecast(new_active)` AGAIN for the active provider at line 371. This is an awaited `hass.services.async_call("weather", "get_forecasts", ...)` -- a real HA service call that hits the weather integration.

**Impact:**
- The active provider's forecast is fetched TWICE per refresh cycle. Since `_refresh_all_providers` is called on every state-change event (line 530) AND on every `get_today_forecast()` call (line 176), and `get_today_forecast()` is called from `energy.py:_update_forecast_temps` every decision cycle (5 min), this is at minimum 2x service calls per provider per refresh.
- The second fetch at line 371 may return a DIFFERENT result than the first at line 342 if the weather integration updated between calls. The `raw_high` in `provider_highs` (from first fetch) and the `raw_high` in the `WeatherForecast` (from second fetch) could diverge, meaning the divergence calculation used stale data relative to the cached forecast.
- The first fetch result for the active provider (line 342) is discarded -- only used to populate `provider_highs`. The `apparent_high` from that first fetch is never stored.

**Fix:** Cache the forecast_data from the first fetch per provider. When building the WeatherForecast object, reuse the already-fetched data for `new_active` instead of fetching again.

**Severity:** CRITICAL -- silent data inconsistency between divergence calculation and cached forecast; doubled service call load on every refresh.

## Finding B2 -- CRITICAL: `_refresh_all_providers` Has No Re-Entrancy Guard -- Concurrent Execution Risk

**File:** `domain_coordinators/weather_manager.py:315,530,176`
**Bug class:** #20 (Concurrent Reload Race) -- variant: concurrent async execution

`_refresh_all_providers` is an async method called from three sites:
1. `async_setup` (line 148) -- once at startup
2. `get_today_forecast` (line 176) -- every EC decision cycle (~5 min)
3. `_handle_provider_state_change` (line 530) via `hass.async_create_task` -- on EVERY state-change event from ANY configured weather provider

The state-change handler fires `hass.async_create_task(self._refresh_all_providers())` which creates a new coroutine each time. If a weather entity updates while `get_today_forecast` is already mid-refresh (both `await self._fetch_provider_forecast` calls are yield points), TWO concurrent executions of `_refresh_all_providers` will interleave, writing to `self._active_provider`, `self._provider_health`, `self._provider_highs`, `self._cached_forecast`, and `self._divergent` in an unpredictable order. The fields have no atomicity guarantee.

Additionally, `_handle_provider_state_change` fires for each provider entity separately. If all 3 providers update within the same event loop tick (common for weather integrations that update on a shared schedule), 3 concurrent tasks are created, each running `_refresh_all_providers`.

**Impact:** Race condition producing inconsistent state: `_active_provider` could point to entity A while `_cached_forecast` holds data from entity B. Divergence flag may flicker. Sensor readings may be transiently wrong.

**Fix:** Add an `asyncio.Lock` as `self._refresh_lock` initialized in `__init__`. Acquire it at the top of `_refresh_all_providers`. This serializes concurrent refreshes. Alternatively, use a flag + debounce pattern (discard redundant refreshes within a short window).

**Severity:** CRITICAL -- state corruption under normal operating conditions (multiple providers updating concurrently is the expected case, not an edge case).

## Finding B3 -- CRITICAL: `SIGNAL_WEATHER_DIVERGENCE_DETECTED` Fires on Every Refresh While Divergent -- Unbounded Signal Spam

**File:** `domain_coordinators/weather_manager.py:440-457`
**Bug class:** Novel (propose: "unconditional signal re-fire on every refresh cycle")

The divergence signal dispatch at line 440 fires every time `is_divergent` is True:
```python
if is_divergent:
    ...
    async_dispatcher_send(self.hass, SIGNAL_WEATHER_DIVERGENCE_DETECTED, ...)
```

Unlike `SIGNAL_WEATHER_PROVIDER_CHANGED` (which is correctly guarded by `if new_active != previous_active`), the divergence signal has no "was already divergent" guard. Since `_refresh_all_providers` runs on every state-change event from every provider, and providers update frequently, this signal will fire continuously whenever divergence is active. Each fire generates a WARNING log line AND a dispatcher broadcast.

**Impact:**
- Log flooding: WARNING-level log on every weather state change for the entire duration of a divergence event (could be hours during a real provider disagreement).
- Any future subscriber to `SIGNAL_WEATHER_DIVERGENCE_DETECTED` will be hammered with redundant dispatches. If a subscriber does work (e.g., writes to DB, sends notification), the work multiplies.

**Fix:** Track `self._was_divergent: bool = False` and only fire the signal on the transition `not was_divergent -> is_divergent`. Reset on the reverse transition. Same pattern as the provider-changed signal.

**Severity:** CRITICAL -- unbounded log spam under normal divergence conditions; sets a trap for any future subscriber.

## Finding B4 -- HIGH: `get_today_forecast` Forces a Full Refresh on Every Call -- Excessive Service Call Load

**File:** `domain_coordinators/weather_manager.py:175-177`
**Bug class:** #17 (Unbounded Retry Loops) -- variant: unbounded refresh

```python
async def get_today_forecast(self) -> WeatherForecast | None:
    await self._refresh_all_providers()
    return self._cached_forecast
```

Every call to `get_today_forecast()` triggers a full refresh of ALL providers (health check + `weather.get_forecasts` service call per usable provider). `_update_forecast_temps` in energy.py calls this every 5-minute decision cycle. Combined with the state-change-driven refreshes, the WPM is making `N_providers * (state_changes_per_5min + 1)` service calls per decision cycle.

The comment says "Probe freshly on each call so callers always get current state" but this is unnecessary because state-change listeners already trigger `_refresh_all_providers` whenever any provider entity updates. The cached forecast is already current by the time a caller asks for it.

**Impact:** Excessive HA service call load. Weather integrations may rate-limit or throttle. On a 3-provider setup with providers updating every 10 min, this adds 3-6 redundant service calls per 5-minute decision cycle.

**Fix:** `get_today_forecast` should return `self._cached_forecast` directly (the state-change listeners keep it current). If the caller needs guaranteed freshness, expose a separate `async_force_refresh()` method.

**Severity:** HIGH -- excessive service call load under normal operations; may degrade weather integration responsiveness.

## Finding B5 -- HIGH: `_handle_provider_state_change` Creates Untracked Tasks

**File:** `domain_coordinators/weather_manager.py:529-532`
**Bug class:** #19 (Untracked Background Tasks)

```python
self.hass.async_create_task(
    self._refresh_all_providers(),
    name="ura_weather_manager_refresh",
)
```

The task created here is not tracked in any collection. The plan (line 8-9 of weather_manager.py) claims "Bug #19: all service calls awaited inline in event handlers; no fire-and-forget" -- but this IS fire-and-forget. The return value of `async_create_task` is discarded, and the task is not added to any `_pending_tasks` set.

If `async_teardown` is called while one of these tasks is mid-flight (awaiting a `weather.get_forecasts` service call), the task will continue running against torn-down state. The unsub handles are cleared, but the running task still holds a reference to `self` and will write to `self._cached_forecast`, `self._active_provider`, etc. after teardown.

**Impact:** On entry reload, a stale `_refresh_all_providers` task can write to the old WPM instance's fields after teardown. The new WPM instance starts clean, so the practical impact is limited to wasted work + potential log noise. However, the task may also fire dispatcher signals (`SIGNAL_WEATHER_PROVIDER_CHANGED`) after the entry has unloaded, which could confuse listeners that haven't yet re-subscribed.

**Fix:** Track created tasks in `self._pending_tasks: set[asyncio.Task]`, cancel them in `async_teardown`, and add `task.add_done_callback(self._pending_tasks.discard)` pattern per the existing URA convention (see `hvac.py:922-924`).

**Severity:** HIGH -- task leak on reload; potential stale signal dispatch after teardown.

## Finding B6 -- HIGH: Divergence Median Overwrites Apparent Temperature with Raw Temperature

**File:** `domain_coordinators/weather_manager.py:388-392`
**Bug class:** #37 (API Contract Change) -- semantic contract violation

```python
if is_divergent and len(provider_highs) >= 2:
    vals = sorted(provider_highs.values())
    mid = len(vals) // 2
    apparent_high = vals[mid] if len(vals) % 2 else (vals[mid - 1] + vals[mid]) / 2
    confidence = "low_divergent"
```

`provider_highs` is populated from `raw_high` (line 350-351: `provider_highs[eid] = raw_high`), NOT from `apparent_high`. But the median result is assigned to `apparent_high` in the `WeatherForecast`. This means when divergence is detected, the forecast's `apparent_high` is silently replaced with a median of RAW temperatures, not apparent temperatures.

The `provider_apparent_highs` dict (line 326) IS populated with apparent values (line 352-353), but the divergence median computation at line 388 uses `provider_highs` (raw), not `provider_apparent_highs` (apparent).

**Impact:** When providers diverge, `WeatherForecast.apparent_high` becomes a median of raw temps, NOT apparent temps. Downstream consumers (Cycle B's `baseline_delta_for_zone`, future EC pre-cool logic) get a raw-temp-based value labeled as "apparent." The delta calculation in Cycle B would be off by the humidity adjustment factor (typically 3-8 degrees F in Texas summer).

**Fix:** The median computation should use `provider_apparent_highs` when available, falling back to `provider_highs` only when apparent values are not available for enough providers.

**Severity:** HIGH -- silent semantic corruption of the apparent temperature primitive under divergence conditions, which is precisely when accuracy matters most.

## Finding B7 -- MEDIUM: Sensors Lack Signal-Driven Refresh -- Stale Until Next HA Poll

**File:** `sensor.py:WeatherActiveProviderSensor`, `sensor.py:WeatherApparentForecastHighSensor`, `binary_sensor.py:WeatherDivergenceBinarySensor`
**Bug class:** Observability gap (related to the existing SIGNAL_*_ENTITIES_UPDATE pattern)

All three new sensor/binary_sensor entities read from `hass.data[DOMAIN]["weather_manager"]` properties on each HA state refresh, but none of them subscribe to `SIGNAL_WEATHER_PROVIDER_CHANGED` or `SIGNAL_WEATHER_DIVERGENCE_DETECTED` to trigger `async_schedule_update_ha_state()`.

Every other URA aggregation sensor follows the pattern of subscribing to its domain's update signal in `async_added_to_hass` and calling `self.async_schedule_update_ha_state()` on signal receipt. The weather sensors skip this.

**Impact:** After a provider failover or divergence event, the sensor entities will not update until HA's next natural polling cycle (which for `SensorEntity` without `should_poll = True` is never -- HA only updates entities that explicitly trigger updates). The plan's acceptance criterion "sensor flips within 5s" cannot be met.

The two new dispatcher signals (`SIGNAL_WEATHER_PROVIDER_CHANGED`, `SIGNAL_WEATHER_DIVERGENCE_DETECTED`) currently have ZERO subscribers. They are defined, they are emitted, but nothing listens to them. This makes the signals dead code at present.

**Fix:** Add `async_added_to_hass` to all three entities, subscribing to the appropriate signal(s) with `async_on_remove(async_dispatcher_connect(...))` per Bug #38 pattern. `WeatherActiveProviderSensor` and `WeatherApparentForecastHighSensor` should subscribe to `SIGNAL_WEATHER_PROVIDER_CHANGED`. `WeatherDivergenceBinarySensor` should subscribe to `SIGNAL_WEATHER_DIVERGENCE_DETECTED`.

**Severity:** MEDIUM -- sensors will display stale data after failover/divergence events; acceptance criteria unmet.

## Reload Resilience Audit

### Setup path (`__init__.py:1488-1498`)

- WPM constructed with current `cm_config`
- `async_setup()` registers state-change listeners, stores unsub handles
- Stored at `hass.data[DOMAIN]["weather_manager"]`
- Wrapped in `try/except` -- WPM failure does not crash entry setup (degraded mode)

### Teardown path (`__init__.py:2642-2649`)

- `hass.data[DOMAIN].pop("weather_manager", None)` -- removes from hass.data
- `await weather_manager.async_teardown()` -- calls all unsub handles
- Wrapped in `try/except`
- **Ordering:** Teardown happens AFTER `coordinator_manager.async_stop()` (line 2638), which is correct -- consumers tear down before the provider

### Unsub completeness (`weather_manager.py:async_teardown`)

- Iterates `self._unsub_handles` and calls each
- Clears the list
- **Gap:** Tasks created by `_handle_provider_state_change` (Finding B5) are NOT cancelled. A mid-flight refresh task could write to the old instance after teardown.

### Entry reload cycle

On options change, HA reloads the entry: `async_unload_entry` (tears down old WPM) then `async_setup_entry` (creates new WPM). The new WPM gets fresh options and fresh listeners. The old WPM's listeners are removed. **This path is correct** modulo Finding B5 (untracked tasks).

## Divergence Median Stability

`vals = sorted([90.0, 95.0, 98.0])` -> `mid = 1` -> `len(vals) % 2 == 1` -> `vals[1] = 95.0`

## Recommendations for QUALITY_CONTEXT.md

1. **New Bug Class candidate: "Unconditional Signal Re-Fire on Persistent State"** -- when a dispatcher signal fires on every evaluation cycle while a condition is true, rather than only on the transition into the condition. The SIGNAL_WEATHER_PROVIDER_CHANGED correctly fires only on change; SIGNAL_WEATHER_DIVERGENCE_DETECTED does not.

2. **New Bug Class candidate: "Double Fetch of Expensive Resource in Refresh Loop"** -- when an async method fetches a resource in a loop (for aggregation) and then fetches the same resource again outside the loop (for detailed extraction), creating inconsistency windows and doubled I/O.

3. **Bug Class #19 expansion:** The current description focuses on tasks with `asyncio.sleep`. The WPM case shows that even tasks WITHOUT sleep (just `await service_call`) should be tracked if the class has a teardown lifecycle.
