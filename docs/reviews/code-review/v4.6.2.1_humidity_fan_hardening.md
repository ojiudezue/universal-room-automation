## Summary

**Verdict: SHIP WITH FIXES.**

Plan is well-scoped. Hysteresis logic is correct in both paths. Max-runtime cap fires in
both Path A and Path B with proper suppression after cap-fire. Constant consolidation is
clean — no surviving literal `60`/`50`/`600` fallbacks near humidity logic. Imports are
all module-level inside the existing `from .const import (...)` blocks; no Bug Class #34
shadowing risk.

However: **two MEDIUM-severity reload/restart resilience holes** exist that silently
disable the new max-runtime safety feature in a real-world scenario the user will hit
(changing humidity threshold via options flow while a fan is mid-cycle). These are not
crash bugs but they defeat the entire point of the cycle (the user's actual ask was the
stuck-sensor cap, and the cap fails to fire for an in-flight fan after a reload). They
should be fixed before deploy or explicitly accepted with a documented limitation.

There are also several LOWs worth listing.

## Recommendations for QUALITY_CONTEXT.md

**Candidate new bug class** — worth adding once a second instance appears:

> **Bug Class #N: Reload-Mid-Cycle State-Anchor Loss**
>
> When in-memory state is the anchor for a time-based safety cap (max-runtime, watchdog,
> grace period), reloading the config entry while the gated entity is mid-cycle resets
> the anchor to None. The next evaluation cycle observes `entity_is_on=True` and
> `anchor=None` — and any "if anchor is not None and elapsed > cap" gate falls through
> silently. The safety feature is silently disabled for the duration of the current
> cycle. Worst case: the failure mode the cap exists to prevent (stuck-sensor runaway)
> survives the reload.
>
> **Symptoms:** A safety/watchdog cap fails to fire after a reload but works on a clean
> start. Indistinguishable from "cap is broken" without tracing through the state
> initialization path.
>
> **Fix pattern:** On entity-state sync, if the entity is observed on with anchor=None,
> seed the anchor to `now` ("assume just started"). This caps the post-reload runaway
> at one cap-window rather than indefinite.
>
> **Discovered:** v4.6.2.1 review (humidity-fan max-runtime cap, both Path A and Path B).
>
> **Relationship to #10:** This is #10 (cross-restart state loss) reframed for the
> *reload* path, which is more common than crash-restart and easier to overlook because
> the rest of HA state remains live.

This shape is not currently in the 38-class catalogue under its own number. #10 is
worded in terms of HA restart and accumulators (billing, load shedding); #14 is about
config snapshots that are read-once-at-init. Neither directly names the "in-flight
safety-cap anchor lost on reload" shape — but the new bug class above is close enough
to #10 that it could be added as a subsection of #10 rather than its own number. Either
is fine. The point is to make the failure mode visible to the next reviewer who
writes a runtime cap.

**Strengthening existing #10:** Add to #10's Prevention checklist:

```
- [ ] If state anchors a safety cap, ensure the post-reload entity-state-sync seeds
      the anchor when the entity is observed in the gated state.
```

## Mental execution trace (kept for audit)

**Scenario (a) — Sensor stuck high (Path A):**
- T0: humidity=75. Fan off, all state None. → activate, on_since=triggered_time=now.
- T+3600s: cap fires. Force off; on_since=None, triggered_time=None, suppressed=True.
- T+3600s+1: humidity=75. on_since=None → cap skipped. Suppressed=True, humidity>off_threshold → return early. Fan stays off. ✓
- Eventually humidity=49: suppression clears (49≤50). fan_is_on=False (triggered_time=None). humidity<threshold. Fan stays off. ✓
- Later humidity=75: suppression already False. Activate. ✓

**Scenario (b) — Shower cycle (Path A):**
- Pre: all None. Humidity=75 → activate.
- Humidity=55: in hysteresis band. fan_is_on=True. `humidity <= off_threshold(50)` is False. Hold. ✓
- Humidity=45: fan_is_on=True AND humidity≤50. Check elapsed≥timeout. Likely yes. Turn off. ✓

**Scenario (c) — Coordinator restart with humidity already > threshold:**
- After restart: all in-memory state None. Humidity=75. fan_is_on=False (triggered_time=None). humidity≥threshold → activate, set both timestamps to now. Idempotent turn_on. Cap fires 60min from restart, not from original on time. **Acceptable** (one-window slip).

**Scenario (d) — Options-flow reload mid-fan-cycle:**
- See findings #1 and #2. Real bug in the hysteresis-band case.

**Scenario (e) — HVAC coordination toggle while fan is running:**
- HVAC ON→OFF: Path A re-engages with all state None and entity on. Same as (d). Findings #1/#2 apply.
- HVAC OFF→ON: Path A returns early (`_is_hvac_managing_fans`). Path A's stale state persists (finding #4). Path B's `RoomFanState` was built at HVAC setup; `humidity_on_since` was set by Path B itself only if a transition happened during a Path B `update()`. If the fan was turned on by Path A and Path B inherits it on toggle: Path B sees `h_currently_on=True`, `humidity_on_since=None` — cap can't fire. Same bug class as #1.

## Recommendation

**Fix findings #1 and #2 before deploy.** Both are 5-line patches:

```python
# hvac_fans.py update() — early in the humidity block, after h_currently_on is computed:
if h_currently_on and room_fan.humidity_on_since is None:
    room_fan.humidity_on_since = now  # Seed anchor on post-reload sync

# automation.py handle_humidity_based_fan_control — after threshold computation:
if self._humidity_on_since is None and self._fan_is_actually_on(humidity_fans):
    self._humidity_on_since = now
    self._humidity_fan_triggered_time = now  # Also seed min-runtime gate
```

(`_fan_is_actually_on` would need a small helper that checks `self.hass.states.get(eid).state == "on"` for any entity in `humidity_fans`. Path A doesn't currently sync from entity state for humidity fans — this would be a small new addition.)

If the orchestrator chooses to defer, the deferred items must be tracked per CLAUDE.md "Plan Completion Tracking" section, and the planning doc's Risks section should add a 6th bullet documenting the reload-mid-cycle limitation.

LOW findings #3-#11 may be deferred to a future cleanup cycle, but #5 (one-line comment) and #6 (one-line comment) and #11 (planning doc nomenclature note) cost nothing.

Findings #8/#9 (test honesty) are worth fixing before deploy — replacing two source-grep
tests with one real behavioral test would tighten the soak-validation signal materially.
