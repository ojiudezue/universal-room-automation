### Cross-coordinator interaction analysis (Review 2)

When EC is skipped due to validation failure:
- **HVAC**: registers normally with `net_power_entity=None`. `_get_net_power()` returns 0.0; `_should_solar_bank()` evaluates False. Solar banking pre-cool decisions skip. Otherwise functional.
- **Notification Manager**: no dependency on EC.
- **Aggregation sensors** (`PredictedCostTodaySensor`, `PredictedBillSensor`, `EnergyCoverageDeltaSensor`, `EnergyCostPerOccupiedHourSensor`): all query `_get_energy_coordinator()` which returns None when EC isn't registered; sensors set `available=False` and `native_value=None`. No crashes.
- **Dispatcher signals**: `SIGNAL_ENERGY_CONSTRAINT` would normally be published by EC. With EC missing, HVAC's listener never fires; energy-constrained setpoint adjustments don't apply. Acceptable graceful degrade.

### Edge case verification

| Scenario | Result |
|---|---|
| First boot after upgrade, Enphase still loading | After-dependencies forces correct order → V2/V4 see entities → validation passes |
| EC disabled, envoy_eid invalid | Validation runs, logs warning, NO repair issue raised (gated `if _energy_enabled`) |
| User fixes config, entry reloads | Validation passes → prior repair issue deleted → EC starts |
| Multiple reloads with same bad config | Stable issue id → same issue updated, no stack |
| HVAC enabled, EC validation failed | HVAC starts with `net_power_entity=None`, log WARNING surfaces, solar banking inert |
| Envoy goes unavailable mid-run | EC unaffected (validation only at startup); existing None-handling in `CostTracker._get_net_power` etc. degrades gracefully |
| Integration removed | Unload path deletes the repair issue → no orphan in Settings → Repairs |
| Form submit with empty envoy_eid | Permitted (V0 only triggers when energy enabled at startup) |
| Form submit with malformed envoy entity ID | V1 fail → `envoy_invalid_format` form error → save rejected |
| Form submit with envoy entity that doesn't exist in HA | V2 fail → `envoy_entity_missing` form error → save rejected |

### Recommended new bug class for QUALITY_CONTEXT.md

**Bug Class candidate: "Orphaned Repair-Issue Lifecycle"**

Pattern: an integration creates a repair issue via `ir.async_create_issue` to surface a config error, but never clears it on `async_unload_entry`. Result: the issue lingers in Settings → Repairs even after the user removes the integration, leaving "phantom" red badges in the HA UI.

Detection rule: any module that calls `ir.async_create_issue` should also have a corresponding `ir.async_delete_issue` in the unload path (or in the success path of a re-validation, as we do here). Any new repair-issue raise site should be matched by at least two delete-site matches: success-path clear + unload-path cleanup.

Add to `docs/QUALITY_CONTEXT.md` after this cycle.
