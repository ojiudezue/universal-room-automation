## Findings

### CRITICAL

#### C1. `get_options` lambda captures stale snapshot on first instantiation (Bug Class #14)

**File:** `energy.py:2555-2558`
**Bug class:** #14 (Config Snapshot Staleness)

```python
if self._dynamic_preset_source is None:
    from .dynamic_preset import DynamicPresetOverrideSource
    self._dynamic_preset_source = DynamicPresetOverrideSource(
        hass=self.hass,
        get_options=lambda: cm_options,
    )
```

The `get_options` lambda captures the local variable `cm_options` as a **closure over the local binding at first-instantiation time**. On subsequent calls to `_async_evaluate_dynamic_presets()`, a fresh `cm_options` dict is computed at line 2533-2537, but the `DynamicPresetOverrideSource` instance was created on the first call with a lambda that permanently closes over the `cm_options` binding from that first invocation.

**Impact:** After the first EC tick where the source is created, every subsequent `evaluate_and_emit()` call reads stale config. If the user changes dwell_minutes, hysteresis, or bucket boundaries via the config flow, the change is silently ignored until HA restart.

**Why this is CRITICAL, not MEDIUM:** The plan's Bug #14 compliance claims "_refresh_config() at top of evaluate_and_emit reads fresh CONF values; tunable knobs live-tunable." This is the central config-staleness prevention and it is broken.

**Fix:** Change the lambda to a method reference that re-reads CM options each call:

```python
# Option A: pass self._read_cm_options as the callable
get_options=self._read_cm_options,

# Then add a method:
def _read_cm_options(self) -> dict:
    from ..const import DOMAIN as _DOMAIN_KEY, CONF_ENTRY_TYPE, ENTRY_TYPE_COORDINATOR_MANAGER
    for entry in self.hass.config_entries.async_entries(_DOMAIN_KEY):
        if {**entry.data, **entry.options}.get(CONF_ENTRY_TYPE) == ENTRY_TYPE_COORDINATOR_MANAGER:
            return {**entry.data, **entry.options}
    return {}
```

Or simpler: create the source once with a stable callable, not a closure over a local.

#### C2. Number entity dwell/hysteresis values are DEAD at runtime (Bug Class #32 variant)

**Files:** `number.py:1594-1600`, `number.py:1668-1673`, `dynamic_preset.py:348-354`
**Bug class:** #32 (Form Field With No Runtime Reader)

The two Number entities (`DynamicPresetDwellMinutesNumber`, `DynamicPresetHysteresisFNumber`) implement `async_set_native_value` by:
1. Setting `self._value = float(value)`
2. Calling `self.async_write_ha_state()`

They do NOT write the new value back to either:
- The EC's `DynamicPresetOverrideSource` directly, or
- The CM `entry.options` dict that `get_options()` reads from.

Meanwhile, `DynamicPresetOverrideSource.evaluate_and_emit()` reads dwell and hysteresis from `self._get_options()` (line 353-354), which returns CM `entry.options`. The Number entities are RestoreEntity -- they persist their state across restarts, but there is no runtime path from the Number entity slider to the Source's config reader.

**Impact:** User adjusts dwell from 60 to 30 minutes via the slider. The source continues using 60 minutes. The builder flagged this as a known gap and the user manual section 10 documents a "reload workaround." However, the plan spec (section B.B.2) says: "CONF_DYNAMIC_PRESET_DWELL_MINUTES (default 60 = 1 hour per user spec). Range 15-240" and "tunable knobs (dwell, hysteresis) live-tunable." This is a spec violation.

**Why this is CRITICAL:** The feature's runtime tunability is a core user-facing promise. Two Number entities exist specifically for live adjustment, but they have no effect. This is indistinguishable from a #32 violation: a form field with no runtime reader.

**Fix path:** In `_async_evaluate_dynamic_presets()`, before passing options to the source, overlay the live Number entity values:

```python
# Read live number entity values (they take precedence over entry.options)
dwell_entity = self.hass.states.get("number.ura_energy_coordinator_dynamic_preset_dwell_minutes")
if dwell_entity and dwell_entity.state not in ("unknown", "unavailable"):
    cm_options[CONF_DYNAMIC_PRESET_DWELL_MINUTES] = float(dwell_entity.state)
# ...similar for hysteresis
```

Or better: have the Number entity setter directly call `ec._dynamic_preset_source.update_config(key, value)`.

Note: This finding and C1 compound -- even if you fix C1 so `get_options()` re-reads CM options each tick, the Number entity values still won't be read because they're stored in RestoreEntity, not in CM options. Both fixes are needed.

**Impact:** User follows the manual, searches for the referenced entity IDs, and finds nothing.

#### H2. Config flow zone_dynamic_preset lists ALL Zone Manager zones, not canonical HVAC zones

**File:** `config_flow.py:4400-4454`

The `async_step_manage_zones()` method (which routes to `async_step_zone_config_menu()` which offers `zone_dynamic_preset`) enumerates zones from the Zone Manager entry's `zones` dict:

```python
for zone_name in zones_data:
    zone_options.append({...})
```

This lists ALL house zones, not just canonical HVAC zones. Per plan section B.B.3.5: "Cycle B's configuration UI + override emission both operate at the canonical HVAC zone level. House zones are never surfaced to the user in this feature."

If Master Suite + Entertainment share a thermostat, the user sees TWO rows (Master Suite AND Entertainment), not one merged row ("Entertainment + Master Suite"). The form then stores dynamic preset config on a per-house-zone basis, but the EC evaluation (energy.py:2563) iterates `iter_canonical_hvac_zones()`. If the user configures "Master Suite" but the canonical zone is "Entertainment + Master Suite", the lookup at energy.py:2577 (`zm_zones.get(zone_name, zm_zones.get(zone_id, {})`) may fail to find the config because `zone_name` from canonical zones is the merged name, not the individual house zone name.

**Impact:** Config entered in the form is silently ignored when canonical zone names don't match house zone names. This directly violates the plan's "Canonical HVAC zones ONLY" specification.

**Fix:** `async_step_manage_zones` (or a new caller for the dynamic_preset path) must enumerate zones from `iter_canonical_hvac_zones()` instead of from the Zone Manager zones dict when routing to `zone_dynamic_preset`. Or, add a separate zone selection step for `zone_dynamic_preset` that explicitly calls `iter_canonical_hvac_zones()`.

#### M3. Sleep floor validation in config_flow adds offset INCORRECTLY

**File:** `config_flow.py:5086-5092`

```python
offset = float(user_input.get(CONF_ZONE_DYNAMIC_PRESET_OFFSET, 0.0))
for _, high_key, _ in bucket_keys:
    sleep_high_key = high_key.replace("home_high", "sleep_high")
    sleep_high = user_input.get(sleep_high_key)
    if sleep_high is not None and float(sleep_high) + offset < SLEEP_FLOOR:
        errors["base"] = "dynamic_preset_sleep_below_floor"
        break
```

The validation checks `sleep_high + offset < 74`. But per plan section B.B.5, the offset is applied AFTER the floor: `sleep_effective = max(74, home_high - 1) + offset`. The auto-derive path in `dynamic_preset.py:compute_sleep_high()` applies offset after the floor correctly. But the form validation is checking `raw_sleep_high + offset < floor`, which is a different check. If a user enters sleep_high=73 with offset=1, the form checks 73+1=74 which passes, but the actual effective value is 73+1=74 which would be correct. If sleep_high=72 and offset=1, check is 72+1=73 < 74 which correctly rejects.

Actually, re-reading: the form stores the user-entered `sleep_high` value directly (not auto-derived). The `_build_overrides` method reads that stored value and adds `zone_offset` to it at runtime (line 483-484 of dynamic_preset.py). So the form validation is checking the RIGHT thing: `stored_sleep_high + offset >= SLEEP_FLOOR`. This is correct.

RETRACTED -- this is not actually a bug. The form validation correctly checks `stored_value + offset >= floor` because at runtime the stored value gets offset added.

#### M4. `DynamicPresetActiveBucketSensor` `_try_restore_to_source` swallows all exceptions silently

**File:** `sensor.py:6589-6610`

```python
def _try_restore_to_source(self, last_state) -> None:
    ...
    try:
        source = _get_dynamic_preset_source(self.hass)
        ...
        source.restore_zone_state(self._zone_id, bucket, last_tx)
    except Exception:
        pass
```

If `_get_dynamic_preset_source` returns None (EC not yet registered at sensor restore time), the restoration silently fails and is never retried. The sensor falls back to `self._restored_bucket` for the display value, which is correct, but the `DynamicPresetOverrideSource` never learns about the persisted state. The dwell timer restarts from zero instead of resuming from the restored timestamp.

**Impact:** After restart, dwell timers for all zones reset to zero. The first EC tick after restart can trigger an unwanted bucket transition that would have been blocked by the remaining dwell.

**Fix:** Subscribe to `SIGNAL_ENERGY_COORDINATOR_READY` and retry `_try_restore_to_source` when EC becomes available (same pattern as EC sub-switch deferred restore).

### 1. OverrideEngine as a new shipped primitive

The OverrideEngine API surface (`get_active_overrides`, `resolve_range`, `describe_active`, `build_guest_mode_overrides`) is well-documented in docstrings. The `PresetOverride` dataclass has typed fields matching the plan spec. The `_eval_predicate` method has a safe default (unknown predicates return False = inactive). - Hysteresis: 2.0 default, range 0.5-5.0. Sane.

### 3. UX concern: 60+ knobs per 3 zones

The form shows all 20 fields for every zone regardless. This is the expected Cycle B scope (plan says "no per-zone-enable switch -- reuse the per-zone opt-in checkbox"). For the single-user single-install context, this is acceptable. A simplification should be a future polish item.
