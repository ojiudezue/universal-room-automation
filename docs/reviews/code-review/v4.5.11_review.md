## Review 1 (Core A) — domain logic against bug classes

### HIGH-1: Timezone mismatch in retention prune (FIXED)

**Bug class:** #11 UTC vs Local Timezone Date Comparison

**File:** `custom_components/universal_room_automation/database.py:cleanup_ac_ramp_events`

**Finding:** Row timestamps written by `log_ac_ramp_event` used `dt_util.now()` (local-with-offset ISO), but the prune cutoff used `dt_util.utcnow()`. SQLite text-MIN/MAX is lexical, not date-aware. ISO strings with different offsets compare incorrectly at edges, causing edge-of-retention rows to be wrongly classified.

**Reproducer:**
- Row written at 2026-04-10T22:00:00-05:00 (local Texas, exactly 30 days ago at 22:00)
- Cutoff computed at 03:00 UTC on day 30: `2026-05-10T03:00:00+00:00`
- Lexical compare: row prefix `2026-04-10` < cutoff prefix `2026-05-10` → row pruned
- But row is only 29h shy of the 30-day window — incorrectly pruned 24h early

**Fix:** Changed cutoff to `dt_util.now() - timedelta(days=retention_days)` so writer/cleaner share the timezone basis. Added inline comment referencing Bug Class #11.

```python
# Before (broken)
cutoff = (dt_util.utcnow() - timedelta(days=retention_days)).isoformat()

# After (fixed)
cutoff = (dt_util.now() - timedelta(days=retention_days)).isoformat()
```

### LOW-1: Cleanup task is fire-and-forget without tracking (DEFERRED — accepted)

**Bug class:** #19 Untracked Background Tasks

**Where:** `OverrideArrester.check_ac_reset` day-rollover hook calls `self.hass.async_create_task(self._db.cleanup_ac_ramp_events())`.

**Why deferred:**
- Cleanup is self-bounded: batched `LIMIT 1000` with internal max-batch counter (500). Self-terminates within seconds.
- Fires once per day, not per cycle. Negligible task pressure.
- Matches existing pattern in `database.py` (cleanup_external_conditions, cleanup_energy_history, etc.) — all fire-and-forget.
- Tracking adds complexity without measurable benefit for a daily, bounded task.

**If we ever care:** wrap in `self.hass.async_create_background_task(coro, "ura_ac_ramp_cleanup")` and let HA's lifecycle manage it.

### LOW-2: `_suppressed_entities` set is consumed lazily (DEFERRED — accepted)

**Where:** OverrideArrester suppresses an entity_id before issuing its own setpoint change. The entry is `.discard()`-ed on the next state-change event for that entity.

**Risk:** If a service call succeeds but no state event ever fires (entity disappears, integration crashes), the entity stays in `_suppressed_entities` until next teardown. Minor memory leak.

**Why deferred:** Existing v3.8.3 OverrideArrester has the same property. URA hasn't seen this leak in 18+ months of production. Fix would require an expiry timer per suppression, which complicates a working pattern. Accept design trade-off.

### LOW-3: Bryant doesn't always honor a 1.5°F nudge (DEFERRED — known limitation)

**Where:** Conceptual. Field-data hypothesis only.

**Risk:** Variable-speed Bryant's internal deadband may treat 1.5°F as no-op → nudge ineffective → escalation to hard reset on every detection → 2-resets/day cap reached → lockout fires daily.

**Mitigation in place:**
- Nudge size is a runtime slider (post-deploy can raise to 2.5–3.0°F without redeploy).
- Hard reset cap (2/day) protects compressor regardless.
- Lockout notification surfaces the pattern for user inspection.
- 1-week observation period planned before tuning defaults (in plan + README).

**Tech debt note:** added to `docs/TECH_DEBT.md` (planned in slice 1 deploy).

## Review 2 (Core B) — race conditions, lifecycle, cross-coord

Independent pass focused on async lifecycle, restart resilience, DB transaction safety, timer cleanup.

### R2.1 — Restart-during-nudge handling (VERIFIED)

**Risk R1 mitigation:** DB write happens BEFORE the `climate.set_temperature` service call in `_perform_soft_nudge`. Verified by `test_db_write_BEFORE_setpoint_change`. If a crash occurs between the DB write and the service call, the next startup audit restores to the original target — which equals the current target — i.e., a benign no-op. The alternative ordering (setpoint first, DB second) would leave Bryant at +1.5°F with no DB record on a crash — orphan drift.

### R2.2 — Day-rollover compressor protection (VERIFIED)

**Risk R2 mitigation:** `get_global_last_hard_reset_ts` does `SELECT MAX(last_hard_reset_ts) WHERE zone_id = ?` — explicitly NO date filter. Verified by `test_global_last_hard_reset_ts_query_is_NOT_date_filtered`. A hard reset at 23:55 followed by midnight rollover correctly blocks a second reset at 00:02 even though the new-date row has count=0.

### R2.3 — Concurrent reload mid-nudge (LOW — accepted)

**Risk:** If config entry is reloaded (NOT full HA restart) while a nudge is in-flight, `teardown()` cancels the restore timer (sync context, can't await service call). The DB row still says in-flight; thermostat sits at +1.5°F until the post-reload first-decision-cycle audit fires (up to 5 min later).

**Accepted because:**
- Reload-without-restart is an unusual operation. URA isn't typically reloaded by users.
- Worst case: 5 minutes at +1.5°F. That's the OPPOSITE direction of the failure mode we're solving (overcooling). For 5 min on the warm side, comfort impact is near-zero in real-world conditions.
- Full HA restart correctly resumes via audit (verified by test).

**Mitigation if ever needed:** Convert teardown to async and fire restore service calls synchronously on shutdown. Out of scope for slice 1.

### R2.4 — Nudge vs user override race (VERIFIED)

**Risk R11 mitigation:** `_suppressed_entities.add(zone.climate_entity)` is called BEFORE the `climate.set_temperature` service call. The suppression is consumed by the very next state-change event for that entity — so URA's own setpoint write is suppressed, while a subsequent genuine user override (minutes later) is correctly classified.

### R2.5 — Timer cleanup in teardown (VERIFIED)

`teardown()` cancels `_nudge_restore_timers` and `_nudge_eval_timers` dicts and clears `_nudge_in_flight` set. Verified by `test_teardown_cancels_nudge_timers`. No leaked callbacks. The DB in-flight rows remain, which is the designed behavior (startup audit handles them).

### R2.6 — DB write-queue back-pressure (VERIFIED)

v4.5.11 writes max ~3 events per zone per detection cycle (detection_fired, nudge_started, nudge_restored). For 3 AC zones × 1 cycle every 5 min = ~9 writes per cycle peak. URA's serialized write worker handles thousands of writes per cycle in normal operation. No back-pressure risk.

### R2.7 — Lockout notification spam (VERIFIED)

`notification_id = f"ura_ac_ramp_lockout_{zone_id}"` per zone. HA dedupes by id, so multiple lockout-engagement attempts on the same day produce one notification. The `lockout_flag` gate (gate 4 of detection) short-circuits further `_engage_lockout` calls within the same day. Test: `test_lockout_uses_unique_notification_id`.

### R2.8 — set_database race (VERIFIED)

`OverrideArrester._db` initialized to `None`. `set_database` is called from HVAC coord setup (after database is in `hass.data`). All v4.5.11 actions check `if self._db is None` and graceful-degrade. Tests: `test_hvac_wires_database_to_arrester`, `test_arrester_has_set_database_method`.

### R2.9 — Daily counter atomicity (VERIFIED)

`_perform_hard_reset_escalation` does read-modify-write on `ac_reset_state` row:
1. Read state via `get_ac_reset_state`
2. Check cap + min-interval gates
3. If both pass, increment counter and write back

The serialized SQLite write queue + single-async-thread decision cycle eliminates concurrent-modify races. The `_nudge_in_flight` set additionally prevents the same zone from entering the action path twice in parallel.

### R2.10 — Lambda/closure scope (VERIFIED)

**Bug class:** #24 Lambda/Closure Scope Escape

- `_perform_soft_nudge` callback captures `zone` and `original_target` from outer scope. Neither rebound after closure definition. Safe (single-fire callback).
- `async_startup_ramp_audit` uses default-arg trick (`z=zone, t=target`) to capture per-iteration values from the for-loop. Critical because the loop reassigns `zone` and `target` each iteration. Verified by inspecting the for-loop body.

### R2.11 — Enum string consistency (VERIFIED)

**Bug class:** #22 Enum Value Mismatch

All `zone.ramp_state` assignments use the `AC_RAMP_STATE_*` constants. None use raw strings. Verified by source-grep + the `AC_RAMP_STATES` tuple defined in `hvac_const.py` (testable surface for slice-2 D7 sensor work).

### R2.12 — Form-field round-trip (VERIFIED)

**Bug class:** #32 Form Field With No Runtime Reader

Every v4.5.11 CONF has a runtime reader:
- Master switch + 6 house-wide CONFs → factory pushes via `setattr(arrester, runtime_field, value)`
- Per-zone kWh threshold → factory pushes via `zone.kwh_rate_threshold = value`
- ac_load_sensor + ramp_zone_enabled → `discover_zones` reads from zone_cfg and applies to ZoneState

Test coverage: `test_v4511_conf_key_defined` (parametrized × 10 CONFs), `test_per_zone_factory_pushes_to_zone_state`, `test_discover_zones_reads_ac_load_sensor`, `test_discover_zones_reads_ramp_zone_enabled`.

### R2.13 — AST import resolution regression guard (NEW LESSON)

The v4.5.10.1 regression test (`test_factory_signal_import_resolves`) inspired a generalized AST-walk in v4.5.11 tests: every `from .` import in number.py, switch.py, button.py, and hvac_override.py is walked, and the target module is text-searched for the imported symbol.

**This test caught a real bug during the v4.5.11 build:** I imported `CONF_ZONE_THERMOSTAT` from `domain_coordinators.hvac_const` in both `_discover_ac_zones` helpers (number.py + button.py), but the constant actually lives in `const.py`. The test failed; I fixed the imports; the test passed. Without it, the bug would have shipped silently because the import path looked plausible.

**Recommendation for QUALITY_CONTEXT.md:** Bug Class #32 (Form Field With No Runtime Reader) and the v4.5.0.1 import-resolution failure already share a theme — symbol present at one end, missing at the other. Consider promoting the AST-walk pattern to a project-wide regression hook (run on every PR).

## Architecture findings

### A1 — Master switch state authority

The master switch's source of truth is `OverrideArrester._ramp_master_enabled` (in-memory). The `HVACACRampMasterSwitch` Switch entity is RestoreEntity-backed, so the last user-set value is restored on startup. URA mirror pattern is consistent with v4.5.10's Solar Cover Management switch.

### A2 — Per-zone tuning surface

User's install: 2 × 3-ton + 1 × 4-ton ACs. Threshold defaults to 0.8 kW per zone; user manually tunes the 4-ton's slider to 1.0 kW post-deploy. No reload required. Documented in the README's live validation plan.

### A3 — Three-layer gating model

Master → per-zone → per-decision gates, identical to v4.5.10's Solar Cover Management pattern. User can disable the entire feature, opt out a single zone, or rely on per-decision kWh/overshoot logic. Consistent UX.
