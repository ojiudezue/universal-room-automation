# Review D — Adversarial Completeness (Bug Class #53 leak hunt)

**Cycle:** v5.5.3 Arbitrage-WAIT inclement-floor fix
**Branch:** `feature/arbitrage-wait-floor` (tip `df57ab1e`)
**Framing:** ADVERSARIAL COMPLETENESS — find a reserve-floor LEAK the fix missed
(computed-but-not-consumed). Backstop pass behind A (clamp arithmetic), B
(state machine), C (tests).
**Claim under test:** *"Under an inclement `partial_hold`, the battery can never
drain/hold below the effective reserve floor in ANY off_peak or mid_peak path."*

---

## LEAD: LEAK FOUND — YES (1 HIGH)

**The claim is FALSE.** There is a reachable `partial_hold` path in **summer
mid_peak** that emits `reserve_level = int(soc)` with **no clamp to
`effective_reserve`**, so the commanded reserve ends up BELOW the inclement
floor.

### D-HIGH-1 — Summer mid_peak "holding charge for peak" emits unclamped `int(soc)`

**File:** `domain_coordinators/energy_battery.py:2914-2923`

```python
summer_peak_ahead = season == "summer" and (
    self._tou is None or self._tou.peak_ahead_before_offpeak(now)
)
if summer_peak_ahead:
    # Summer mid-peak, peak still ahead: hold charge for upcoming peak
    hold_reserve = int(soc) if soc is not None else 100      # <-- NOT clamped
    return self._result(
        BATTERY_MODE_SELF_CONSUMPTION,
        "Mid-peak (summer) — holding charge for peak",
        current_mode,
        reserve_level=hold_reserve,                           # <-- sub-floor possible
        season=season,
    )
```

`effective_reserve` IS computed for this tick at `energy_battery.py:2841`
(`effective_reserve = max(self.reserve_soc, decision.reserve_floor)`) and IS
consumed by both sibling mid_peak discharge branches:

- `energy_battery.py:2941` — `reserve_level=effective_reserve` (clamped)
- `energy_battery.py:2956` — `reserve_level=max(int(soc or 0) - 5, effective_reserve)` (clamped)

…but the **peak-ahead HOLD branch at 2921 reads neither `effective_reserve` nor
`hold_depth`.** This is the exact Bug Class #53 inversion: the floor is computed
and consumed by its siblings, and this one branch silently fails to consume it.
The v5.5.3 fix added clamps to the 6 arbitrage/attain emit sites and the
off_peak drain/hold fallback (2837/3057) but **did not touch this mid_peak
direct-emit branch** — it isn't one of the 6 `_floor_reserve` sites and isn't
the off_peak fallback.

#### Reachability — two independent repros

The branch at 2921 is reached in summer mid_peak (peak ahead) whenever the D1b
attain gate at `2876-2899` does **not** return a decision. Two ways that happens:

**Repro 1 — gate condition false (no attain involvement at all).**
Operator config is legal and unremarkable: `partial_hold_reserve_floor` slider
range is **0-100** (`config_flow.py:3557-3562`), default 50
(`energy_const.py:239`); `peak_buffer_target` Number range is **30-95**
(`number.py:67` → `PeakBufferTargetNumber(hass, entry, 80, 30, 95)`). The two
knobs are independent, so `floor > peak_buffer_target` is a normal config.

- Config: `peak_buffer_target = 30`, `partial_hold_reserve_floor = 60`,
  `reserve_soc = 20`.
- Active **partial_hold** (e.g. a condition-only / watch-uncorroborated overnight
  watch — the exact scenario A-CRIT-1 at 3029-3037 exists to protect).
  `effective_reserve = max(20, 60) = 60` (`energy_battery.py:2841`).
- `tou_period = "mid_peak"`, `season = "summer"`, peak ahead, `soc = 45`.
- D1b gate at 2876 requires `soc < self._peak_buffer_target` → `45 < 30` =
  **False** → attain branch is skipped entirely.
- `summer_peak_ahead = True` → line 2916: `hold_reserve = int(45) = 45` →
  `_result(reserve_level=45)`.
- **45 < floor 60 → reserve commanded 15 points BELOW the partial_hold floor.**

**Repro 2 — attain runs but returns None.**
Even with default `peak_buffer_target = 80 > floor`, the attain branch can return
`None` and fall through to 2914. With `partial_hold_reserve_floor = 70`,
`peak_buffer_target = 80`, `soc = 75`:
- D1b gate `75 < 80` True → attain runs.
- `_attain_state == "inactive"` and `_should_attain_peak_buffer(...)` returns
  `should_attain = False` (`energy_battery.py:2621-2622`) → returns `None`.
  (Also reachable via the holding/charging release returns at 2404/2410/2477/
  2485/2490.)
- Fall through to 2914, `summer_peak_ahead` True → `hold_reserve = int(75) = 75`.
- **75 < floor 70?** No — 75 ≥ 70 here, but set floor = 78 and SOC = 75:
  `hold_reserve = 75 < 78` → **sub-floor.** Reachable with stock 80 target.

Repro 1 is the cleaner demonstration (no attain dependency), but Repro 2 shows
the leak survives even with the default `peak_buffer_target`.

#### Why downstream does NOT save it

`energy.py:_apply_evse_battery_hold` (2453-2499) is `max()`-safe (2483-2491) but
only against the **EVSE-hold captured SOC** (`_evse_hold_soc`) — it has no
independent knowledge of the inclement floor. It can only raise the existing
reserve action toward an EV-charging hold value; it will not lift 45 → 60. And
when no EVSE is charging, it is not called at all (`energy.py:2576`/`2900`). The
leaked `reserve_level=45` is already baked into the action by `_result`
(`energy_battery.py:3098-3110`) and is clamped only to `[0,100]`, not to the
floor. **No downstream consumer recovers the floor.**

#### Severity: HIGH

Not CRITICAL only because it requires summer + mid_peak + peak-ahead + an active
partial_hold simultaneously, and the SOC must sit below the floor. But every one
of those is a normal operating state — summer afternoons are precisely when an
inclement partial_hold matters most (pre-storm), and mid_peak (14:00-16:00) is a
multi-hour daily window. During that window the battery would discharge toward
`int(soc)` instead of holding the storm reserve — defeating the partial_hold.
The fix's own headline guarantee is violated.

#### Suggested fix (for builder, not applied here)

Clamp the hold branch identically to its siblings:

```python
hold_reserve = int(soc) if soc is not None else 100
if decision.hold_depth == "partial_hold":
    hold_reserve = max(hold_reserve, effective_reserve)
```

(or route it through `_floor_reserve(hold_reserve, effective_reserve,
decision.hold_depth)`). Add a regression test mirroring
`test_arbitrage_hold_clamped_when_floor_above_target` but driving
`determine_mode("mid_peak", "summer", ...)` with `soc < floor` and the D1b gate
NOT firing.

**`_get_attainability_hold_current_decision` (2107-2156) cleared:** it returns
`"actions": []` — it commands nothing, deliberately preserving in-flight Enphase
state. It is only reachable while `_attain_state == "charging"` mid-reboot
(`energy_battery.py:2588-2598`), i.e. hardware is charging UP toward
`peak_buffer_target` with reserve already high. It cannot LOWER reserve below the
floor; it issues no reserve action at all. The "prior tick's low reserve
persists" concern raised in the hunt brief does not apply here: to be in
`charging` state the prior emit was a CHARGE toward target (high reserve), not a
sub-floor value. Not a leak. (State-machine continuity of this path is Reviewer
C's framing; from the completeness axis it emits no sub-floor reserve.)

**Default `_result(reserve_level=None)` (3074/3098):** when `reserve_level is
None`, NO reserve action is appended (`3098: if reserve_level is not None`). The
only None-reserve emit reachable under partial_hold is grid-disconnect backup
(2804-2809), which is the emergency-backup mode — it preserves whatever reserve
the hardware holds and is out of scope for a discharge-floor leak. No implicit
sub-floor reserve. CLEAR.

**Downstream of `determine_mode` (`energy.py`):** `_apply_evse_battery_hold`
(2453) is the only post-`determine_mode` reserve mutation. It is `max()`-safe
(2483-2491) and cannot lower a floor coming out of `determine_mode`. CLEAR — but
note it also cannot RAISE a *leaked* sub-floor value to the inclement floor
(only to the EVSE-hold SOC), so it does not rescue D-HIGH-1.

## Hunt items, resolved

1. **7th reserve site?** Enumerated all 17 emits (table above). The 6 clamped +
   the determine_mode-direct sites are the complete set EXCEPT site 2921, which
   is the 7th — and it is the leak. No drain-target/early-return/exception path
   with an implicit reserve was found beyond those tabled.
2. **Floor lost downstream?** No — `_apply_evse_battery_hold` is max-safe and
   cannot lower a floor; but it also cannot recover the D-HIGH-1 leak.
3. **Phase-transition / latch emits bypassing the 6 sites?** The mid_peak hold
   at 2921 is exactly such a non-`_floor_reserve` direct emit. The
   `actions=[]` hold-current path (2139) emits nothing — cleared.
4. **mid_peak D1b attain path covered?** The *attain* sub-path IS covered (sites
   4/5 threaded via 2887-2897). But the D1b gate's **fall-through** (gate false
   OR attain None) lands on the unclamped 2921 branch — D-HIGH-1. So mid_peak is
   only PARTIALLY covered.
5. **v5.5.0 off_peak drain/hold composition gap?** off_peak (3037/3057) and
   arbitrage/attain (6 sites) compose correctly; no gap between them in off_peak.
   The gap is in **mid_peak**, not off_peak.

---

## Verdict

**LEAK FOUND (D-HIGH-1, HIGH).** The fix correctly clamps the 6 arbitrage/attain
sites and the off_peak drain/hold fallback, but the **summer mid_peak
"holding charge for peak" branch (`energy_battery.py:2921`) emits
`reserve_level = int(soc)` with no `effective_reserve` clamp**, and is reachable
under a normal summer-afternoon partial_hold with `soc` below the floor (two
independent repros, the cleaner needing only `peak_buffer_target < floor` — a
legal config given the 30-95 vs 0-100 slider ranges). Downstream
`_apply_evse_battery_hold` cannot recover it. No test covers this path.

**Recommend: do NOT ship until D-HIGH-1 is clamped and a mid_peak-summer-hold
regression test is added.**
