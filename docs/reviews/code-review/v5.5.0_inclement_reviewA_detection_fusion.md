## CRITICAL

### A-CRIT-1 — `partial_hold` is inert in `off_peak`: elevated reserve floor is computed but the off_peak branch never reads `effective_reserve`
**Bug class:** Decision-logic / no-op guard (sibling of #51 day-boundary; "computed-but-not-consumed").
**Files:** `energy_battery.py:2858–2945` (off_peak branch) vs `:2730` (`effective_reserve = max(self.reserve_soc, decision.reserve_floor)`); `inclement.py:580–591` (uncorroborated watch off_peak → partial_hold), `:657–669` (condition-only off_peak → partial_hold).

**Reasoning / repro:**
The build threads `effective_reserve` into the **peak** branch (`:2786, 2801`) and **mid_peak** branch (`:2826, 2854`). It is NOT threaded into the **off_peak** branch at all. The off_peak branch returns via three paths — `_get_arbitrage_decision` (`:2873`), `_run_attain_branch` (`:2888`), and the drain-target fallback (`:2924` drains to `drain_target`, `:2937` holds at `int(soc)`) — none of which consult `effective_reserve` / `decision.reserve_floor`.

The fusion produces `partial_hold` with `reserve_floor=50` for two off_peak rows:
- **Uncorroborated watch @ off_peak** (`inclement.py:580`, reason `watch_uncorroborated_offpeak_partial_hold`).
- **Condition-only @ off_peak** (`inclement.py:658`, reason `condition_only_offpeak_partial_hold`).

In both cases the matrix (PLANNING D-D, rows "watch (uncorroborated) off_peak → partial_hold" and "Condition-only off_peak → partial_hold") promises the battery retains a 50% floor. The drain-target path will happily drain to `drain_target` (commonly 20–30% depending on tomorrow class), i.e. **below the partial-hold floor of 50%**, during an active (if low-confidence) storm watch overnight. `sensor...battery_mode` will report `inclement_hold_depth=partial_hold` and `inclement_reserve_floor=50` while the battery actually drains past it — an observability lie on top of the functional miss.

This is the canonical "real storm discharges the battery" case for the low-certainty/condition-only overnight scenario the operator explicitly motivated ("at night with 6–12 hours of darkness and no solar recharge").

**Why tests didn't catch it:** `test_off_peak_watch_skips_surplus_projection_FIN3` (test_battery_inclement_precedence.py:229) only asserts `inclement_hold_depth` via `_inclement_attrs()` and the FIN-3 surplus-skip; it never asserts the **emitted reserve action value** floors at 50 in off_peak. There is no off_peak partial_hold reserve-floor assertion anywhere.

**Fix options:**
1. Thread `effective_reserve` into the off_peak drain/hold/arbitrage paths (raise `drain_target` / `hold_reserve` to `max(…, decision.reserve_floor)`), OR
2. If off_peak partial_hold is intentionally a softer posture, change the matrix rows to `full_hold` (the plan already says off_peak "holds readily"), OR
3. At minimum, document the off_peak partial_hold as a no-op and correct the attributes so they don't claim a floor that isn't enforced.

Given PLANNING D-D explicitly lists off_peak partial_hold with a reserve effect, option 1 or 2 is required — option 3 alone leaves the matrix wrong.

## HIGH

### A-HIGH-1 — Overnight-fallback solar-class set diverges from spec and is over-permissive
**Bug class:** #22-adjacent (enum/literal mismatch between policy spec and runtime class strings).
**File:** `inclement.py:312` (`_GOOD_TOMORROW_CLASSES = {"fair", "good", "excellent", "moderate"}`), consumed at `:421` via `_overnight_fallback`.

**Reasoning:**
PLANNING D-G / FIN-3 specifies the overnight fallback fires only when `classify_tomorrow_solar() in {fair, good}`. The actual `classify_tomorrow_solar()` (`energy_battery.py:541–571`) returns one of `{"excellent", "good", "moderate", "poor", "very_poor", "unknown"}` (custom-mode: arbitrary class names; "very_poor" on miss). It **never returns `"fair"`** — so `"fair"` in the set is dead, and the set instead admits **`"moderate"`**, a marginal day the spec's `{fair, good}` did not clearly include. Net effect: during a corroborated mid_peak/peak watch where today's surplus is short, a merely `moderate` tomorrow forecast flips `recoverable=True` → `partial_hold` instead of `full_hold` → the battery is allowed to discharge into a real watch on the strength of a mediocre tomorrow. This loosens the recoverability bar that FIN-2 was specifically tightened to raise.

**Fix:** Pin the set to the *actual* classifier vocabulary and to the spec intent. Recommended: `{"good", "excellent"}` (the unambiguous "expect sun to refill" classes), or if `moderate` is intended, say so in the plan. Remove the dead `"fair"`. Note custom-mode installs can define arbitrary class names — consider keying off a numeric/threshold comparison rather than a hardcoded name set to be robust to custom thresholds.

## MEDIUM

### A-MED-1 — Warn-tier product-folding can be silently demoted to watch by the severity filter; matrix says warn "always holds"
**Bug class:** Ordering / spec-vs-impl precedence.
**File:** `inclement.py:230–238`.

A `"...Warning"` product folds to `tier="warn"` (`:232`), then the severity noise filter (`:237`) demotes one tier if `Severity < warn_min_severity`. So a `Tornado Warning` with `Severity=Moderate` (below default "Severe") becomes `watch`, not `warn`. This is *consistent with* `test_severity_below_min_demotes_one_tier` and is arguably intended (severity is a noise filter). BUT the PLANNING matrix line "Warn rows hold at any TOU period without consulting recoverability (high-certainty alerts always hold)" combined with the gate-first framing can read as "a Warning always warns." This is a spec-clarity / reviewer-trap, not necessarily a code bug. **Recommend:** confirm with operator that a `Warning` product below `warn_min_severity` SHOULD demote to watch (i.e. become recoverability-gated). If yes, no code change; add a comment at `:237` noting product-folded warns are still severity-demotable. If no, the severity filter must run before product-folding for Warning products.

### A-MED-2 — `condition_only` path is unreachable when an alert tier exists but resolves to allow_discharge; condition cross-check is dropped
**Bug class:** Decision-logic precedence gap.
**File:** `inclement.py:538–544`.

`condition_only = (not has_alert_hold) and condition_stormy and count>=2`. When `tier in ("warn","watch")`, `has_alert_hold=True`, so condition-only is suppressed — correct. But when an alert exists at `tier=notice` (e.g. a gated-out or severity-demoted event) AND ≥2 providers are stormy, `has_alert_hold=False` so condition_only *can* fire — good. The subtle gap: an **uncorroborated watch that returns allow_discharge at mid_peak/peak** (`:592`) exits via `_allow_discharge_decision` and the stormy local conditions are never reconsidered as an independent condition-only hold. Per D-L the condition path is a *fallback when NWS is absent*, so this is likely acceptable, but a stormy sky + uncorroborated watch at peak yields full discharge. **Recommend:** confirm this is intended (it likely is — uncorroborated + not-stormy-enough-to-corroborate), else allow the condition-only path to run as a floor.

### A-MED-3 — `_minutes_to_sunset` / risk-window uses `_daylight_bounds` "next_rising/next_setting" projected onto anchor date — post-sunset risk window can be wrong
**Bug class:** #21 (timezone / day-rollover).
**File:** `inclement.py:432–446`, depends on `energy_battery.py:1700–1740` (`_daylight_bounds` projects `sun.sun`'s `next_setting` HOUR onto the anchor's date).

After today's sunset, `sun.sun.next_setting` is *tomorrow's* setting; `_daylight_bounds(now)` projects its hour onto **today's** date, yielding a `sunset_today` that is already in the past, so `_minutes_to_sunset` walks to `now+1day` (`:441`). That is correct for "next sunset," but the risk-window `min(alert.Expires, next_sunset)` at `inclement.py:351–363` can then place `window_end` ~24h out for an evening peak watch, inflating `mins_to_window` and thus the projected surplus. In practice `_expected_solar_surplus_pct` re-derives its own daylight bounds and returns ~0 post-sunset, so the surplus stays conservative — impact is bounded. Flagging as MEDIUM because the risk-window minutes are surfaced as a (possibly misleading) attribute and the design intent is "minutes until *this* sunset" not "next." **Recommend:** when `now` is already past today's sunset and the alert is a same-evening peak/mid_peak event, clamp the window to the alert Expires only (don't add a 24h-out sunset). Verify with an evening-peak fixture.
