# AUDIT: Foyer AI Theta dewarp feasibility (Frigate 2 restream vs per-still dewarp)

Date: 2026-11-16 01:3x CDT. Read-only probe. No Frigate config edits, no restarts, no credentials used (HA camera proxy only). Dewarped test images stayed in the session scratchpad and are not committed.
Card: FOYER-FISHEYE-DEWARP-1 (see AUDIT_vision_interior_d0g_pilot_2026_11_16.md:18,43).

## Answer
Feasible both ways. **Recommendation: dewarp the single still (option B) before each interior-vision call. Do not build a continuous restream now.** Reasons below. The still path costs about one v360 pass per model call (tens of ms), needs no Frigate change, and cannot touch F2 stability. The restream adds a permanent encode pipeline on a host with a history of OOM and hangs, and is only needed if Frigate's own detection/face-rec should see the dewarped view (not required by the current ask).

## Findings
1. **Host / management.** Frigate 2 is the only Frigate (F1 retired 2026-08-15). Bare host 192.168.13.18, docker container `frigate` (ghcr.io/blakeblackshear/frigate:0.18.2, healthy, `docker ps` 2026-11-16 01:29). Config at `/home/okosisi/config/config.yaml` on F2; snapshots in homelab-automation `configs/snapshots/frigate2/`; docs `docs/CONFIGS.md:117-118,368`. Entry 051: config changes follow a snapshot/backup-then-docker-restart routine.
2. **Headroom (2026-11-16 01:29 CDT, `vmstat 5 3`, top).** 12 threads, CPU idle 41-48%, load 5-8 (down from 8 on 15 min avg). RAM: 31.9 GB total, 27.4 GB used, **4.4 GB available, swap 2047/2048 MB full**, uptime 8 d. This is the weak resource: entries 073/091 record F2 failures as global OOM/memory pressure with a 31 GiB box. iGPU: QSV h264 decode is **enabled globally** (`ffmpeg.hwaccel_args: preset-intel-qsv-h264`, config.yaml:10; 25 ffmpeg procs carry `-hwaccel qsv`); this supersedes the entry-058 "dead-end" (CONFIGS.md:514-524; hevc_qsv excluded since 2026-10-01 for GPU hangs). Face recognition large runs on the iGPU.
3. **Foyer camera today.** config.yaml:516-536: record+audio on the high channel (XdYH...), detect on the second channel (EFQQ...) at 1280x1280, global QSV decode; detect ffmpeg for it measured ~4.6% of a core. Raw circular fisheye, no dewarp.
4. **v360 available.** `docker exec frigate /usr/lib/ffmpeg/8.0/bin/ffmpeg -filters` (n8.1.1) and 7.0 both list `v360`; also lenscorrection, remap, scale_qsv, vpp_qsv. Frigate 0.18 uses ffmpeg 8.0 by default. go2rtc binary is present; `exec:`/ffmpeg sources are therefore possible, but I did not test one (would need a config edit + restart). v360 is a CPU filter: with QSV decode, frames must be downloaded to system memory first (`hwdownload`), then filtered, then re-uploaded or software-encoded.
5. **Offline still test.** Source: HA proxy `camera.foyer_fisheye_low_resolution_channel` returned a **2560x2560** JPEG (not the low channel's 720; the proxy serves the high-res still) at 01:30 CDT. The image circle fills the square (about 180 degree fisheye). Filter used on the Mac (ffmpeg v360, local only):
   `v360=input=fisheye:ih_fov=180:iv_fov=180:output=flat:h_fov=110:v_fov=110:yaw=-30:pitch=-35:roll=-25:w=1280:h=1280`
   Result: straight lines straighten (window grid, white cabinet, floor tape line), floor is visible and plausible for people. Three crops were produced and viewed. Limits observed: the still was taken at night (noisy, dark), no person was in frame so **recognition benefit is unverified**; a fixed yaw/pitch/roll shows only about one quarter of the room per view and the crop shows black outside the lens circle at the edges; the mount orientation (image rotated about 40 degrees) means yaw/pitch/roll need a one-time per-camera calibration, with a second crop for the other half of the foyer. Compare day, person-present stills before shipping.
6. **Cost, restream.** Measured locally on the Mac (Apple silicon), synthetic 1280x1280 at 5 fps for 20 s with the same v360 filter: 1.64 s user CPU for 100 frames, so ~16 ms/frame, ~8% of a core at 5 fps. On F2 CPUs (unmeasured; assume 2-3x slower) ~0.2-0.3 core per view for the filter alone at 1280 input. At 2560 input the pixel count is 4x, so ~1-1.2 core per view, not recommended. A restream also needs a re-encode (libx264 CPU, or h264_qsv which adds iGPU load that already shares with face-rec) plus a go2rtc exec process, and it would not replace the raw record leg (raw stays for Protect-compatible recording). Memory: a new ffmpeg process roughly 100-300 MB (ffmpeg procs on F2 are 20-100 MB RSS each today); on a box with 4.4 GB available and swap full this is the risk, not CPU. QSV path: can offload decode (already on) but not v360; vpp_qsv/scale_qsv can scale but not remap, so QSV buys little. Honest uncertainty: F2-side cost is an estimate, not measured, because measuring it would require running ffmpeg on the production host.
7. **Cost, still dewarp.** One v360 pass on one 1280-2560 frame: single-digit to low tens of ms on a modern CPU (Mac measure above: 16 ms/frame at 1280 including test-source generation); ~0.1 s at 2560 on slower CPU. At the vision pilot's call rate (a few calls per hour per camera, much less than 1/s) this is negligible and can run in URA's frame fetch (Python: ffmpeg subprocess or a precomputed remap with numpy/OpenCV, if those exist in the HA environment, unverified) or on the Mac/homelab. No Frigate change, no F2 load, easily reversible, and gives the model the dewarped crop(s) the operator wants. Risks: ffmpeg is not guaranteed in the HA container (unverified; HA OS core image does ship ffmpeg for the stream component, but I did not check it has v360), per-call latency of tens to hundreds of ms in an already-slow vision path, and the fixed-view calibration above.

## Comparison
| | Restream via F2 | Dewarp the still |
|---|---|---|
| F2 change/restart | yes (config + go2rtc exec) | none |
| F2 CPU/RAM | ~0.2-0.3 core + 100-300 MB continuous, est. | zero |
| Benefits | Frigate detect/face on dewarped view; continuous | Vision model sees dewarped crop(s) |
| Failure surface | F2 OOM/hang history (051, 073, 091, 099) | one failed call falls back to raw still |
| Reversibility | config rollback + restart | delete a function |

## Recommendation
Build the per-still dewarp (option B), using 2 fixed v360 crops calibrated once from a daytime still; validate against a person-present still before relying on it. Revisit a restream only if the operator wants Frigate detection/face recognition itself on the dewarped view, and then trial it with memory headroom measured first (the swap-full state on 2026-11-16 is the blocker). An unverified, cheaper restream variant to price later: a detect-role `output_args` `-vf v360` on the existing detect leg, which would avoid a new process; not tested.
